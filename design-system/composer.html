The composer

One input, used by every conversation in the studio — new world, character, canon, scene. The anatomy is taken from opencode's prompt-input v2 so the behaviour is familiar and proven; the skin, the words and the accepted file kinds are ours.

Built, and shipping. This page was written for review before any of it existed; it is kept as the reference for what was agreed. Two things differ from the drawings below and both are marked where they occur: the masked key, which we cannot show, and the cost figure, which we will not invent. What arrived since is on Since the prototype.

These are opencode's rules, read from packages/app/src/components/prompt-input/ on the dev branch. They are worth copying because each one solves a problem we would otherwise hit.

Where we deliberately differ

opencodeArke Studio

“Ask anything…”the placeholder says what this conversation is for; each screen sets its own
attachments are context for one turnan attachment is filed as an artifact and stays in the world after the turn
The last row is the important one

In opencode an attachment is scaffolding for a question. In a studio it is source material — the photograph a character is drawn from, the notes a world came out of. So attaching a file files it in artifacts/ and it is citable afterwards. That is a product decision, not a copy, and it is the one I would most like your view on.

07Attaching a document, and the offer

Attaching a document is usually a way of saying “this already exists — use it”. So the studio offers to read it. But reading it is a model turn that costs money, and nothing in this app spends without you, so the offer comes before the reading, never after.

The offer lives in a strip under the composer — not in the transcript, because you have not said anything yet, and not inside the chip, because it is about what happens next rather than what the file is. One line, dismissible, and it never blocks you from just carrying on typing.

Offered · you decide before it reads, not after.

Empty-handed · said plainly, because a silent nothing reads as a failure.

RuleWhy
Offer, don't readExtraction is a model turn. The button is the consent.
No figure it cannot stand behindExtraction runs through the harness, not the job queue, so there is no estimate and no ledger line to quote. Rather than a plausible number, the offer names no cost at all — and the reading is stoppable, which is the guarantee that actually holds.
Every ending is namedFound, nothing, no text to read, stopped, or the writing service is down. A silent nothing reads as a failure.
Only documentsAn image or an audio file has nothing to extract yet; they file silently with no offer.
Never blocks typingThe strip is advisory. Ignoring it and carrying on is a valid answer.
Facts quote their sourceThe existing pipeline verifies each candidate against a real span; the offer inherits that.
This reuses a pipeline that already exists

Filing, extraction and per-candidate accept/reject are already built — file-artifact, extract-artifact and resolve-extraction. The only new thing here is the offer: a surface that puts an existing capability where the intent is, instead of leaving it on a screen you have to go and find.
