Approved design rules

1 · Status. 26 October 2026 · Revision 1 · Approved by the owner on 26 October 2026; implementation under qualification. This design replaces the top-right proposal icon with a system/performance icon. All measurements, service states and times in these drawings are illustrative. Actual-component review is recorded in the notes; packaged and physical-device acceptance remain separate.

2 · Existing design sources. Reuse 227a/k/m writing-room drawings, current client icon components, semantic typography/color/spacing tokens and the 206/239 rounded Activity shell. The phone content drawing has no titlebar; add the current AppChrome phone grammar: Back to chapters, no centred brand, five 44px utility targets and 52px bar. No replacement workspace, logo, icon paths or model controls.

3 · Only the shortcut changes. Replace the current Inbox/Proposals titlebar slot with native Cpu labelled System. Order: Chat, System, Activity, Settings, Account. System is application-scoped and available without an open world. This turn does not remove proposal creation, gate decisions, the proposal route or existing review panels. Existing Activity open-proposal items still reach their proposals. Audit alternate access before any later proposal-screen removal.

4 · A quiet entry. Use the normal neutral icon at rest and the existing small warning-dot vocabulary for a current actionable finding. A reading gap alone does not claim failure or health. Tooltip and accessible label name System and any warning. Opening and closing never starts a repair, stops work or approves anything.

5 · Same rounded shell. Desktop: 440px floating card, top 50px, right 10px, all four corners 12px, full border, popover surface and shadow-lg. Use content height bounded 12px above the bottom; the page keeps its width. Header and footer remain fixed while content scrolls. Coordinate overlays with Activity/Settings/Arke so only one operational dialog owns focus.

6 · Host identity. Header says System / This desktop. In a remote browser these remain host measurements, never phone/tablet hardware measurements. A production host label must come from the authenticated host context; a disconnected remote session must say it cannot refresh. The Example data label belongs to the design fixture.

7 · Performance is measured. CPU utilisation, used/total RAM, GPU utilisation and GPU memory are distinct facts. Show units and source sample time; utilisation is not a universal capacity gate. No made-up performance score, automatic tuning, prediction, historical sparkline or hardware-fit guarantee. Unsupported collectors say Unavailable; implement host collection separately before binding these examples.

8 · Storage by actual destination. Name the registered destination and measured volume capacity, with available bytes explicit. Bars show used capacity, not reserved work. Do not add available capacity from different volumes. The example waiting export compares 6 GiB available with 9 GiB required including reserve, leaving a 3 GiB deficit. Admission still uses its fresh authoritative collector, never the display sample.

9 · Service and cloud health. Local AI rows distinguish Ready, Working, Not running and Unknown, alongside check time. A stopped optional service is not automatically a fault. Cloud shows configured provider connections as Not checked until an applicable bounded probe exists. Configuration, internet connectivity and process health cannot prove provider availability, inference quality or completed work. No cloud CPU/GPU performance is invented.

10 · Freshness and absence. The unavailable drawing marks retained CPU/RAM values Last with an explicit 3-minute stale label and removes their live bars. Unsupported GPU readings and failed drive probes say Unavailable, never zero. Each collector owns its freshness budget; there is no single global fresh/healthy badge. Refresh asks for bounded collection and preserves missing facts until measured.

11 · Warnings lead to Diagnostics. Show the measured cause, affected work and next step. Review in Diagnostics and the persistent Diagnostics control open the existing diagnostic surface/finding. Detailed diagnosis and reviewed remedies remain there or in the Studio assistant. There are no cleanup, delete, restart, kill, retry-work or automatic-provider buttons in this overview. Opening a warning does not dismiss an incident.

12 · Tablet and phone. Tablet is modal, 440px wide within 16px outside gaps. Phone is modal below the existing 52px bar plus 12px gap, inset 12px with safe bottom area and four rounded corners. Controls are at least 44px; content scrolls independently. In reduced visible height the close and footer remain reachable. Modal background is inert and Tab is contained; Escape/Close return focus to System.

13 · Implementation boundary. SPEC-061 R-2/R-5 and SPEC-062 R-5/R-21 inform explicit evidence/freshness and measured warnings; both capability specs are proposed. SPEC-032 owns derived diagnostics. The authorized implementation uses a separate transient host-resource projection and the existing native lifecycle owner; source-list and shortcut amendments accompany integration. The production panel reports actual evidence and does not infer the example waiting export or deficit. Component review does not establish successful GPU counters, packaged Electron or physical-device acceptance.

14 · Acceptance. Review desktop/tablet/phone/reduced height in light and dark; native icons, tokens, shell border/radius/shadow, warning text, units, stale data, independent scrolling, 44px phone controls, focus containment/return, overlay coordination and Diagnostics handoff. Structural checks and prototype gestures are separate from rendered visual inspection and later native application acceptance.
