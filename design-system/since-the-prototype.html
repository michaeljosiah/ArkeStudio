Arke Studio · design system · what shipped

Since the prototype

Six surfaces exist in the app that the prototype never drew, and two it drew differently. None of them is a redesign: each came out of a question asked while using the thing. This page records what they look like and why, so the prototype and the product can be read together without one quietly contradicting the other.

How to read this against the prototype

Arke Studio Prototype.dc.html is still the reference for everything it covers — the fan, the hub, the production screens, the shape of the settings modal. This page is additive. Where it disagrees, the disagreement is stated and reasoned, never implied.

01Settings has a fifth tab

The prototype's settings modal has four: Providers, Local runtime, Who does what, About. There are now five. Agents sits after Local runtime, because it is about what this machine writes with rather than about routing a paid job.

It exists because the app never chose which model ran its writing assistants, and no screen said which one was running. That is now a decision, per agent.

RuleWhy

The harness names themThe list is what it can actually run — three providers and forty-one models on a real machine, against 5,864 in its full catalogue. Each provider's own default sorts first and says so.

Edited is visibleAn agent running a rewritten brief says so, so a strange answer has somewhere to be traced to.

02The setup screen, once it is finished

The prototype only ever draws setup working: the reel, a bar, a count. There was no drawing of the moment it is done, so the product kept the working furniture and put a live button in the middle of it — a bar at 100%, a byte count that had stopped moving, and a sentence about where worlds live.

All of those answer what is it doing. When the answer is "nothing", the panel is a door and a version number.

03Key art, on the world's hub

The prototype puts a Generate from the logline button on the new-world screen, beside the form. It could never work there: an image job needs a world folder to land in, and on that screen there is no world yet. It sat disabled from the first release until it was removed — a control that can never be enabled reads as broken rather than as not-yet.

The working one is on the hub, under the world's own name and logline, where everything it needs already exists.

The harness writes the promptA logline is written for a reader; an image model wants a subject, a light, a material and a lens. The art-director agent translates. If it cannot, the plain assembly is used and the picture is still made.
It lands beside, not overThe candidate waits in incoming/world-image/. The world keeps the image it has until told otherwise.
The offer comes from the diskWhether there is something to answer is read from the world, not from the job that made it. A finished job stays in the log for good, so asking it brought the offer back on every visit, over a file already used.
Every ending is namedNo logline, no provider with a key, a provider refusal — each says which, and what to go and fix.

04Archiving a world

The prototype has no way to remove a world. Archiving moves the folder to archive/ whole — journal, artifacts, lock file and all — so recovery is a move back rather than a restore from anything.

Not "are you sure?"

That question tells you nothing about whether your writing survives. The words name the outcome — where it goes, and that nothing is deleted — which is the only part worth confirming. Archiving is refused while jobs are still running for that world.

05Who does what: models you cannot use

The prototype draws each capability with a pill naming a model. The list behind that pill used to be every model in the manifest, whether or not its provider had a key — so a dispatch could be routed into a dead end and fail only at the end, after an estimate had been shown and accepted.

Unusable models stay listed, because knowing the option exists is worth something, and are unselectable, sorted below the usable ones, saying what is missing.

06The composer, as built

The composer was proposed on its own page and is now implemented: drop, paste, the large-paste rule, the greyed refusal chip, and the extraction offer with its states. Two things there differ from what that page drew, and it says so on the page — the masked key we cannot show, and the cost figure we will not invent.

07One chrome, on every screen

This is the one place the product now disagrees with the prototype outright, so it is worth setting out plainly. The app had five different top bars. A world put settings and activity as icons on the left and the words "Arke Studio" in the middle; home put the lockup at top-left and the same two destinations as text buttons on the right; the production bar, the new-world bar and the activity bar each carried a bare "Arke" in the top-right and neither control at all. Three placements for the same three things.

world · icons left, "Arke Studio" centre, "Arke" right home · lockup left, Activity/Settings as buttons right production · title centre, "Arke" right new world · back left, label centre, "Arke" right launch · "Arke" right, nothing else

None of that is visible from any single screen. You only see it by walking all forty-one, which is now what a test does.

Left: where you are. Centre: the wordmark. Right: activity, then settings — always in that order.

The wordmark is centred on the window, not on the row. The desktop shell parks its native window controls in the top-right ~138px and the bar reserves that margin, so a flex-centred mark lands about 69px left of true centre on desktop and dead centre in a browser — the same code drawing two different layouts. It is absolutely placed instead.

The prototype drew home's lockup at top-left, and that is what changed. It is a better composition on that one screen. It is also the reason the mark moved on every other screen, and a mark that moves is not a mark. Consistency across forty-one screens is worth more than the one composition it came from.
