Journey decisions & implementation boundaries

1 · Approved design. Approved by the owner on 28 October 2026. Implement these journeys with selection-specific readiness; manual writing remains available without AI. The drawing itself does not install or configure services.

2 · One installer. Use the existing Windows desktop installer and bundled core. Preserve its destination choice and Launch Arke action. Do not add a second installer, persona-specific binary or website wizard in this turn. The persona choice happens on first app launch, before any optional AI acquisition.

3 · Current visual language. Use the current launch-creation poster, split/stacked launch shell, Jost wordmark, Geist typography, launch tokens and current native icons. Launch remains dark in both application themes. New controls use neutral surfaces and 44px minimum targets.

4 · Guided defaults. Check the computer and qualified model catalogue first. Offer local writing only when a supported model fits that device and destination; offer cloud accounts otherwise. If compatible installed assistants are found, let the user explicitly select one before preparing writing. Add Kokoro/Whisper and managed ComfyUI only when their own support checks pass. Review the resulting package before download. OpenCode stays included but its name is not essential in Guided copy.

5 · Optional. Voice cloning, image/video recipe weights, larger text models, cloud provider connections and remote-device access remain opt-in. Voice providers/models are selected later from the supported catalogue; no Ming-specific first-run choice. The media engine alone does not enable generation.

6 · Readiness. Core entry requires a connected coordinator, valid writable data location and working create/save path. The starter package is ready only after selected files are verified, selected engines are healthy and capability-specific checks pass. A small local model response can qualify the selected writing path; runtime health alone cannot.

7 · Useful while preparing. Start writing is available once the core is ready; selected local AI may finish in Activity. Pending or failed AI remains explicitly unavailable for the affected feature. Setup-complete and app-usable are distinct facts. No automatic provider or paid fallback.

8 · Estimates. The 8 GB download, 24 GB peak-space requirement, 180 GB free and timing in these frames are illustrative. Real review uses missing selected files, per-destination measured free space and verified expansion requirements. Show download size, disk retained and temporary peak separately; never total the entire optional catalogue. Unknown figures are labelled rather than invented.

9 · Recovery. Keep completed components and resumable download receipts. Offer Resume, change folder, edit plan and continue manually. Closing pauses unfinished transfers; restart makes their status explicit. Unselected components do not raise incidents.

10 · Hardware and permissions. Run non-mutating device/location checks before showing a local starter package. Unsupported hardware gets an explained manual/cloud/existing-service choice, not an incompatible mandatory download. A read-only or full core data folder still needs a valid destination before worlds can be saved.

11 · Writing connection. First-run OpenCode accounts are ChatGPT and GitHub Copilot. Arke is visible but disabled, with no sign-in action or availability date. Use the harness-reported supported account method; no API-key path is in this first-run shortlist. A connected account plus an accessible supported writing model is required before Ready. Local writing requires healthy Ollama and a responding model after download. Existing Claude Code/Codex keep their own adapter/account route.

12 · Smart eligibility. Local suitability uses a qualified model and its supported device profile, available RAM/VRAM where required, OS/CPU/backend compatibility, working context and disk/download peak. A missing GPU alone is not disqualifying if a supported CPU model fits. Ollama being installable is not proof of a suitable writing model. Unknown checks cannot be shown as suitable: explain the incomplete check, offer retry/online/manual, and do not download automatically. No invented universal RAM threshold or fixed model for every PC.

13 · Simple wording. Guided and Lightweight explain outcomes: writing help, on this computer, online account, read aloud and picture/video tools. Keep OpenCode, Ollama, ComfyUI, Python/CUDA, harness and API-key terminology in Advanced/technical details. Product names remain when needed to choose a recognised installed assistant or account.

14 · Existing assistant choice. Only compatible found installations are offered in Guided. Skip the choice when none exist. Keep installation discovery distinct from account/model readiness; selection checks the chosen assistant and offers its supported sign-in steps if needed. Do not copy personal sign-ins or change the selected assistant on failure. The example-computer controls are outside the product and do not scan this PC.

Journey decisions & implementation boundaries

1 · Approved design. Approved by the owner on 28 October 2026. Reuse the same installer, core and destination as Guided and Lightweight. No second settings system or new daemon.

2 · Capabilities first. Offer writing, local media and preset voice/dictation in familiar language. OpenCode writing then offers cloud or local, as in Guided; cloud is not a separate competing writing capability. Voice cloning is chosen later from supported providers. Reveal only selected controls and dependencies.

3 · Managed default. Arke-managed Ollama and ComfyUI are the default sources for selected local capabilities. Mere detection never adopts an existing install. Reuse requires an explicit source selection and compatibility check.

4 · Existing services. Use only source types already supported by the selected engine. A personal service stays under the user’s lifecycle; Arke does not silently install packages into it, upgrade it or promise to restart it. A URL-only ComfyUI connection cannot supply a local Python interpreter for Ming.

5 · Selected readiness. Check the capabilities selected for preparation. A failed service holds only its dependent features. The user can correct the connection, review a managed alternative or enter with the working capabilities. Never label an omitted capability broken.

6 · Providers. The initial account picker offers ChatGPT and GitHub Copilot, plus disabled future Arke. Reuse the existing harness-owned sign-in and model flows behind this scoped onboarding shortlist (proposed amendment to SPEC-030 R-7); do not replace the general provider catalogue. Enable a row only when the shipped harness reports a supported sign-in method. Confirm account and model access; no undisclosed paid generation. Cloud excludes local writing downloads.

7 · Advanced controls. Folders, supported addresses and transfer controls sit behind Advanced or the relevant source field. Keep normal users out of service details. Avoid a new arbitrary limit, universal model-size assumption or forced migration of existing model stores.

8 · Returning users. A saved plan and explicit overrides survive restart and app update. Start only selected managed owners needed by enabled features. Recheck capability readiness without rerunning onboarding or ejecting an open world. A changed package is offered with its cost before additional downloads.

9 · Included harness. OpenCode v2 remains bundled in every path. It is the default authoring harness and connects to Ollama for local writing. Bundled does not mean selected or always running; a selected alternative is not silently replaced by OpenCode on failure. Do not make nontechnical users choose a harness.

10 · Existing harness choice. Reuse SPEC-005 harness availability, discovery, explicit path and selection. Offer detected Claude Code and Codex with version/compatibility and authentication states kept distinct. This drawing illustrates detected installations; it is not a live scan. A ChatGPT or Claude website session alone is not a detected executable.

11 · Selection-specific readiness. Claude Code/Codex use their supported adapter and account flow. Do not require Ollama, download a local writing model or imply local routing merely because writing is selected. Keep hosted inference costs and content destination clear. Compatibility/account verification must not trigger undisclosed paid inference. The current private Studio diagnostic route remains separately qualified; manual Diagnostics still works.

Journey decisions & implementation boundaries

1 · Approved design. Approved by the owner on 28 October 2026. Lightweight is the same desktop application with zero additional AI downloads, not a separate product or a promise of a smaller base executable.

2 · Bundled baseline. The current base includes client, coordinator, OpenCode v2, Voxa, ffmpeg, native index and the bundled sample where present. They remain installer contents across all three paths. The 0 GB claim refers only to additional AI downloads; the installer and extracted app still occupy disk.

3 · No forced AI. Do not fetch/start ComfyUI, Ollama, text weights, Kokoro/Whisper weights or Ming for an unselected lightweight plan. Bundled tools may start only where needed by enabled core functions. No cloud account, key, GPU or network is required for manual authoring.

4 · Immediate use. Once the coordinator and writable workspace are ready, allow world creation by form, editing, browsing, bundled sample exploration and supported import/preview of existing media. AI chat, generated media, narration and dictation need their own configured capability.

5 · Add on first use. An unavailable AI action offers its capability, complete missing dependency list, download/storage costs, destination and alternative provider choice. Not now returns without losing the creative draft. After approval only this capability is prepared; existing verified dependencies are reused.

6 · Provider dependency clarity. A later local voice-provider selection reveals only that provider’s required runtime/support/model downloads, reusing compatible installed dependencies where possible. A hosted choice reveals account and usage costs. Never assume every supported voice provider shares one runtime or capabilities.

7 · Quiet states. Not set up is normal. Do not repeatedly nag, open dialogs or show fault badges for declined optional features. Actual failed accepted downloads can offer a contextual next step. Model-free diagnostics remain useful without a diagnostic model.

8 · Device scope. The compact frame is a narrow desktop window. Phones/tablets connecting to an existing host use the existing pairing journey; this design does not download desktop services onto a phone or bypass host approval.

9 · Approval boundary. The owner approved these drawings and implementation on 28 October 2026. Reconcile SPEC-016 R-1–R-5 and the later mandatory-runtime policy in the implementation commits. Existing users keep their configuration; no migration or new startup downloads are performed by this review.

10 · One Worlds landing. All setup paths enter /worlds. Reuse the current FirstRunScreen card treatment: 290px by at least 380px, dashed Create card at -1.5 degrees and solid sample card at +1.5 degrees, native Plus/Sparkle rings, buttons and hover lift. Retain Import a world and the existing Open publication action in the Worlds header. This folds FirstRunScreen into the Worlds empty state instead of adding another onboarding destination. Existing worlds retain their grid/archive behaviour; an installed sample becomes its existing world card, not a duplicate offer. Sample availability/download size follow the current source.

Source: current client launch.tsx / launch.css / launch tokens / native icons; SPEC-016 (draft), R-1–R-8; current managed local runtime guidance. Proposal changes the current mandatory runtime gate. No product behaviour has changed.
