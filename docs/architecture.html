How the whole system is put together

One program, two halves, one folder of truth.

Arke Studio is a desktop app made of two real, separate things that talk over a network protocol on your own machine. One half is a React client that draws screens and sends commands. The other is the coordinator — the part that owns your files, enforces the rules, runs the queue and holds the keys.

Around them: two optional helper programs, a folder of plain files that is the only durable truth, and a set of cloud providers that are only ever called when you ask. This document is the pieces, the layers, the wire, the state and the trust boundaries — and a plain answer to the question that always comes first.

Section two · the question that always comes first

Is this client/server?

Yes — genuinely, and on one machine. The client and the server are two real, separate things that speak a real network protocol to each other. They are simply packaged and shipped as one program, and they share a lifetime.

That is a deliberate decision, recorded in the foundation spec as decision D2: the coordinator is embedded in the app because it is the domain layer, not a service anybody else talks to. Giving it a lifecycle of its own would invent a class of failure — "the app is running but its server is not" — that this product has no use for.

Not a metaphor

Really a server

A Node HTTP server with a WebSocket server on it, bound to 127.0.0.1 on a port chosen at start-up. It accepts connections, sequences frames per connection, and broadcasts to all of them. Two windows would both get updates.

A plain web app

Really a client

An ordinary React single-page app. It reaches the coordinator only by sending JSON and receiving JSON, and fetches images over plain HTTP. It has no filesystem access, no credentials, and no rule it is trusted to enforce.

No port, no login

Not a service

Loopback only, on a port that changes every launch. No accounts, no authentication, no sessions. The first message a client sends is hello, and there is nothing to log in to. Quitting the app stops the server.

The proof it is real: the app already runs in a browser

This is not a claim about a possible refactor. Two commands run the system split apart today, with a browser tab as the client: 

Terminal one — the coordinator as its own processnpm run dev:coordinator

  → reads a real app root at .dev\root (seeded from fixtures the first time)
  → discovers OpenCode if it is installed, supervises it, degrades if not
  → listens on ws://127.0.0.1:8791
Terminal two — the client as an ordinary web appnpm run dev

  → Vite dev server
  → window.arke is absent, so the client falls back to a plain WebSocket
  → same frames, same commands, same coordinator

There is no mock in that arrangement. It is the same coordinator class, the same world provider, the same accept gate, the same SQLite index, driven by the same message set. The desktop app differs only in who starts the coordinator and which extra host abilities exist.

What the split actually gives you

If you wanted to…StatusHow much of it already works
Run the UI in a browser instead of a window works today You lose the host-only gestures — dropping a file onto the composer, the "choose a file" dialog, native notifications, the OS theme — because those need a desktop shell, not a server. Everything else renders and behaves.
Build a second front end — a CLI, a plug-in, a phone app ready The contract is already the whole surface. A client is anything that can send 123 kinds of command and fold 59 kinds of event. Both are Zod schemas in one shared package, so a new client gets types and validation for free.
Run the coordinator headless — tests, automation, a service works today The tests rely on it. The coordinator is plain Node. Every Electron-specific ability is an injected seam: the key cipher, the file picker, the encoder, the updater, the sidecar, the "open this folder" call. Leave one out and that feature says why it is unavailable instead of crashing.
Swap the writing harness, or add a provider designed for The harness sits behind an adapter interface whose capabilities are probed from the harness's own API document rather than pinned to a version. Providers are a registry of small HTTP clients, each declaring what it can do.
Put the coordinator on another machine, or share a world between people not today The wire is ready; the rest is not, and deliberately. Five things assume one machine — below.

And what it does not give you — the honest part

It is tempting to read "client/server" as "one config change from being a hosted product." It is not, and the reasons are architectural rather than cosmetic.

The filesystem is the only durable truth

Not a design detail — the product promise. Worlds are folders you can open, copy and back up. A remote coordinator would still work, but it would own its disk, not yours, and that is a different product.

One writer per world, enforced by a lock file

Concurrency is resolved by exclusion, not by merging. Two people editing one world would need a real multi-writer model, which the versioning scheme — one monotonic canon revision, one version per sheet — does not currently describe.

There is no authentication, and nothing to authorise against

Any connection that says hello gets the full snapshot. That is correct for loopback and completely wrong for anything else.

Keys are encrypted against this machine's OS

Windows DPAPI, via Electron's safeStorage. The ciphertext is not portable, by design. A shared coordinator would need a different secret story entirely.

The helper processes are local children

OpenCode and Voxa are spawned per app instance, given loopback ports, leashed to the process, and reaped on exit. Voxa in particular exists because speech should never leave the machine.

The useful way to hold it. The client/server split is not there so the server can move away. It is there so the UI can never be the thing that decides.

Every judgement — can this be accepted, what does it ripple into, what will it cost, is that key valid — happens on the far side of a schema-checked wire, where it can be tested without a browser and cannot be bypassed by the browser. Portability is a side effect of that discipline, and a real one.

Section three

The layers.

Reading top to bottom: what you look at, what holds a copy of state, the wire, the rules, and the things that persist or reach outward. One package — contracts — runs down the whole side, because every layer speaks the same vocabulary.

The one rule that keeps this honest: the host shell is at the bottom, not the middle. The coordinator never imports Electron. Anything only a desktop shell can do is passed in as a function when the coordinator is constructed — the cipher that encrypts a key, the dialog that picks a file, the encoder that renders an export, the updater. Leave one out and the feature reports why it is unavailable. That is exactly what makes the headless and browser configurations above possible rather than aspirational.

Section four

The packages, and which way the arrows point.

An npm-workspaces monorepo: six libraries and one app. Every arrow below means "depends on", and every arrow points down. Nothing points back up, and nothing points sideways.

Section five

The wire between the two halves.

Only two kinds of thing ever come down: a snapshot — the whole state the client should render — and an event. Both carry a sequence number that only ever increases, counted per connection. 

The entire downward protocoltype Frame =
  | { kind: "snapshot"; seq: number; state: ClientState }
  | { kind: "event";    seq: number; event: DomainEvent }

Five properties worth naming

PropertyWhat it means in practice
Validated in both directions The coordinator parses every incoming command against its schema and closes the socket on a malformed one. It also validates every frame on the way out, so a frame that fails its own schema never reaches a client. The client parses every frame it receives and drops a bad one loudly. Version skew shows up as a clear error rather than a subtly wrong screen.
Push, never poll Nothing in the client asks "has anything changed?". Work that takes time — a generation, a download, an authoring turn — reports itself as events as it goes.
Commands are fire-and-forget A command has no return value. Its outcome arrives as an event, which means the same outcome reaches every connected client, and reconnecting mid-operation loses nothing.
Reconnect means "start again" Recorded as decision D4: a world is small enough to re-send, and a replay protocol is a source of divergence bugs with no compensating benefit at this scale.
Images ride the same server The coordinator's HTTP side serves GET /media/<world>/<file>, read-only, no caching, with the resolver guarding against path traversal. That is why pictures appear in a browser tab with no desktop shell involved.
Section six

Inside the coordinator.

Not one object with a thousand methods. A set of services with one message loop in front of them, and a small number of primitives underneath that everything else is built from.

world/commit.ts

The commit primitive

The only way a world file changes. Snapshot the outgoing version, write the new one atomically, bump the version, append to the change log. Interruptible at any point without losing both copies.

gate/proposals.ts

The accept gate

One path into the world. A proposal is materialised with the hashes it was drafted against, previewed with its ripples, verified under the lock, and accepted as exactly one commit — or discarded, leaving one log line.

read-model.ts

The read model

Folds world state and events into the shape the client renders. Pure: validation happens at the boundaries, never here. The client has a copy of the same fold, which is what keeps both sides in step.

index-db/

The derived index

SQLite per world, with a full-text table over canon. Structurally prevented from becoming a source of truth — it is populated only from a scan of the folder. Delete it and it rebuilds.

queue/

The job queue

Durable before the network, and never trusts silence. Every state change is written down before the action it authorises, and a gap in observation is an unknown to reconcile rather than a failure to retry.

supervisor.ts

The supervisor

One generic implementation for both children. Spawn, allocate a loopback port, probe health, restart with backoff, stop gracefully, and never leave an orphan — even when the app is force-killed.

What the message loop does with a command

Parse it

Against the command schema. A malformed message is a client bug, and the socket closes rather than the coordinator guessing.

Route it to a service

Canon, sheets, the gate, productions, the queue, voice, artifacts, world chat, providers, setup, updates.

Do the work, writing before acting

Anything durable is on disk before the thing it authorises happens — the proposal before the edit, the queued job before the network call.

Broadcast an event

To every connected client, each with its own sequence number. The client that sent the command learns the outcome the same way everyone else does.

Section seven

The two execution paths.

This is the architectural distinction the specification exists to protect. Two completely separate routes hang off the coordinator, and confusing them is the failure mode the design guards against hardest.

The two lanes end in the same word, but they mean different things. On the left, nothing exists until you accept — the writing happened in a folder that is not the world. On the right, the file exists the moment the provider returns it; what you are accepting is that it becomes the shot's answer. Pretending otherwise would mean holding generated media in limbo outside the world, which is worse.

The right-hand lane carries one detail worth spelling out, because it is where money is involved. A job is written down with an idempotency key before the provider is called, and again when it moves to "submitting", also before the call. If the app dies in that window, the job comes back in an unknown state and is never blindly re-sent: providers that can be queried by that key are asked, providers that can list recent work are searched, and providers that can do neither leave the job held for you to decide — with the cost of a possible duplicate stated plainly.
Section eight

Where each kind of state lives.

There is no database of record. There are five homes, and the rule for each is different.

HomeWhat lives thereRule
The world folder Sheets, canon, productions, scenes, takes, references, artifacts. The only durable truth. Delete everything else and the world survives. Readable and editable by hand.
.history/ A complete copy of every previous version of every versioned file. Full snapshots, not diffs — because there is no version-control system underneath, and a sheet is a few kilobytes. Restoring is a file copy.
changes.jsonl One line per accepted change: what, from which version to which, which fields, from what source, at what canon revision. Append-only, never rewritten. It is the audit trail, the Activity feed's backing store, and the answer to "how did this get here".
.index/world.db Entities, citations, takes, jobs, ledger rows and a full-text table over canon. A cache. Deletable with no loss; rebuilt from a scan. No write path may take a value from here and persist it into a world file.
App-level files queue/jobs.jsonl, ledger.jsonl, config.json, credentials.dat, logs. Outside every world, so exporting a world can never carry a key or another world's spending.

Two version counters, not one

Canon has a single world-level revision number that advances once per accepted canon change. Each sheet has its own version, independent of canon and of every other sheet. Both exist for the same reason: something else cites them. A take records { canonRevision: 42, sheets: { maren-kest: 4 } }, and that record never changes afterwards — which is what makes "accepted takes stay on the version they were made with" and "14 reference images predate this change" computable rather than decorative.

Section nine

What happens when you accept something.

The most load-bearing sequence in the system, so it is worth following end to end.

Intent

You type into a form, or you talk it through. Either way the result is the same kind of object.

A proposal is staged

A folder under .proposals/ holding the complete proposed files, not patches. It records, per target, the version and content hash the drafting began from.

Ripples are computed from the index

What else this touches — which reference images predate it, which scene briefs re-render, which productions pick it up. Advisory, and shown before you decide.

You accept

Under the world lock, every target's hash is checked against the world as last committed. If anything moved underneath, the accept refuses and says so rather than overwriting.

One commit

The outgoing file is copied to .history/ first, the new file is written atomically, the version bumps, and the canon revision bumps if canon changed.

A crash mid-way leaves either the old file intact or the snapshot beside the new one — never neither.

The trail is written and the index catches up

One line in changes.jsonl; the index updated; an event pushed to every connected client. Because proposals are whole files, accepting is a move — there is no patch application to get wrong.

The gate protects the authored record — the facts a production cites. It does not protect the audit trail, the job queue, the ledger or the index: those are the record of gating, and gating them would be circular.
Section ten

The processes, and keeping them honest.

Three processes at most, and only one of them is required.

ProcessWhat it isHow it is reachedIf it is missing
Arke Studio The app: window, renderer and coordinator in one. You launch it. There is no app.
OpenCode A file-editing agent, bundled with the installer — but an existing installation is preferred and reported. HTTP on a loopback port allocated at start-up. Health-checked at /api/health. Authoring switches off with a stated reason. Everything else works: browsing, forms, generation, exports.
Voxa A self-contained speech runtime — Kokoro for voices, Whisper for dictation. Entirely local. HTTP and WebSocket on a loopback port. Health-checked at /health, including that its architecture matches this build. Local voice and dictation switch off with a stated reason. Cloud voice, if configured, still works.

Never leaving an orphan

A supervised child has to die with the app even when the app is killed and none of its cleanup code runs at all. So every spawn is tethered three ways:

Job object

A kernel leash

The child is bound to the app's lifetime by the operating system. If the app dies by any means, the kernel takes the child with it.

Swept at next start

A pidfile ledger

Every spawn is recorded. The next launch reads that record and reaps anything still running from a previous run.

For shell shims

A descendant snapshot

On Windows the process you spawned may be a wrapper, and the real work is its grandchild. Once healthy, the live descendants are recorded too, so stopping can reach past a dead wrapper.

Section eleven

Trust boundaries.

Four boundaries, each doing what it can actually do — and one place where the residual risk is stated rather than assumed away.

BoundaryWhat holds it
Renderer ↔ everything else Context isolation on, Node integration off, sandbox on. The renderer receives exactly one object exposing connect, send and subscribe, plus a few host gestures that deliberately hand over nothing: asking for a file picker returns "artifacts now exist", never a path.
Keys Encrypted by the OS and written outside every world folder, with the file's permissions reset to you alone. Plaintext exists only in main-process memory, for one request. Handed to the harness by environment variable at spawn, never written into its configuration file.
Logs and diagnostics Redaction is applied at the logging boundary, not at each call site — so a new call site cannot leak by forgetting. Diagnostics bundles go through the same filter and carry no world content.
The harness Four layers: the world is never its working directory; escape-capable tools are disabled; out-of-band writes are detected by hash comparison at accept; and anything still missed is caught at next open by reconciliation.
Stated plainly, because the specification does. An agent with shell access running as you can, in principle, reach world files between commits. Arke Studio detects that and preserves history; it does not prevent it. True prevention needs an operating-system boundary around the harness process, which is the correct hardening and is recorded as deferred — not as solved.
Section twelve

What this architecture costs.

Every choice above buys something and gives something up. The trades, without spin.

The choiceWhat it costs
Files as the only truth, no database of record Questions a database answers instantly need an index, which then needs rebuilding, staleness detection and a rule that it can never become truth. Three problems traded for one promise — that your worlds are yours and outlive this app.
One writer per world No collaboration, and a world open in a second instance is refused rather than merged.
History as full snapshots Disk. A sheet is a few kilobytes, so six versions cost about twenty-five, which is the right trade against reimplementing merge and patch machinery with no version-control system underneath.
Fresh snapshot on every reconnect A little bandwidth on a loopback socket, in exchange for never debugging a divergence caused by a replay protocol.
Coordinator embedded, not separate You cannot point a second machine at it today. What you get instead is that "the app is up but its server is down" is not a state that exists.
Two optional child processes Every feature that depends on one needs a designed degraded state — visible, disabled, and explaining itself. That is more work than letting things fail, and it is why the app starts and stays usable when both are missing.
Schemas at every boundary The same shape is declared once and enforced in several places, which costs a little ceremony. It buys version skew that announces itself instead of corrupting a screen.
