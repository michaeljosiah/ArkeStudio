A production-scoped creative workspace

Build the world. Then direct the story.

World Chat — specified by issue #70, not yet built — explores what may belong in the world; explicit review and the accept gate decide what becomes true. The production Story workspace explores what this film, series, or micro-drama does with accepted world truth. Conversation stays close to the work without becoming another source of truth. Both sit on a conversation and candidate layer that does not exist today; #70 owns it, and this feature consumes it.

Grounded in what Arke already says

Not a new product. A missing bridge.

The design prototype already establishes the flow: create a production, land on Day One, shape the story in a conversation beside a structured draft, then draft scenes through chat. The current application implements the shells, but the authoring bridge is incomplete — and in two places it is thinner than it looks, which the code check below sets out claim by claim. This feature connects those approved ideas and extends them carefully for serial video and micro-drama work.

01 / CURRENT CODE

Day One already exists.

The production dashboard already inherits cast, Canon, and tone, and offers a first-scene path. Creation does not navigate there yet, and Story is not merely unstyled: nothing in the codebase writes story.json, so the overview is read-only until a file is authored by hand.

02 / APPROVED PROTOTYPE

Story is already conversational.

Prototype frame 10b puts "Find the spine together" beside an Overview draft. Frame 9a does the same for scenes. The proposal holds staged work; accepted production files become authoritative only after a separate review and Accept action.

03 / AGREED EXTENSION

Series, seasons, and progressive detail.

Micro-drama remains a Video profile. One Series can hold several Season productions; users begin with Season 1 and see only the episode board until later seasons or genuine branches make deeper structure useful.

The distinction that keeps the experience coherent.

World Chat asks, "What belongs to this world?" The Story workspace can move between Series, Season, and Episode scope. Scene chat asks, "What happens in this moment, and how should it be covered?" Generate permits shot-local prompt overrides and explicit dispatch, but it cannot mutate Canon, the season architecture, or scene script. The interfaces may share a conversation framework, but their scopes and candidate types are different. That shared framework — a durable thread, typed candidates that exist before any proposal — is issue #70's, and it is unbuilt. Today the only conversational surfaces are entity-scoped chats on a canon thread or a sheet, and they stage a proposal before the first turn rather than after exploration.

The simplified professional hierarchy

Keep the depth. Reveal only the next useful level.

Arke stores the hierarchy that makes a long-running series coherent, but the user mainly moves through three creative workspaces: Season board, Episode workspace, and Scene workspace. Creating the first micro-drama creates the Series and Season 1 together. Series management becomes prominent only when Season 2 exists.

OPEN / MUST SETTLE FIRST

Where does a Series live on disk?

The world layout puts productions/<slug>/ flat under the world root. A Series is a new durable owner between world and production, and the folder is the only durable truth. The recommendation: keep it a thin joining record — id, title, engine prose, ordered season production ids — and leave recurring cast in world sheets. A Series that describes characters becomes a second place a character exists, which is the drift SPEC-012 D1 exists to prevent.

OPEN / DOWNSTREAM

Seven episodes are seven deliverables.

The cut is derived by sorting every scene in the production into one timeline. If an episode is a range over scenes, then the cut, exports, and the export presets all need an episode dimension, and the presets are landscape-only today. That is SPEC-013 work this brief implies and must name.

OPEN / CHEAP NOW, EXPENSIVE LATER

Scene order is in the file name.

Inserting an episode before another episode renumbers scenes, and a scene's number is part of its file name — so a renumber renames the file and moves its history path. Chapters solved this by putting order in frontmatter. Scenes should be fixed before episodes reference scene ranges, not after.

One shot plan, two kinds of storyboard.

The editorial Scene board is the human view of every accepted shot and may contain placeholders. A Generation storyboard is compiled for one provider request after a model is selected. It may be text-only, a panel sheet, ordered frames, or native shot objects. Both are derived from the accepted shot plan; neither becomes a second script.

Continuity / boundary chained

Pass 2 waits for the reviewed final owned frame of pass 1. Slower, but the boundary is intentional.

Alternative / independent

Run passes concurrently for speed. The cut may need stronger visual repair at the join.

Oversize shot

A shot longer than the cap must be shortened, split explicitly, or sent to a longer-cap model. Arke never splits it silently.

Prerequisite / frame transport

Boundary chaining needs a start frame inside the request. Today the pinned frame is computed, chained on accept, drawn on the board, and never sent: no dispatch path attaches one, and the model's declared frame capability is used only for picker copy and a warning. This must be built before the pass plan, not alongside it.

Prerequisite / vertical output

A 9:16 micro-drama has nowhere to land. Aspect is computed only for character images; shot dispatch carries prompt, references, duration, and provenance. The video path needs an explicit output spec and per-model aspect capability.

Chained authorization is durable and explicit

Review dispatch creates one scene-dispatch plan with pass dependencies and an aggregate maximum estimate. It may pre-authorize every dependent request, but Pass 2 is materialized and submitted only after Pass 1's boundary frame is durable. A review-gated policy stops after Pass 1 and requires another visible dispatch before later spend. Dependency, cancellation, and stale-boundary state belong to the durable queue plan, never an in-memory UI timer. None of this exists: a job carries its own estimate with no dependency field, and a whole-scene dispatch enqueues every pass at once. An authorization that outlives a single job needs its own restart and reconciliation story against SPEC-009, which makes it the one item here that deserves a specification of its own rather than a roadmap line.

LINEAR

One route is still a graph.

Episode order, hooks, cliffhangers, and payoffs can be analyzed without showing nodes and edges to the user.

BRANCHING

Complexity appears honestly.

Choices, conditions, merges, and endings become visible only when authored. The graph answers what can happen, not what media is selected.

HEALTH

Structure, never taste.

Reachability, dead ends, missing payoffs, route coverage, duration, and budget are computed. Arke never scores whether the story is good.

Overall Arke architecture

Eight questions, eight owners.

The feature works only if it refuses to collapse distinct records into one graph or one conversation. This table is the implementation boundary: each question has one durable owner, while dashboards, graphs, health, budgets, and cuts are derived views over those owners.

Build in this order

Items 1 to 3 ship against the architecture as it stands today and need no new entity. Everything after item 4 depends on a conversation layer this repository does not have.

  1. Ship the creation handoff.Navigate to Day One on create, matching prototype 6a to 33a. The coordinator already computes the production slug and throws it away, and the message carries no request id — so this needs an acknowledgement frame, not only a route change.
  2. Let Story author its own overview.Write story.json through the existing gate using the reserved story-overview proposal kind, and correct the master layout, which still lists only story.md. The read side already distinguishes structured overview from treatment prose; this is a writer and a documentation fix, not a model decision.
  3. Finish SPEC-012 R-3's second seed source.Uncovered work from other productions, which Day One and this brief both lean on and which no code produces.
  4. Land issue #70's conversation and candidate layer.Durable threads and typed candidates that exist before a proposal. Every scoped conversation below consumes it; building Story threads first would either duplicate that design or silently force it.
  5. Move scene order out of the file name.Order in the file, stable name, as chapters already do. Inserting an episode renumbers scenes, and today a renumber renames files and moves history paths.
  6. Specify production entities.Define Series foundation, Season Production profile/direction, Episode cards, episode boundaries, graph, proposal materialization, rebase, and ripples before building candidate types. Settle where a Series lives on disk first.

  8. Add the missing Scene script layer.Extend Scene with stable action/dialogue blocks, let shots cite covered blocks, and derive coverage/staleness before generation.
  9. Make Story, Episode, and Scene conversations real.Persistent scoped threads with typed candidates against the now-defined production entities and ordinary proposal acceptance, on top of item 4.
  10. Make the cut and exports episode-aware.Seven episodes are seven deliverables. The cut derives one timeline from every scene in the production; an episode range needs its own cut, its own export, and vertical presets.
  11. Add frame transport.Carry start and end frames into the provider request. Declared per model, computed per shot, warned about at dispatch, and never sent today — and chained passes cannot work without it.
  12. Compile boards and model-aware passes.Keep the editorial Scene board local; compile provider-ready Generation storyboards per pass from model duration, storyboard transport, frame, reference, audio, and shot-count capability.
  13. Specify, then build, durable scene-dispatch plans.Aggregate authorization, pass dependencies, late boundary-frame materialization, cancellation, retry, and review-gated versus pre-authorized downstream spend, preserving SPEC-009's durable-before-network rule.   14. Migrate linear order deliberately.Legacy productions continue to derive order from Scene.number. A graph-enabled production switches authority only through an accepted migration proposal; cuts then traverse the graph route rather than sort scene numbers.
  15. Add branching deliberately.Choice, outcome, merge, ending, typed state, playtests, route health, and branch budget. Branching Video remains a future profile decision, not an implicit v1 format change.
The collective product decision.

Do not make World Chat the universal front door. Do not create a second disconnected Director app. Keep Day One as Season Production home, evolve Story into a scope-aware Series / Season / Episode workspace, keep scene chat contextual, and reveal graph complexity progressively. Script answers what happens; shots answer how it is filmed; the editorial board shows the complete shot plan; model capability compiles one or more generation storyboards. The shared framework is conversation + candidates + proposals; explicit dispatch remains the only spend boundary.

And a decision about this document. It is a brief, not a specification: no frontmatter, no numbered requirements, no acceptance criteria, no testing section — nothing here is estimable yet. It should become three things. Items 1 to 3 of the roadmap are ordinary issues that can be written today. Items 6 to 9 belong in one specification for production entities, gated behind issue #70 landing. Item 13 belongs in a specification of its own, gated behind frame transport.
