Arke Studio · feature brief · revision 1

Interactive video — direct routing, a branch map, and named findings

The implementation authority for epic #401, accepted through issue #392. Sources: the revised Scope §01, §03, §11; design turn 78; SPEC-023 (the narrative domain); SPEC-012/019 (scenes, dispatch). Revision 1, 2026-08-20. Nothing here is implemented because it appears here — this is the decision record #401's issues build against.

1 · The bound boundary, restated as schema law

Binding. A choice selects the next scene and does nothing else. No variables, conditions, unlocks, inventory, statistics, relationships, or hidden author logic — not as disabled features but as fields that do not exist. Every routing schema is strict(): an imported document carrying a condition key fails parse with the key named, which is what "unrepresentable" means in this codebase.
Binding. Playback state belongs to the player. Current scene, position, selected route and resume progress live in the player's local store (preview: the app's session state; export: localStorage of the self-hosted page), are never written into the world, and are never readable by authored content.
Amended by turn 100. Interactive is a Video kind, not a third medium. Current creation writes medium: "video", kind: "interactive" from the Video kind step. The old interactive-video medium remains readable and resolves to this shape. The branch map draws for the Interactive kind alone.
Binding. Findings, never a score. Validation reports named findings with evidence; no percentage, no health number, no aggregate grade exists anywhere in the medium.

2 · Domain: files, IDs, schemas

Scenes are ordinary SPEC-012 scenes — same files, same shots, same dispatch. What Interactive video adds is one routing record per production, the single graph authority (the same one-authority shape as SPEC-023's episode.scenes): 

productions/<slug>/routing.json         · versioned track "routing", gated field-by-field
{
  "version": 3,
  "start": "sc_01",                        · exactly one start scene
  "choices": [                             · the complete edge list, in authored order
    { "id": "ch_dawn-or-dark", "from": "sc_01", "label": "Wait for dawn", "to": "sc_02" }
  ],
  "endings": [ { "sceneId": "sc_09", "title": "The bell answers" } ],
  "excluded": [ { "sceneId": "sc_07", "reason": "held for a later season" } ],
  "groups":  [ { "id": "grp_act-1", "title": "Act I", "scenes": ["sc_01","sc_02"] } ]
}
  • Choice: ch_<slug>, exactly { id, from, label, to }, strict. Ids survive edits and reorders; labels are the words the player reads.
  • Ending: a designation of an existing scene, never a second scene kind. A scene listed in endings offers no choices; one listed with outgoing choices is a named finding.
  • Deliberate exclusion: the durable record that makes "unreachable" an author's decision rather than a validator's guess. Carries its reason; surfaces in the map, dimmed.
  • Groups: optional, non-logical, presentation-only. A scene may appear in one group. Groups carry no routing, no gates, no logic — a group with any other field fails parse.
  • Publication state lives on the production (status, change-logged) plus the export record (§6); routing.json stays the graph and nothing else.
  • Provenance: routing.json is versioned and gated, so every change is a proposal or a direct edit with a change line — the same audit trail every other track has.

Episodes, reconciled with SPEC-023

Interactive video v1 ships one kind, interactive, which is not episodic: SPEC-023 R-11's "every scene in exactly one episode" applies to episodic kinds only (EPISODIC_KINDS) and Interactive video does not join that set. If a future episodic Interactive kind arrives, Episode is a release grouping over publications — which routes ship together — never scene ownership, because a reconverging scene belongs to every route that reaches it. That decision is recorded here so #393's unqualified rule is never inherited by accident.

3 · The branch map

The structural view for this Video kind only (design turn 78 third binding; reassigned frame 34e). Deterministic layered layout, no dependency: longest-path layering from the start scene, stable in-layer order by authored choice order then scene id — the same graph always draws the same picture, and no force simulation ever jiggles an author's mental map. No external layout library: the graphs this kind allows (hundreds of nodes, not millions) do not justify a licensing surface.

  • Editing: choices are created by drawing from a scene's out-port to a scene, renamed inline, retargeted by dragging the arrowhead, deleted with confirmation naming what breaks. Every edit is a routing.json commit through the gate.
  • Keyboard and focus: every node and edge reachable by Tab/arrows in layout order; Enter opens, Delete removes with the same named confirmation; the map is a listbox to a screen reader, each node announced as "scene title, N choices in, M out".
  • Zoom/pan: wheel and keyboard (+/−/0), fit-to-view default; large maps virtualise by layer and offer a minimap past 60 nodes; reconvergence draws as edges joining an existing node, never a duplicated node.
  • States: start (ringed), ending (flagged), excluded (dimmed with reason on hover/focus), unreachable (finding badge), empty map (one card: "Draw the first choice from the start scene").
  • Narrow windows: below 900px the map lists layers vertically, edges as "goes to" rows — the same data, no horizontal scroll of the page.
  • Threads: the production's Development thread (SPEC-023) gains routing candidates — a proposed choice/edge materialises into routing.json through the same gate as everything else.

  • Traversal evidence is durable: the preview player appends productions/<slug>/routing-evidence.jsonl lines { ts, routingVersion, choiceId, route }. Evidence is version-scoped: a line recorded at routing v3 counts only while the choice it names still exists with the same from/to; a retargeted edge sheds its old evidence at once.
  • Stale findings: findings are derived, never stored — the fold of routing.json + evidence + scene list, recomputed on read, so a graph edit can never leave a finding lying about a shape that no longer exists (the SPEC-023 script-digest pattern).
  • Reconvergence continuity is checked with the canon Arke holds: both inbound routes' scenes are compared for contradictory establishment (a death on one route, a survival on the other, feeding one continuation) — flagged with both routes named, resolved by neutralising the shared scene or splitting continuations. Warns, because only the author knows what the shared scene actually assumes.

5 · The player

  • Local preview runs in the app: plays the current cut of each scene, presents choices at scene end, records traversal evidence, and offers route-so-far and restart controls. Resume/route state is playback state (§1) — kept per production in app-local state, never in the world folder.
  • Playback state schema (player-owned, both preview and export): { sceneId, positionSec, route: choiceId[], updatedAt }. Nothing else exists to persist, by construction.
  • Accessibility: choices are buttons with labels, keyboard-first, with a configurable choice timer default OFF (an untimed choice is the accessible default; a timed one is a per-production option with a stated default action). Subtitles ride WebVTT tracks per scene cut.

6 · Delivery: exportable first

  • The export is a folder: player.html (self-contained, inline CSS/JS, no network), manifest.json (routing snapshot + media map + version + provenance: production, routing version, export stamp, content hashes), and media/ (one file per published scene, plus VTT). Relative paths only; it plays from file:// or any static host; offline by construction.
  • Deterministic export validation: the exporter re-reads its own output, verifies every manifest hash against the copied bytes and every choice destination against the shipped scene set, and refuses (naming the file) rather than shipping a package that cannot play.
  • Publication gate: export refuses while any blocking finding stands (§4), in the findings' own words.
  • Managed hosting (an Arke URL) is a later paid convenience and never the only route — exportability is the local-first promise kept.
  • Privacy: the exported player stores playback state in the viewer's localStorage, sends nothing anywhere, and carries no telemetry of any kind.

7 · Canon promotion

A branch outcome never becomes world canon by implication. Promotion is an explicit proposal through the existing gate, whose draft records the source — production, ending or outcome scene, and the route that reaches it — so the canon entry's provenance names the branch it came from, and the gate's ripple view shows what the promotion touches before anyone accepts it.
