# Steering an active conversation

Public implementation brief for [issue #1138](https://github.com/michaeljosiah/ArkeStudio/issues/1138), recorded on 13 September 2026. Implementation progress and review belong on that issue; the capability remains proposed.

## Problem and desired behavior

An author should be able to correct Arke while it is answering: “Keep her motivation, but make the scene quieter.” Today the busy composer blocks submission and the WorldChat runner refuses a second send while the conversation has an active run. The author must wait or stop and restart to add direction.

Add **Add to reply** for verified native steering and **Send next** for an explicit, durable next-message queue. Show whether the message entered the current reply, is waiting, is paused, or has an uncertain delivery outcome. Keep the existing single-run and approval guarantees.

## Specification and status

The detailed specification is in the owner's private document set at `specifications/045.steering-an-active-conversation.md`, following the repository's document policy. ## Scope

- World Chat and production, episode, scene, chapter and editor conversations sharing the WorldChat runner and log.
- Typed corrections and submitted final voice transcripts, with existing attachment, selected-subject and reply-only constraints.
- Explicit current-reply versus next-reply delivery, durable input identity, FIFO queueing, accurate receipts, Stop, reconnect and restart recovery.
- Provider-neutral adapter controls and verified native execution/input correlation.
- Context/evidence, structured-result repair, approval provenance, compatible persistence and shared composer accessibility.

Independent Genesis, Stage construction and proposal-authoring runners are outside this first scope. Adding Codex as an engine is #1125; model selection and per-agent overrides belong to #1122–#1124. This issue changes neither media-job authorization nor automatic approval.

## Acceptance criteria

- [ ] **Editable during work:** the composer keeps typing, selection, focus and attachments usable. It offers Add to reply when the current engine/phase can safely steer; otherwise Send next with a clear reason. Stop remains available. (R-1–R-2, R-30–R-31)
- [ ] **One durable message:** persist input before clearing the editor, acknowledging success or calling the harness. Retrying a submission uses the same identity and produces one row; changed-payload reuse is refused. Capture world, conversation, run, subject and constraints at submission. (R-3–R-4, R-20)
- [ ] **One active run:** serialize admission, completion, cancellation and queue advancement without holding a lock across model/network waits. Never run two answers for one conversation or let a late correction reach a successor. (R-5, R-10)
- [ ] **Honest delivery:** distinguish native acceptance from confirmed model-input inclusion. Show Sending, Added to this reply, Queued for next reply, Paused or Delivery unclear from observed state. Assistant prose is not delivery evidence. (R-6, R-9–R-13)
- [ ] **Ordered and bounded:** preserve submission order; a later input cannot overtake an earlier queued input. Keep the existing per-message limits and cap unresolved additional inputs at ten, with unsent text preserved on refusal. (R-7–R-8)
- [ ] **Explicit fallback:** unsupported engines and non-steerable phases use the coordinator's queue. Do not emulate steering by cancelling/restarting, changing models or dispatching an ordinary second prompt. Do not inject direction into compaction, repair or finalization. (R-9–R-15)
- [ ] **Stop stays stopped:** Stop pauses queued work before requesting native interruption. Failure, timeout, budget end, restart, world close, ownership loss and uncertain delivery also pause. Continue is explicit; reconnect or another Send cannot restart the queue. (R-16–R-21)
- [ ] **Safe recovery:** uncertain native delivery is reconciled using its original identity and never blindly retried. Explicit recovery requires the earlier execution to be settled/fenced. Queue removal is revision-checked and cannot pretend delivered input was unsent. (R-13, R-17–R-20, R-28)
- [ ] **Correct context:** the final reply records which user inputs it could have answered. Included corrections survive summaries and explicit Retry once, in order. Queued or uncertain messages cannot support the current answer's evidence. New attachments/targets cannot widen the active run's access; incompatible changes queue as a whole input. (R-12, R-22–R-24, R-26)
- [ ] **Approval remains exact:** steering supplies intent, never approval. Cards from the affected run cannot be approved against unresolved or obsolete input provenance. Previously approved effects use their existing cancellation/undo workflow. Reply-only and selected-passage restrictions survive. (R-24–R-25)
- [ ] **Compatibility and privacy:** raise the world compatibility boundary before new durable semantics; preserve old logs and make older builds refuse incompatible worlds. Keep authenticated transport and content-free diagnostics. (R-20, R-27–R-29)
- [ ] **Proven support:** at least one supported live engine passes true native steering, completion races and interrupted/lost-receipt recovery; every remaining shipped engine passes the visible queue fallback. An enabled composer or passing mock alone does not complete this issue. (R-32)

## Implementation work

1. **T-1: protocol evidence.** Record exact supported engine versions and prove active-turn targeting, correlated inclusion, completion ordering, reconciliation and interruption. OpenCode v2 inbox events, Claude SDK input iteration and Codex app-server steering each need their own proof. If no available engine meets the contract, report the gap before weakening it.
2. **T-2: contracts and compatibility.** Define input/queue receipts, native attempt correlation, final run provenance and the persistent compatibility boundary.
3. **T-3: durable coordinator scheduling.** Reuse the conversation event log and its flushed appends; add the input scheduler, queue controls, duplicate-content checks and lifecycle fencing.
4. **T-4: runner, context and approvals.** Attribute all messages/results to their native attempt, preserve admitted corrections through repair/retry, and validate output/cards against a closed input boundary.
5. **T-5: adapters.** Add proven native controls and normalization, with explicit queue fallback elsewhere. Coordinate Codex work with #1125.
6. **T-6: shared UI.** Update World Chat and the shared production conversation composer, status projection, pending rows and accessibility. Cover chapter/passage, reply-only and submitted voice input.
7. **T-7: verification and documentation.** Complete SPEC-045 §3.2's 25-case test matrix and update the code map/testing guide when implementation changes entry points or commands.

## Verification

Use controlled native-server/SDK fixtures and synchronization barriers. Assert request counts, exact identities/input contents, durable events and side effects. Cover duplicate sends; completion before/after offer; stale run ids; late events; Stop/removal/promotion races; crashes at each delivery boundary; reconnect; routing changes; constraints/attachments; summary/retry; evidence and approval gates; incompatible readers; IME/keyboard and voice submission.

Run the implementation code gate (`npm run lint`, `npm run typecheck`, `npm run build`, `npm test`) and Windows/Linux CI. Run client tests from their workspace and typecheck after test edits. Verify the shared flow in a packaged sandboxed Electron file page, including reconnect and actual native interruption. Keep paid/live probes explicitly opt-in with synthetic prompts. Documentation-only changes require link and content checks; the application gates above apply to implementation changes.
