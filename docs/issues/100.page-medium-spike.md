# 100 — The page spike: what held in SPEC-026 and what did not

SPEC-026 was written before anything had rendered a page. It rests on three assumptions that
nothing in this repository had tested:

1. that prompt-level space reservation works against real image routes (R-6b);
2. that type composited over generated art reads as a designed page rather than a caption
   pasted on a picture (R-6);
3. that **one renderer** can serve both the editor's page and a 300dpi print document (R-11a).

Assumption 3 is the one the spec cannot survive losing. R-11a is the product's central promise
stated for paper — *the page a parent approves is the page that arrives* — and if screen and
print need two layout engines, the approval is a guess.

This is the result of rendering one page end to end. **Throwaway code**, kept out of the tree;
what is worth keeping is below.

---

## 1. What was run

One page of a picture book: full-bleed art, one narration run from an `action` block, one balloon
from a `dialogue` block attributed to a speaker, on an 8.5×8.5in trim with 0.125in bleed and a
0.375in safe area.

The art is real — `kids-page1.png`, recovered from `bdd14e9^`, generated for the Kids design
canvas in the ART style. It is a genuine picture-book illustration with no text in it, which
makes it the right subject: the case R-6 describes.

Everything ran in Electron 43's Chromium, which is the renderer the product already ships.

§2–§6 need no provider. §7 is a separate live test of R-6b against fal, using the key already in
the desktop app's credential store.

| Rendering | What it is |
|---|---|
| `print` | The page at trim size, through `printToPDF` with `preferCSSPageSize`. |
| `screen` | The identical document, scaled by `transform: scale(0.62)`. |
| `reflow` | The naive preview — page box re-laid-out at 62%, type left at its absolute point size. Present only to be measured. |

Each rendering was probed by walking every editorial run character by character, grouping the
characters into line boxes, and reporting each line's **text** and **rect in page-space inches**.
That measures the thing that actually breaks: where the words break, and where the lines sit.

## 2. R-11a holds — and the mechanism is scaling, never re-layout

| Comparison | Line breaks identical | Line geometry within 0.01in |
|---|---|---|
| screen vs print | **7/7 (100%)** | **21/21 (100%)** |
| reflow vs print | 0/12 (0%) | 5/21 (24%) |

**What was compared, precisely.** Both figures above are DOM line boxes: the screen-mode DOM
against the **print-mode DOM**. That is not the PDF. Everything after layout — export scaling,
clipping, pagination, font substitution — happens past the last DOM a walk can see, so the table
above is evidence about the layout, not about the artefact.

Reading the exported PDF's own content stream afterwards (inflate, track the text matrix, group
glyph runs by baseline) closes part of that gap and not all of it:

| | DOM | PDF content stream |
|---|---|---|
| narration lines | 5 | **5** |
| balloon lines | 2 | **2** |
| speaker label | 1 run | **1 run, 4 glyphs** |
| point sizes | 19 / 15 / 9 | **19 / 15 / 9** |
| leading | 0.375in | **0.375in** |
| absolute placement | x 4.205in, y 0.840in | **not confirmed** |

Line count, font sizes and leading match exactly, and Georgia is embedded and subsetted, so no
substitution occurred. Absolute placement did not reconcile: the parser's frame is offset by a
constant it did not resolve, and whether that is Chromium's page transform or the parser's own
composition was not run to ground. **So: the layout is one layout, and the PDF carries the same
lines at the same sizes with the same leading. That the PDF places them at the same absolute
coordinates is consistent with what was measured but not demonstrated by it.**

**And the exported file names no cut line.** Chromium's `printToPDF` emits `/MediaBox` and nothing
else — no `/TrimBox`, no `/BleedBox`, no `/CropBox`. The 8.75in page is all a vendor sees, with no
indication that 8.5in of it is the book. The trim being an inset the *layout* knows about is
invisible in the artefact, so print boxes are a post-pass over the exported bytes rather than
something the renderer can be asked for. That is the second thing the Chromium path cannot do
unaided; the timestamps in §3 are the first.

One renderer is achievable, and the way to get it is narrow:

- express the page in **physical units**, so a slot rect means the same thing in both places;
- print with `preferCSSPageSize` so the document's own `@page` rules the paper — the exported
  `/MediaBox` came back `8.75×8.75in` exactly, from the CSS and not from the export call;
- preview by **scaling the print layout**. Layout happens once at trim size and is only painted
  smaller, so line breaks cannot diverge — they are the same layout.

The reflow row is why R-11a deserves to be a requirement rather than a note. It is not the same
page with slightly different spacing. A five-line paragraph became eight lines, the balloon went
from two lines to four, and **not one line of the twelve broke where the printed page breaks
it**. A parent approving that preview approves a page that does not exist.

> `"Pip had never once put a paw in"` — printed
> `"Pip had never once"` — the preview of the same page

**Nothing in the spike had to branch on destination inside the page.** The one place the two
renderings differ is the shell around `.page` — an `@page` rule on one side, a transform on the
other. That is the shape R-11a should be held to: if anything inside the page reads the
destination, the two renderers have already started to drift.

## 3. R-11's byte-identical claim is false as written

Two exports of an unchanged page differ in **exactly six bytes**: the seconds field of
`/CreationDate` and of `/ModDate`. Everything else — all 1.9MB, including every image — is
identical.

```
/Producer (Skia/PDF m150)  /Creator (Chromium)
/CreationDate (D:20260822210059+00'00')   <- run 1
/CreationDate (D:20260822210202+00'00')   <- run 2
```

So the *rendering* is deterministic and R-11's intent is sound. But the requirement as written —
*"the outputs are byte-identical"* — fails its own test against the writer the product uses, for
a reason that has nothing to do with the book. Two exports in the same second pass; two exports a
second apart do not, which is worse than failing outright because it will pass in CI and fail for
a user.

**R-11 needs a clause normalizing time-varying document metadata.** Six bytes, and then the
requirement is true and testable.

## 4. Editorial text is real vector type

`/FontFile` present, `/BaseFont /AAAAAA+Georgia` — the typeface is embedded and subsetted. R-6's
rationale holds literally: text kept as a layer arrives as vector type a printer can set, not as
pixels baked into a take.

The balloon's translucent rounded backing and its shadow rasterize as a `/DeviceGray` soft mask,
at **314×278 dpi** over the balloon's own 3.40×1.36in box. That is print-adequate, and it is
worth knowing that CSS effects rasterize while the type does not.

## 5. Print resolution is an upstream problem, not a renderer setting

The art embedded at **942×941px across an 8.75in page — 108 dpi**.

This is not the renderer downsampling, and it cannot be fixed by asking it for more. The same
document was printed at four zoom factors:

| zoom | page box | art px | art dpi | lines |
|---|---|---|---|---|
| 1 | 8.75×8.75in | 942x941 | 108 | 7 |
| 2 | 8.75×8.75in | 942x941 | 108 | 7 |
| 3 | 8.75×8.75in | 942x941 | 108 | 7 |
| 4 | 8.75×8.75in | 942x941 | 108 | 7 |

Chromium embedded the visible crop **at its native resolution**. There were never more pixels.
Two upstream causes, and both belong in the spec:

- **The take is too small.** 941px on its short edge. 300dpi at this trim needs 2625.
- **`cover` threw away 44% of the width.** A 1672×941 image cropped to a square keeps 941 of
  1672 columns — and in this case the crop amputated the protagonist, who was composed into the
  left third. The art was fine. The layout ate it.

### Which routes can actually print

Of the seven image routes in the shipped manifest:

| route | provider | square-page edge | 300dpi up to |
|---|---|---|---|
| `nano-banana-2` | fal | 4096px | 13.65in |
| `nano-banana-pro` | fal | 4096px | 13.65in |
| `text2image_soul_v2` | higgsfield | 2048px | 6.83in |
| `flux-2-pro` | fal | 2000px | 6.67in |
| `gpt-image-2` | openai | 1024px | 3.41in |

**Two of seven reach a board book.** The rest cannot produce a printable page at any trim a
picture book uses, and `gpt-image-2` — the obvious default — tops out at 3.41in.

The good news is that both print-capable routes offer `1:1`, `4:5`, `3:4` and `2:3`, so the
aspect a page needs is purchasable today. Nothing currently asks for it. **R-6b tells a dispatch
to express the reserved region and to suppress text; it does not tell it to ask for the page's
aspect ratio**, which is the failure that actually destroyed this page.

## 6. Legibility over art is computable, and R-13 does not list it

The same art, the same renderer, two layouts — one with the type in the reserved region, one with
it moved onto the busy lower-left quarter. Contrast sampled from the composited page, ranked, and
read at the 5th percentile:

| layout | run | mean | p05 | verdict |
|---|---|---|---|---|
| reserved region | narration | 8.70 | **7.17** | ok |
| dark quarter | narration | 4.13 | **1.26** | fails 4.5:1 |

Both layouts are valid by every rule SPEC-026 currently states. Both sit inside the safe area,
inside their slots, within their declared degrees of freedom. One of them cannot be read.

This is exactly R-13's shape — *computed from the derivation, never stored as a flag, reported
with the measurement that produced it* — and it is missing from R-13's list. So is effective
resolution. Those two are the findings that will actually bite, because **neither is visible on
screen**: a 108dpi page and an unreadable caption both look perfect in the editor at 62%.

*Caveat: a run on a backing is scored against the art behind it, which is wrong when the backing
is opaque. The real measure composites the backing first. The spike flags backed runs instead of
scoring them.*

## 7. R-6b against a live route: one half works, the other does not

Four dispatches to `fal-ai/nano-banana-2` at 1:1 and 4K, using the key already configured in the
desktop app, one variable at a time. Same scene, same character locks, same ART suffix. $0.32.

| | reservation | text negative | detail in reserved region | ink contrast there | text in the picture |
|---|---|---|---|---|---|
| **A** control | — | — | 0.86× the rest | **2.28** | **yes** — *Sea Breeze*, *Morning Star* |
| **B** reserve only | yes | — | **0.30×** | **12.08** | no |
| **C** suppress only | — | yes | 1.16× the rest | **1.88** | **yes** — *Doris*, *The Gull*, others |
| **D** both | yes | yes | **0.36×** | **8.80** | no |

*Detail is mean gradient magnitude inside the reserved rect against the rest of the frame. Ink
contrast is the 5th-percentile WCAG ratio a page's narration colour would get over that region;
4.5 is the readable threshold.*

### The reserved region works, decisively

Composition guidance took the reserved quarter to **0.30–0.36×** the detail of the rest of the
picture, and the worst-case contrast for type set over it from **~2:1, unreadable**, to
**8.8–12.1:1**. That is the difference between a page whose words cannot be read and one whose
words sit comfortably, from prompt language alone. **R-6b's reserved-region half is verified.**

### The negative control does not

C carried the strongest text negative I could write — *no text, no lettering, no words, no
writing, no letters, no numbers, no signage, no captions, no watermark* — and the model lettered
the boat hulls anyway. It produced **more** lettering than the control did.

So this, from R-6b's own rationale, is false:

> *Preventing generated editorial text is cheap and reliable. Removing it afterwards is neither.*

It is cheap. It is not reliable. And **what actually removed the text was the composition
guidance, not the negative** — B carried no text negative at all and came back clean, because
emptying the region and simplifying the scene removed the surfaces that attract lettering in the
first place. The negative was the half that did nothing.

### Diegetic text arrives unbidden

Nobody asked for *Sea Breeze*, *Morning Star*, *Doris* or *The Gull*. Both unreserved variants
invented boat names. R-6a is written as though diegetic lettering is something a prompt requests —
*"WHEN a prompt asks for diegetic lettering THEN the request SHALL name the exact string"* — and
so nothing records the string when the model supplies it uninvited. The guarantee R-6a exists to
give, that what the picture says is readable without looking at the picture, does not hold for the
case that actually occurs.

**This flips the reasoning under open question 3.** Text removal was held back because it is *"a
repair path for a case prevention should make rare."* Prevention does not make it rare.

### Also confirmed

1:1 at 4K returned **4096×4096** — 468dpi at an 8.75in trim. The aspect and the resolution a page
needs are purchasable today (§5, R-6c). Generation took 36–41s per image.

**Caveat: one image per variant, one scene, one route.** The separation is stark enough to act on
and the mechanism is legible in the pictures, but this is four images, not a study. What it
establishes is that the negative control *can* fail on a plain scene — which is enough, because
R-6b was relying on it not failing.

### One thing the recovered art shows

`kids-spread` was generated **with the gutter drawn into the picture**. Under R-3 a spread is
derived and the gutter comes from the print profile, so art generated as a spread is wrong at the
model level, however good it looks. Worth a line in the art direction, not the spec.

## 8. Proposed amendments

| Requirement | Change | Evidence |
|---|---|---|
| **R-11** | Normalize time-varying document metadata before the reproducibility claim | §3 — six bytes |
| **R-11a** | Name the mechanism: one layout pass in physical units, preview by scaling it, nothing inside the page branches on destination | §2 — 0/12 line breaks the other way |
| **R-13** | Add **effective resolution** and **text legibility over art** to the computed findings | §5, §6 — 108dpi and 1.26:1, both invisible on screen |
| **R-6c** | A dispatch expresses the **page's aspect ratio**, not only its reserved region | §5 — `cover` discarded 44% of the width and the protagonist with it |
| **R-6b** | The negative control is best-effort and SHALL NOT be relied on | §7 — the strongest negative produced more lettering than none |
| **R-6a1** | Cover diegetic text the model supplies **unasked**, recorded against the take | §7 — four boat names nobody asked for |
| **R-12** | Profiles carry the resolution and contrast thresholds R-13a fires against | §5, §6 — a threshold in the checker would make every profile this one |
| **Open q. 3** | Reasoning inverted: prevention does not make removal rare | §7 |

### What the evidence does and does not support

Worth stating precisely, because the two halves of §7 rest on different amounts of evidence:

- **"The negative control is not reliable" is established.** It is a refutation, and one
  counterexample settles it. There is one.
- **"The reservation is what works" is not.** One unseeded sample per variant cannot separate the
  reservation from ordinary variance, however clean the separation looks. The *region* measurably
  changed — 0.30–0.36× detail against 0.86–1.16× — but the absence of lettering in both reserved
  variants is an observation, not a demonstrated cause.

The spec reflects that asymmetry: R-6b requires only that nothing trust the negative, and records
the reservation's effect as measured rather than as an invariant. Open question 5 holds the rest.

None of these changes the architecture. A panel is still a shot, a page is still a layout over
panels, the book is still derived. **SPEC-026's foundation held.** What the spike found is places
where the spec was not specific enough to build against — and one, R-6b's negative control, where
it was simply wrong about how the world behaves.
