# 0. Purpose and status

This document is the implementation specification for GitHub issue #70, **Add a worldbuilding
chat that turns conversation into reviewable world changes**.

The issue establishes the product direction. This document settles the architecture and behavior
needed to implement it safely. In particular, it defines the missing layer between an exploratory
conversation and an accepted proposal:

```text
conversation
    -> detected change candidates
    -> explicit user staging
    -> existing proposal and accept gate
    -> accepted world files
```

World Chat is not another wrapper around `draft-with-studio`. Existing authoring starts with a
known file and creates a proposal before the first turn. World Chat starts with a world and an
idea; it may discover no change, one change, or several changes across different entities. It
therefore needs a durable conversation and candidate lifecycle that exists before any proposal.

This specification deliberately preserves the product's strongest boundary:

> OpenCode may discuss and suggest authored changes. Only explicit Studio UI actions may stage,
> accept, discard, or dispatch work. Media generation remains in the job queue. The accept gate
> remains the only path from authored draft to the live world.

# 1. Product contract

## 1.1 Summary

World Chat is a persistent, world-scoped creative workspace. A user may talk naturally about an
open world without first deciding whether an idea belongs in Canon, a character, a location, a
faction, a relationship, an open thread, or an image brief.

The Studio replies conversationally and maintains a separate panel of **detected changes**. Each
detected change is a structured candidate with stable identity, editable fields, stated
settledness, visible world checks, and an independent lifecycle. The user may continue exploring,
edit a candidate in a form, dismiss or defer it, group related candidates, or stage it through the
existing proposal system.

The transcript is not a proposal. A candidate is not a proposal. A staged proposal is not an
accepted world change. Every transition is visible and deliberate.

## 1.2 Goals

- Let the user explore ideas without choosing an entity type or form in advance.
- Preserve the distinction between brainstorming, tentative ideas, unresolved questions, and
  settled facts.
- Check relevant accepted Canon and sheets before describing an idea as new or selecting an
  amendment target.
- Turn concrete ideas into structured, editable candidates with stable identity.
- Let one conversation produce several related or independent changes.
- Keep candidate correction, dismissal, grouping, and staging durable across navigation and app
  restart.
- Reuse proposal materialization, base capture, ripple calculation, rebase, conflicts, and atomic
  acceptance from SPEC-004.
- Reuse the shared Composer and the existing direct forms rather than introducing a parallel set
  of controls.
- Keep actual media dispatch behind an explicit queue action with visible cost.
- Remain useful when OpenCode or the derived index is unavailable.

## 1.3 Non-goals

- A general assistant unrelated to the open world.
- Treating every user sentence as a world change.
- Treating conversational agreement as staging or acceptance.
- Replacing Canon Q&A. Q&A answers from accepted facts; World Chat explores what the world should
  become.
- Replacing direct Canon and sheet forms.
- Letting OpenCode call media providers, enqueue jobs, accept proposals, or commit world files.
- Generating media against unaccepted candidate or proposal state in the first version.
- Semantic/vector retrieval. Existing lexical retrieval remains the v1 authority.
- Multi-user collaboration or cloud synchronization.
- Portable export of unfinished conversations. Normal world export excludes them.
- Vision, audio, or video understanding inside World Chat unless an existing extraction produces
  text the chat can cite.

## 1.4 Required user outcomes

- A user can open World Chat from the world overview or navigation and begin with a plain-language
  idea.
- A user can enter the same workspace from a Canon question or a character/location/faction with
  that context visible and preselected.
- A turn can produce no detected change without being treated as a failure.
- A tentative statement cannot silently become settled Canon or settled sheet content.
- A later correction updates the existing candidate instead of leaving contradictory duplicates.
- A dismissed candidate stays dismissed unless later conversation changes it materially or the
  user explicitly restores it.
- A candidate can be reviewed and edited through the appropriate form without losing the
  conversation.
- Related changes can stage into one mixed proposal and land atomically.
- Independent changes can stage into separate proposals.
- A media opportunity can prefill the correct generation surface but cannot dispatch by itself.
- Conversation and candidate state survives restart; an in-flight model session does not need to.

# 2. Normative requirements

## 2.1 Conversation and persistence

- **R-1** A world SHALL support multiple persistent World Chat conversations, each with a stable
  `cv_<ULID>` identity, title, status, creation time, update time, and optional entry context.

- **R-2** Conversation identity SHALL be a Studio identity, not an OpenCode session ID. Harness
  sessions are ephemeral implementation details and MAY be replaced between turns.

- **R-3** User messages SHALL be appended durably before model dispatch. A failed, cancelled, or
  interrupted turn SHALL retain the user's message.

- **R-4** Completed Studio messages, candidates, groups, dismissals, deferrals, proposal links,
  and run outcomes SHALL survive renderer reload, navigation, app restart, and loss of the
  harness session.

- **R-5** Full conversation history SHALL NOT be embedded in the ordinary whole-world snapshot.
  The snapshot SHALL carry conversation summaries; one conversation SHALL be loaded and paged by
  ID.

- **R-6** Conversation writes SHALL be durable before their corresponding client events are
  broadcast. Reconnecting to a fresh snapshot and loading the conversation SHALL never duplicate
  a message or candidate mutation.

## 2.2 Conversation is not consent

- **R-7** No user or model text, including "yes", "do it", "make it so", or equivalent language,
  SHALL directly stage, accept, discard, or dispatch anything.

- **R-8** Only explicit typed client commands produced by visible UI actions MAY stage a
  candidate, change a proposal, accept/discard a proposal, or enqueue media.

  A conversational request such as "draft that" MAY cause the Studio to refine the candidate and
  recommend it as ready for review, but it SHALL NOT mark it `user-confirmed`. Only the visible
  Review/Stage action may perform the `user-confirmed` transition. This deliberately resolves
  issue #70's otherwise ambiguous phrase "explicitly asks the Studio to draft it" in favor of the
  stronger consent boundary.

- **R-9** The world-builder agent SHALL have no write access to the live world, proposal files,
  conversation records, queue, credentials, shell, process execution, or network tools.

## 2.3 Detected candidates

- **R-10** Detected changes SHALL be represented by a strict discriminated candidate schema, not
  only prose in the assistant reply.

- **R-11** Every candidate SHALL have a stable `cand_<ULID>` identity and an optimistic revision.
  The same proposition corrected over time SHALL retain its identity and increment its revision.

- **R-12** The first version SHALL support these classifications:

  - create Canon;
  - amend Canon;
  - open a Canon thread;
  - create a character, location, or faction sheet;
  - edit a character, location, or faction sheet;
  - change a relationship or cross-reference;
  - propose an image opportunity;
  - undecided classification requiring clarification.

- **R-13** Every candidate SHALL distinguish `settled`, `tentative`, and `unresolved` intent.
  Tentative or unresolved material SHALL NOT stage as a settled fact. Unresolved material MAY
  stage as an open Canon thread.

- **R-14** A turn MAY intentionally produce no candidates. No placeholder or "no change"
  candidate SHALL be created.

- **R-15** Candidate forms SHALL expose every value that would be materialized into an authored
  file. The user SHALL be able to correct classification, target, and values before staging.

- **R-16** User-edited candidate fields SHALL NOT be overwritten by later model output without an
  explicit user action resolving the difference.

## 2.4 Checks and grounding

- **R-17** A candidate that claims an idea is new, an amendment, or related to an existing entity
  SHALL include structured receipts for the accepted Canon and sheets consulted.

- **R-18** Check receipts SHALL be coordinator-owned observations, not model assertions or
  rendered `tool.activity` strings.

- **R-19** Any quoted user, Canon, sheet, or extracted-artifact span used as evidence SHALL be
  mechanically verified against its immutable source and version/hash.

- **R-20** If retrieval is unavailable, the Studio MAY continue brainstorming, but novelty and
  amendment targeting SHALL be marked unknown. The UI SHALL NOT label a candidate confidently
  new merely because no check ran.

- **R-21** Likely duplicates and contradiction candidates SHALL be framed as editorial aids, not
  detected truth. Lexical overlap SHALL NOT block staging by itself.

  A likely duplicate or plausible amendment target SHALL block a Canon-create candidate from
  becoming ready until the user selects an amendment target or explicitly chooses Create anyway.
  A contradiction candidate alone remains non-blocking.

## 2.5 Corrections, dismissal, and grouping

- **R-22** A later correction to the same proposition SHALL update or withdraw the existing
  candidate rather than create a contradictory duplicate.

- **R-23** Dismissal SHALL create a durable tombstone. The same target, fields, and value digest
  SHALL stay suppressed until the user restores it or later conversation changes it materially.

- **R-24** Candidates MAY be placed into an explicit atomic group. Staging an atomic group SHALL
  stage all named candidate revisions in one proposal.

- **R-25** Independent candidates SHALL remain independently stageable. A long conversation SHALL
  NOT imply one all-or-nothing proposal.

- **R-26** A media opportunity SHALL NOT be included in an atomic authored-file proposal. It may
  depend on that proposal, but media dispatch remains a separate action.

## 2.6 Staging and the accept gate

- **R-27** Merely discussing or detecting an idea SHALL NOT reserve a Canon ID, allocate a sheet
  slug, or create a proposal.

- **R-28** Canon IDs and final new-sheet slugs SHALL be allocated by the coordinator at staging,
  under the world serialization boundary. Model output SHALL NOT choose filesystem paths or
  authoritative IDs.

- **R-29** Staging SHALL revalidate candidate revisions, target existence, settledness, evidence,
  and world checks against current state before materialization.

- **R-30** Related Canon and sheet changes SHALL materialize as one mixed `worldbuilding`
  proposal and SHALL land through exactly one SPEC-002 commit.

- **R-31** Every staged target SHALL capture its live base at the moment it enters the proposal.
  Extending a proposal later SHALL capture newly added target bases at extension time.

- **R-32** A staged World Chat proposal SHALL use the existing stale-base, rebase, conflict,
  ripple, re-confirmation, no-op, acceptance, and discard behavior.

- **R-33** Final proposal review SHALL show entity names, actions, fields, before values, proposed
  values, and candidate origins. A list of paths alone is insufficient.

- **R-34** Once staged, proposal files are authoritative. Later model suggestions SHALL NOT
  silently mutate the staged draft. Applying a suggested update to a staged proposal requires an
  explicit UI action and optimistic proposal revision.

## 2.7 Media opportunities

- **R-35** A media candidate MAY carry a target, purpose, rationale, and editable brief. It SHALL
  carry no provider command and SHALL NOT enqueue work.

- **R-36** Opening a media candidate SHALL route to the existing appropriate generation surface
  with its brief prefilled. The existing surface SHALL still show provider/model, references,
  estimate, and the explicit Generate action.

- **R-37** If the brief depends on unaccepted candidates or proposals, Generate SHALL be disabled
  until those dependencies are accepted in v1.

## 2.8 Failure, degradation, and safety

- **R-38** One active model run SHALL be allowed per conversation. Duplicate send request IDs
  SHALL be idempotent.

- **R-39** Every run SHALL be cancellable and bounded by wall-clock and token budgets. Cancellation
  SHALL end the local wait immediately and request harness interruption.

- **R-40** A failed or invalid model result SHALL apply no partial Studio message, candidate, or
  group mutations. The user message and all prior state SHALL remain.

- **R-41** Structured output and evidence failures SHALL receive at most one corrective retry.
  A second failure SHALL be stated and SHALL offer retry/direct-form paths.

- **R-42** Opening another world while a turn is running SHALL invalidate that turn's world-query
  lease and end it with a stated interruption. A turn SHALL never query whichever world happens
  to be open later.

- **R-43** With OpenCode unavailable, existing conversations and candidates SHALL remain readable
  and form-editable. The composer SHALL state why chat is unavailable and link to direct forms.

- **R-44** With the index unavailable, the UI SHALL distinguish retrieval degradation from
  harness degradation.

## 2.9 Privacy, accessibility, and presentation

- **R-45** Conversation content, candidate content, excerpts, attachments, and world names SHALL
  not enter app logs, coordinator logs, diagnostics bundles, crash metadata, or analytics.

- **R-46** World Chat SHALL display whether the selected authoring model is local, cloud, or
  unknown before the first send and when routing changes. The first cloud-routed send is the
  user's deliberate disclosure after that notice; no separate prompt is required on every turn.
  Unknown routing SHALL not be presented as local.

- **R-47** The transcript and detected-changes panel SHALL be keyboard operable, have logical focus
  order, and provide non-color status text. Streaming tokens SHALL not flood assistive live
  regions.

- **R-48** Desktop and narrow layouts SHALL remain usable. On narrow layouts, detected changes
  SHALL become a clearly labelled panel/drawer rather than shrinking forms below usable width.

- **R-49** World Chat SHALL disclose the selected harness/model's retention boundary. Studio
  SHALL request deletion of each ephemeral harness session where the adapter supports it and
  SHALL never claim that a user-installed or incapable harness retained nothing.

- **R-50** A conversation with an active run or unresolved staged proposal SHALL NOT be physically
  deletable. Archiving SHALL remain available, and deletion SHALL require explicit confirmation
  after all proposal links resolve.

# 3. Architectural decision

## 3.1 Add a durable candidate layer

The existing authoring path is:

```text
known path -> proposal -> authoring session -> accept/discard
```

World Chat requires:

```text
world conversation
    -> checked, editable candidates
    -> explicit staging decision
    -> one or more proposals
    -> accept/discard
```

The candidate layer is not optional UI state. Without it, one of two unsafe behaviors follows:

1. every speculative idea creates a durable proposal and possibly reserves IDs; or
2. detected ideas live only in renderer/model memory and disappear on restart.

Candidates are therefore durable World Chat state. They are authoritative before staging. After
staging, the proposal is authoritative and the candidate becomes a linked projection of the
proposal state.

## 3.2 Reuse, do not replace, proposals

World Chat does not introduce a second commit system. It uses `ProposalManager` for:

- whole-file materialization;
- base capture;
- mixed targets;
- ripple preview and authoritative recomputation;
- stale detection;
- field-level rebase and conflicts;
- one atomic commit;
- restart recovery and needs-you contribution.

This feature requires proposal extensions and richer review projections, but it must not create a
parallel "chat commit" path.

## 3.3 Use fresh, bounded model sessions

The durable conversation, not the OpenCode session, holds continuity. Each World Chat turn uses a
new or deliberately rotated session assembled from durable context. This avoids:

- losing continuity on app restart;
- depending on hidden model context that Studio cannot inspect or bound;
- unbounded token growth in a long-running foreign session;
- confusing a provider session ID with product identity;
- a stale session silently querying a different open world.

Session reuse may be introduced later as an optimization only if the assembled durable context
remains authoritative and behavior is identical after session loss.

# 4. Filesystem and persistence model

## 4.1 Location

Store unfinished conversations under the owning world:

```text
<world>/
  .conversations/
    cv_<ULID>/
      conversation.json
      events.jsonl
      checkpoint.json
```

This is operational workspace state, like `.proposals`, not accepted authored world content.

Reasons for world-local storage:

- a world archive carries its unfinished thinking with the world;
- identity does not depend on the current app-root registry;
- restore and manual full-folder copy remain understandable;
- candidate references to world entities cannot become detached from their owner;
- no app-level database becomes a second source of truth.

Normal **Export world** excludes `.conversations`, matching its exclusion of `.proposals` and
other unfinished operational state. A manual full-folder copy includes it.

Introducing `.conversations` requires a world schema-version increment. Older builds otherwise
copy unknown directories during export and would leak conversations despite not understanding the
new exclusion. The migration changes only `world.json.schemaVersion`; no conversation directory is
created until the user starts one. Older builds then refuse the newer world rather than exporting
it incorrectly.

World-local conversation records do not repeat `worldId`. A cloned world may receive a new
`worldId`; local entity references remain valid without a clone-time rewrite.

## 4.2 Files and authority

### `conversation.json`

Immutable identity header only:

```ts
interface WorldChatConversationMeta {
  schemaVersion: 1;
  id: `cv_${string}`;
  createdAt: string;
}
```

Title, active/archived state, current entry context, and `updatedAt` are folded from
`conversation.created`, `conversation.metadata-updated`, `conversation.archived`, and
`conversation.unarchived` events. They are cached in `checkpoint.json` for list discovery. This
leaves one authority instead of racing mutable metadata against the event log.

### `events.jsonl`

The append-only authority for messages, runs, candidates, groups, dismissals, attachments,
proposal links, and resolution events.

Each complete line is a validated envelope:

```ts
interface WorldChatEventEnvelope {
  schemaVersion: 1;
  seq: number;
  eventId: `wce_${string}`;
  at: string;
  requestId?: string;
  event: WorldChatStoredEvent;
}
```

The sequence is monotonic per conversation. A duplicate `requestId` returns the result of the
existing operation rather than appending a second mutation.

### `checkpoint.json`

A derived acceleration file containing the latest folded candidate/group state, summary, and
the event sequence through which it was computed. It is atomically rewritten and may be deleted
and rebuilt from `events.jsonl` without loss.

The checkpoint is not trusted if its sequence is beyond the complete event tail or its schema
does not validate.

## 4.3 JSONL durability

Use the existing crash discipline from world change logs and the job journal:

- serialize writers in-process;
- validate before append;
- append one complete JSON line;
- call `sync()` before reporting success;
- permit truncation to the last complete newline as the sole rewrite of the authoritative log;
- surface malformed interior records as a named conversation problem while retaining valid
  earlier records;
- never rewrite the authoritative event log during ordinary use.

Before each append, verify the expected byte length, last complete sequence, and tail digest
recorded by the in-process conversation writer. A mismatch means another process or program
changed the operational file; refuse the append and surface a conversation-integrity problem.
Ignoring `.conversations` in the world watcher must not mean accepting concurrent external edits
silently.

One completed turn is appended as one terminal event containing the complete Studio message,
verified check receipts, full candidate snapshots changed by the turn, and full group snapshots
changed by the turn. This prevents a crash from persisting the reply without its candidates or
half of a related candidate set.

## 4.4 Watcher, scanner, index, history, and export

`.conversations/` SHALL be:

- ignored by the live external-edit watcher;
- excluded from `scanWorld()` and the accepted-world manifest;
- excluded from the derived index;
- excluded from version history and `changes.jsonl`;
- excluded from ordinary world export;
- included when the complete world directory is archived or manually copied.

Conversation writes are app-owned and must not produce "This world changed outside Arke Studio".

## 4.5 Loading and paging

`WorldBundle` receives only summaries:

```ts
interface WorldChatSummary {
  id: ConversationId;
  title: string;
  status: "active" | "archived";
  updatedAt: string;
  entryContext?: WorldChatContext;
  activeCandidateCount: number;
  needsClarificationCount: number;
  stagedCandidateCount: number;
  lastMessagePreview?: string;
}
```

The full active workspace is loaded by conversation ID and contains:

- metadata;
- the latest 50 messages;
- all non-terminal candidates;
- compact terminal-candidate history;
- active groups;
- current run state;
- current context summary;
- a cursor for older messages.

Older messages are loaded before a sequence cursor. Renderer reconnection reloads this view rather
than depending on event replay.

# 5. Identity and domain schemas

## 5.1 IDs

Keep product and provider identities separate:

| Prefix             | Meaning                                                          |
| ------------------ | ---------------------------------------------------------------- |
| `cv_`              | durable World Chat conversation                                  |
| `turn_`            | one user input and its processing lifecycle                      |
| `msg_`             | immutable user or Studio message                                 |
| `run_`             | one model attempt for a turn                                     |
| `check_`           | one coordinator-owned retrieval receipt                          |
| `cand_`            | one stable detected change                                       |
| `grp_`             | one atomic candidate group                                       |
| `wca_`             | one private World Chat attachment                                |
| `pr_`              | existing proposal identity                                       |
| harness session ID | ephemeral OpenCode identity, never persisted as product identity |

All Studio IDs are generated before the operation they identify and persisted before external
work begins.

## 5.2 Conversation context

```ts
type WorldChatContext =
  | { kind: "world" }
  | { kind: "canon-question"; question: string; candidateEntryIds: string[] }
  | { kind: "canon-entry"; entryId: string }
  | { kind: "sheet"; sheetKind: "character" | "location" | "faction"; sheetId: string }
  | { kind: "attachment"; attachmentId: string }
  | { kind: "media-target"; target: WorldChatEntityRef; purpose: ImagePurpose };
```

The active context is always visible in the UI. Changing focus does not delete earlier messages or
candidates.

## 5.3 Messages and runs

```ts
interface WorldChatMessage {
  id: MessageId;
  turnId: TurnId;
  role: "user" | "studio";
  text: string;
  /** Conversation-private attachment identities, not world artifact IDs. */
  attachmentIds: string[];
  createdAt: string;
}

interface WorldChatRun {
  id: RunId;
  turnId: TurnId;
  basedOnConversationSeq: number;
  status: "running" | "completed" | "cancelled" | "timeout" | "budget-exceeded" | "interrupted" | "failed";
  adapter: string;
  model?: string;
  harnessSessionId?: string;
  harnessCleanup: "not-required" | "pending" | "confirmed" | "unsupported" | "unconfirmed";
  contextDigest: string;
  startedAt: string;
  endedAt?: string;
  safeDetail?: string;
}
```

Streaming assistant text is transient presentation and is never the durable message. Only a
validated completed turn appends the Studio message.

Before remote session creation, persist cleanup `pending` with a deterministic, caller-generated
ownership tag derived from `conversationId + runId`. An adapter may advertise crash-recoverable
session cleanup only when it can create/tag, find, and delete Studio-owned sessions by that tag.
After creation, append a synced `run.session-created` event with the returned session ID before
sending the user's content. On startup, a pending run with no recorded session ID asks the adapter
to find every owned session carrying the tag and deletes them; zero matches confirms there is
nothing to clean, one match is deleted, and multiple matches are all deleted and recorded as an
adapter defect. This closes the crash window between remote creation and local receipt.

An adapter that can delete only by returned session ID but cannot recover by ownership tag does
not advertise crash-recoverable deletion. Persist `unsupported` before send and disclose that
limitation. Harness session IDs and ownership tags are operational identifiers and never enter
diagnostics.

## 5.4 Entity references

```ts
type WorldChatEntityRef =
  | { kind: "world" }
  | { kind: "canon"; entryId: string }
  | { kind: "sheet"; sheetKind: "character" | "location" | "faction"; sheetId: string };

type WorldChatLinkRef =
  | { kind: "canon"; entryId: string }
  | { kind: "sheet"; sheetId: string }
  | { kind: "pending-entity"; ref: ModelOrStoredCandidateRef };

type WorldChatCitableRef =
  | { kind: "canon"; entryId: string }
  | { kind: "sheet"; sheetKind: "character" | "location" | "faction"; sheetId: string };

type WorldChatSheetRef =
  | { kind: "sheet"; sheetKind: "character" | "location" | "faction"; sheetId: string }
  | {
      kind: "pending-sheet";
      sheetKind: "character" | "location" | "faction";
      ref: ModelOrStoredCandidateRef;
    };

type WorldChatCanonRef =
  { kind: "canon"; entryId: string } | { kind: "pending-canon"; ref: ModelOrStoredCandidateRef };

type ModelOrStoredCandidateRef = { candidateId: CandidateId; revision: number } | { temporaryId: string };
```

Model output uses domain references. It never supplies world-relative or absolute paths.

`pending-*` references allow one atomic group to create entities that cite each other before final
Canon IDs or sheet slugs exist. In model output, `{ temporaryId }` may reference a create operation
from the same turn; while applying the complete turn, the coordinator allocates final candidate
IDs first and rewrites every temporary reference to `{ candidateId, revision: 1 }`. No temporary
reference is ever persisted. Every stored pending reference must then name a pinned candidate
revision in the same atomic group and staging request. Staging allocates all entity identities
first, resolves the reference graph, then materializes files. A missing, stale, independently
staged, or media-candidate reference rejects the whole staging operation.

## 5.5 Candidate common shape

```ts
interface WorldChangeCandidateBase {
  id: CandidateId;
  conversationId: ConversationId;
  revision: number;
  status:
    | "suggested"
    | "needs-clarification"
    | "ready"
    | "deferred"
    | "dismissed"
    | "withdrawn"
    | "superseded"
    | "staged"
    | "accepted"
    | "handed-off";
  settledness: "settled" | "tentative" | "unresolved";
  authority: "studio-suggested" | "user-edited" | "user-confirmed";
  classification: WorldChangeClassification;
  title: string;
  rationale: string;
  sourceMessageIds: MessageId[];
  evidence: CandidateEvidence[];
  /** JSON-pointer-like field keys explicitly edited or confirmed by the user. */
  userOwnedFields: string[];
  checks: CandidateChecks;
  groupId?: CandidateGroupId;
  createdAt: string;
  updatedAt: string;
  stageBinding?: CandidateStageBinding;
  pendingStagedUpdate?: CandidatePendingUpdate;
  splitFrom?: CandidateId;
  supersedes?: CandidateId[];
}
```

Do not display model-generated confidence percentages. `authority` records who has reviewed the
classification and values; it is not a probability that a fact is true.

```ts
interface CandidateStageBinding {
  proposalId: string;
  stagedCandidateRevision: number;
  stagedProposalDraftRevision: number;
  targetPaths: string[];
  acceptedProposalDigest?: string;
}

interface CandidatePendingUpdate {
  basedOnCandidateRevision: number;
  basedOnProposalDraftRevision: number;
  proposed: {
    classification: WorldChangeClassification;
    title: string;
    rationale: string;
    settledness: "settled" | "tentative" | "unresolved";
    draft: WorldChangeDraft;
    evidence: CandidateEvidence[];
    checks: CandidateChecks;
  };
  conflictingFields: string[];
}
```

`userOwnedFields` gives R-16 field-level meaning. A model update may change fields outside this
set. A different value for a user-owned field becomes a pending conflict; it never overwrites.

```ts
type WorldChangeClassification =
  | "canon.create"
  | "canon.amend"
  | "canon.thread"
  | "sheet.create"
  | "sheet.edit"
  | "relationship.change"
  | "media.image-opportunity"
  | "undecided";

type WorldChangeCandidatePayload =
  | CanonCreateCandidate
  | CanonAmendCandidate
  | CanonThreadCandidate
  | SheetCreateCandidate
  | SheetEditCandidate
  | RelationshipChangeCandidate
  | ImageOpportunityCandidate
  | UndecidedCandidate;

type WorldChangeCandidate = WorldChangeCandidateBase & WorldChangeCandidatePayload;
type WorldChangeDraft = WorldChangeCandidatePayload["draft"];
```

`WorldChangeCandidatePayload` is the discriminated union in §5.6.

## 5.6 Candidate classifications and payloads

### Create Canon

```ts
interface CanonCreateCandidate {
  classification: "canon.create";
  draft: {
    type: "rule" | "lore" | "location" | "faction" | "timeline" | "tone";
    title: string;
    statement: string;
    links: WorldChatLinkRef[];
  };
}
```

No Canon ID exists before staging.

### Amend Canon

```ts
interface CanonAmendCandidate {
  classification: "canon.amend";
  target: { kind: "canon"; entryId: string };
  draft: {
    type?: CanonEntryType;
    title?: string;
    statement?: string;
    links?: WorldChatLinkRef[];
  };
```


The coordinator derives `CandidateChecks`; the model does not supply duplicate/amendment sets or
completeness directly. It uses only verified receipts from the current run and the candidate
classification:

| Candidate                 | Required checks                                                    |
| ------------------------- | ------------------------------------------------------------------ |
| `canon.create`            | Canon search for title + statement concepts                        |
| `canon.amend`             | target entry read; Canon search if target was inferred this turn   |

| `undecided`               | checks needed by each plausible action, or remain partial          |

and contradiction candidates using configured lexical thresholds. `state` is `complete` only when
all `required` categories are in `completed`; it is `unavailable` when a required operation could
not run, `partial` when more clarification/search is needed, and `stale` when an observed source
moved. The model may provide `explanation` prose, but the coordinator suppresses it if it names
entities outside the computed sets.

# 6. Candidate lifecycle

## 6.1 State transitions

```text
                         clarification / checks
suggested --------------------------------------------> ready
    |                         |                           |
    |                         |                           | explicit Stage
    |                         v                           v
    +--> needs-clarification / deferred -------------> staged
    |                                                     |
    +--> dismissed                                        +--> accepted
    |                                                     |
    +--> withdrawn / superseded                           +--> ready (proposal discarded)

media ready --> ready (generation surface opened; editable brief remains)
media ready --> handed-off (a correlated job was durably queued)
```

Terminal history (`accepted`, `withdrawn`, `superseded`, `handed-off`) remains visible in a
collapsed history view and is not included in the active count.

## 6.2 Readiness rules

A candidate is `ready` only when:

- its payload validates;
- its target exists and is not retired, or it is a valid create candidate;
- its classification is not `undecided`;
- it has verified user intent evidence;
- required checks are complete, or the user made an explicit disclosed override;
- a Canon-create candidate with likely duplicates or possible amendment targets has a durable
  `create-anyway` override; otherwise it must be reclassified to `canon.amend` with the selected
  target;
- a settled fact is marked `settled`;
- an open-thread candidate is marked `unresolved`;
- no staged binding already owns the candidate revision;
- every referenced candidate/group revision still exists.

Model output may suggest readiness. The coordinator computes it.

Settledness rules by classification:

| Classification                                      | Required before Stage                          |
| --------------------------------------------------- | ---------------------------------------------- |
| `canon.create`, `canon.amend`                       | `settled` and `user-confirmed`                 |
| `canon.thread`                                      | `unresolved` and `user-confirmed`              |
| `sheet.create`, `sheet.edit`, `relationship.change` | `settled` and `user-confirmed`                 |
| `media.image-opportunity`                           | may be tentative, but handoff remains explicit |
| `undecided`                                         | never stageable                                |

The Stage button may perform the explicit `user-confirmed` transition and staging in one typed UI
command after presenting the values and consequences. Conversational text cannot perform that
transition.

## 6.3 Corrections

The coordinator owns candidate identity and merge behavior. The model proposes operations; it
does not append arbitrary cards.

For a correction such as "not her mother, her aunt":

1. the result references the existing candidate;
2. the evidence identifies the correcting message;
3. the coordinator verifies the expected candidate revision;
4. the same candidate ID receives a full new snapshot;
5. its structural key remains the same if target and owned fields are unchanged;
6. old evidence is replaced or retained only where still applicable.

If one candidate is split into two propositions, two new candidates receive `splitFrom`, and the
old candidate becomes `superseded`. If two candidates are consolidated, the survivor records
`supersedes` and the others become `superseded`.

An accepted candidate is immutable history. A later correction creates a new amend/edit candidate
against accepted world state.

## 6.4 Dismissal and resurfacing

Dismissal records:

- candidate ID and revision;
- a coordinator-computed structural key;
- normalized payload digest;
- target and owned field keys;
- dismissing message ID or UI request ID;
- timestamp.

Re-detecting an identical digest is suppressed. The same candidate may return to `suggested` only
when:

- a later user message exists;
- target, value, settledness, or classification changed materially; or
- the user selected Restore.

The model cannot clear a dismissal tombstone.

## 6.5 Staged candidates

Staging freezes `stagedCandidateRevision` in the proposal origin metadata. A later model turn may
suggest a change to a staged candidate, but that suggestion is stored as `pendingStagedUpdate`.
It does not alter proposal files.

The user may:

- apply the update to the staged proposal after reviewing a diff;
- keep the staged version;
- split the update into a separate candidate/proposal;
- dismiss the pending update.

Direct form edits on a staged candidate are explicit user actions and update proposal files using
`expectedDraftRevision`.

After staging, the original candidate revision remains immutable seed history. Explicit proposal
form edits create a new candidate **projection revision** linked to the proposal's new
`draftRevision`. Acceptance records the final proposal digest and final projection revision, so
the UI never claims that the original seed values were accepted when the user changed them.

## 7.1 Stored event union

The first version needs these durable event types:

```text

conversation.unarchived

run.retry-started
run.session-created
run.finished

```

`turn.completed` atomically carries:

- the completed Studio message;
- all check receipts produced for the turn;
- full updated candidate snapshots;
- full updated group snapshots;
- the completed run outcome.

Separate candidate/status events are used for explicit user actions after the turn.

`turn.started` atomically carries the immutable user message and initial running `WorldChatRun`.
The store syncs that one event before model dispatch, so there is no crash window containing an
accepted user message with no retryable run. `run.retry-started` names the existing turn and adds
only a new run. A failed/cancelled/interrupted attempt ends with `run.finished`; a successful
attempt ends inside `turn.completed` with its Studio message and mutations.

## 7.2 Fold invariants

- Message IDs are immutable and unique.
- A user message and its first run begin in the same `turn.started` event.
- One turn may have multiple run attempts but at most one completed Studio message.
- Candidate/group revisions increase exactly by one.
- A candidate update with the wrong expected revision is rejected and does not append.
- A staged binding references a proposal and the exact candidate revision staged.
- A proposal resolution may occur once; duplicate reconciliation is idempotent.
- A `running` run with no terminal event at startup folds to `interrupted` in memory and appends a
  durable terminal event before another run starts.

`attachment.created` carries the complete immutable `WorldChatAttachment` metadata after bytes are
atomically published. `attachment.promoted` carries its world artifact ID after artifact filing is
durable. Startup reconciles attachment directories against these events: unreferenced staging is
removed; published bytes without a completed creation event are quarantined/deleted; a promoted
artifact is recovered by the operation request ID rather than filed twice.

# 8. Model and harness protocol

## 8.1 Dedicated purpose and agent

Add:

```text
SessionPurpose: world-chat
Agent: world-builder
```

The `world-builder` agent:

- replies through one strict structured response;
- has no edit/write tool;
- has no shell, process, or network tool;
- reads accepted world state only through a run-scoped read-only MCP lease;
- may read only the explicitly selected document attachments exposed by that lease;
- cannot access the queue, providers, credentials, proposal directories, or conversation files.

Remembered harness grants do not override these hard denials. A permission request for a denied
class is rejected automatically and recorded as a configuration defect, not shown as a normal
creative-workflow prompt.

## 8.2 Per-turn scratch directory

Each run receives a new scratch directory outside the world:

```text
%APP_ROOT%/run/world-chat/<conversationId>/<runId>/
  opencode.json
```

It contains no transcript authority and no world files. It is deleted best-effort after the run
and swept at next startup after a crash. The MCP lease token in `opencode.json` expires when the
run ends.

## 8.3 Structured model result

The assistant's entire completed message is JSON conforming to a strict schema:

```ts
interface WorldChatTurnResult {
  reply: string;
  candidateOperations: Array<
    | { op: "create"; temporaryId: string; candidate: ModelCandidateDraft }
    | {
        op: "update";
        candidateId: CandidateId;
        expectedRevision: number;
        candidate: ModelCandidateDraft;
      }
    | {
        op: "withdraw";
        candidateId: CandidateId;
        expectedRevision: number;
        reason: string;
      }
    | {
        op: "split";
        candidateId: CandidateId;
        expectedRevision: number;
        replacements: ModelCandidateDraft[];
      }
  >;
  groupOperations: ModelGroupOperation[];
}
```

`ModelCandidateDraft` is the model-facing candidate union from §5.6 plus:

```ts
interface ModelCandidateCommon {
  title: string;
  rationale: string;
  settledness: "settled" | "tentative" | "unresolved";
  evidence: CandidateEvidence[];
  /** Optional supporting reads; these cannot satisfy the coordinator-owned required check plan. */
  checkReceiptIds: CheckReceiptId[];
}
```

It omits final candidate ID, revision, status, authority, user-owned fields, group binding, stage
binding, paths, proposal IDs, and job/provider fields; the coordinator computes those.

`ModelGroupOperation` may suggest create/update/split/withdraw of a group using temporary IDs or
existing group IDs and exact candidate revisions. The coordinator validates all membership and
assigns final group IDs/revisions.

```ts
type ModelGroupOperation =
  | {
      op: "create";
      temporaryId: string;
      title: string;
      rationale: string;
      members: Array<ModelCandidateRef>;
    }
  | {
      op: "update";
      groupId: CandidateGroupId;
      expectedRevision: number;
      title: string;
      rationale: string;
      members: Array<ModelCandidateRef>;
    }
  | {
      op: "withdraw";
      groupId: CandidateGroupId;
      expectedRevision: number;
      reason: string;
    };

type ModelCandidateRef = { candidateId: CandidateId; revision: number } | { temporaryId: string };
```

Temporary candidate references may point only to candidates created in the same turn result.

The freeform `reply` does not carry machine references to candidates. Candidate cards render from
the structured operations beside the reply. Therefore invalid candidate IDs are rejected in
operations, not inferred from reply prose.

The model may reference existing candidate/group IDs supplied in context. It does not create
final IDs, paths, Canon IDs, sheet slugs, proposal IDs, or job IDs.

## 8.3.1 Coordinator-owned check plan

The coordinator builds and executes required candidate checks; the model cannot choose the search
scope used to establish readiness.

For a candidate create/update operation:

1. validate its classification/payload enough to derive a check plan;
2. normalize deterministic search inputs from title, statement/name, target, links, and changed
   fields;
3. execute the classification matrix in §5.7 through the same world-bound query lease;
4. persist canonical queries, corpus/version, thresholds, result IDs, counts, and receipts;
5. derive `CandidateChecks` and readiness;
6. treat model-supplied receipt IDs only as additional visible context/evidence.

A model may perform exploratory searches while composing its reply, but those arbitrary searches
do not mark `required` categories complete. The coordinator's canonical queries are bounded,
reproducible in tests, and rerun at staging when observations are stale.

The result has hard bounds:

- reply: 8,000 characters;
- at most 12 candidate operations;
- at most 6 group operations;
- title: 160 characters;
- rationale/explanation: 1,000 characters;
- image brief: 4,000 characters;
- no arbitrary unrecognized fields.

## 8.4 Validation and retry

Validation order:

1. parse JSON;
2. validate the response schema;
3. verify candidate IDs and expected revisions;
4. validate each candidate payload;
5. verify message/world/attachment evidence;
6. verify check-receipt references were produced by this run;
7. compute structural keys and deduplication;
8. compute readiness and staged-update handling;
9. validate group membership and atomicity;
10. append one `turn.completed` event.

Any failure rejects the whole result. The coordinator sends one corrective turn naming only the
safe validation errors and requiring the complete result again. If the retry fails, no Studio
message or candidate operations are applied. The original user message remains with a failed run
and a visible Retry action.

This all-or-nothing rule prevents a reply that refers to candidate cards which did not persist.

## 8.5 Context assembly

Each run receives bounded durable context:

| Context section                  |                                                 Initial bound |
| -------------------------------- | ------------------------------------------------------------: |
| System/protocol instructions     |                                               fixed, reviewed |
| Durable conversation summary     |                                              8,000 characters |
| Active/staged candidate registry |                                             16,000 characters |
| Last eight complete turns        |                                             32,000 characters |
| Focused accepted-world context   |                                             32,000 characters |
| Dismissed tombstones             |                              structural keys and digests only |
| Current user message             | never truncated; oversized paste becomes a private attachment |

The exact budget may be tuned, but it must remain explicit and tested. If a section exceeds its
bound, deterministic prioritization is used; the model is never allowed to inherit unbounded
history invisibly.

## 8.6 Summaries

After eight turns or when recent-turn context reaches its bound, a separate bounded summarization
run creates a compact summary with `throughSeq` and source message IDs. The summary is context,
not authority:

- messages remain the source for what was said;
- candidates remain the source for detected changes;
- world files remain the source for accepted facts;
- evidence never cites the summary;
- summary failure leaves the previous summary in place.

# 9. World-bound retrieval and checks

## 9.1 Run-scoped query lease

The current world-query server resolves every call against whichever store is open at call time.
World Chat must replace that behavior with a run-scoped lease:

```text
lease token -> world/store identity + conversationId + runId + allowed attachment IDs + expiry
```

Every call verifies:

- the token exists and is unexpired;
- the requested run is active;
- the same world/store remains open;
- the operation is allowed;
- the request stays within size and result limits.

Switching/closing the world invalidates the lease. It must never redirect the lease to the newly
open world.

## 9.2 Tool surface

The v1 read-only tool surface is:

| Tool                                 | Purpose                                                        |
| ------------------------------------ | -------------------------------------------------------------- |
| `search_canon(query, limit)`         | ranked accepted Canon search, full statement for quotations    |
| `search_sheets(query, kind, limit)`  | lexical search over accepted sheets                            |
| `get_entry(id)`                      | one accepted Canon entry and revision lineage                  |
| `get_sheet(id)`                      | one accepted sheet and current version                         |
| `list_entities(kind, status, limit)` | bounded entity list                                            |
| `related(id)`                        | accepted incoming/outgoing references                          |
| `get_attachment_text(id, range)`     | bounded text from an explicitly linked conversation attachment |

There is no write operation and no filesystem path parameter.

`search_sheets` is a SPEC-003 extension. It indexes only production-reference text appropriate to
entity matching: name, type, role/region, and declared prose sections. It excludes operational
metadata, voice IDs, media paths, and retired sheets. Ranking is FTS5/BM25 with the same bounded
result discipline as Canon search. Index migration/rebuild is required when this corpus is added.

Images, audio, and video may be attached and linked to the conversation, but World Chat v1 does
not claim to inspect them. The UI says whether an attachment was **attached privately**, **read as
text**, **filed in the world**, or **not readable in this chat**. Existing extraction may produce
text/candidates separately after explicit promotion.

## 9.3 Structured check receipts

The coordinator wraps every tool call and records a receipt:

```ts

  id: CheckReceiptId;
  runId: RunId;
  tool:
    | "search-canon"
    | "search-sheets"
    | "get-entry"
    | "get-sheet"
    | "list-entities"
    | "related"
    | "get-attachment-text";
  status: "complete" | "empty" | "unavailable" | "failed";
  querySummary?: string;
  consulted: Array<{
    ref: WorldChatEntityRef;
    observedVersion: number;
    contentHash: string;
  }>;
  searchedCount?: number;
  at: string;
}
```

`querySummary` is safe product text, not raw tool JSON. It must not enter app diagnostics.

The UI may render transient `tool.activity` immediately, but candidate cards and completed turns
render persisted receipts.

## 9.4 Retrieval degradation

If the index is unavailable:

- direct `get_entry`/`get_sheet` from the accepted bundle may continue;
- lexical search and related queries report unavailable;
- the Studio may continue creative conversation;
- candidates requiring novelty/duplicate checks remain `needs-clarification`;
- the user may explicitly choose a target or choose Create anyway after seeing the limitation;
- the override is durable and visible in final review.

## 10.3 Snapshot behavior

conversation explicitly. On reconnect:

1. receive fresh app/world snapshot;
2. restore the selected conversation ID from the route;
3. send `world-chat-load`;
4. replace the local workspace with the durable folded view;
5. ignore stale incremental events at or before the loaded sequence.

```ts
interface Proposal {
  // existing fields
  draftRevision?: number; // defaults to 1
  worldChatOrigins?: WorldChatProposalOrigin[];
}
```

The source string is `world-chat:<conversationId>`.

Origin metadata explains the draft but does not govern acceptance. Proposed files and captured
bases remain the gate's authority.

## 11.2 Server-side materialization

The coordinator materializes every candidate. The model never serializes authoritative files.

For each classification:

- Canon create: allocate an ID, create validated Canon Markdown.
- Canon amend: read accepted entry, apply allowed draft fields, serialize and validate.
- Canon thread: allocate an ID, create `type: thread`, `status: open` Markdown.
- Sheet create: allocate unique stable slug, build a sketch from `SHEET_SHAPES`, serialize and
  validate.
- Sheet edit: read accepted sheet, apply allowed fields/sections, serialize and validate.
- Relationship: produce the minimum necessary sheet target(s), respecting one-sided links.
- Media opportunity: reject from proposal materialization.

Before writing proposal files, parse every proposed entity through its domain schema. A malformed
candidate must fail staging without leaving a proposal directory.

## 11.3 Atomic ID allocation and staging

Existing form helpers may allocate a Canon ID before calling `gate.stage()`. Mixed World Chat
staging needs a recoverable operation that spans conversation intent and proposal materialization:

1. append `staging.intent-recorded` with `requestId`, candidate/group revisions, destination,
   planned proposal ID, and no allocated IDs yet;
2. under the world serialization boundary, revalidate candidates against the current world;
3. reserve required Canon IDs and choose unique sheet slugs, carrying the `requestId` into the
   allocation commit and each allocation audit record;
4. materialize all target contents using those identities;
5. capture bases and write the proposal under the planned ID with the same `requestId` in every
   World Chat origin;
6. append `staging.completed` with proposal ID, allocations, target paths, and proposal digest;
7. fold candidate/group links from the completed event.

A startup reconciliation folds incomplete intents:

- proposal with matching `requestId` exists and validates -> append `staging.completed`;
- no proposal exists, but allocation audit lines exist -> retry materialization with those burned
  IDs or append `staging.failed` and require a fresh Stage action; never allocate a second set
  silently;
- neither proposal nor allocation exists -> safely resume the same intent;
- conflicting/malformed proposal -> append a problem and require manual discard/recovery.

This is a recoverable saga, not a false cross-file atomicity claim. A crash may burn IDs, but a
single `requestId` can resolve to at most one proposal and one completed staging outcome.

This requires adding optional `requestId` to `CommitInput`, the prepared commit journal, and Canon
allocation change records. Recovery matches allocations to a staging intent by that exact value,
not by conversation-scoped `source` text.

## 11.4 Extending a staged proposal

Proposal extension is explicit and applies only to a `worldbuilding` proposal.

Extension SHALL:

- require `expectedDraftRevision`;
- refuse while accept, rebase, conflict resolution, or another proposal update is active;
- allocate identities for newly created entities at extension time;
- capture bases for newly added target paths at extension time;
- merge changes to an existing target at domain-field granularity;
- surface an overlap if a new candidate and the existing draft both changed the same field;
- append origins and increment `draftRevision`;
- recompute the advisory ripple preview;
- leave the prior proposal unchanged if any validation fails.

There is no automatic extension simply because later conversation discovers a related idea.

## 11.4.1 Proposal draft journal

World Chat proposal edits and extensions use a proposal-local recoverable journal; they must not
reuse the current unjournaled `updateFile()` sequence.

```text
.proposals/<proposalId>/.draft-commit/<operationId>.json
```

The prepared record contains `requestId`, expected/current/next `draftRevision`, target additions,
complete next target contents, complete next origin metadata, next candidate projections, and the
next preview inputs. Update order is:

1. validate and write the prepared record atomically;
2. write all next files to proposal-local staging paths;
3. mark the record committing;
4. atomically rename target files and base additions;
5. atomically replace manifest/origins and candidate projection sidecar with `nextDraftRevision`;
6. recompute/write the preview;
7. mark complete and remove the draft journal.

Startup rolls a committing operation forward idempotently or removes a prepared-only operation.
The manifest revision and proposal-local candidate projections therefore cannot lag behind an
authoritative target-file edit after a crash. Accept/rebase/conflict operations first recover and
then refuse while any draft operation remains unresolved.

## 11.5 Proposal review projection

Extend `StagedProposal` with a coordinator-computed review projection:

```ts
interface ProposalReviewProjection {
  targets: Array<{
    path: string;
    entity: WorldChatEntityRef | { kind: "new-canon" | "new-sheet"; label: string };
    action: "create" | "amend";
    fields: Array<{
      field: string;
      before: string | string[] | null;
      proposed: string | string[] | null;
      candidateIds: CandidateId[];
    }>;
  }>;
}
```

The projection is derived from base/live and proposed files, not trusted from model prose. Long
prose fields are expandable and fully reviewable.

## 11.6 Proposal resolution

On accept:

- proposal behavior remains SPEC-004;
- after the commit is durable, append conversation events marking linked candidate revisions and
  groups accepted;
- unlock dependent media opportunities;
- if app termination occurs between commit and conversation update, startup recovery detects the
  proposal ID in `changes.jsonl` and repairs candidate state idempotently.

On discard:

- discard remains durable in `changes.jsonl`;
- linked candidates return to `ready` with a "staged draft discarded" note;
- they are not automatically dismissed;
- startup recovery repairs this state if the direct conversation event was missed.

Add explicit `proposalId` to discard audit records so recovery need not parse it from an entity
path.

# 12. Forms and review behavior

## 12.1 One state, two editors

Before staging, candidate forms read and write the durable candidate. After staging, forms read
and write the proposal draft through a typed coordinator command. Component-local form state is a
temporary editing buffer only; navigation reloads from the durable candidate/proposal.

This corrects the current pattern in which chat edits one proposal while a form holds unrelated
component-local fields and may stage another proposal.

## 12.2 Reusable form controls

Extract reusable controls from existing screens:

- Canon type, title, statement, links;
- sheet common frontmatter;
- declarative section fields from `SHEET_SHAPES`;
- thread title and question;
- relationship target and prose;
- image purpose and brief.

The same controls render in direct create/edit routes and candidate review. Direct forms remain
fully usable without OpenCode.

## 12.3 Changing classification

The user may change:

- Canon create to Canon amend, selecting a target;
- Canon amend to create;
- tentative fact to open thread;
- sheet create to edit, selecting an existing sheet;
- sheet edit to Canon change when the content is Canon-owned;
- undecided to any compatible classification.

Changing classification creates a new candidate revision, invalidates incompatible checks, and
recomputes readiness. It does not stage automatically.

# 13. Attachments

## 13.1 Filing and linkage

World Chat attachments are private unfinished workspace by default and live beneath:

```text
.conversations/<conversationId>/attachments/<attachmentId>/<safe-name>
```

They are content-hashed, immutable, and referenced by conversation attachment ID. They are not
ordinary world artifacts, do not enter the index, and are excluded with `.conversations` from
normal export.

The user may explicitly choose **File in world** to promote a conversation attachment through the
existing artifact filing path. Promotion creates an immutable artifact and records the artifact ID
on the conversation attachment; it does not delete the private copy until the user explicitly
deletes the conversation and all proposal/media dependencies are resolved.

An attachment chip means "refer to this attachment in this conversation". Removing it stops
future turns from referring to it; the private attachment remains in the conversation until
conversation deletion. A promoted artifact remains filed in the world.

Attachment linkage is scoped to one conversation. Files attached in another conversation in the
same world must not appear automatically.

## 13.2 What the model may read

- Text/document attachment: may be exposed through bounded `get_attachment_text` if explicitly
  linked to the current turn.
- Long pasted text: stored as a private document attachment and treated identically.
- Image/audio/video: may be named as an attachment and used to create a media opportunity, but the
  chat must not claim to have inspected it without an existing verified extraction/multimodal
  capability.
- Extracted/promoted artifact text: may be read and quoted with its artifact hash/line evidence.

The UI distinguishes filed, readable, read, and unsupported states.

# 14. Media handoff

## 14.1 Route mapping

| Purpose                                       | Destination                                    |
| --------------------------------------------- | ---------------------------------------------- |
| `world-key-art` with `{ kind: "world" }`      | existing world-image generation action/surface |
| `character-main-photo` with a character sheet | `/w/:worldId/cast/:sheetId/main-photo`         |
| `character-look` with a character sheet       | `/w/:worldId/cast/:sheetId/looks`              |

Every other target/purpose combination is invalid in v1. Replacing an existing image is expressed
by one of these purpose-specific workflows, not a generic `replacement` value without asset
identity.

The route includes conversation/candidate identity so the screen loads the durable brief rather
than relying only on transient router state.

## 14.2 Dependency rule

In v1, every authored candidate/proposal dependency must be accepted before Generate is enabled.
The media card explains which proposal is still pending and links to review.

This avoids introducing proposal-aware prompt assembly, staged provenance, and orphaned generated
media when a proposal is later discarded.

## 14.3 Queue boundary

World Chat never sends a queue command. The existing generation screen:

- resolves the accepted world state;
- shows the routed model and estimate;
- allows brief editing;
- receives explicit user Generate;
- composes the provider request server-side;
- enqueues through the durable job queue.

After a correlated enqueue acknowledgement, the media candidate may record `handed-off` and the
job IDs. That record is informational and cannot control the queue.

Opening the generation surface does not change candidate status. The durable brief remains owned
by the candidate and the generation surface saves user edits back with `expectedRevision` before
dispatch. Generation commands add optional provenance-only correlation:

```ts
{
  worldChatOrigin?: {
    conversationId: ConversationId;
    candidateId: CandidateId;
    candidateRevision: number;
  };
}
```

The coordinator copies that origin into the correlated `queue.enqueue-result`; it does not put
conversation content into the provider request beyond the already reviewed brief.

The job journal adds an optional local-only origin containing only
`{ conversationId, candidateId, candidateRevision, handoffRequestId }`. It contains no chat text,
candidate title, or brief beyond the provider-ready params the user already approved. The origin
is persisted in the initial `queued` row before provider submission and returned on
`queue.enqueue-result`.

Only an accepted result with at least one durable job ID appends the idempotent `handed-off`
candidate transition. If the app crashes before that transition, startup finds journal jobs by
`handoffRequestId` and repairs it without enqueueing again. Navigation alone, rejected enqueue,
and `not-queued` results do not. Once handed off, the job is fully self-contained and conversation
deletion cannot affect it.

# 15. UI specification

## 15.1 Routes and entry points

Add:

```text
/w/:worldId/chat
/w/:worldId/chat/:conversationId
```

`/chat` opens the most recently active conversation or the new-conversation state. Users can
create, rename, archive, restore, and explicitly delete conversations.

Archive/unarchive is reversible and leaves all data intact. Delete is permanent and requires:

- no active run;
- no open/stale/conflicted proposal linked to the conversation;
- no unresolved staging intent;
- no pending media handoff that depends on conversation-only data;
- explicit confirmation naming that private attachments and unstaged history will be removed.

Accepted/discarded proposal audit records and accepted world files remain. Proposal origins keep
the conversation ID as historical provenance even after the conversation is deleted; links back
to content become unavailable rather than dangling into another conversation.

Every conversation operation runs through one per-world conversation operation coordinator. It
serializes appends/checkpoint writes and tracks active readers/runs that may later write. Once a
conversation enters `deleting`, **all** commands and callbacks for it are rejected or drained,
including messages, run completions, metadata changes, candidate/group edits, attachment
create/link/unlink/promotion, staging completion, proposal reconciliation, media handoff, and
summary/checkpoint writes.

Deletion runs exclusively through that coordinator:

1. mark the conversation `deleting` in the operation coordinator and reject new operations;
2. interrupt any active model run and wait for all existing writers/callbacks to drain;
3. recheck every deletion precondition;
4. append and sync `deletion.intent-recorded` inside the conversation;
5. atomically rename the directory to `.conversations/.deleted/<conversationId>-<operationId>`;
6. update the in-memory summary list to remove it;
7. recursively remove the tombstoned directory best-effort.

The authoritative deletion point is the atomic rename. Startup sweeps `.deleted`; a crash before
rename leaves the conversation intact, while a crash after rename leaves it deleted and only
cleanup remains. Because the deletion event moves with the tombstoned directory, it is recovery
context rather than the sole deletion authority. A request ID makes repeated Delete idempotent.

Entry points:

- world navigation: **World Chat**;
- world overview: **Talk about this world**;
- Canon refusal: **Draft an answer in World Chat**, carrying the question and retrieved entries;
- Canon New: optional **Talk it through**, while retaining the direct form;
- character/location/faction detail: **Talk about this**, carrying sheet context;
- future image actions: carry media target context into the same workspace.

The world name and current optional focus are always visible.

- Initial copy invites exploration and explains that discussion changes nothing by itself.
- User and Studio turns are visually distinct without anthropomorphic status theater.
- Tool progress is shown in product language while a run is active.

  `Image opportunity`);

# 16. Concurrency and idempotency

## 16.1 Revisions

Use three explicit optimistic revisions:

- conversation event sequence;
- candidate/group revision;
- proposal `draftRevision`.

Every mutation compares its expected value and returns the current durable state on mismatch.

## 16.2 Request IDs

Mutating client commands use ULID request IDs. The conversation store retains enough operation
receipts to make reconnect retries idempotent. At minimum:

- send does not duplicate the user message/run;
- stage does not allocate another Canon ID or proposal;
- candidate update does not create another revision;
- media handoff does not mark twice.

## 16.3 Active runs

- One active model run per conversation.
- A second send receives `already-running` and does not append a message.
- Cancellation marks the run, aborts the local event iterator, and asks the adapter to interrupt.
- A conversation may be read and candidates form-edited while no model run mutates them.
- A model result based on stale candidate revisions is rejected and retried/reviewed, not merged
  with user edits silently.

## 16.4 World switching

The product currently has one read-write open world. If the user opens another world while a
World Chat run is active:

1. invalidate the old world-query lease;
2. interrupt the run;
3. append `interrupted` with reason `world changed`;
4. retain the user message and prior candidates;
5. allow retry when the original world is reopened.

# 18. Privacy, security, and diagnostics

## 18.1 Plaintext and user expectations

Conversation records are plaintext inside the world, like the world's other readable authored
and operational files. The UI must not imply encryption. Credentials never enter them.

Normal world export excludes conversations because they are unfinished workspace. An explicit
future "include workspace" export may be added only with clear disclosure.

World Chat sends bounded conversation/world context to the selected authoring model. Before the
first send, the UI shows `local`, `cloud`, or `unknown` from application-owned model-routing
metadata. Sending while `cloud` is shown is the user's deliberate disclosure. If routing is
`unknown`, the UI says that clearly and does not imply local processing.

The harness may retain session content independently of Studio. Add optional adapter capability
and methods for session deletion, invoke deletion after each ephemeral run, and report whether it
was confirmed. A user-installed or under-capable harness with no confirmed deletion support is
labelled accordingly. Studio's scratch cleanup is not presented as deletion from the harness.

## 18.2 Logs

Never write these to app/coordinator logs or diagnostics:

- message text;
- candidate titles, statements, section prose, or image briefs;
- world names;
- retrieval queries or excerpts;
- attachment names/content;
- proposed file paths;
- model structured response.

Safe operational records may include:

```text
kind
worldId
conversationId
runId
status/category
durationMs
candidate operation counts
check counts
adapter/model IDs
token count
```

Even safe IDs pass through the existing redaction boundary. Diagnostics include aggregate counts
and safe failure categories only.

## 18.3 Agent confinement

World-builder sessions are read-only and stricter than proposal authoring sessions:

- scratch cwd, not world/proposal/conversation directory;
- edit/write denied;
- shell/exec/network denied;
- read-only MCP lease only;
- no remembered grant can expand capability;
- no queue or provider tools;
- no arbitrary path parameter;
- expiring per-run token;
- result accepted only through strict schema validation.

This remains defense in depth, not an OS sandbox claim.

## 18.4 Harness retention

Extend harness capability discovery with optional `session-delete` and application-owned routing
metadata:

```ts
interface AuthoringRouteInfo {
  provider: string;
  model: string;
  locality: "local" | "cloud" | "unknown";
}
```

Locality comes from Studio's provider/runtime registry, not model-name heuristics. Before a turn,
the route shown in the UI must match the route written into session configuration. If the harness
selects a different route unexpectedly, the run fails before sending world content.

When `session-delete` is supported, Studio requests deletion after the completed/failed run and
waits for a confirmed adapter result within a bounded cleanup time. Unsupported, unconfirmed, or
failed deletion is recorded as safe operational status and disclosed in the conversation's
privacy note. It does not erase the local conversation and does not claim remote deletion.

# 19. Performance and limits

Initial product limits:

- 16,000 characters per typed message; larger pasted content becomes a private conversation
  attachment;
- 20 linked conversation attachments per turn;
- 50 recent messages in initial load;
- 100 messages per history page maximum;
- 12 candidate operations per model turn;
- 100 active candidates per conversation before the user must resolve/archive some;
- one active model run per conversation;
- bounded MCP results (default 8, hard maximum 20);
- bounded document ranges and total attached text per run;
- checkpoint after 100 durable events or 1 MiB since the previous checkpoint;
- no automatic deletion/expiry of conversations or proposals.

Limits produce stated errors or review prompts. They never silently truncate a user message,
candidate value, proposed file, or evidence quote.

# 21. Test specification

## 21.1 Contract tests

- Parse every candidate classification and reject unknown fields.
- Reject tentative settled-fact staging.
- Reject media candidates inside proposal groups.
- Validate candidate/group revision and stage bindings.
- Validate message, run, check receipt, event envelope, summary, and paging cursors.
- Parse old proposals after optional World Chat fields are added.
- Reject model-supplied paths and authoritative IDs.

## 21.2 Persistence tests

- User message is durable before fake adapter dispatch begins.
- Clean turn appends message/check/candidate/group changes atomically.
- Initial user message and first running attempt append atomically in `turn.started`.
- Crash/truncated final line loses only the incomplete event.
- Duplicate send/stage request IDs are idempotent.
- Checkpoint deletion rebuilds identical state.
- Corrupt checkpoint falls back to event fold.
- Interior event corruption produces a named problem without inventing state.
- Navigation/reconnect/restart restores candidates, dismissals, groups, draft forms, and recent
  messages.
- Running turn at crash becomes interrupted exactly once.

## 21.3 Classification scenarios

- "The bells cannot ring below the western lock" -> settled Canon create candidate.
- "Maybe the bells are whale bone" -> tentative/clarification, not ready Canon.
- Restatement of an existing fact -> duplicate receipt, no new ready Canon.
- Change to an existing fact -> Canon amendment candidate with target.
- "We should remember who rang the first bell" -> unresolved open-thread candidate.
- Character history plus family rule -> grouped sheet edit plus Canon create.
- Relationship update -> one-sided link plus only necessary prose targets.
- Three possible villains -> no candidate or explicit undecided candidate, never three facts.
- Portrait should show a badge -> image opportunity, no job.
- Pure brainstorming -> completed reply with zero candidate operations.

## 21.4 Correction and dismissal tests

- "mother" corrected to "aunt" updates one candidate ID/revision.
- Retraction withdraws candidate.
- Split creates new IDs and supersedes the original.
- Dismissed identical candidate does not reappear on the next turn.
- Material target/value change resurfaces the same ID with a new revision.
- User-edited field survives later model update and produces a conflict/pending update.
- Accepted candidate correction creates a new amendment candidate.

## 21.5 Grounding tests

- Candidate world quote must exist at the cited version/revision and content hash.
- Candidate message quote must match exact immutable message span.
- Attachment quote must match the linked attachment hash/text; promoted artifact evidence also
  verifies the artifact hash.
- Model cannot cite a check receipt from another run.
- Empty search is distinct from unavailable search.
- Index unavailable cannot yield confident "new" readiness without user override.
- Lexical contradiction candidates remain non-blocking and honestly labelled.
- World switch cannot redirect a query lease to the new world.

## 21.6 Structured-output adversarial tests

- Malformed JSON -> one retry -> failure without partial mutations.
- Unknown candidate type -> retry/failure.
- Candidate tries to include path/job/provider command -> rejected.
- Candidate tries to stage/accept in output -> ignored/rejected by schema.
- Stale candidate revision -> no overwrite.
- More than operation limit -> rejected.
- Tool activity claims a check that no receipt confirms -> candidate cannot use it.

## 21.7 Staging and gate tests

- Suggested Canon reserves no ID.
- Stage reserves exactly one ID and is idempotent after retry/crash.
- Crash after staging intent, allocation, and proposal write is reconciled to one proposal and one
  terminal staging outcome.
- Two concurrent stages receive distinct Canon IDs/sheet slugs.
- Pending Canon/sheet references within one group resolve to the allocated identities.
- Pending cross-reference to a candidate outside the atomic group is rejected.
- Mixed Canon + sheet group becomes one proposal and one commit.
- Independent candidates become separate proposals.
- Relationship materializes minimum targets.
- Open thread remains a proposal until explicit accept.
- Every materialized file parses through its entity schema.
- Extension captures new target base at extension time.
- Crash at every proposal draft-journal phase rolls forward or preserves the previous complete
  draft revision; target files and manifest/projection never disagree.
- Overlapping proposal field update requires review.
- Stale proposal uses existing rebase/conflict flow.
- Accept updates candidates; crash-window recovery repairs linkage.
- Discard returns candidates to ready and does not dismiss them.
- Final review projection matches actual proposed files.

## 21.8 Media boundary tests

- Image candidate alone creates no job/journal/ledger entry.
- "Generate it" in chat creates no queue command.
- Pending proposal dependency disables Generate and names the dependency.
- Accepted dependency enables existing generation screen with brief.
- Explicit Generate follows normal queue acknowledgement and estimate flow.
- Conversation deletion is blocked while a media handoff depends on conversation-only data;
  deletion after queue acknowledgement does not affect the job.

## 21.9 Client and accessibility tests

- World overview/nav/contextual entry opens correct world/conversation context.
- Composer disabled copy names harness reason and direct-form alternatives.
- Retrieval degradation is distinct from harness degradation.
- Candidate cards expose settledness/readiness/checks as text.
- Review form edits durable candidate and survives remount.
- One keyboard path reaches all actions.
- Focus returns after closing review drawer.
- Completed messages, not streaming tokens, reach live region.
- Desktop and narrow visual snapshots match approved frames.

## 21.10 Privacy and confinement tests

- Search app/coordinator logs and diagnostics after a full conversation: no message/candidate/world
  content appears.
- World-builder has no edit/write/shell/network capability.
- Remembered grants cannot enable denied tools.
- MCP rejects expired, wrong-world, wrong-run, and unapproved-attachment tokens.
- Tool surface accepts no path.
- Scratch directory contains no credentials or durable transcript.
- Crash-startup sweep removes stale scratch/config files.
- Normal world export excludes `.conversations`.
- An older supported build refuses the incremented world schema rather than exporting
  `.conversations` accidentally.
- Session deletion is requested and its confirmed/unsupported outcome is represented honestly.

# 22. Rollout and compatibility

## 22.1 Feature flag

Ship behind an application-owned feature flag until persistence, safety, and staging tests are
complete. The flag may hide entry points but must not make existing `.conversations` unreadable.

## 22.2 Existing worlds

Creating the first conversation upgrades `world.json.schemaVersion` through the ordinary commit
primitive before `.conversations` is created. `.conversations` remains optional operational state
and its files carry their own schema version. Opening an existing world without creating a
conversation does not require eager directory creation, but using World Chat requires the schema
upgrade.

## 22.3 Existing proposals

New Proposal fields are optional/defaulted so existing manifests parse unchanged. The new
`worldbuilding` kind is used only by new proposals. Accepted entity file formats remain unchanged.

## 22.4 Downgrade behavior

An older build refuses the newer world schema before scanning, exporting, or modifying it. This is
required because older exporters do not know to exclude `.conversations`. Accepted entity file
formats remain ordinary Canon/sheet formats; returning to an older build requires an explicit
future downgrade/export process, not silent opening.

# 23. Decisions and deferred work

## 23.1 Decisions made here

| Question                         | Decision                                                               |
| -------------------------------- | ---------------------------------------------------------------------- |
| Conversation cardinality         | Multiple topic conversations per world                                 |
| Durable location                 | Hidden world-local `.conversations/` workspace                         |
| Normal export                    | Exclude unfinished conversations                                       |
| Transcript format                | Per-conversation append-only JSONL plus derived checkpoint             |
| Product identity                 | Studio conversation/turn/message/run IDs, not harness IDs              |
| Model continuity                 | Fresh/rotated sessions over bounded durable context                    |
| Speculative ideas                | Durable candidates, no proposal until explicit Stage                   |
| Candidate corrections            | Stable candidate IDs with revisions                                    |
| Dismissal                        | Durable tombstone with material-change resurfacing                     |
| Confidence                       | Settledness + review authority, no percentages                         |
| Grouping                         | Explicit atomic groups; independent candidates stay separate           |
| Staged authority                 | Proposal files; later model changes require explicit Apply             |
| Canon IDs/sheet slugs            | Allocate at staging under serialization                                |
| Mixed changes                    | One proposal when logically/referentially atomic                       |
| Open thread                      | Stage and accept through normal gate                                   |
| Media with staged facts          | Require acceptance first in v1                                         |
| Conversation language as consent | Never; UI commands only                                                |
| Retrieval evidence               | Coordinator-owned receipts and verified quotations                     |
| Attachments                      | Private conversation attachments; explicit promotion to world artifact |
| Logging                          | No content-bearing World Chat events in app-level logs                 |

## 23.2 Deferred

- Semantic/vector retrieval.
- Multimodal image/audio/video understanding in World Chat.
- Media generation directly against a selected proposal snapshot.
- Collaborative/multi-user conversations.
- Cloud sync.
- Including conversations in normal world export.
- Model-generated confidence percentages.
- Autonomous staging or acceptance.
- More than one simultaneous run per conversation.
- OS-level sandboxing of the harness.
