# 0. Purpose and status

This document is the implementation specification for GitHub issue #70, **Add a worldbuilding
chat that turns conversation into reviewable world changes**.

The issue establishes the product direction. This document settles the architecture and behavior
needed to implement it safely. In particular, it defines the missing layer between an exploratory
conversation and an accepted proposal:

```text
conversation
    -> a running understanding, correctable by talking
    -> one explicit wrap-up, which closes the conversation
    -> one or more proposals and the existing accept gate
    -> accepted world files
```

World Chat is not another wrapper around `draft-with-studio`. Existing authoring starts with a
known file and creates a proposal before the first turn. World Chat starts with a world and an
idea; it may discover no change, one change, or several changes across different entities. It
therefore needs a durable conversation and candidate lifecycle that exists before any proposal.

This specification deliberately preserves the product's strongest boundary:

> OpenCode may discuss and suggest authored changes. Only explicit Studio UI actions may create,
> accept, discard, or dispatch work. Media generation remains in the job queue. The accept gate
> remains the only path from authored draft to the live world.

## 0.1 Revision note: review continuously, decide in a batch

An earlier draft of this document required the user to triage each detected change as it appeared:
stage it, defer it, dismiss it, group it. Twelve detected changes in one session meant twelve
interruptions, each demanding a judgment while the user was engaged in something else. That is a
real cost, and it damages the one thing conversation is good for.

This revision separates **reviewing** from **deciding**:

- Reviewing happens continuously and passively. The user reads a running summary of what the
  Studio understood. Correcting it is done by talking, not by operating controls.
- Deciding happens exactly twice. **Wrap-up** turns the conversation into proposals and closes it.
  **Accept** commits a proposal through the existing gate.

The durable candidate layer is unchanged in substance and remains necessary: stable identity is
what makes a later correction update one proposition rather than accumulate a contradictory
second one. What changes is that candidate status, readiness, and grouping are no longer a user
triage surface. They become internal state that surfaces once, at wrap-up.

Batched approval is defensible only because review was continuous. The two halves are one design;
adopting the batch without the running summary would be strictly worse than per-change staging.

# 1. Product contract

## 1.1 Summary

World Chat is a persistent, world-scoped creative workspace. A user may talk naturally about an
open world without first deciding whether an idea belongs in Canon, a character, a location, a
faction, a relationship, an open thread, or an image brief.

The Studio replies conversationally and maintains a **running understanding**: a summary of the
propositions it has taken from the conversation, grouped by subject and written as sentences. The
understanding is a review surface, not a control surface. It carries no per-item actions. If a
line is wrong, the user says so and it changes.

When the user chooses, one **wrap-up** action converts the understanding into proposals and closes
the conversation. Those proposals are approved on a dedicated screen through the existing accept
gate.

The transcript is not a proposal. The understanding is not a proposal. A proposal is not an
accepted world change. Every transition is visible and deliberate.

## 1.2 Goals

- Let the user explore ideas without choosing an entity type or form in advance.
- Let the user talk for an extended period without being asked to make a decision.
- Show the user continuously what the Studio has understood, so a misunderstanding is caught when
  it happens rather than at the end.
- Preserve the distinction between brainstorming, tentative ideas, unresolved questions, and
  settled facts.
- Check relevant accepted Canon and sheets before describing an idea as new or selecting an
  amendment target.
- Keep stable identity behind each proposition, so a later correction revises it rather than
  adding a contradiction.
- Let one conversation produce several related or independent changes, grouped by the coordinator
  rather than by the user.
- Keep the understanding, its corrections, and its proposal links durable across navigation and
  app restart.
- Reuse proposal materialization, base capture, ripple calculation, rebase, conflicts, and atomic
  acceptance from SPEC-004.
- Reuse the shared Composer and the existing direct forms rather than introducing a parallel set
  of controls.
- Give proposals from every source a dedicated approval screen with real field-level values.
- Keep actual media dispatch behind an explicit queue action with visible cost.
- Remain useful when OpenCode or the derived index is unavailable.

## 1.3 Non-goals

- A general assistant unrelated to the open world.
- Treating every user sentence as a world change.
- Treating conversational agreement as wrap-up or acceptance.
- A per-change approval queue during the conversation. Reviewing is continuous; deciding is
  batched.
- Replacing Canon Q&A. Q&A answers from accepted facts; World Chat explores what the world should
  become.
- Replacing direct Canon and sheet forms.
- Letting OpenCode call media providers, enqueue jobs, accept proposals, or commit world files.
- Generating media against unaccepted candidate or proposal state in the first version.
- Semantic/vector retrieval. Existing lexical retrieval remains the v1 authority.
- Multi-user collaboration or cloud synchronization.
- Portable export of unfinished conversations. Normal world export excludes them.
- Vision, audio, or video understanding inside World Chat unless an existing extraction produces
  text the chat can cite.

## 1.4 Required user outcomes

- A user can open World Chat from the world overview or navigation and begin with a plain-language
  idea.
- A user can enter the same workspace from a Canon question or a character/location/faction with
  that context visible and preselected.
- A user can talk for an entire session without being asked to approve, defer, or dismiss
  anything.
- A turn can produce no detected change without being treated as a failure.
- A user can tell, at a glance, whether the Studio has understood them, and correct it by saying
  so.
- A tentative statement cannot silently become settled Canon or settled sheet content, and cannot
  be silently discarded at wrap-up either.
- A later correction updates the existing proposition instead of leaving contradictory duplicates.
- A retraction in conversation removes a proposition without needing a control.
- Wrap-up states, before it acts, what will become proposals, what will not, and what it needs
  decided.
- Related changes land in one mixed proposal atomically; independent changes land in separate
  proposals; the user does not have to work out which is which.
- A proposal can be accepted, sent back to its conversation, or discarded, and its values can be
  corrected in place before acceptance.
- A media opportunity can prefill the correct generation surface but cannot dispatch by itself.
- Conversation and understanding state survives restart; an in-flight model session does not need
  to.

# 2. Normative requirements

## 2.1 Conversation and persistence

- **R-1** A world SHALL support multiple persistent World Chat conversations, each with a stable
  `cv_<ULID>` identity, title, status, creation time, update time, and optional entry context.

- **R-2** Conversation identity SHALL be a Studio identity, not an OpenCode session ID. Harness
  sessions are ephemeral implementation details and MAY be replaced between turns.

- **R-3** User messages SHALL be appended durably before model dispatch. A failed, cancelled, or
  interrupted turn SHALL retain the user's message.

- **R-4** Completed Studio messages, candidates, groups, tombstones, wrap-up outcomes, proposal
  links, and run outcomes SHALL survive renderer reload, navigation, app restart, and loss of the
  harness session.

- **R-5** Full conversation history SHALL NOT be embedded in the ordinary whole-world snapshot.
  The snapshot SHALL carry conversation summaries; one conversation SHALL be loaded and paged by
  ID.

- **R-6** Conversation writes SHALL be durable before their corresponding client events are
  broadcast. Reconnecting to a fresh snapshot and loading the conversation SHALL never duplicate
  a message or candidate mutation.

## 2.2 Conversation is not consent

- **R-7** No user or model text, including "yes", "do it", "make it so", or equivalent language,
  SHALL directly create a proposal, accept, discard, or dispatch anything.

- **R-8** Exactly two typed client commands produced by visible UI actions MAY cross a boundary:
  the wrap-up command, which creates proposals and closes the conversation, and the proposal
  accept command. Proposal discard, send-back, in-place edit, and media enqueue are likewise
  typed commands from visible actions.

  A conversational request such as "draft that" MAY cause the Studio to refine a proposition and
  say it is ready, but it SHALL NOT create anything. This deliberately resolves issue #70's
  otherwise ambiguous phrase "explicitly asks the Studio to draft it" in favor of the stronger
  consent boundary.

- **R-8a** The conversation surface SHALL NOT offer per-proposition approval, deferral,
  dismissal, or staging controls. Corrections and retractions are made in conversation. The only
  action on the understanding panel is one that quotes a proposition into the composer, which
  targets it for discussion and decides nothing.

- **R-9** The world-builder agent SHALL have no write access to the live world, proposal files,
  conversation records, queue, credentials, shell, or process execution.
  - Amended 2026-08-23: network tools left this list and became the `web` confinement intent,
    off unless `research.web` is on. World Chat is where someone says go and look this up, and an
    agent that answers rather than authors has no other way to get a fact it does not hold. It
    still writes nothing — what it reads reaches the world only through the accept gate.

## 2.3 The running understanding

- **R-10** Detected changes SHALL be represented by a strict discriminated candidate schema, not
  only prose in the assistant reply. The user-facing understanding panel is rendered from that
  schema; it is not a second, free-text summary the model writes independently.

- **R-11** Every candidate SHALL have a stable `cand_<ULID>` identity and an optimistic revision.
  The same proposition corrected over time SHALL retain its identity and increment its revision.

- **R-12** The first version SHALL support these classifications:

  - create Canon;
  - amend Canon;
  - open a Canon thread;
  - create a character, location, or faction sheet;
  - edit a character, location, or faction sheet;
  - change a relationship or cross-reference;
  - propose an image opportunity;
  - undecided classification requiring clarification.

- **R-13** Every candidate SHALL distinguish `settled`, `tentative`, and `unresolved` intent.
  Tentative material SHALL NOT become a proposal. Unresolved material MAY become an open Canon
  thread. Neither SHALL be silently dropped: the approvals screen SHALL name what did not carry
  over and why (R-27d), and the proposition SHALL remain in its conversation.

- **R-14** A turn MAY intentionally produce no candidates. No placeholder or "no change"
  candidate SHALL be created, and the understanding panel SHALL NOT acknowledge a turn that
  produced nothing.

- **R-15** The understanding panel SHALL group propositions by the entity or subject they concern,
  not by classification. Settled propositions SHALL be rendered as statements and unresolved ones
  as questions, so settledness is carried by the wording and not by colour or a badge alone.

- **R-15a** Every value that would be written into an authored file SHALL be exposed and editable
  on the approvals screen before acceptance (§11.5, §12). The conversation surface is not required
  to expose them, and SHALL NOT offer field editing.

- **R-16** The understanding panel SHALL reflect the current state of each proposition, not the
  history of what was said. A correction SHALL replace the displayed line rather than appending a
  second one. Superseded values remain in the event log and are not shown in the panel.

## 2.4 Checks and grounding

- **R-17** A candidate that claims an idea is new, an amendment, or related to an existing entity
  SHALL include structured receipts for the accepted Canon and sheets consulted.

- **R-18** Check receipts SHALL be coordinator-owned observations, not model assertions or
  rendered `tool.activity` strings.

- **R-19** Any quoted user, Canon, sheet, or extracted-artifact span used as evidence SHALL be
  mechanically verified against its immutable source and version/hash.

- **R-20** If retrieval is unavailable, the Studio MAY continue brainstorming, but novelty and
  amendment targeting SHALL be marked unknown. Neither the reply nor the understanding panel SHALL
  describe a proposition as new merely because no check ran. The panel SHALL state what could not
  be checked, and wrap-up SHALL turn that into an explicit choice rather than a silent assumption.

- **R-21** Likely duplicates and contradiction candidates SHALL be framed as editorial aids, not
  detected truth. Lexical overlap SHALL NOT by itself prevent a proposition from becoming a
  proposal.

  Where a Canon-create proposition has a likely duplicate or a plausible amendment target, the
  Studio SHALL say so in the reply and in the understanding panel when it is detected. If the
  conversation does not settle it, wrap-up SHALL still create the proposal, and that proposal
  SHALL carry the unresolved choice (R-34c). A contradiction candidate alone requires no decision.

## 2.5 Corrections, retraction, and grouping

- **R-22** A later correction to the same proposition SHALL update or withdraw the existing
  candidate rather than create a contradictory duplicate.

- **R-23** A retraction expressed in conversation ("forget that", "drop the whale bone idea")
  SHALL withdraw the proposition and record a durable tombstone. The same target, fields, and
  value digest SHALL stay suppressed until later conversation changes it materially. There is no
  UI dismiss control and no restore control; the user retracts and reinstates by talking.

- **R-24** Grouping SHALL be computed by the coordinator, not performed by the user. Propositions
  that are referentially or logically dependent SHALL be placed in one atomic group so they land
  in one proposal. The model MAY suggest grouping; the coordinator SHALL validate it against
  current world state.

- **R-25** Independent propositions SHALL become separate proposals. A long conversation SHALL NOT
  produce one all-or-nothing proposal.

- **R-26** A media opportunity SHALL NOT be included in an authored-file proposal. It may depend
  on one, but media dispatch remains a separate action.

## 2.6 Wrap-up and the accept gate

- **R-27** Merely discussing or detecting an idea SHALL NOT reserve a Canon ID, allocate a sheet
  slug, or create a proposal. Nothing is written outside `.conversations` until wrap-up.

- **R-27a** Wrap-up SHALL be a single user action that goes directly to the approvals screen. It
  SHALL NOT interpose a preview or confirmation step. The control SHALL state its consequences
  before it is pressed: how many propositions become how many proposals, and that the conversation
  closes.

  An earlier draft required a two-step wrap-up with a preview. The preview summarised the screen
  it stood in front of, so it was removed. Everything it carried is reported on the approvals
  screen instead, against the real proposed values rather than a summary of them (R-27d, R-21).

- **R-27d** On arrival from a wrap-up, the approvals screen SHALL state, for that conversation:
  which propositions became open Canon threads; which propositions did not carry over, naming each
  and its reason; and that media opportunities were retained as ideas. A proposition that did not
  carry over SHALL remain in its conversation rather than being discarded.

- **R-27b** Wrap-up SHALL close the conversation. A closed conversation SHALL accept no further
  messages, its composer SHALL state why, and its transcript and understanding SHALL remain
  readable with each proposition marked with the proposal it became.

- **R-27c** A closed conversation SHALL be reopened only by sending one of its proposals back
  (R-34a). Reopening SHALL return that proposal's propositions to the understanding and re-enable
  the composer.

- **R-28** Canon IDs and final new-sheet slugs SHALL be allocated by the coordinator at wrap-up,
  under the world serialization boundary. Model output SHALL NOT choose filesystem paths or
  authoritative IDs.

- **R-29** Wrap-up SHALL revalidate candidate revisions, target existence, settledness, evidence,
  and world checks against current state before materialization.

- **R-30** Related Canon and sheet changes SHALL materialize as one mixed `worldbuilding`
  proposal and SHALL land through exactly one SPEC-002 commit.

- **R-31** Every proposal target SHALL capture its live base at the moment the proposal is
  written.

- **R-32** A World Chat proposal SHALL use the existing stale-base, rebase, conflict, ripple,
  re-confirmation, no-op, acceptance, and discard behavior.

- **R-33** Proposal review SHALL show entity names, actions, fields, before values, proposed
  values, and the conversation each change came from. A list of paths alone is insufficient.

- **R-34** Once created, proposal files are authoritative. The user MAY correct values in place on
  the approvals screen; every such edit is an explicit typed command carrying the expected draft
  revision. No model output SHALL mutate a proposal.

- **R-34a** Every proposal SHALL offer three terminal actions: accept, discard, and send back to
  its originating conversation. Send-back SHALL remove the proposal, return its propositions to
  that conversation's understanding, and reopen the conversation. Send-back SHALL be unavailable
  for a proposal whose conversation has been deleted; discard remains.

- **R-34b** An accept-all action MAY be offered, SHALL name the exact count of proposals it will
  accept, and SHALL be unavailable while any pending proposal is stale, conflicted, awaiting
  re-confirmation, or carrying an unresolved choice.

- **R-34c** A proposal MAY carry an unresolved choice that the coordinator could not make on the
  user's behalf. In the first version the only such choice is whether a Canon-create should
  instead amend a named entry (R-21). The choice SHALL be shown on the proposal it concerns,
  beside the values it would change, and SHALL be visible in the pending list. A proposal with an
  unresolved choice SHALL NOT be acceptable until it is answered; discard and send-back remain
  available. Answering "amend instead" rewrites that proposal's target, base capture, and ripple
  under the world serialization boundary, and increments its draft revision.

## 2.7 Media opportunities

- **R-35** A media candidate MAY carry a target, purpose, rationale, and editable brief. It SHALL
  carry no provider command and SHALL NOT enqueue work.

- **R-36** Opening a media candidate SHALL route to the existing appropriate generation surface
  with its brief prefilled. The existing surface SHALL still show provider/model, references,
  estimate, and the explicit Generate action.

- **R-37** If the brief depends on unaccepted propositions or proposals, Generate SHALL be
  unavailable until those dependencies are accepted in v1, and the media surface SHALL name the
  proposal it is waiting on and link to it.

- **R-37a** Media opportunities SHALL survive wrap-up as ideas attached to their target. They are
  not proposals, are not closed with the conversation, and SHALL be named on the approvals screen
  so the user knows they were kept rather than dropped (R-27d).

## 2.8 Failure, degradation, and safety

- **R-38** One active model run SHALL be allowed per conversation. Duplicate send request IDs
  SHALL be idempotent.

- **R-39** Every run SHALL be cancellable and bounded by wall-clock and token budgets. Cancellation
  SHALL end the local wait immediately and request harness interruption.

- **R-40** A failed or invalid model result SHALL apply no partial Studio message, candidate, or
  group mutations. The user message and all prior state SHALL remain.

- **R-41** Structured output and evidence failures SHALL receive at most one corrective retry.
  A second failure SHALL be stated and SHALL offer retry/direct-form paths.

- **R-42** Opening another world while a turn is running SHALL invalidate that turn's world-query
  lease and end it with a stated interruption. A turn SHALL never query whichever world happens
  to be open later.

- **R-42a** A failed wrap-up SHALL leave no proposal and SHALL NOT close the conversation. There
  is no partially closed state: the conversation closes only after every proposal it produced is
  durable.

- **R-43** With OpenCode unavailable, existing conversations and their understanding SHALL remain
  readable, existing proposals SHALL remain approvable, and wrap-up SHALL remain available for a
  conversation that already has propositions. The composer SHALL state why chat is unavailable and
  link to direct forms.

- **R-44** With the index unavailable, the UI SHALL distinguish retrieval degradation from
  harness degradation.

## 2.9 Privacy, accessibility, and presentation

- **R-45** Conversation content, candidate content, excerpts, attachments, and world names SHALL
  not enter app logs, coordinator logs, diagnostics bundles, crash metadata, or analytics.

- **R-46** World Chat SHALL display whether the selected authoring model is local, cloud, or
  unknown before the first send and when routing changes. The first cloud-routed send is the
  user's deliberate disclosure after that notice; no separate prompt is required on every turn.
  Unknown routing SHALL not be presented as local.

- **R-47** The transcript, the understanding panel, and the approvals screen
  SHALL be keyboard operable, have logical focus order, and express state in text rather than
  colour alone. Streaming tokens SHALL not flood assistive live regions. Only completed messages
  and completed changes to the understanding SHALL be announced.

- **R-48** Desktop and narrow layouts SHALL remain usable. On narrow layouts the understanding
  SHALL become a clearly labelled panel or sheet rather than shrinking below readable width, and
  no more than one floating layer SHALL be open at a time.

- **R-49** World Chat SHALL disclose the selected harness/model's retention boundary. Studio
  SHALL request deletion of each ephemeral harness session where the adapter supports it and
  SHALL never claim that a user-installed or incapable harness retained nothing.

- **R-50** A conversation with an active run, an incomplete wrap-up, or an unresolved proposal
  SHALL NOT be physically deletable. Archiving SHALL remain available for an open conversation.
  Deletion SHALL require explicit confirmation after all proposal links resolve, and SHALL
  permanently remove send-back as an option for any proposal that originated there.

# 3. Architectural decision

## 3.1 Add a durable candidate layer

The existing authoring path is:

```text
known path -> proposal -> authoring session -> accept/discard
```

World Chat requires:

```text
world conversation
    -> checked candidates, shown as a running understanding
    -> one explicit wrap-up decision, which closes the conversation
    -> one or more proposals
    -> accept / send back / discard
```

The candidate layer is not optional UI state. Without it, one of two unsafe behaviors follows:

1. every speculative idea creates a durable proposal and possibly reserves IDs; or
2. detected ideas live only in renderer/model memory and disappear on restart.

Candidates are therefore durable World Chat state. They are authoritative before wrap-up. After
wrap-up the proposal is authoritative and the candidate becomes a linked projection of it.

Note that the candidate layer is required by durability and correctness, not by the user
interface. It survives the change described in §0.1 unchanged in substance. What that change
removes is the presentation of candidate status as a per-item triage queue: the user reads
propositions and corrects them by talking, while status, readiness, and grouping remain internal
until wrap-up needs them.

## 3.2 Reuse, do not replace, proposals

World Chat does not introduce a second commit system. It uses `ProposalManager` for:

- whole-file materialization;
- base capture;
- mixed targets;
- ripple preview and authoritative recomputation;
- stale detection;
- field-level rebase and conflicts;
- one atomic commit;
- restart recovery and needs-you contribution.

This feature requires proposal extensions and richer review projections, but it must not create a
parallel "chat commit" path.

## 3.3 Use fresh, bounded model sessions

The durable conversation, not the OpenCode session, holds continuity. Each World Chat turn uses a
new or deliberately rotated session assembled from durable context. This avoids:

- losing continuity on app restart;
- depending on hidden model context that Studio cannot inspect or bound;
- unbounded token growth in a long-running foreign session;
- confusing a provider session ID with product identity;
- a stale session silently querying a different open world.

Session reuse may be introduced later as an optimization only if the assembled durable context
remains authoritative and behavior is identical after session loss.

# 4. Filesystem and persistence model

## 4.1 Location

Store unfinished conversations under the owning world:

```text
<world>/
  .conversations/
    cv_<ULID>/
      conversation.json
      events.jsonl
      checkpoint.json
```

This is operational workspace state, like `.proposals`, not accepted authored world content.

Reasons for world-local storage:

- a world archive carries its unfinished thinking with the world;
- identity does not depend on the current app-root registry;
- restore and manual full-folder copy remain understandable;
- candidate references to world entities cannot become detached from their owner;
- no app-level database becomes a second source of truth.

Normal **Export world** excludes `.conversations`, matching its exclusion of `.proposals` and
other unfinished operational state. A manual full-folder copy includes it.

Introducing `.conversations` requires a world schema-version increment. Older builds otherwise
copy unknown directories during export and would leak conversations despite not understanding the
new exclusion. The migration changes only `world.json.schemaVersion`; no conversation directory is
created until the user starts one. Older builds then refuse the newer world rather than exporting
it incorrectly.

World-local conversation records do not repeat `worldId`. A cloned world may receive a new
`worldId`; local entity references remain valid without a clone-time rewrite.

## 4.2 Files and authority

### `conversation.json`

Immutable identity header only:

```ts
interface WorldChatConversationMeta {
  schemaVersion: 1;
  id: `cv_${string}`;
  createdAt: string;
}
```

Title, lifecycle state, current entry context, and `updatedAt` are folded from
`conversation.created`, `conversation.metadata-updated`, `conversation.archived`,
`conversation.unarchived`, `wrapup.completed`, and `conversation.reopened` events. They are cached
in `checkpoint.json` for list discovery. This leaves one authority instead of racing mutable
metadata against the event log.

### `events.jsonl`

The append-only authority for messages, runs, candidates, groups, tombstones, attachments,
wrap-up, proposal links, and resolution events.

Each complete line is a validated envelope:

```ts
interface WorldChatEventEnvelope {
  schemaVersion: 1;
  seq: number;
  eventId: `wce_${string}`;
  at: string;
  requestId?: string;
  event: WorldChatStoredEvent;
}
```

The sequence is monotonic per conversation. A duplicate `requestId` returns the result of the
existing operation rather than appending a second mutation.

### `checkpoint.json`

A derived acceleration file containing the latest folded candidate/group state, summary, and
the event sequence through which it was computed. It is atomically rewritten and may be deleted
and rebuilt from `events.jsonl` without loss.

The checkpoint is not trusted if its sequence is beyond the complete event tail or its schema
does not validate.

## 4.3 JSONL durability

Use the existing crash discipline from world change logs and the job journal:

- serialize writers in-process;
- validate before append;
- append one complete JSON line;
- call `sync()` before reporting success;
- permit truncation to the last complete newline as the sole rewrite of the authoritative log;
- surface malformed interior records as a named conversation problem while retaining valid
  earlier records;
- never rewrite the authoritative event log during ordinary use.

Before each append, verify the expected byte length, last complete sequence, and tail digest
recorded by the in-process conversation writer. A mismatch means another process or program
changed the operational file; refuse the append and surface a conversation-integrity problem.
Ignoring `.conversations` in the world watcher must not mean accepting concurrent external edits
silently.

One completed turn is appended as one terminal event containing the complete Studio message,
verified check receipts, full candidate snapshots changed by the turn, and full group snapshots
changed by the turn. This prevents a crash from persisting the reply without its candidates or
half of a related candidate set.

## 4.4 Watcher, scanner, index, history, and export

`.conversations/` SHALL be:

- ignored by the live external-edit watcher;
- excluded from `scanWorld()` and the accepted-world manifest;
- excluded from the derived index;
- excluded from version history and `changes.jsonl`;
- excluded from ordinary world export;
- included when the complete world directory is archived or manually copied.

Conversation writes are app-owned and must not produce "This world changed outside Arke Studio".

## 4.5 Loading and paging

`WorldBundle` receives only summaries:

```ts
interface WorldChatSummary {
  id: ConversationId;
  title: string;
  status: "open" | "closed" | "archived";
  updatedAt: string;
  entryContext?: WorldChatContext;
  /** Live propositions in the understanding. Zero for a conversation that produced nothing. */
  pointCount: number;
  /** Proposals produced by wrap-up that are still awaiting a decision. */
  openProposalCount: number;
  /** Set when a closed conversation was reopened by a send-back. */
  reopened?: boolean;
}
```

The list orders by pending consequence, not recency alone: a conversation with unresolved
proposals outranks one with live propositions, which outranks one with neither. `lastMessagePreview`
is deliberately absent. What is pending tells the user whether to return; the previous sentence
does not, and it costs a line on every row.

The full workspace is loaded by conversation ID and contains:

- metadata, including lifecycle state and any reopening;
- the latest 50 messages;
- all live propositions, grouped for display;
- compact withdrawn/superseded history;
- proposal links for a closed conversation;
- current run state;
- current context summary;
- a cursor for older messages.

Older messages are loaded before a sequence cursor. Renderer reconnection reloads this view rather
than depending on event replay.

# 5. Identity and domain schemas

## 5.1 IDs

Keep product and provider identities separate:

| Prefix             | Meaning                                                          |
| ------------------ | ---------------------------------------------------------------- |
| `cv_`              | durable World Chat conversation                                  |
| `turn_`            | one user input and its processing lifecycle                      |
| `msg_`             | immutable user or Studio message                                 |
| `run_`             | one model attempt for a turn                                     |
| `check_`           | one coordinator-owned retrieval receipt                          |
| `cand_`            | one stable detected change                                       |
| `grp_`             | one atomic candidate group                                       |
| `wca_`             | one private World Chat attachment                                |
| `pr_`              | existing proposal identity                                       |
| harness session ID | ephemeral OpenCode identity, never persisted as product identity |

All Studio IDs are generated before the operation they identify and persisted before external
work begins.

## 5.2 Conversation context

```ts
type WorldChatContext =
  | { kind: "world" }
  | { kind: "canon-question"; question: string; candidateEntryIds: string[] }
  | { kind: "canon-entry"; entryId: string }
```

## 5.3 Messages and runs

```ts
interface WorldChatMessage {
  id: MessageId;
  turnId: TurnId;
  role: "user" | "studio";
  text: string;
  /** Conversation-private attachment identities, not world artifact IDs. */
  attachmentIds: string[];
  createdAt: string;
}

interface WorldChatRun {
  id: RunId;
  turnId: TurnId;
  basedOnConversationSeq: number;
  status: "running" | "completed" | "cancelled" | "timeout" | "budget-exceeded" | "interrupted" | "failed";
  adapter: string;
  model?: string;
  harnessSessionId?: string;
  harnessCleanup: "not-required" | "pending" | "confirmed" | "unsupported" | "unconfirmed";
  contextDigest: string;
  startedAt: string;
  endedAt?: string;
  safeDetail?: string;
}
```

Streaming assistant text is transient presentation and is never the durable message. Only a
validated completed turn appends the Studio message.

Before remote session creation, persist cleanup `pending` with a deterministic, caller-generated
ownership tag derived from `conversationId + runId`. An adapter may advertise crash-recoverable
session cleanup only when it can create/tag, find, and delete Studio-owned sessions by that tag.
After creation, append a synced `run.session-created` event with the returned session ID before
sending the user's content. On startup, a pending run with no recorded session ID asks the adapter
to find every owned session carrying the tag and deletes them; zero matches confirms there is
nothing to clean, one match is deleted, and multiple matches are all deleted and recorded as an
adapter defect. This closes the crash window between remote creation and local receipt.

An adapter that can delete only by returned session ID but cannot recover by ownership tag does
not advertise crash-recoverable deletion. Persist `unsupported` before send and disclose that
limitation. Harness session IDs and ownership tags are operational identifiers and never enter
diagnostics.


`pending-*` references allow one atomic group to create entities that cite each other before final
Canon IDs or sheet slugs exist. In model output, `{ temporaryId }` may reference a create operation
from the same turn; while applying the complete turn, the coordinator allocates final candidate
IDs first and rewrites every temporary reference to `{ candidateId, revision: 1 }`. No temporary
reference is ever persisted. Every stored pending reference must then name a pinned candidate
revision in the same atomic group and wrap-up request. Wrap-up allocates all entity identities
first, resolves the reference graph, then materializes files. A missing, stale, separately
proposed, or media-candidate reference rejects the whole wrap-up operation.

| Status       | Meaning                                                    |
| ------------ | ---------------------------------------------------------- |
| `live`       | in the understanding, correctable by talking               |
| `withdrawn`  | retracted in conversation                                  |
| `superseded` | replaced by a split or consolidation                       |
| `proposed`   | carried into a proposal by wrap-up                         |
| `accepted`   | its proposal was accepted                                  |
| `discarded`  | its proposal was discarded; it does **not** return         |
| `handed-off` | a media idea whose job was durably queued                  |

Discard and send-back are deliberately different. Send-back returns propositions to `live` and
reopens the conversation (R-34a). Discard is the user saying they have changed their mind, and
those propositions stay `discarded`. Having both is what makes discard safe to offer at all.

**Removed by the §0.1 revision.** `authority`, `userOwnedFields`, `CandidateStageBinding`, and
`CandidatePendingUpdate` are gone. `authority` recorded who had reviewed a candidate, which only
mattered when candidates were reviewed one at a time. `userOwnedFields` protected user field edits
from later model output, and there are no in-conversation field edits to protect. `pendingStagedUpdate`
handled a later turn suggesting a change to something already staged, which can no longer happen:
wrap-up closes the conversation, so no turn exists after a proposal is created. Field-level
conflict between the user and the model is therefore not a case this feature has to handle.

The coordinator derives `CandidateChecks`; the model does not supply duplicate/amendment sets or

classification:

| Candidate                 | Required checks                                                    |
| ------------------------- | ------------------------------------------------------------------ |
| `canon.create`            | Canon search for title + statement concepts                        |
| `canon.amend`             | target entry read; Canon search if target was inferred this turn   |

| `relationship.change`     | both target sheets read and related lookup                         |
| `media.image-opportunity` | target read only                                                   |
| `undecided`               | checks needed by each plausible action, or remain partial          |

and contradiction candidates using configured lexical thresholds. `state` is `complete` only when
all `required` categories are in `completed`; it is `unavailable` when a required operation could
not run, `partial` when more clarification/search is needed, and `stale` when an observed source
moved. The model may provide `explanation` prose, but the coordinator suppresses it if it names
entities outside the computed sets.

# 6. Candidate lifecycle

## 6.1 State transitions

```text
                 correction / retraction, by talking
        +----------------------------------------------+
        |                                              |
        v                                              |
      live ---------------------------------------> withdrawn
        |  \                                           superseded
        |   \
        |    +--> handed-off        (media only, after a durable enqueue)
        |
        |  wrap-up: one action, the whole conversation
        v
    proposed ---> accepted          (the existing gate)
        |
        +-------> discarded         (stays discarded)
        |
        +-------> sent back --------> live, conversation reopened
```

Only `live` propositions appear in the understanding panel. `withdrawn` and `superseded` are
history, kept in the event log and available in a collapsed view. `proposed`, `accepted`, and
`discarded` are shown on a closed conversation as the proposal each became.

There is no `ready`, `deferred`, `dismissed`, or `needs-clarification` state. The first three were
user triage, which this design removes. The fourth described a candidate waiting for the user to
answer a question, which is now just a question the Studio asked in the reply.

## 6.2 What may become a proposal

Readiness is no longer a per-candidate state the user acts on. It is evaluated once, for every
live proposition, when wrap-up runs. A proposition becomes part of a proposal only when:

- its payload validates;
- its target exists and is not retired, or it is a valid create;
- its classification is not `undecided`;
- it has verified user intent evidence;
- required checks are complete, or the user answers the corresponding question in the wrap-up
  preview;
- a settled fact is marked `settled`;
- an open-thread proposition is marked `unresolved`;
- every referenced candidate/group revision still exists.

Model output may suggest that something is settled. The coordinator decides.

Settledness rules by classification:

| Classification                                      | At wrap-up                                                 |
| --------------------------------------------------- | ---------------------------------------------------------- |
| `canon.create`, `canon.amend`                       | must be `settled`                                          |
| `canon.thread`                                      | must be `unresolved`; becomes an open thread proposal      |
| `sheet.create`, `sheet.edit`, `relationship.change` | must be `settled`                                          |
| `media.image-opportunity`                           | never becomes a proposal; retained as an idea (R-37a)      |
| `undecided`                                         | never becomes a proposal                                   |

A `tentative` proposition of any authored classification cannot become a proposal. It is not
silently dropped: it stays in the conversation, and the approvals screen names it and says why
(R-13, R-27d).

Where a Canon-create proposition still has an unresolved likely duplicate or amendment target, the
proposal carries that choice and cannot be accepted until it is answered (R-21, R-34c). In
practice this is the only decision the coordinator genuinely cannot make.

## 6.3 Corrections

The coordinator owns candidate identity and merge behavior. The model proposes operations; it
does not append arbitrary cards.

For a correction such as "not her mother, her aunt":

1. the result references the existing candidate;
2. the evidence identifies the correcting message;
3. the coordinator verifies the expected candidate revision;
4. the same candidate ID receives a full new snapshot;
5. its structural key remains the same if target and owned fields are unchanged;
6. old evidence is replaced or retained only where still applicable.

If one candidate is split into two propositions, two new candidates receive `splitFrom`, and the
old candidate becomes `superseded`. If two candidates are consolidated, the survivor records
`supersedes` and the others become `superseded`.

An accepted candidate is immutable history. A later correction creates a new amend/edit candidate
against accepted world state.

## 6.4 Retraction and resurfacing

Retraction is expressed in conversation, not by a control (R-23). "Forget that", "drop the whale
bone idea", "no, ignore what I said about the aunt" withdraw the proposition. The coordinator
records:

- candidate ID and revision;
- a coordinator-computed structural key;
- normalized payload digest;
- target and field keys;
- the retracting message ID;
- timestamp.

Re-detecting an identical digest is suppressed, so the same idea does not reappear on the next
turn simply because it is still in context. A withdrawn proposition returns to `live` only when a
later user message changes its target, value, settledness, or classification materially, or the
user plainly reinstates it in conversation.

The model cannot clear a tombstone on its own initiative; only a user message can produce the
material change or reinstatement that lifts one.

## 6.5 Propositions carried into a proposal

Wrap-up freezes `proposedCandidateRevision` in the proposal origin metadata and sets each
contributing proposition to `proposed`. From that moment the proposal files are authoritative and
the proposition is a linked projection of them.

Because wrap-up closes the conversation, there is no later turn that could suggest a change to a
proposal. The pending-update machinery of the earlier draft is therefore unnecessary and has been
removed (§5.5).

Corrections after wrap-up happen in one of two places:

- **On the approvals screen**, by editing values in place before accepting. Each edit is a typed
  command carrying `expectedDraftRevision`, and updates the proposal draft rather than the
  proposition. Acceptance records the final proposal digest, so the UI never claims the original
  wording was what landed when the user changed it.
- **Back in the conversation**, by sending the proposal back (R-34a). Its propositions return to
  `live`, the conversation reopens, and the discussion continues from there.

An accepted proposition is immutable history. A later change to that same fact is a new
proposition, in a new or reopened conversation, against accepted world state.

# 7. Conversation storage events

## 7.1 Stored event union

The first version needs these durable event types:

```text
conversation.created
conversation.metadata-updated
conversation.archived
conversation.unarchived
conversation.reopened
turn.started
run.retry-started
run.session-created
run.finished
turn.completed
candidate.status-changed
attachment.created
attachment.linked
attachment.unlinked
attachment.promoted
wrapup.intent-recorded
wrapup.completed
wrapup.failed
proposal.resolved
summary.updated
deletion.intent-recorded
```

`turn.completed` atomically carries:

- the completed Studio message;
- all check receipts produced for the turn;
- full updated candidate snapshots;
- full updated group snapshots;
- the completed run outcome.

`wrapup.completed` atomically carries the created proposal IDs, the allocated Canon IDs and sheet
slugs, the target paths, each proposal's digest, the final status of every proposition including
those that did not carry over, and the transition of the conversation to `closed`.

`candidate.status-changed` now covers only outcomes the conversation did not cause: a proposal
being accepted, discarded, or sent back, and a media idea being handed off after a durable
enqueue. The earlier draft's `candidate.updated`, `group.updated`, and
`candidate.pending-staged-update` events are removed. During a conversation, candidate and group
state changes only inside `turn.completed`, because the user has no controls that could change it
independently.

`turn.started` atomically carries the immutable user message and initial running `WorldChatRun`.
The store syncs that one event before model dispatch, so there is no crash window containing an
accepted user message with no retryable run. `run.retry-started` names the existing turn and adds
only a new run. A failed/cancelled/interrupted attempt ends with `run.finished`; a successful
attempt ends inside `turn.completed` with its Studio message and mutations.

## 7.2 Fold invariants

- Message IDs are immutable and unique.
- A user message and its first run begin in the same `turn.started` event.
- One turn may have multiple run attempts but at most one completed Studio message.
- Candidate/group revisions increase exactly by one.
- A candidate update with the wrong expected revision is rejected and does not append.
- A proposal binding references a proposal and the exact candidate revision it carried.
- A conversation may complete wrap-up at most once without an intervening `conversation.reopened`.
- `wrapup.completed` never precedes the durability of every proposal it names.
- A proposal resolution may occur once; duplicate reconciliation is idempotent.
- A `running` run with no terminal event at startup folds to `interrupted` in memory and appends a
  durable terminal event before another run starts.

`attachment.created` carries the complete immutable `WorldChatAttachment` metadata after bytes are
atomically published. `attachment.promoted` carries its world artifact ID after artifact filing is
durable. Startup reconciles attachment directories against these events: unreferenced staging is
removed; published bytes without a completed creation event are quarantined/deleted; a promoted
artifact is recovered by the operation request ID rather than filed twice.

# 8. Model and harness protocol

## 8.1 Dedicated purpose and agent

Add:

```text
SessionPurpose: world-chat
Agent: world-builder
```

The `world-builder` agent:

- replies through one strict structured response;
- has no edit/write tool;
- has no shell or process tool, and receives public-web tools only when `research.web` is on;
- reads accepted world state only through a run-scoped read-only MCP lease;
- may read only the explicitly selected document attachments exposed by that lease;
- cannot access the queue, providers, credentials, proposal directories, or conversation files.

Remembered harness grants do not override these hard denials. A permission request for a denied
class is rejected automatically and recorded as a configuration defect, not shown as a normal
creative-workflow prompt.

## 8.2 Per-turn scratch directory

Each run receives a new scratch directory outside the world:

```text
%APP_ROOT%/run/world-chat/<conversationId>/<runId>/
  opencode.json
```

It contains no transcript authority and no world files. It is deleted best-effort after the run
and swept at next startup after a crash. The MCP lease token in `opencode.json` expires when the
run ends.

## 8.3 Structured model result

The assistant's entire completed message is JSON conforming to a strict schema:

```ts
interface WorldChatTurnResult {
  reply: string;
  candidateOperations: Array<
    | { op: "create"; temporaryId: string; candidate: ModelCandidateDraft }
    | {
        op: "update";
        candidateId: CandidateId;
        expectedRevision: number;
        candidate: ModelCandidateDraft;
      }
    | {
        op: "withdraw";
        candidateId: CandidateId;
        expectedRevision: number;
        reason: string;
      }
    | {
        op: "split";
        candidateId: CandidateId;
        expectedRevision: number;
        replacements: ModelCandidateDraft[];
      }
  >;
  groupOperations: ModelGroupOperation[];
}
```

`ModelCandidateDraft` is the model-facing candidate union from §5.6 plus:

```ts
interface ModelCandidateCommon {
  title: string;
  rationale: string;
  settledness: "settled" | "tentative" | "unresolved";
  evidence: CandidateEvidence[];
  /** Optional supporting reads; these cannot satisfy the coordinator-owned required check plan. */
  checkReceiptIds: CheckReceiptId[];
}
```

It omits final candidate ID, revision, status, subject grouping, group binding, proposal binding,
paths, proposal IDs, and job/provider fields; the coordinator computes those.

`ModelGroupOperation` may suggest create/update/split/withdraw of a group using temporary IDs or
existing group IDs and exact candidate revisions. The coordinator validates all membership and
assigns final group IDs/revisions.

```ts
type ModelGroupOperation =
  | {
      op: "create";
      temporaryId: string;
      title: string;
      rationale: string;
      members: Array<ModelCandidateRef>;
    }
  | {
      op: "update";
      groupId: CandidateGroupId;
      expectedRevision: number;
      title: string;
      rationale: string;
      members: Array<ModelCandidateRef>;
    }
  | {
      op: "withdraw";
      groupId: CandidateGroupId;
      expectedRevision: number;
      reason: string;
    };

type ModelCandidateRef = { candidateId: CandidateId; revision: number } | { temporaryId: string };
```

Temporary candidate references may point only to candidates created in the same turn result.

The freeform `reply` does not carry machine references to candidates. The understanding panel
renders from the structured operations beside the reply. Therefore invalid candidate IDs are
rejected in operations, not inferred from reply prose.

The model may reference existing candidate/group IDs supplied in context. It does not create
final IDs, paths, Canon IDs, sheet slugs, proposal IDs, or job IDs.

## 8.3.1 Coordinator-owned check plan

The coordinator builds and executes required candidate checks; the model cannot choose the search
scope used to establish readiness.

For a candidate create/update operation:

1. validate its classification/payload enough to derive a check plan;
2. normalize deterministic search inputs from title, statement/name, target, links, and changed
   fields;
3. execute the classification matrix in §5.7 through the same world-bound query lease;
4. persist canonical queries, corpus/version, thresholds, result IDs, counts, and receipts;
5. derive `CandidateChecks` and readiness;
6. treat model-supplied receipt IDs only as additional visible context/evidence.

A model may perform exploratory searches while composing its reply, but those arbitrary searches
do not mark `required` categories complete. The coordinator's canonical queries are bounded,
reproducible in tests, and rerun at wrap-up when observations are stale.

The result has hard bounds:

- reply: 8,000 characters;
- at most 12 candidate operations;
- at most 6 group operations;
- title: 160 characters;
- rationale/explanation: 1,000 characters;
- image brief: 4,000 characters;
- no arbitrary unrecognized fields.

## 8.4 Validation and retry

Validation order:

1. parse JSON;
2. validate the response schema;
3. verify candidate IDs and expected revisions;
4. validate each candidate payload;
5. verify message/world/attachment evidence;
6. verify check-receipt references were produced by this run;
7. compute structural keys and deduplication;
8. compute what may be claimed about each proposition;
9. validate group membership and atomicity;
10. append one `turn.completed` event.

Any failure rejects the whole result. The coordinator sends one corrective turn naming only the
safe validation errors and requiring the complete result again. If the retry fails, no Studio
message or candidate operations are applied. The original user message remains with a failed run
and a visible Retry action.

This all-or-nothing rule prevents a reply that refers to propositions which did not persist.

## 8.5 Context assembly

Each run receives bounded durable context:

| Context section                  |                                                 Initial bound |
| -------------------------------- | ------------------------------------------------------------: |
| System/protocol instructions     |                                               fixed, reviewed |
| Durable conversation summary     |                                              8,000 characters |
| Live proposition registry        |                                             16,000 characters |
| Last eight complete turns        |                                             32,000 characters |
| Focused accepted-world context   |                                             32,000 characters |
| Retraction tombstones            |                              structural keys and digests only |
| Current user message             | never truncated; oversized paste becomes a private attachment |

The exact budget may be tuned, but it must remain explicit and tested. If a section exceeds its
bound, deterministic prioritization is used; the model is never allowed to inherit unbounded
history invisibly.

## 8.6 Summaries

After eight turns or when recent-turn context reaches its bound, a separate bounded summarization
run creates a compact summary with `throughSeq` and source message IDs. The summary is context,
not authority:

- messages remain the source for what was said;
- candidates remain the source for detected changes;
- world files remain the source for accepted facts;
- evidence never cites the summary;
- summary failure leaves the previous summary in place.

# 9. World-bound retrieval and checks

## 9.1 Run-scoped query lease

The current world-query server resolves every call against whichever store is open at call time.
World Chat must replace that behavior with a run-scoped lease:

```text
lease token -> world/store identity + conversationId + runId + allowed attachment IDs + expiry
```

Every call verifies:

- the token exists and is unexpired;
- the requested run is active;
- the same world/store remains open;
- the operation is allowed;
- the request stays within size and result limits.

Switching/closing the world invalidates the lease. It must never redirect the lease to the newly
open world.

## 9.2 Tool surface

The v1 read-only tool surface is:

| Tool                                 | Purpose                                                        |
| ------------------------------------ | -------------------------------------------------------------- |
| `search_canon(query, limit)`         | ranked accepted Canon search, full statement for quotations    |
| `search_sheets(query, kind, limit)`  | lexical search over accepted sheets                            |
| `get_entry(id)`                      | one accepted Canon entry and revision lineage                  |
| `get_sheet(id)`                      | one accepted sheet and current version                         |
| `list_entities(kind, status, limit)` | bounded entity list                                            |
| `related(id)`                        | accepted incoming/outgoing references                          |
| `get_attachment_text(id, range)`     | bounded text from an explicitly linked conversation attachment |

There is no write operation and no filesystem path parameter.

`search_sheets` is a SPEC-003 extension. It indexes only production-reference text appropriate to
entity matching: name, type, role/region, and declared prose sections. It excludes operational
metadata, voice IDs, media paths, and retired sheets. Ranking is FTS5/BM25 with the same bounded
result discipline as Canon search. Index migration/rebuild is required when this corpus is added.

Images, audio, and video may be attached and linked to the conversation, but World Chat v1 does
not claim to inspect them. The UI says whether an attachment was **attached privately**, **read as
text**, **filed in the world**, or **not readable in this chat**. Existing extraction may produce
text/candidates separately after explicit promotion.

## 9.3 Structured check receipts

The coordinator wraps every tool call and records a receipt:

```ts
interface WorldChatCheckReceipt {
  id: CheckReceiptId;
  runId: RunId;
  tool:
    | "search-canon"
    | "search-sheets"
    | "get-entry"
    | "get-sheet"
    | "list-entities"
    | "related"
    | "get-attachment-text";
  status: "complete" | "empty" | "unavailable" | "failed";
  querySummary?: string;
  consulted: Array<{
    ref: WorldChatEntityRef;
    observedVersion: number;
    contentHash: string;
  }>;
  searchedCount?: number;
  at: string;
}
```

`querySummary` is safe product text, not raw tool JSON. It must not enter app diagnostics.

The UI may render transient `tool.activity` immediately, but the understanding panel and completed
turns render persisted receipts.

## 9.4 Retrieval degradation

If the index is unavailable:

- direct `get_entry`/`get_sheet` from the accepted bundle may continue;
- lexical search and related queries report unavailable;
- the Studio may continue creative conversation;
- the panel states what could not be checked and never calls a proposition new;
- wrap-up presents the unchecked-novelty decision, so the user chooses a target or creates anyway
  after seeing the limitation;
- that choice is durable and visible in final review.


The approvals screen uses gate commands rather than World Chat commands, because it serves

```text

proposal-resolve-conflict    existing
```

`world-chat-set-candidate-status`, `world-chat-restore-candidate`, `world-chat-group-candidates`,

computed; and staging is replaced by wrap-up.

## 10.1.1 Private attachment contract

```ts
interface WorldChatAttachment {
```

`world-chat-attach-files` and `world-chat-attach-text` are host-mediated like existing file

`world-chat-send` carries:

```ts
{
  kind: "world-chat-send";
```

Wrap-up is one command. It creates the proposals, closes the conversation, and returns what the
approvals screen needs to explain itself:

```ts
{

  requestId: string;
  worldId: string;
  conversationId: ConversationId;
  expectedConversationSeq: number;
}

interface WrapUpResult {
  proposalIds: string[];
  /** Unresolved propositions that became open Canon threads. */
  threadProposalIds: string[];
  /** Named, never merely counted (R-13, R-27d). */
  notCarried: Array<{
    candidateId: CandidateId;
    summary: string;
    reason: "tentative" | "undecided" | "target-missing" | "invalid";
  }>;
  /** Retained against their target; never proposals (R-37a). */
  mediaIdeaIds: CandidateId[];
  /** Choices the coordinator could not make; each names the proposal carrying it (R-34c). */
  openChoices: Array<{
    proposalId: string;
    choiceId: string;

    question: string;
    options: Array<{ optionId: string; label: string }>;

```

There is deliberately no preview command. An earlier draft had one; it computed this same result
without writing, showed it in a sheet, and then a second command replayed it. That sheet stood in
front of the approvals screen and said less than it did. The result above is now delivered to that
screen directly.

A stale `expectedConversationSeq` is refused outright rather than silently re-planned, because the
propositions being written must be the ones the user was last shown in the panel.

`proposal-resolve-choice` carries the proposal ID, its expected draft revision, the `choiceId` and
the chosen `optionId`. Choosing to amend retargets the proposal, recaptures its base, recomputes
its ripple, and increments `draftRevision` (R-34c).

`proposal-send-back` carries the proposal ID and its expected draft revision, removes the
proposal, returns its propositions to `live`, and appends `conversation.reopened`. It fails if the
originating conversation has been deleted.

## 10.2 Domain events

Use schema-validated transport events:

```text
world-chat.summary-updated
world-chat.loaded
world-chat.turn-started
world-chat.run-status
world-chat.progress
world-chat.turn-completed
world-chat.understanding-updated
world-chat.wrapup-plan
world-chat.wrapup-completed
world-chat.conversation-reopened
world-chat.problem
```

`world-chat.understanding-updated` carries the full live set for the conversation rather than a
per-candidate delta. The panel is a small, wholly-derived view, and sending it whole removes a
class of ordering bug for no meaningful cost.

Content-bearing World Chat transport events SHALL NOT be appended to the app-level coordinator
change log. Their durable source is the world-local conversation event log. This avoids creating a
second copy of world content under `%APP_ROOT%/logs` and prevents diagnostics leakage.

The coordinator needs a validated broadcast path that distinguishes:

- audit events safe and intended for the coordinator change log;
- transient/content-bearing events whose authority exists elsewhere.

## 10.3 Snapshot behavior

The ordinary snapshot includes conversation summaries only. The route loads the selected
conversation explicitly. On reconnect:

1. receive fresh app/world snapshot;
2. restore the selected conversation ID from the route;
3. send `world-chat-load`;
4. replace the local workspace with the durable folded view;
5. ignore stale incremental events at or before the loaded sequence.

# 11. Wrap-up and proposal integration

## 11.1 New proposal kind and origin metadata

Add `worldbuilding` to `ProposalKindSchema`.

World Chat proposals add backward-compatible optional/defaulted fields:

```ts
interface WorldChatProposalOrigin {
  requestId: string;
  conversationId: ConversationId;
  candidateId: CandidateId;
  candidateRevision: number;
  groupId?: CandidateGroupId;
  targetPaths: string[];
  fields: string[];
}

interface ProposalOpenChoice {
  choiceId: string;
  kind: "duplicate-or-amend" | "unchecked-novelty";
  question: string;
  options: Array<{ optionId: string; label: string }>;
}

interface Proposal {
  // existing fields
  draftRevision?: number; // defaults to 1
  worldChatOrigins?: WorldChatProposalOrigin[];
  /** Unanswered questions this proposal carries; blocks its own acceptance only (R-34c). */
  openChoices?: ProposalOpenChoice[];
}
```

`openChoices` is what lets wrap-up be one step. A question the coordinator cannot answer travels
with the proposal it concerns rather than holding up the whole wrap-up behind a dialog, so the
user answers it beside the values it would change and every other proposal stays acceptable.

The source string is `world-chat:<conversationId>`.

Origin metadata explains the draft but does not govern acceptance. Proposed files and captured
bases remain the gate's authority.

## 11.2 Server-side materialization

The coordinator materializes every candidate. The model never serializes authoritative files.

For each classification:

- Canon create: allocate an ID, create validated Canon Markdown.
- Canon amend: read accepted entry, apply allowed draft fields, serialize and validate.
- Canon thread: allocate an ID, create `type: thread`, `status: open` Markdown.
- Sheet create: allocate unique stable slug, build a sketch from `SHEET_SHAPES`, serialize and
  validate.
- Sheet edit: read accepted sheet, apply allowed fields/sections, serialize and validate.
- Relationship: produce the minimum necessary sheet target(s), respecting one-sided links.
- Media opportunity: reject from proposal materialization.

Before writing proposal files, parse every proposed entity through its domain schema. A malformed
candidate must fail wrap-up without leaving a proposal directory.

## 11.3 Wrap-up: allocation, materialization, and closing

Existing form helpers may allocate a Canon ID before calling `gate.stage()`. Wrap-up needs a
recoverable operation that spans conversation intent, several proposals, and closing:

1. append `wrapup.intent-recorded` with `requestId`, `expectedConversationSeq`, the
   candidate/group revisions per planned proposal, planned proposal IDs, and no allocated IDs yet;
2. under the world serialization boundary, revalidate every proposition against the current world;
3. reserve required Canon IDs and choose unique sheet slugs for all planned proposals at once,
   carrying the `requestId` into the allocation commit and each allocation audit record;
4. materialize all target contents using those identities;
5. capture bases and write each proposal under its planned ID with the same `requestId` in every
   World Chat origin;
6. append `wrapup.completed` with every proposal ID, the allocations, target paths, digests, the
   final status of each proposition, and the transition to `closed`;
7. fold proposition and group links from that one event.

The conversation closes in step 6 and not before. There is no half-closed state (R-42a): either
every planned proposal is durable and the conversation is closed, or nothing was created and it
remains open.

A startup reconciliation folds an incomplete intent:

- every planned proposal exists and validates -> append `wrapup.completed`;
- some proposals exist, others do not -> complete the remainder using the already-burned IDs, or
  remove the partial set and append `wrapup.failed`; never allocate a second set silently;
- no proposal exists but allocation audit lines exist -> retry materialization with those burned
  IDs, or append `wrapup.failed` and require a fresh wrap-up;
- neither proposals nor allocations exist -> safely resume the same intent;
- conflicting or malformed proposal -> append a problem and require manual discard and recovery.

This is a recoverable saga, not a false cross-file atomicity claim. A crash may burn IDs, but a
single `requestId` resolves to at most one set of proposals and one terminal wrap-up outcome.

This requires adding optional `requestId` to `CommitInput`, the prepared commit journal, and Canon
allocation change records. Recovery matches allocations to a wrap-up intent by that exact value,
not by conversation-scoped `source` text.

## 11.4 No proposal extension

The earlier draft specified explicit extension of a staged `worldbuilding` proposal, so that later
conversation could add to work already staged. Wrap-up closes the conversation, so there is no
later conversation to extend from. Extension, its overlap detection, and its field-granularity
merge are removed.

A user who wants to add to accepted work starts a new conversation. A user who wants to change a
proposal that has not been accepted either edits its values in place on the approvals screen or
sends it back (R-34a), which reopens the conversation it came from.

## 11.4.1 Proposal draft journal

In-place edits on the approvals screen use a proposal-local recoverable journal; they must not
reuse the current unjournaled `updateFile()` sequence.

```text
.proposals/<proposalId>/.draft-commit/<operationId>.json
```

The prepared record contains `requestId`, expected/current/next `draftRevision`, the complete next
target contents, the complete next origin metadata, the next candidate projections, and the next
preview inputs. An edit never adds a target or a base, because the set of targets is fixed at
wrap-up. Update order is:

1. validate and write the prepared record atomically;
2. write all next files to proposal-local staging paths;
3. mark the record committing;
4. atomically rename target files;
5. atomically replace manifest/origins and candidate projection sidecar with `nextDraftRevision`;
6. recompute/write the preview;
7. mark complete and remove the draft journal.

Startup rolls a committing operation forward idempotently or removes a prepared-only operation.
The manifest revision and proposal-local candidate projections therefore cannot lag behind an
authoritative target-file edit after a crash. Accept/rebase/conflict operations first recover and
then refuse while any draft operation remains unresolved.

## 11.5 Proposal review projection

Extend `StagedProposal` with a coordinator-computed review projection:

```ts
interface ProposalReviewProjection {
  targets: Array<{
    path: string;
    entity: WorldChatEntityRef | { kind: "new-canon" | "new-sheet"; label: string };
    action: "create" | "amend";
    fields: Array<{
      field: string;
      before: string | string[] | null;
      proposed: string | string[] | null;
      candidateIds: CandidateId[];
    }>;
  }>;
}
```

The projection is derived from base/live and proposed files, not trusted from model prose. Long
prose fields are expandable and fully reviewable.

## 11.6 Proposal resolution

On accept:

- proposal behavior remains SPEC-004;
- after the commit is durable, append conversation events marking linked candidate revisions and
  groups `accepted`, recording the final proposal digest;
- unlock dependent media opportunities;
- if app termination occurs between commit and conversation update, startup recovery detects the
  proposal ID in `changes.jsonl` and repairs candidate state idempotently.

On discard:

- discard remains durable in `changes.jsonl`;
- linked propositions become `discarded` and do **not** return to the conversation;
- the conversation is not reopened;
- startup recovery repairs this state if the direct conversation event was missed.

On send back:

- the proposal directory is removed and the removal is durable in `changes.jsonl` with an explicit
  `sent-back` reason, distinct from discard;
- linked propositions return to `live` with `returnedFrom` set;
- `conversation.reopened` is appended and the conversation leaves `closed`;
- if the originating conversation has been deleted, send-back is refused and only discard remains;
- startup recovery that finds a removed-as-sent-back proposal without the conversation event
  repairs the propositions and the conversation status idempotently.

Add explicit `proposalId` and the discard/send-back distinction to audit records so recovery need
not parse either from an entity path.

# 12. Forms and review behavior

## 12.1 One editor, one authority

There is no candidate form. Before wrap-up, propositions are changed by talking; the understanding
panel is read-only (R-8a, R-15a). After wrap-up, forms read and write the proposal draft through a
typed coordinator command carrying `expectedDraftRevision`. Component-local form state is a
temporary editing buffer only; navigation reloads from the durable proposal.

This is a stronger version of the fix the earlier draft was reaching for. That draft had two
editors over two authorities and had to keep them from disagreeing. Here there is one editable
surface, the approvals screen, and one authority, the proposal draft.

It also corrects the current pattern in which chat edits one proposal while a form holds unrelated
component-local fields and may stage another proposal.

## 12.2 Reusable form controls

Extract reusable controls from existing screens:

- Canon type, title, statement, links;
- sheet common frontmatter;
- declarative section fields from `SHEET_SHAPES`;
- thread title and question;
- relationship target and prose;
- image purpose and brief.

The same controls render in direct create/edit routes and on the approvals screen. Direct forms
remain fully usable without OpenCode.

## 12.3 Changing what kind of change something is

Classification can change in three places, and deliberately not on the approvals screen.

**In conversation, at any time.** "That is not a rule, that is just Maren." "Make that an open
question instead." The coordinator produces a new candidate revision, invalidates incompatible
checks, and reruns the required check plan. Nothing else happens, because nothing has been
created.

**At the wrap-up decision point**, for the one case the coordinator cannot decide: a Canon-create
proposition with a likely duplicate or plausible amendment target. Choosing to amend reclassifies
it to `canon.amend` against the selected entry before materialization (R-21, R-27a).

**Not on the approvals screen.** Changing a Canon create into an amendment after the proposal
exists would change which file it targets, which base was captured, and which ripple was computed.
That is a different proposal, not an edit to this one. The approvals screen edits values within
the shape the proposal already has; to change the shape, send it back (R-34a) and say so in the
conversation.

# 13. Attachments

## 13.1 Filing and linkage

World Chat attachments are private unfinished workspace by default and live beneath:

```text
.conversations/<conversationId>/attachments/<attachmentId>/<safe-name>
```

They are content-hashed, immutable, and referenced by conversation attachment ID. They are not
ordinary world artifacts, do not enter the index, and are excluded with `.conversations` from
normal export.

The user may explicitly choose **File in world** to promote a conversation attachment through the
existing artifact filing path. Promotion creates an immutable artifact and records the artifact ID
on the conversation attachment; it does not delete the private copy until the user explicitly
deletes the conversation and all proposal/media dependencies are resolved.

An attachment chip means "refer to this attachment in this conversation". Removing it stops
future turns from referring to it; the private attachment remains in the conversation until
conversation deletion. A promoted artifact remains filed in the world.

Attachment linkage is scoped to one conversation. Files attached in another conversation in the
same world must not appear automatically.

## 13.2 What the model may read

- Text/document attachment: may be exposed through bounded `get_attachment_text` if explicitly
  linked to the current turn.
- Long pasted text: stored as a private document attachment and treated identically.
- Image/audio/video: may be named as an attachment and used to create a media opportunity, but the
  chat must not claim to have inspected it without an existing verified extraction/multimodal
  capability.
- Extracted/promoted artifact text: may be read and quoted with its artifact hash/line evidence.

The UI distinguishes filed, readable, read, and unsupported states.

# 14. Media handoff

## 14.1 Route mapping

| Purpose                                       | Destination                                    |
| --------------------------------------------- | ---------------------------------------------- |
| `world-key-art` with `{ kind: "world" }`      | existing world-image generation action/surface |
| `character-main-photo` with a character sheet | `/w/:worldId/cast/:sheetId/main-photo`         |
| `character-look` with a character sheet       | `/w/:worldId/cast/:sheetId/looks`              |

Every other target/purpose combination is invalid in v1. Replacing an existing image is expressed
by one of these purpose-specific workflows, not a generic `replacement` value without asset
identity.

The route includes conversation/candidate identity so the screen loads the durable brief rather
than relying only on transient router state.

## 14.2 Dependency rule

In v1, every authored candidate/proposal dependency must be accepted before Generate is enabled.
The media card explains which proposal is still pending and links to review.

This avoids introducing proposal-aware prompt assembly, staged provenance, and orphaned generated
media when a proposal is later discarded.

## 14.3 Queue boundary

World Chat never sends a queue command. The existing generation screen:

- resolves the accepted world state;
- shows the routed model and estimate;
- allows brief editing;
- receives explicit user Generate;
- composes the provider request server-side;
- enqueues through the durable job queue.

After a correlated enqueue acknowledgement, the media candidate may record `handed-off` and the
job IDs. That record is informational and cannot control the queue.

Opening the generation surface does not change candidate status. The durable brief remains owned
by the candidate and the generation surface saves user edits back with `expectedRevision` before
dispatch. Generation commands add optional provenance-only correlation:

```ts
{
  worldChatOrigin?: {
    conversationId: ConversationId;
    candidateId: CandidateId;
    candidateRevision: number;
  };
}
```

The coordinator copies that origin into the correlated `queue.enqueue-result`; it does not put
conversation content into the provider request beyond the already reviewed brief.

The job journal adds an optional local-only origin containing only
`{ conversationId, candidateId, candidateRevision, handoffRequestId }`. It contains no chat text,
candidate title, or brief beyond the provider-ready params the user already approved. The origin
is persisted in the initial `queued` row before provider submission and returned on
`queue.enqueue-result`.

Only an accepted result with at least one durable job ID appends the idempotent `handed-off`
candidate transition. If the app crashes before that transition, startup finds journal jobs by
`handoffRequestId` and repairs it without enqueueing again. Navigation alone, rejected enqueue,
and `not-queued` results do not. Once handed off, the job is fully self-contained and conversation
deletion cannot affect it.

# 15. UI specification

## 15.1 Routes and entry points

Add:

```text
/w/:worldId/chat
/w/:worldId/chat/:conversationId
/w/:worldId/proposals
/w/:worldId/proposals/:proposalId
```

`/chat` opens the most recently active conversation or the new-conversation state. Users can
create, rename, archive, restore, and explicitly delete conversations.

`/proposals` is the approvals screen. It is not a World Chat screen: it lists pending proposals
from every source, including authoring and art direction, grouped by origin. The world overview's
existing "Needs you" section becomes an entry point to it rather than a place to act. This screen
is a prerequisite for World Chat rather than an addition to it, because wrap-up produces several
proposals at once and a rail cannot review them honestly.

Archive/unarchive is reversible and leaves all data intact. Delete is permanent and requires:

- no active run;
- no open/stale/conflicted proposal linked to the conversation;
- no unresolved wrap-up intent;
- no pending media handoff that depends on conversation-only data;
- explicit confirmation naming that private attachments and unproposed history will be removed,
  and that any proposal originating here will lose send-back.

Accepted/discarded proposal audit records and accepted world files remain. Proposal origins keep
the conversation ID as historical provenance even after the conversation is deleted; links back
to content become unavailable rather than dangling into another conversation.

Every conversation operation runs through one per-world conversation operation coordinator. It
serializes appends/checkpoint writes and tracks active readers/runs that may later write. Once a
conversation enters `deleting`, **all** commands and callbacks for it are rejected or drained,
including messages, run completions, metadata changes, attachment create/link/unlink/promotion,
wrap-up completion, proposal reconciliation, send-back, media handoff, and summary/checkpoint
writes.

Deletion runs exclusively through that coordinator:

1. mark the conversation `deleting` in the operation coordinator and reject new operations;
2. interrupt any active model run and wait for all existing writers/callbacks to drain;
3. recheck every deletion precondition;
4. append and sync `deletion.intent-recorded` inside the conversation;
5. atomically rename the directory to `.conversations/.deleted/<conversationId>-<operationId>`;
6. update the in-memory summary list to remove it;
7. recursively remove the tombstoned directory best-effort.

The authoritative deletion point is the atomic rename. Startup sweeps `.deleted`; a crash before
rename leaves the conversation intact, while a crash after rename leaves it deleted and only
cleanup remains. Because the deletion event moves with the tombstoned directory, it is recovery
context rather than the sole deletion authority. A request ID makes repeated Delete idempotent.

Entry points:

- world navigation: **World Chat**;
- world overview: **Talk about this world**;
- Canon refusal: **Draft an answer in World Chat**, carrying the question and retrieved entries;
- Canon New: optional **Talk it through**, while retaining the direct form;
- character/location/faction detail: **Talk about this**, carrying sheet context;
- future image actions: carry media target context into the same workspace.

The world name and current optional focus are always visible.

## 15.2 Desktop composition

Use the established SpecOne shell and Composer rather than a generic chat product layout.

Recommended canonical composition:

```text
+---------------------------------------------------------------+
| App chrome / world / World Chat / conversation / context      |
+-----------------------------------------+---------------------+
| conversation                            | WHAT I'VE UNDERSTOOD|
|                                         | n points            |
| messages and check receipts             |                     |
|                                         | grouped by subject, |
|                                         | read-only           |
|                                         |                     |
| composer                                | Turn this into      |
|                                         | proposals           |
+-----------------------------------------+---------------------+
```

The understanding rail is a reading column, not a control surface, so it needs less width than the
earlier card rail: **340px minimum**, collapsing below **900px**, which is an existing breakpoint
in `fidelity.css`. The transcript takes the difference.

The conversation switcher lives in the screen's own head row, not in `AppChrome`. That component
records a settled decision that its left side is "where you are", and the world is where you are;
a conversation is what you are doing inside it.

## 15.3 Conversation behavior

- Initial copy invites exploration and explains that discussion changes nothing by itself.
- User and Studio turns are visually distinct without anthropomorphic status theater.
- Tool progress is shown in product language while a run is active.
- Completed checks collapse into inspectable receipts naming consulted entities.
- One active run disables Send and exposes Cancel; the draft text may remain preserved.
- A failed turn leaves the user message in place with Retry.
- A closed conversation disables the composer and states why, naming the proposals it became.
- The UI never renders raw model JSON, tool payloads, session IDs, or filesystem paths.

## 15.4 The understanding panel

The panel shows live propositions only, grouped by subject (R-15), with:

- a subject heading naming the entity or "Still open";
- one sentence per proposition, a statement if settled and a question if not;
- where relevant, one quieter line of consequence or caveat, such as which existing sheet line
  would change or which entry it is close to;
- a header count and one sentence stating that nothing here is a decision.

It shows no status vocabulary, no readiness, no group boundaries, no classification labels, and no
per-proposition controls. The single interaction is clicking a proposition to quote it into the
composer (R-8a).

One action sits at the foot, where `Begin in this world` sits on Genesis: **Turn this into
proposals**, present only once the conversation has at least one live proposition. It states its
consequences, then creates the proposals and goes to them in one step (§11.3, R-27a).

The panel's copy is load-bearing. A column with no controls that reads like machine-extracted noun
phrases will not be read, and if it is not read the batch approval loses its justification (§0.1).
Sentences should be short, in the user's register, and recognisable as the thing they just said.

## 15.5 Approvals screen

Two panes: proposals grouped by origin on the left, the selected proposal in full on the right.

The detail pane shows, per target entity: its name and kind, its current version or "id assigned
on accept", and every changed field with its before and proposed values. Long prose is expandable
and fully reviewable. Atomic grouping is stated in words. The advisory ripple follows.

On arrival from a wrap-up the screen states what came with the conversation and what did not,
naming each not-carried proposition and its reason (R-27d). A proposal carrying an unresolved
choice shows it beside the values it would change, and is flagged in the pending list (R-34c).

Actions are **Accept**, **Send back to the conversation**, and **Discard** (R-34a). Values are
editable in place before accepting (§12.1). An **Accept all** action names its exact count and is
unavailable while anything pending is stale, conflicted, or carrying an unresolved choice (R-34b).

## 15.6 Narrow layout

At narrow widths:

- conversation remains primary;
- a persistent **What I've understood, n points** control in the flow above the composer raises
  the panel as a single sheet;
- there is never more than one floating layer, because nothing inside the panel opens (R-48);
- the control appears once the conversation has produced its first proposition and then stays for
  the session, reading a zero state rather than disappearing;
- approvals are a list that becomes a detail view by ordinary navigation, not a stack of overlays;
- before/proposed values stack vertically rather than scrolling sideways;
- no horizontal scrolling is required for primary actions;
- closing the panel restores transcript position and composer draft.

## 15.7 Accessibility

- Transcript uses a labelled log, but only completed messages are announced.
- Progress has a separate polite status region and does not announce every token.
- The understanding panel is a labelled region with subject headings and a count; a completed
  change to it is announced once, not per token.
- Focus moves predictably when opening and closing the narrow panel, and returns to the control
  that opened it.
- Keyboard users can traverse conversations, transcript, propositions, and the approvals screen
  including in-place edits and unresolved choices.
- Settledness, retrieval state, and proposal state are expressed in text, not colour alone.
- Reduced motion removes streaming and panel transition animation without removing status.

# 16. Concurrency and idempotency

## 16.1 Revisions

Use three explicit optimistic revisions:

- conversation event sequence;
- candidate/group revision;
- proposal `draftRevision`.

Every mutation compares its expected value and returns the current durable state on mismatch.

## 16.2 Request IDs

Mutating client commands use ULID request IDs. The conversation store retains enough operation
receipts to make reconnect retries idempotent. At minimum:

- send does not duplicate the user message/run;
- wrap-up does not allocate another set of Canon IDs or another set of proposals;
- resolving a choice twice does not retarget a proposal twice;
- wrap-up does not close a conversation twice;
- send-back does not reopen a conversation twice or restore propositions twice;
- an in-place proposal edit does not create another draft revision;
- media handoff does not mark twice.

## 16.3 Active runs

- One active model run per conversation.
- A second send receives `already-running` and does not append a message.
- Cancellation marks the run, aborts the local event iterator, and asks the adapter to interrupt.
- A conversation may be read while a run is active.
- Wrap-up refuses while a run is active; the user cancels or waits.
- A model result based on stale candidate revisions is rejected and retried, not merged silently.

## 16.4 World switching

The product currently has one read-write open world. If the user opens another world while a
World Chat run is active:

1. invalidate the old world-query lease;
2. interrupt the run;
3. append `interrupted` with reason `world changed`;
4. retain the user message and prior candidates;
5. allow retry when the original world is reopened.

# 18. Privacy, security, and diagnostics

## 18.1 Plaintext and user expectations

Conversation records are plaintext inside the world, like the world's other readable authored
and operational files. The UI must not imply encryption. Credentials never enter them.

Normal world export excludes conversations because they are unfinished workspace. An explicit
future "include workspace" export may be added only with clear disclosure.

World Chat sends bounded conversation/world context to the selected authoring model. Before the
first send, the UI shows `local`, `cloud`, or `unknown` from application-owned model-routing
metadata. Sending while `cloud` is shown is the user's deliberate disclosure. If routing is
`unknown`, the UI says that clearly and does not imply local processing.

The harness may retain session content independently of Studio. Add optional adapter capability
and methods for session deletion, invoke deletion after each ephemeral run, and report whether it
was confirmed. A user-installed or under-capable harness with no confirmed deletion support is
labelled accordingly. Studio's scratch cleanup is not presented as deletion from the harness.

## 18.2 Logs

Never write these to app/coordinator logs or diagnostics:

- message text;
- candidate titles, statements, section prose, or image briefs;
- world names;
- retrieval queries or excerpts;
- attachment names/content;
- proposed file paths;
- model structured response.

Safe operational records may include:

```text
kind
worldId
conversationId
runId
status/category
durationMs
candidate operation counts
check counts
adapter/model IDs
token count
```

Even safe IDs pass through the existing redaction boundary. Diagnostics include aggregate counts
and safe failure categories only.

## 18.3 Agent confinement

World-builder sessions are read-only and stricter than proposal authoring sessions:

- scratch cwd, not world/proposal/conversation directory;
- edit/write denied;
- shell/exec denied; public-web search and page reading gated by `research.web`;
- read-only MCP lease only;
- no remembered grant can expand capability;
- no queue or provider tools;
- no arbitrary path parameter;
- expiring per-run token;
- result accepted only through strict schema validation.

This remains defense in depth, not an OS sandbox claim.

## 18.4 Harness retention

Extend harness capability discovery with optional `session-delete` and application-owned routing
metadata:

```ts
interface AuthoringRouteInfo {
  provider: string;
  model: string;
  locality: "local" | "cloud" | "unknown";
}
```

Locality comes from Studio's provider/runtime registry, not model-name heuristics. Before a turn,
the route shown in the UI must match the route written into session configuration. If the harness
selects a different route unexpectedly, the run fails before sending world content.

When `session-delete` is supported, Studio requests deletion after the completed/failed run and
waits for a confirmed adapter result within a bounded cleanup time. Unsupported, unconfirmed, or
failed deletion is recorded as safe operational status and disclosed in the conversation's
privacy note. It does not erase the local conversation and does not claim remote deletion.

# 19. Performance and limits

Initial product limits:

- 16,000 characters per typed message; larger pasted content becomes a private conversation
  attachment;
- 20 linked conversation attachments per turn;
- 50 recent messages in initial load;
- 100 messages per history page maximum;
- 12 candidate operations per model turn;
- 100 live propositions per conversation, after which the composer states that the conversation is
  large and suggests wrapping up; it is not blocked, because refusing to accept a sentence mid-idea
  is worse than a long panel;
- 40 proposals produced by one wrap-up, after which the plan is refused and the user is asked to
  wrap up a narrower conversation;
- one active model run per conversation;
- bounded MCP results (default 8, hard maximum 20);
- bounded document ranges and total attached text per run;
- checkpoint after 100 durable events or 1 MiB since the previous checkpoint;
- no automatic deletion/expiry of conversations or proposals.

Limits produce stated errors or review prompts. They never silently truncate a user message,
candidate value, proposed file, or evidence quote.

# 21. Test specification

## 21.1 Contract tests

- Parse every candidate classification and reject unknown fields.
- Reject a tentative settled-fact proposition at wrap-up, and require it be named as not carried.
- Reject media candidates inside proposal groups.
- Validate candidate/group revision and proposal bindings.
- Validate the wrap-up command and result schemas, including not-carried reasons and unresolved
  choices.
- Reject a wrap-up whose expected conversation sequence is stale.
- Validate message, run, check receipt, event envelope, summary, and paging cursors.
- Parse old proposals after optional World Chat fields are added.
- Reject model-supplied paths and authoritative IDs.

## 21.2 Persistence tests

- User message is durable before fake adapter dispatch begins.
- Clean turn appends message/check/candidate/group changes atomically.
- Initial user message and first running attempt append atomically in `turn.started`.
- Crash/truncated final line loses only the incomplete event.
- Duplicate send and wrap-up request IDs are idempotent.
- Checkpoint deletion rebuilds identical state.
- Corrupt checkpoint falls back to event fold.
- Interior event corruption produces a named problem without inventing state.
- Navigation/reconnect/restart restores the understanding, tombstones, and recent messages.
- A closed conversation reloads closed, with each proposition showing the proposal it became.
- A reopened conversation reloads open, with returned propositions live.
- Running turn at crash becomes interrupted exactly once.

## 21.3 Classification scenarios

- "The bells cannot ring below the western lock" -> settled Canon create proposition, rendered as
  a statement under a lock subject heading.
- "Maybe the bells are whale bone" -> tentative, rendered as a question under "Still open", and
  named as not carried at wrap-up.
- Restatement of an existing fact -> duplicate receipt, and the panel says so rather than calling
  it new.
- Change to an existing fact -> Canon amendment proposition with target.
- "We should remember who rang the first bell" -> unresolved open-thread proposition.
- Character history plus family rule -> one atomic group, computed without user involvement.
- Relationship update -> one-sided link plus only necessary prose targets.
- Three possible villains -> no proposition or one explicit undecided, never three facts.
- Portrait should show a badge -> image idea, no job, retained through wrap-up.
- Pure brainstorming -> completed reply, zero candidate operations, panel unchanged and silent.

## 21.4 Correction and retraction tests

- "mother" corrected to "aunt" updates one candidate ID/revision, and the panel shows one line.
- "Forget that" withdraws the proposition without any control being used.
- Split creates new IDs and supersedes the original.
- A withdrawn proposition does not reappear on the next turn from context alone.
- Material target/value change resurfaces the same ID with a new revision.
- Reinstating in conversation lifts the tombstone; model output alone does not.
- Accepted proposition corrected later creates a new amendment proposition in a new conversation.

## 21.5 Grounding tests

- Candidate world quote must exist at the cited version/revision and content hash.
- Candidate message quote must match exact immutable message span.
- Attachment quote must match the linked attachment hash/text; promoted artifact evidence also
  verifies the artifact hash.
- Model cannot cite a check receipt from another run.
- Empty search is distinct from unavailable search.
- Index unavailable cannot yield confident "new" readiness without user override.
- Lexical contradiction candidates remain non-blocking and honestly labelled.
- World switch cannot redirect a query lease to the new world.

## 21.6 Structured-output adversarial tests

- Malformed JSON -> one retry -> failure without partial mutations.
- Unknown candidate type -> retry/failure.
- Candidate tries to include path/job/provider command -> rejected.
- Model output tries to wrap up, create, accept or discard a proposal -> no schema field exists.
- Model output tries to close or reopen a conversation -> no schema field exists.
- Stale candidate revision -> no overwrite.
- More than operation limit -> rejected.
- Tool activity claims a check that no receipt confirms -> the panel cannot repeat the claim.
- Model-suggested grouping that spans an invalid reference -> rejected at wrap-up, not trusted.

## 21.7 Wrap-up and gate tests

- A long conversation reserves no ID and writes nothing outside `.conversations`.
- Wrap-up reaches the approvals screen in one action, with no intermediate confirmation.
- The wrap-up result names every not-carried proposition with a reason; nothing is dropped unnamed.
- A not-carried proposition is still live in its conversation afterwards.
- A wrap-up against a stale conversation sequence is refused.
- A proposal carrying an unresolved choice cannot be accepted, and accept-all excludes it.
- Answering "amend instead" retargets the proposal and recaptures its base.
- Wrap-up reserves exactly one ID per new entity and is idempotent after retry or crash.
- Crash after intent, after partial allocation, and after each proposal write reconciles to one
  set of proposals and one terminal wrap-up outcome; no second allocation ever occurs.
- The conversation is not closed until every proposal it produced is durable.
- Two concurrent wrap-ups in different conversations receive distinct Canon IDs and sheet slugs.
- Pending Canon/sheet references within one group resolve to the allocated identities.
- Pending cross-reference to a proposition outside the atomic group is rejected.
- Mixed Canon and sheet group becomes one proposal and one commit.
- Independent propositions become separate proposals.
- Relationship materializes minimum targets.
- Open thread remains a proposal until explicit accept.
- Every materialized file parses through its entity schema.
- Crash at every proposal draft-journal phase rolls forward or preserves the previous complete
  draft revision; target files and manifest/projection never disagree.
- In-place edit with a stale `expectedDraftRevision` is refused, not merged.
- Stale proposal uses existing rebase/conflict flow.
- Accept updates propositions; crash-window recovery repairs linkage.
- Discard marks propositions discarded, does not return them, and does not reopen.
- Send back returns propositions to live, reopens the conversation, and is idempotent.
- Send back is refused when the originating conversation was deleted; discard still works.
- Accept-all is unavailable while any pending proposal is stale or conflicted, and names its count.
- Final review projection matches actual proposed files.

## 21.8 Media boundary tests

- Image candidate alone creates no job/journal/ledger entry.
- "Generate it" in chat creates no queue command.
- Pending proposal dependency disables Generate and names the dependency.
- Accepted dependency enables existing generation screen with brief.
- Explicit Generate follows normal queue acknowledgement and estimate flow.
- Conversation deletion is blocked while a media handoff depends on conversation-only data;
  deletion after queue acknowledgement does not affect the job.

## 21.9 Client and accessibility tests

- World overview/nav/contextual entry opens correct world/conversation context.
- Composer disabled copy names harness reason and direct-form alternatives.
- Composer copy for a closed conversation names the proposals it became and offers send-back.
- Retrieval degradation is distinct from harness degradation.
- The understanding panel exposes settledness and checks as text, never colour alone.
- The panel offers no approve, defer, dismiss, or stage control anywhere.
- Clicking a proposition quotes it into the composer and changes nothing else.
- A turn with no candidate operations leaves the panel unchanged and announces nothing.
- The wrap-up button is absent until the first proposition exists.
- In-place edits on the approvals screen survive remount and reload from the proposal.
- One keyboard path reaches all actions, including in-place edits and unresolved choices.
- Focus returns to the opening control after closing the narrow panel.
- Completed messages, not streaming tokens, reach the live region.
- Desktop and narrow visual snapshots match approved frames.

## 21.10 Privacy and confinement tests

- Search app/coordinator logs and diagnostics after a full conversation: no message/candidate/world
  content appears.
- World-builder has no edit/write/shell capability; public-web tools follow `research.web`.
- Remembered grants cannot enable denied tools.
- MCP rejects expired, wrong-world, wrong-run, and unapproved-attachment tokens.
- Tool surface accepts no path.
- Scratch directory contains no credentials or durable transcript.
- Crash-startup sweep removes stale scratch/config files.
- Normal world export excludes `.conversations`.
- An older supported build refuses the incremented world schema rather than exporting
  `.conversations` accidentally.
- Session deletion is requested and its confirmed/unsupported outcome is represented honestly.

# 22. Rollout and compatibility

## 22.1 Feature flag

Ship behind an application-owned feature flag until persistence, safety, and staging tests are
complete. The flag may hide entry points but must not make existing `.conversations` unreadable.

## 22.2 Existing worlds

Creating the first conversation upgrades `world.json.schemaVersion` through the ordinary commit
primitive before `.conversations` is created. `.conversations` remains optional operational state
and its files carry their own schema version. Opening an existing world without creating a
conversation does not require eager directory creation, but using World Chat requires the schema
upgrade.

## 22.3 Existing proposals

New Proposal fields are optional/defaulted so existing manifests parse unchanged. The new
`worldbuilding` kind is used only by new proposals. Accepted entity file formats remain unchanged.

## 22.4 Downgrade behavior

An older build refuses the newer world schema before scanning, exporting, or modifying it. This is
required because older exporters do not know to exclude `.conversations`. Accepted entity file
formats remain ordinary Canon/sheet formats; returning to an older build requires an explicit
future downgrade/export process, not silent opening.

## 23.2 Deferred

- Semantic/vector retrieval.
- Multimodal image/audio/video understanding in World Chat.
- Media generation directly against a selected proposal snapshot.
- Collaborative/multi-user conversations.
- Cloud sync.
- Including conversations in normal world export.
- Model-generated confidence percentages.
- Autonomous staging or acceptance.
- More than one simultaneous run per conversation.
- OS-level sandboxing of the harness.
- Partial wrap-up, taking a subset of propositions and leaving the conversation open. It would
  reintroduce some of the choosing this design removes, so it waits for evidence that a long
  session genuinely needs it.
- Any prompt or expiry for a conversation nobody wraps up. It sits open indefinitely, which may
  turn out to be fine.
- Editing a proposal's classification on the approvals screen. Send it back instead (§12.3).

# 25. Definition of done

- [ ] All normative requirements have automated coverage or a documented packaged/manual
      verification step.
- [ ] A user can hold a full session without the interface asking for a decision, and the
      conversation surface offers no approve, defer, dismiss, or stage control.
- [ ] Conversations, messages, propositions, groups, tombstones, and proposal links survive forced
      process termination and restart.
- [ ] No conversational text can wrap up, create, accept, discard, or dispatch.
- [ ] Model output cannot express paths, provider calls, queue commands, or authoritative IDs, and
      cannot close or reopen a conversation.
- [ ] Wrap-up reaches the proposals in one action, and names everything that did not carry over.
- [ ] Wrap-up is atomic in effect: either every proposal exists and the conversation is closed, or
      neither happened.
- [ ] Mixed Canon and sheet propositions land atomically through the existing gate.
- [ ] Proposal review shows actual field-level before/proposed values and allows in-place edits.
- [ ] Send back returns propositions and reopens the conversation; discard does neither.
- [ ] World switching cannot cause a turn to read another world.
- [ ] Evidence for every proposition is mechanically verified.
- [ ] No World Chat content appears in app logs or diagnostics.
- [ ] Media opportunities require explicit existing-screen generation and accepted dependencies.
- [ ] Direct forms remain usable without OpenCode.
- [ ] The understanding panel's copy has been tested against real conversations, not only fixtures.
- [ ] Desktop and narrow designs are approved and regression-tested.
- [ ] Typecheck, build, lint, format, unit, integration, and packaged smoke tests pass.
- [ ] Issue #70 links to this document as its implementation authority.
