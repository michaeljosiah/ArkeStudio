# 101 — Breaking up `screens/production.tsx`

`packages/client/src/screens/production.tsx` is **8,408 lines** holding **95 top-level
declarations**, **29 exports** and what are, by any ordinary reading, **fourteen screens**. It is
the largest source file in the repository by a wide margin and it is still growing: every one of
the last four editor issues landed in it.

This is the plan for taking it apart. Nothing here changes behaviour. That is the whole point —
a file this size can only be moved safely if every step is a *pure move*, and the existing test
suite is what proves each step was one.

---

## 1. Why now, and why it is not merely untidy

Three costs are already being paid, and the review on 2026-09-13 paid all three in one sitting.

**Renders are coupled that have no business being coupled.** `CutScreen` is 1,488 lines and holds
the transport, the render plan, the selection, the drag state, the import queue, the shortcut
table and the export sheet's state. Anything that moves re-renders all of it. That is how
`buildRenderPlan` came to run four times a second: the plan is derived in a component that the
transport re-renders on a 250 ms clock, and nothing in 8,408 lines makes that visible to the
person editing it. The fix was a `useMemo`; finding it was the work.

**Nobody can see the seams.** `Wave` — a 17-line decorative SVG — is imported by
`reference-picker.tsx`, `world.tsx` and `production-artifacts.tsx`. It lives in a screen file
because there was no other file for it to live in. Three unrelated modules now depend on a screen.

**The editor already has a home and this file is squatting in it.** `screens/editor-timeline.tsx`,
`editor-audio.tsx`, `editor-subtitles.tsx`, `editor-clip-menu.tsx`, `editor-marks.tsx`,
`editor-gesture.ts` and `editor-requests.tsx` exist and total 2,290 lines. The Cut screen's own
4,060 lines sit outside them, in a file also containing the cast screen and the manuscript
importer.

A fourth cost is latent: `oxlint`, `tsc` and the test runner all treat this file as one unit, so
the feedback loop on any editor change is as slow as the whole thing.

### Why `cut.tsx` and not `editor-cut.tsx`

The route is `/w/:worldId/p/:prodId/cut` and the screen registry calls it `cut`. Every other
editor module is a part the screen composes; the screen itself should be named for the route, as
`world.tsx`, `storyboard.tsx` and `bench.tsx` are.

## 4. How each slice is done

**Every slice is a pure move.** Cut the declarations out, paste them into the new file, add the
imports the new file needs, and export from it. Nothing else:

- no renames, not even of a local that now collides;
- no reordering beyond what the move forces;
- no extracting a helper that "obviously" wants extracting;
- no fixing a bug noticed in passing — open an issue and leave it.

A reviewer must be able to read the diff as *the same text, somewhere else*. The moment a slice
also changes something, the test suite stops being proof that the move was safe, and there is no
other proof available for four thousand lines.

**`production.tsx` re-exports what has moved, until it is empty.** Each slice ends with
`export { ... } from "./<new-file>.js";` in the old file, so the 23 importers keep working and no
slice has to touch files unrelated to it. The final slice deletes those lines, repoints the
importers, and deletes `production.tsx`.

**`git log --follow` will not see through these moves**, because each slice moves many
declarations out of one file into several. Use `git log -C -C --find-copies-harder` when chasing
history through the boundary, and expect `blame` on the new files to point at the slice commit.
This is a known and accepted cost; it is the reason to do it in six commits rather than sixty.

### What validates a slice

Per [CLAUDE.md](../../CLAUDE.md): `npm run lint`, `npm run typecheck`, `npm run build`,
`npm test`. For the client slices, run its tests from `packages/client` — from the repo root they
all fail at once and it reads as a catastrophic regression rather than a wrong directory. Run
`typecheck` after the last test edit, not before: `tsx` does not typecheck.

The client suite is **1,864 tests** and eighteen of its files import from `screens/production.js`.
A slice that keeps them green without editing them is a slice that moved nothing but position.
A slice that needs a test edited has changed something; find out what.

Additionally, per slice:

- `node scripts/check-client-policy.mjs` — the moved CSS-adjacent code still has no hard-coded
  colour, and note that this rule reads the *whole file text including comments*, so an issue
  reference written `#1130` is read as a hex colour and fails the build. Write `issue 1130`.
- Update [the code map](../development/code-map.md). `production.tsx` is named in four of its
  rows — *Borrow another world's files into a Cut*, *Production scene/plan*, *Story dashboard and
  daily progress* and *Chapter workspace (story)*. Each slice fixes the rows it invalidates; the
  map being wrong is worse than the file being large.

## 5. The slices, in order

The order is chosen so that the riskiest move happens when the surrounding file is smallest, and
so that no slice depends on one that has not merged.

Tracked under epic [#1130](https://github.com/michaeljosiah/ArkeStudio/issues/1130).

| # | Slice | Moves | Why here |
|---|---|---:|---|
| [1131](https://github.com/michaeljosiah/ArkeStudio/issues/1131) | **Shared components out of the screen** | ~34 | `Wave` and `Mentions` are the only things three *other* modules import. Smallest possible slice, and it proves the re-export shim works before anything large rides on it. |
| [1132](https://github.com/michaeljosiah/ArkeStudio/issues/1132) | **Cast and wardrobe** | ~361 | Self-contained, one route, no editor coupling. The rehearsal. |
| [1133](https://github.com/michaeljosiah/ArkeStudio/issues/1133) | **Story, chapters and manuscript** | ~940 | Touches the two shared `new-scene` / `new-chapter` contexts, which is the first real test of whether a context survives a move. |
| [1134](https://github.com/michaeljosiah/ArkeStudio/issues/1134) | **Takes and generation** | ~1,345 | Large but loosely coupled; shares only `takeMediaPath` / `takeMediaView` with the Cut, which the first slice's pattern handles. |
| [1135](https://github.com/michaeljosiah/ArkeStudio/issues/1135) | **Production shell and dashboard** | ~1,310 | `ProductionLayout` is the route parent for everything above, so it moves once its children are already out and the diff is legible. |
| [1136](https://github.com/michaeljosiah/ArkeStudio/issues/1136) | **The Cut** | ~4,060 | Eight files, done as one slice because the parts are mutually recursive through `CutScreen` and splitting the split would leave half-moved state on `main`. | [1137](https://github.com/michaeljosiah/ArkeStudio/issues/1137) | **Delete `production.tsx`** | — | Drop the re-export shim, repoint 23 importers, delete the file, update the code map and `docs/development/README.md`. |

1132–1135 can be done in any order once 1131 has proved the shim. 1136 wants them all merged;
1137 wants everything.

### Slice 6 is the one to be careful about

`CutScreen` reaches into every part of the editor, and several of the parts reach back:
`ArtifactPanel` takes fourteen callbacks, `CutInspector` takes the selection and the command
sender, `ExportSheet` takes the render plan. None of that should be redesigned during the move.
Export what is needed, import it back, and accept the wide prop lists — narrowing them is real
design work with real behaviour risk, and it belongs to a later issue against a file where it can
be seen.

The one thing slice 6 may do beyond moving: extract `CutScreen`'s keyboard block
(`shortcuts` / `shortcutActions` refs and the `keydown` effect, ~90 lines) into a
`useEditorShortcuts` hook in `cut.tsx`, because it is already written as a self-contained unit
against two refs and moving it out is what brings `cut.tsx` under the target. If that turns out to
change behaviour, drop it and let `cut.tsx` be ~890 lines.

---

## 6. What this does not do

- **No component is redesigned.** Prop lists stay as wide as they are.
- **No state is lifted or lowered.** The known render-coupling problems in `CutScreen` — a plan
  that has to be memoised by hand, an `ArtifactPanel` that renders while closed — are left exactly
  as they are. Fixing them is the *point* of doing this, but doing both at once means neither can
  be reviewed.
- **No tests are rewritten**, beyond import paths in slice 7.
- **`screens/registry.ts` and `App.tsx` keep their current route wiring** until slice 7.

---

## 7. After it lands

The work this unblocks, roughly in order of what the editor review found:

1. `ArtifactPanel` should not render while it is closed; in its own file that is a three-line
   guard rather than an argument.
2. The render plan should be derived by a hook the editor owns, not by hand in a screen body, so
   the next person cannot reintroduce the four-times-a-second rebuild.
3. `ClipLanes` — the legacy pre-timeline placement path — can be retired once placements are
   folded, and in its own file the retirement is a file deletion.
