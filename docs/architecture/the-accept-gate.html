The accept gate

How a change actually happens

Three promises hold this product up. Nothing authored enters your world without you accepting it. You see what a change will affect before you decide, not after. And a write that is interrupted can never leave your world half-changed.

Everything else in Arke is built on top of this one mechanism, which is what makes it safe to let something else do the writing. And the gate is deliberately the same for everything it covers: a character sheet, a canon rule, a scene, a chapter the studio drafted — they differ in how you edit them and in what they affect, never in how they get in. A special path for one kind of thing is treated as a defect, not a convenience.

The loop, end to end

It runs the same way whether you filled in a form or talked it through with the studio. The examples below are the real files from the sample world, unedited.

  1. The change is drafted somewhere else first

    It is staged in .proposals/, in a folder of its own, as a complete copy of the file as it would be. Your real file has not been touched, and will not be until you say so.

  2. The draft writes down exactly what it was based on

    Not just which file, but which version of it, and a fingerprint of its precise contents at the moment drafting began. This is the thing that makes the whole gate trustworthy later.

    .proposals/pr_01J8H0000000000000000000P1/proposal.json { "id": "pr_01J8H0000000000000000000P1", "kind": "sheet-edit", "summary": "Maren pays for scene four — her left ear is gone, and the sheet should say so", "targets": [ { "path": "characters/maren-kest.md", "baseVersion": 4, "baseHash": "sha256:9f2c66a1b0e4d8c2f7a31d5e" } ], "baseCanonRevision": 42, "reservedCanonIds": [], "source": "chat:sess_9f2", "created": "2026-07-30T18:00:00Z" }

  3. Arke works out what else this touches

    Before you decide, not after. The consequences are worked out from the world's own index — from what actually cites what — and written down beside the proposal.

    .proposals/pr_01J8H0000000000000000000P1/ripple.json { "computedAt": "2026-07-30T18:00:01Z", "governing": false, "items": [ { "kind": "stale-reference-tiles", "summary": "3 reference tiles and the compiled model sheet were made against v4 — regenerate looks after accept", "targets": ["references/maren-kest"] }, { "kind": "productions-pick-up", "summary": "Saltlight has unfinished shots citing maren-kest — its next dispatch picks up v5", "targets": ["saltlight"] }, { "kind": "takes-pinned-to-old-version", "summary": "2 accepted takes stay pinned to v4; the cut keeps playing them", "targets": ["tk_01J8F0000000000000000000B2", "tk_01J8A0000000000000000000A1"] }, { "kind": "owning-canon-rules", "summary": "CANON-002 owns tide-calling's cost — the sheet change must not restate the rule", "targets": ["CANON-002"] } ] }

  4. You accept, or you discard

    Discarding removes the folder and leaves one line in the change log saying so. Accepting runs the checks below. If anything is wrong the accept is refused and says which thing — it never quietly does half of what you asked.

  5. The change lands as one act

    The previous version is copied into .history/, the live file is replaced, the version number goes up, a line is appended to changes.jsonl, and the index and your screen catch up. All of it, or none of it.

What a proposal is

A folder. Inside it are whole files, not a list of edits — the complete file as it would be if you accepted, sitting beside a copy of the file as it was when drafting started.

.proposals/ pr_01J8H0000000000000000000P1/ proposal.json what this is, and what it was based on ripple.json what it would affect, worked out in advance characters/maren-kest.md the sheet as it would be — a complete file _base/ characters/maren-kest.md the same sheet as it was when drafting began

The sample world ships the first three of these; _base/ is written by the running application whenever the target already existed.

Whole files rather than a list of edits costs a few kilobytes and buys three things. Showing you the before and the after is reading two files, with no patching to get wrong. The folder is what an authoring session is handed instead of your world, so an assistant that goes wrong can only ruin a draft. And accepting becomes a set of file swaps, which can be made safe against a power cut — see what accepting does.

What the manifest records

kind
What sort of change this is — a sheet edit, a new sheet, a canon amendment, a settled canon rule, a scene, a chapter, a story overview, a change to the world's look. Sixteen kinds in all. It decides which editor you get, never how it gets in.
summary
One line in your own language, shown on the card. The second sample below is a good one.
targets
Every file this would write. Each carries the version it was drafted against and a fingerprint of that version's exact contents. A file being created has neither — it records nothing, which is itself the claim that nothing was there.
baseCanonRevision
Which revision of the world's rules the draft was written against.
reservedCanonIds
Numbers claimed for new canon rules at the moment the draft needed one. Discarding the proposal does not hand them back — a number is burned rather than reused, so a reference to CANON-071 never comes to mean a different rule than it did.
source
Where the draft came from: form if you filled it in yourself, or the named chat session that produced it, like chat:sess_9f2. It ends up on the change-log line, so months later you can tell which conversation wrote a sentence.
conflicts
Only present after a rebase. Each names one field that both you and the world changed, with all three readings side by side, and cannot be accepted until you pick a side.
openChoices
A question the studio could not answer for itself — "this looks close to an existing rule; is it a new one, or a change to that one?" It blocks this proposal and no other, so it waits beside the values it would change rather than holding up everything else.

A second proposal, for variety — a canon amendment raised from a form rather than a conversation, and one where the summary is doing real work:

.proposals/pr_01J8H0000000000000000000P6/proposal.json { "kind": "canon-edit", "summary": "1847 belongs in the watch rule — the year the ledger does not explain, recorded where the next watchkeeper will actually read it", "targets": [ { "path": "canon/CANON-019.md", "baseVersion": 60, "baseHash": "sha256:4b7d20c9e16a83f5" } ], "baseCanonRevision": 90, "source": "form" }

What staging buys you. The draft survives the application being closed, killed or updated. It passes between the conversation and the form without losing anything. More than one draft may target the same sheet at once — you are told, and not stopped. And because the live file is genuinely untouched, "discard" is a real discard: there is nothing to undo.

The ripple: consequences, before you decide

The ripple is not a warning written by a model. It comes from the world's own record of what cites what, so it can be specific: which three tiles, which production, which two takes.

It is worked out when the draft is staged, again every time the draft changes, and then once more at the moment you press accept — after the checks, while the world is held still. That last one is the one that counts, and that is what "governing" means in the file: false on the copy you have been reading, true only on the set worked out at the decision itself. The reason is unglamorous. A preview may be minutes or days old, and if the change would now affect eleven things rather than three you were shown a number that is no longer true — so the accept stops, replaces the preview with the real set, and asks you to look again.

What it reports

ConsequenceWhat it is telling you
Reference tiles predate this Pictures made from the old version of this sheet. They are not deleted and not silently redone — you regenerate the look afterwards if you want to.
Productions pick this up Productions with unfinished shots citing this sheet. Their next dispatch uses the new version. Work already sent is not recalled.
Scene briefs re-render Scenes whose cast block is built from this sheet and will read differently next time.
Accepted takes stay pinned Footage you already chose was made with the old version and remains pinned to it. The cut keeps playing what it has. This is the item people find most reassuring and it is the one most often forgotten.
A canon rule owns this The subject is governed by a rule that lives elsewhere, so the edit should not restate it. One fact, one home.
Possible contradictions Existing rules sharing this vocabulary, so you can read both sentences side by side. Advisory only — it blocks nothing, and says so.
Entries gain a cross-reference Rules linking here, which now read against amended text.
Productions see the new revision Any canon change moves the world's revision number, and every production sees it on its next dispatch.

A change to the world's look reports its own four: how many visual assets stay exactly as they are, how many reference kits and productions will see the new look next time, and how many accepted takes become pinned to the look being replaced. That last count deliberately includes work made under the look you are about to change — counting only what was already old would describe the previous decision rather than this one.

The refusals

There are nine distinct ways an accept can decline, and each says which one it is in words rather than a code. That matters more than it sounds: a refusal you cannot act on is no better than a crash.

What it saysWhat it meansWhat you do
The world moved while this was open The file this draft was based on is not the file that is there now — you edited it in another window, or in a text editor, or another draft landed first. Rebase onto current, then read the result. Or discard.
The consequences changed What this would affect is materially different from the set you were shown. The panel now shows the real one. Read the new set and accept with those consequences, or discard.
Nothing to accept Every part of the draft already matches what the world says. There is no decision left to make. Nothing. The card retires itself and notes it in the log.
Review the merged result This was rebased onto newer work. Something was merged and you have not looked at it yet. Read it. Marking it seen unblocks the accept.
Conflicted fields await a choice You and the world changed the same field. Arke will not pick for you. For each one, choose this proposal or the world. Both readings are shown.
The target was retired The sheet or rule this would change has been retired since drafting. Discard. A retired thing cannot be edited, only discarded.
This draft cannot be written as it stands Something in it is outside what may be written — a character's role over its length limit, or a structured record the world could not read back. Ask the studio to fix it, or discard. Nothing has landed.
An edit to this proposal did not finish An in-place edit to the draft stopped halfway and its outcome cannot be determined. The half-finished edit is dealt with first. Accepting past it would write something nobody reviewed.
The studio is still drafting A turn is currently writing into this proposal's folder. It is not settled enough to act on. Cancel the run, or wait for it. This one clears itself the moment the run ends.

Staleness is detected, never merged. When a file has moved underneath a draft, Arke stops and names the file. It does not combine the two versions behind your back, and it does not overwrite the newer one with the older. Merging is a separate, explicit step you ask for — and even then it merges field by field, hands you anything both sides touched, and refuses to be accepted until you have read the result. There is no path through this gate where two versions of your writing are silently reconciled.

What accepting does — all at once, or not at all

Five things happen, and they are one act:

Snapshotthe outgoing version is copied into .history/
→
Replacethe live file becomes the proposed file
→
Versionthe number goes up; canon moves the world's revision once
→
Logone line appended to changes.jsonl
→
Catch upthe index and your screen follow

One proposal is one act, however many files it touches. A change amending a sheet and two canon rules lands all three together and moves the world's revision number exactly once, not three times.

Why the power going out cannot hurt you

Before anything real is touched, the whole set of steps is written down as a plan on disk — every file that will move, and a fingerprint of what it should look like before and after. Only then does anything happen. The plan carries a marker with three states, and that marker is what makes the guarantee work:

StateWhat has happenedWhat the next open does
prepared The plan is written. Nothing live has been touched — the copies into .history/ and the new files are being staged off to one side. Undoes it. The staged work is thrown away and your world is byte-for-byte what it was.
committing The point of no return. The staged files are being swapped into place, one at a time. Finishes it. Every step checks the recorded fingerprint first, so a step already done is simply skipped.
done Everything is in place and logged. Sweeps up the leftovers. The world is already whole.

There is no fourth state and no in-between for you to find: either the change happened or it did not. Underneath, every write follows the same discipline — the new contents go to a temporary neighbour, are flushed properly to the disk, then renamed over the target, a rename being the one operation the filesystem will not leave half done.

Opening a world read-only reports an unfinished plan but will not act on it: finishing means moving real files, and only the copy that owns the world may do that. It is left for whoever opens the world properly — see one owner at a time.

The change log

changes.jsonl sits at the top of your world folder, one line per change, oldest first. It is the audit trail, it is what the search index is rebuilt from, and it is the evidence that a change finished. Here is a real line:

changes.jsonl {"ts":"2026-07-14T09:00:00Z","entity":"characters/maren-kest", "fromVersion":3,"toVersion":4, "fieldsChanged":["appearance","voice-written"], "source":"chat:sess_9f2","canonRevisionAfter":41, "proposalId":"pr_01J8H0000000000000000000P0"}
ts
When, to the second.
entity
What changed, by its place in the world rather than its filename.
fromVersion / toVersion
Three became four. A new thing has null going in, which is how a creation reads.
fieldsChanged
Which parts moved — here, her appearance and her written voice. Not the text, just the names.
source
What caused it: form, or the named chat session. This is how you find the conversation behind a sentence a year later.
canonRevisionAfter
Which revision of the world's rules was in force once this landed.
proposalId
The draft it came from, when it came through the gate.

Lines written by a running world also carry the identifier of the act that wrote them, which is how an interrupted write can tell whether it already logged itself. Other line shapes cover a discard, a retirement, a reserved canon number, a file that vanished.

It is only ever appended to. Never rewritten, never reordered, never compacted. And a crash during an append leaves a torn final line — that is expected rather than fatal. The reader discards a partial last line, and the next append starts by finishing the broken one off with a newline so it can never be swallowed into the middle of a valid record. A damaged log costs you the last line, not the file.

History, and putting something back

.history/ holds a complete copy of every version ever accepted. Not the differences between versions — the whole file, every time.

.history/ characters/maren-kest/ v3.md the whole sheet, as it was at version three v4.md canon/CANON-002/ v42.md canon is filed by the world revision it belonged to

Full copies rather than differences, for two reasons. There is no version-control system underneath Arke, and building one — replaying a chain of edits to reconstruct a file, correctly, for ever — to save twenty kilobytes on a sheet is a bad trade. And you can open v3.md in any text editor and simply read it. A stack of differences is not readable by a person, and a chain that must be replayed has a first broken link.

Restoring reads one of these copies and puts its contents in as a new version. Restore version four while the sheet is at six, and you get version seven; five and six stay in .history/ exactly where they were. Nothing about going back destroys the record of having gone forward, so restoring is never a decision you can regret.

Pictures, video and audio are never snapshotted. Takes never change once they exist and are addressed by their own identity, so the reference to a take is the version — there is nothing to keep a copy of. See takes and the cut.

What does not go through the gate, and why

The gate protects the authored record — the facts a production cites. It does not cover everything in the folder, and the distinction is worth stating clearly.

Generated takes

A take exists the moment a provider hands it back; holding it outside your world until you approved it would leave generated material in limbo. What needs your acceptance is not the take existing but the take becoming a shot's answer and entering the cut — a different decision, on a different object.

Operational records

Jobs, charges, review decisions, the change log itself, the lock file, the search index. Written by the system as work happens. They are records of things that occurred rather than claims about what is true — and putting the change log behind the gate would be circular.

Directly authored prose

Chapter prose after acceptance, and the world bible, are written straight to disk by you. Still versioned, still copied into .history/, still logged — every save is restorable. They simply do not wait for a decision, because you are making it as you type.

Two more that surprise people

A look chosen while creating a world does not pass through the gate. It is written straight in as an accepted first version, with no proposal behind it and — a real consequence — no first copy in .history/, because there was no earlier version to keep. Every later change to the look does go through the gate, and does write history.

Creating a world is not itself one all-or-nothing act. The folder and the world file can exist before the first change-log line is appended. That is deliberate: the all-or-nothing machinery protects changes to a world, and needs the world to exist first. Both facts are written down plainly in the repository's own record of what touches the disk, rather than left for someone to discover.

One owner at a time

A world open in one copy of Arke is locked against another. The lock is a small file at the top of the folder called world.lock, recording which running program holds the world and when that program started.

Claiming has to be a single indivisible act. "Look whether the lock file is there, and if it is not, write one" is not a lock — it is two separate acts with a gap between them, and two copies of Arke opening the same world at the same instant both look, both see nothing, both write, and both come away believing they own it. So the claim is made with the one operation that means create this file, and fail if it already exists. Exactly one caller can win that, always. The loser reads the winner's record and is told who has the world.

While a world is open, the holder touches the lock file every twenty seconds — a heartbeat. If Arke crashed rather than closing properly, the lock is left behind with nobody alive holding it; a lock whose owner is dead or whose heartbeat stopped over a minute ago is treated as debris and cleared. You are never shut out of your own work by a program that is no longer running.

Letting go takes the same care in reverse. Releasing removes only a lock that still names you: a copy declared crashed and reclaimed still believes it holds the world, and deleting whatever the file happens to say would unlock the world underneath its new owner. If that has happened it is raised rather than passed over quietly — you are entitled to know a program has been writing to a world it no longer owned.

Editing a world in a text editor while Arke is closed

You can. The files are yours, they are plain text, and nothing stops you. Honestly, here is what happens.

On the next open, Arke compares inventoried entity files with the last state it wrote. A changed file is reported, not merged or silently adopted: it appears in the waiting queue as "files changed outside the app" and stays there until you deal with it. While a world is open, the watcher only hot-reloads the author-owned bible; other entity changes are found on the next open.

Accepting the reconciliation takes what is on disk as the truth: the version goes up, the last committed version is filed before it is replaced, and a change-log line is added with a source of external-edit, so the trail is honest that this change did not come through the gate. A file you deleted outside the app stays deleted and gains a line saying so. A file with no version to move gets a log line and nothing else.

A world first opened by this build files its current version so a later outside edit always has an outgoing snapshot. If an older build recorded only a hash and no matching history snapshot survives, Arke refuses adoption rather than pretending it can preserve bytes it no longer has.

Compatibility notes

Two older shapes remain worth naming because worlds and proposal manifests outlive the build that made them.

read-only context
Proposal folders hold _base/, the before-copy used for merging. Context outside the proposal's target scope is read through the confined world-query tool; no copied _context/ tree exists.
restore
restore is a reserved, currently unused proposal kind. Restore actions commit directly as new versions; the deliberate human action is not staged for the same person to accept again.
adoption snapshot
The outside-edit snapshot described in the section above is built: adoption supplies the last committed bytes to the journalled commit before replacing the live file. built
