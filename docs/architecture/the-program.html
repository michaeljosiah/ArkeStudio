The program

Two halves, a private wire between them, and some helpers

What you install is one application. Inside it are two halves and a handful of helper programs. The split is not decoration: it is what keeps the rules of the studio enforceable in exactly one place.

The window Everything you see and click. It holds no files and knows no file paths — it asks the engine for everything. (In the code: the renderer.)
↔
The engine Your world on disk, the accept gate, canon, the search index, the job queue, the spend ledger. All the rules live here. (In the code: the coordinator.)
→
The helpers Separate programs the engine starts, watches, restarts and stops: the writing assistant, the speech program, the image engine.

The engine is not a server you install. It is a library loaded into the same process that puts the window on screen. Two things follow: nothing about Arke is reachable from a network, because there is no network part to reach; and quitting really does stop everything, because nothing is left over to stop.

The window is deliberately ignorant. It never opens a file, never learns where your worlds are, never holds a key. Drag a file onto it and the path is resolved in the shell and leaves at once as a message; the window never sees it. Everything on screen arrived as a message from the engine, which is why a screen can never be right about something the engine has wrong.

What a world is belongs to other pages: the world, productions, takes & the cut, the accept gate. This one is only about how the program is put together.

How the two halves talk

They talk over a private connection on your own machine — the address only your own computer can reach, on a port picked fresh at each launch. Nothing outside can dial it.

When the window connects it says hello. The engine replies with one complete picture of the current state, then one small message per change, each numbered in order, which the window applies to the picture it holds.

If the connection drops, the window asks for a whole fresh picture rather than for the changes it missed. Partial replay was considered and refused, and the reason is the point: patching from an unknown starting point is how a screen ends up quietly wrong. A window that redraws is briefly blank; a window that guesses is confidently mistaken, and nothing on screen says which.

Counted from the source at 0.5.47, taking only the top-level members of each list. A large application with a small, single, written-down vocabulary.

Both directions are checked against that vocabulary, and the two ways of failing are handled differently on purpose. Bytes that are not readable at all close the connection: that is a fault, and faults should be loud. A readable message the engine has never heard of is only dropped and logged, because that is usually one half of the app being a build ahead of the other — and closing the connection over it made the whole studio read as disconnected on one keystroke.

The bridge

The window runs sandboxed. It is given exactly one small object to talk through, and that object is the entire surface between the halves: connect, send, listen, plus a short list of host chores — open the data folder, set the theme, quit. No file system, no paths, never a credential. Where a feature needs a file dialog, the dialog belongs to the shell and so does the path it returns; the window learns only that an attachment exists.

Video, and why it is served differently

Pictures and video do not travel over the message channel. The same private connection also answers ordinary web requests, and media is fetched from a local address shaped like /media/<world>/<file> — resolved to a real file, refused if it is not genuinely inside the named world, then streamed.

The reason is byte ranges — being able to ask for just the part from here to here. A video element cannot seek without them. Serve a file whole and the player reports it has nothing to seek within, then silently ignores every attempt to move the playhead: playback works, scrubbing does not, and nothing says why. So ranges are answered properly, including the awkward form meaning "the last N bytes".

Media is served with caching switched off. Generated grids and boards are recompiled in place under the same name, and a cached copy would show you the old picture with no way to tell.

The helpers, and never leaving one behind

Three helper programs run beside Arke, each looked after by the same piece of code. They differ in what they say, not in how they live.

The writing assistant

The agent that drafts with you. See the assistant.

The local speech program

Text-to-speech and dictation on your own machine, at no cost per line.

The local image engine

Optional. Where you have ComfyUI, Arke generates on your own graphics card rather than pay a service. See generation & spend.

Each gets a free local port, a health check, a restart budget and a stated reason when it cannot run. A missing helper is an ordinary state, not a broken one: the app opens and works regardless, and the affected feature says what is unavailable and why.

Three belts, because one is not enough

Arke promises never to leave a helper running after it exits. That has to hold when Arke is force-killed and none of its own cleanup code runs at all, so it is kept three ways.

  1. The operating system holds the leash

    Each helper is tied to Arke's own lifetime by the operating system, through a handle Arke holds and the system closes when Arke dies — however it dies. The child and everything it spawned go with it. This is the only belt that survives a force-kill.

  2. A small file the next start-up sweeps

    Every helper Arke starts is written into a small register at run\children.json and released when it exits cleanly. The next launch reads that file: anything recorded whose owner is gone is an orphan, and is killed. This covers the runs where the leash could not attach.

  3. Descendants are recorded too

    Sometimes the thing Arke launched is only a wrapper around the real program, and killing the wrapper leaves the worker running — which is how stray assistant processes used to pile up. So once a helper is healthy its living descendants are recorded beside it, and both the stop path and a later sweep can reach past a dead wrapper.

Why three and not one: the register and the exit sweep run no code at all if Arke is force-killed, so only the first belt covers that; and a wrapper hides the process doing the work, so only the third belt reaches it. All three are careful about identity — process numbers get reused quickly, so a recorded helper is killed only when the process now holding that number still bears the right program name and started when the record was made. A leaked helper is a nuisance. Killing a stranger's process is not.

Everything the engine needs from outside is handed to it

The engine never reaches out for anything. It does not open a file dialog, fetch an encryption key, find a video encoder or load a model. All of those are handed to it as options when the app starts, and the shell is the only part that knows how to get them.

This buys two things. The rules can be tested without a machine — no screen, no network and no graphics card appear anywhere in the engine's tests, because anything needing one arrives as a plain object a test can supply. And a missing capability becomes a stated consequence rather than a crash: every option's absence has a written-down meaning. Real examples from the engine's own list:

The rule, and the fact that it is checkable

The search index

Two small databases make searching and listing fast. One sits at the app level: the list of worlds, so the picker can draw without opening any of them, plus a mirror of the job log and the spend log. The other sits inside each world and holds the searchable text — canon, character sheets, who mentions whom.

Both are caches, and only caches. Each is built purely from files that are themselves the truth, and each is structurally prevented from becoming truth itself. Delete either and it rebuilds. That is why deleting a cache can never lose spend history: the ledger on disk is the record and the database is only a copy made for speed. It is also why a change to the shape of a cache throws the tables away and rebuilds, rather than migrating anything.

Two details an engineer will want. Full-text search has to actually be compiled into the database engine, so rather than assume it Arke proves it at every open, by creating a tiny search table and dropping it again. And the database library is compiled code that must match the exact application it is loaded into — the copy tests use and the copy the desktop app loads are different builds of the same thing under different names, which is why packaging has a rebuild step. If it does not load, the engine is told so and says it: search and counts degrade, authoring still works.

Building and shipping

build
Builds the window, then flattens the shell and its bridge into two files, stamping in the version number read from one place so the About box cannot disagree with the installer.
test
Runs every workspace's tests.
package
Stages the helper runtimes, checks every bundled component has a recorded licence obligation, builds, then makes an installer.
release
The same, driven by pushing a version tag; the tag and the version in the package must agree or the build stops.

The shipped installer is Windows x64 only, and the reason is worth retelling. ARM64 installers were built until 0.2.9 and should not have been. The database library has no ready-made ARM64 build for this application, so it must be cross-compiled, and the compiler component that needs was never installed on any packaging machine. The build step had been set to tolerate a failed native build, so it tolerated it, silently, every time: every ARM64 installer ever produced shipped with the search index switched off.

A build that quietly drops a feature is worse than no build. ARM64 was withdrawn and the tolerance setting removed with it; Windows on ARM runs the x64 build under emulation, the honest fallback until the toolchain exists on the packaging machines.

The gate every change must pass runs on both Windows and Linux. Windows because that is what ships. Linux because it is unforgiving about the two assumptions Windows lets you make for years without noticing: which way a path separator leans, and whether two names differing only in capital letters are the same file.

Tests

There are 232 test files across the repository, unevenly spread: 137 of them cover the engine and 56 cover the window.

For the engine, test code very nearly matches source code by volume — 39,860 lines of test against 43,645 lines of engine, roughly nine lines of test for every ten of code. Across the whole repository it is 63,867 against 107,956.

The contributing guide names four places where a mistake is expensive and quiet and asks anyone touching them to say how they know the change is safe: the world folder, the accept gate, the job queue and packaging. That is where the weight sits — the four places where being wrong costs someone their work, their money, or an installer that lies about what is inside it.

Designed, and not built yet

Stated plainly, because a document that describes only what exists will read as though everything exists.

Arke assumes four things: one person, at one machine, spending their own money, publishing to a local file. Each is load-bearing somewhere in the code, and each is wrong for a hosted product built on the same engine. The plan is not to make Arke multi-user, metered or moderated. It is to make those four assumptions replaceable — four small interfaces, each with a default that gives exactly today's behaviour, so the same engine could sit underneath a hosted product without anyone forking it.

Where a specification and the code disagree, this page follows the code and says so. The host ports are the clearest case in the repository: the design is detailed, reviewed and revised, and not a line of it exists yet.
