How Arke Studio is built

The world is a folder. Everything else is a view of it.

Arke Studio is one program that runs on your own computer. Everything it knows sits in ordinary files, in an ordinary folder you can open, copy, back up or read in a text editor. These pages explain what those files are, how they describe a world and the things you make from it, and how the program around them is put together.

Most creative software keeps your work in a database, or on a server, or inside a project file only that software can open. Arke does none of those. There is no cloud account, no database, and no hidden version control. If you delete Arke tomorrow, your worlds are still there, still readable, still yours.

That is not a nice extra. It is the decision everything else hangs off, and it explains most of what follows — why prose is stored as plain text, why every accepted change leaves a line in a log you can read, and why the parts of the program that are working something out can always be thrown away and rebuilt.

Written for anyone

No code anywhere in this set. Where a file name or a field matters it is named and explained in plain words, because those are the names you would see if you opened your own world folder.

Read off the code

Every layout, field and rule here was read out of the source and the sample world that ships with the app. The specifications describe what is intended; these pages describe what is there.

Honest about gaps

Things that are designed and not yet built are marked designed wherever they come up, rather than described as though they exist.

The set

Eight pages. If you read two, read The world and The accept gate — between them they carry the whole idea.

1 · Files on disk

The complete map. Every folder and every file, on your machine and inside a world, with what it is and whether losing it costs you anything. The page to open when you see a name you do not recognise.

2 · The world

The asset itself: the world's own record, characters and places, canon, the bible, the look, and the picture kits that keep a cast recognisable from shot to shot.

3 · Productions

What you make out of a world. Stories with chapters, films with scenes and shots, series with seasons and episodes — all of them pointing at the world's cast rather than copying it.

4 · Takes and the cut

Every generated result is kept and never edited. Which one you are using is recorded somewhere else entirely, and the cut is worked out from the two rather than stored. The most important shape in the product.

5 · The accept gate

How a change actually happens: drafted somewhere else first, consequences shown before you decide, and an interrupted write that can never leave your world half-changed.

6 · The assistant

The AI that drafts with you, and the fence around it: what it can see, what it can touch, why it has to cite what it read, and why it cannot browse your folder.

7 · Generation and spend

From pressing the button to a clip landing: what is written down before anything is sent, what happens when it goes wrong, where your keys live, and how every charge is recorded.

8 · The program

How the application is assembled — the two halves, the helper programs, where the code lives, and how it is built and shipped. The one page an engineer should start on.

The shape of it, in one screen

What you install is one application. Inside it there are two halves and up to four helpers, and the split is what makes the rules further down enforceable rather than merely stated.

The window Everything you see and click. It holds no files and knows no file paths — it asks the engine for everything.
↔
The engine Your world on disk, the accept gate, canon, the search index, the job queue, the spend ledger. All the rules live here.

The two talk over a private connection on your own machine that nothing outside can reach. Around them sit the helper programs: the writing assistant, local speech, an optional local image and video engine, and ffmpeg for measuring and encoding video. Each is a separate program the engine starts and looks after, and each can be absent — which Arke reports as a stated consequence rather than a failure. The program covers all of it properly.

The rules that hold it together

Nine of them. Every page in this set is, in the end, an explanation of how one or two of these are actually enforced.

RuleWhat it means for youWhere
The folder is the only truth Everything else — the index, the caches, the thumbnails — can be deleted and rebuilt. Nothing you made lives only in a cache. Files on disk
Nothing authored lands without an accept Sheets, canon and scenes change when you say so, never behind your back, and never while you are still reading the proposal. The accept gate
You see the consequences before you decide What else a change touches is worked out before the accept, not reported after it. The accept gate
The canon refuses rather than guesses Asked something it cannot support, the world says so and cites the closest it has. An invented citation fails verification and takes the answer with it. The assistant
A take is never edited Every result you generated is still there. Choosing between them is a separate, reversible act. Takes and the cut
Staleness is refused, never merged If something changed underneath a pending edit, Arke stops and tells you rather than silently combining two versions. The accept gate
Identity travels A character's main photo and composite sheet follow her into every generation that accepts a reference, so consistency is structural rather than a function of prompt luck. The world
Nothing is filed by hand Where a file came from is recorded at the moment it arrives, so anything that cited a character turns up against that character later. The world
No lock-in Open format, open licence, no absolute paths, no keys inside a world. Copy the folder to another machine and it works. Files on disk

Designed, and not built yet

Stated here as well as in place, because a document that describes only what exists reads as though everything exists.

designed The narrative game

Branching narrative with a chapter graph, playthrough state and an engine-neutral export.

designed Recovery from the archive

Archiving a world moves it whole today. Bringing one back is specified and not written.

designed The four host ports

Arke assumes one person, at one machine, spending their own money, publishing to a local file. All four are meant to become replaceable, so the same engine can sit underneath a hosted product without forking. None of the four exists in the code yet.

in build Voice mode

Speaking a world into existence rather than typing it.
