Productions

How story and screen are written down

A production is something you make out of a world — a film, a novella, a vertical series, a set of stills. It lives inside the world folder, and it shares the world's cast and canon by pointing at them rather than by taking a copy.

The sample world that ships with Arke Studio, The Undersong, holds two of them. One is filmed, one is prose. They sit side by side under productions/, and they draw on the same six locations and the same five characters.

the-undersong/ one world folder ├─ characters/ locations/ canon/ the cast and the canon — shared by everything below ├─ series/ │ └─ bell-watch.json a thin series record, where a world has one └─ productions/ ├─ saltlight/ something filmed │ ├─ production.json what this production is │ ├─ story.md the treatment — freeform prose, optional │ ├─ scenes/ │ │ ├─ 02-the-tables-say-neap.json │ │ ├─ 04-the-verse-rises.json │ │ └─ 06-slack-water.json │ ├─ boards/ compiled scene boards │ ├─ takes/ every generated result, one folder each │ ├─ selections.json which take each shot is using │ ├─ reviews.jsonl every accept and reject, in order │ └─ cut.json audio tracks and overlays only └─ the-ledger-of-nights/ prose ├─ production.json ├─ story.json logline, spine, acts, target length └─ chapters/ ├─ 01-neap.md ├─ 02-the-same-ink.md ├─ 03-nothing-wrong-with-it.md └─ 04-her-own-hand.md

What a production says about itself

The whole of a production's own record is one small file. Here are both of the sample world's, complete and unabridged:

productions/saltlight/production.json { "id": "saltlight", "format": "video", "title": "Saltlight", "logline": "One night on the Vigil, the verse rises early.", "status": "in-progress", "created": "2026-06-01T10:00:00Z", "updated": "2026-07-30T14:04:11Z" }
productions/the-ledger-of-nights/production.json { "id": "the-ledger-of-nights", "format": "story", "title": "The Ledger of Nights", "logline": "Four watches, two hundred years apart, written in the same hand.", "status": "drafting", "created": "2026-06-18T08:30:00Z", "updated": "2026-07-28T16:41:00Z" }

Notice how little is here. Nothing about the cast, nothing about the look, nothing about the world. All of that is somewhere else, once.

Three words for what a production is, and why

A production carries up to three classification words, and the reason there are three is entirely about not lying to a reader.

format
The oldest of the three, and frozen: it is only ever story, video or stills. It is always written, even for productions the word barely fits, because a copy of Arke that predates the other two fields will read this one and must not be misled by it.
medium
What the audience receives: story or video. Optional. When it is absent it is worked out from format — story stays story, video stays video, and the retired stills becomes video. It is written down only when it says something the old word cannot.
kind
The named form beneath the medium: film, microdrama, music-video, interactive, book. A kind only sets starting numbers and which screens appear; every video kind has the same scenes, shots, takes and cut. An unrecognised kind falls back to the medium's ordinary behaviour rather than making the production disappear.

That is why both files above carry only format. Neither is a micro drama or an interactive piece, so writing medium and kind would add two keys that say nothing new — and adding them marks the world as needing a newer build. A plain creation stays readable by every version that ever existed.

Four more things a production may carry

aspect
The shape it delivers in — 16:9, 9:16. It sits on the production and not on the world, because one world routinely holds a wide film and a vertical cut of the same material, and a single world-level shape cannot hold both without one production silently changing the other's. Absent means 16:9, which is what everything made before the field existed actually rendered. Written in one tidy form: " 9 : 16 " and 9:16 are stored the same, and something that is not two numbers around a colon is refused at the point of typing rather than stored to fail later.
musicPolicy
A production may make the world's music rule stricter and never looser. The world can say either "environmental sound only" or "the model may score it"; the production may only say "environmental sound only", and there is deliberately no way to write the permissive value here at all. That rule is built into the shape of the file rather than into a screen, because a screen can be worked around and a file that cannot express the wrong thing cannot be talked into it.
failureModes
Standing "don't do this" notes, sent with every generation — up to twenty, each a sentence or so. The production's are added to the world's, world first, never instead of them: the world's are the ones every production is entitled to assume.
styleOverride
A visual language just for this production. It is deliberately conspicuous: the world's art-direction screen lists it by name among the exceptions to the house look, so a production that has quietly wandered off is visible from the world level. partly wired The exception is listed and the field is stored, but nothing in the code that assembles a shot's instructions reads it yet.

Nothing is copied

This is the central idea of the whole model, and it is worth stating on its own. Creating a production copies nothing out of the world. Not a character, not a location, not a rule. The production points, and resolves what it points at when it needs it.

←

What that buys is simple and large: edit Maren's sheet once and the change reaches every production that cites her, on its next dispatch. There is no migration, no sync, no "update from world" button, and no possibility of a production quietly running on a version of a character nobody remembers approving. A production is a view of the world with a running order attached to it.

The exception proves it. A production may own a guest — a character who belongs to this film and not to the world. A guest is an ordinary sheet in the ordinary place with one extra line naming its owner, and it versions, gates, gets a reference kit and gets a voice exactly as a world character does. The ownership decides only where it is shown. See the world for how sheets themselves work.

Two shapes: prose, and something filmed

Beneath production.json, a production takes one of two shapes. The medium decides which, and the two do not overlap: a prose production has chapters and no scenes, a filmed one has scenes and no chapters.

A story

story.json is the overview the whole thing is drafted against. Here is the real one from Saltlight, which is a filmed production that still keeps one — the overview is about the story, not about the medium:

productions/saltlight/story.json { "version": 4, "logline": "One night on the Vigil, the verse rises early — and the bill goes to the man standing next to her.", "spine": "A tide-caller takes an ordinary watch, finds the water a hand-span wrong, and puts it back. She has done this a hundred times and it has never cost her much, and she has never once asked why not. Eleven minutes to make an audience notice the thing she has spent a career not noticing.", "acts": [ { "title": "Dusk · the watch", "summary": "Maren alone on the rail. The tables say neap; the water disagrees. Establish the ledger, the six columns, and the tithe-box at the north gate that nobody looks at twice." }, // "Bells · the correction" and "Slack water · the rupture" follow ], "targetLength": "short film · 11 minutes" }

Four fields, all optional, all prose except the version. There is no act structure enforced, no beat template, no required number of anything. The file exists so the thing you are writing towards is written down once, in your words, where the assistant can read it too.

The prose itself lives one file per chapter under chapters/, as ordinary Markdown with a small block of facts at the top. This is the real head of the sample novella's first chapter:

productions/the-ledger-of-nights/chapters/01-neap.md --- id: neap number: 1 title: Neap status: drafted version: 4 words: 3120 draws: sheets: [the-vigil, maren-kest] canon: [CANON-019, CANON-002] --- The ledger of the Vigil is kept in a hand that changes every generation and a form that never has: date, moon, tide predicted, tide observed, bells, name of the watch. Six columns since 1747…
order vs number
order is the one authority on position. number is the older field, still on disk in the sample, and read only when order is missing. Reordering writes order and leaves number alone — nothing is rewritten just to rename a key. Neither is required: a chapter whose position cannot be worked out falls back to filename order, predictably, rather than vanishing from the book.
the filename
01-neap.md is a convenience, not a fact. Order is never taken from it, because if it were, reordering would rename files, and renaming a file moves its version history — so dragging chapter four above chapter three would break the history of a chapter that had not changed.
words · status · version
A word count, a state you choose the vocabulary for (drafted, outlined, whatever suits), and a version that ticks up each time an accepted change lands. Typing into your own chapter saves in place and cuts no version; a chapter the assistant drafted arrives as a proposal. See the accept gate.
draws
Which sheets and which canon entries this chapter leans on. It is what lets a change to CANON-019 tell you which chapters were written against it.

Something filmed

scenes/ holds one file per scene, and each scene carries its shots inside it. That is the rest of this page.

A scene, and the shots inside it

Here is a complete scene file from the sample world — the fourth scene of Saltlight, unedited:

productions/saltlight/scenes/04-the-verse-rises.json { "id": "sc_04", "number": 4, "slug": "the-verse-rises", "title": "The verse rises", "status": "accepted", "version": 2, "inherits": { "location": "the-vigil", "timeOfDay": "night", "tone": "quiet dread" }, "board": { "version": 2, "compiledAt": "2026-07-29T11:02:00Z", "image": "board-v2.png" }, "shots": [ { "id": "sh_12", "number": 12, "title": "Maren at the rail, listening", "description": "@maren-kest grips the rail of @the-vigil, head tilted. She hears it first.", "camera": "MCU · slow push-in", "audio": { "kind": "vo", "speaker": "maren-kest", "line": "the verse, under the water" }, "durationSec": 4 }, { "id": "sh_13", "number": 13, "title": "The lamps answer", "description": "The green-white lamps of @the-vigil flare and settle, one by one, down the rail.", "camera": "WS · static", "audio": { "kind": "sfx", "line": "bells, far under" }, "durationSec": 6 }, // "Bray stops mid-story" (sh_14) and "The harbour holds its breath" (sh_15) ] }

Everything in that file is a decision, not a detail. Here are the ones worth understanding.

  • @maren-kest is a live reference, not text

    When Arke assembles the instructions for this shot, that token is replaced by whatever the character sheet says at that moment, and her model sheet is attached alongside as a reference picture. Edit her sheet tonight and tomorrow's dispatch picks it up. Nothing was copied into the scene to go stale. The mentions are also the only cast list — there is no second list of who is in the shot to fall out of step with the description. And because sheets are pointed at by a stable short name, renaming Maren does not silently drop her out of the shots that mention her.

  • number is identity; order is position

    A scene's number is its name — "Scene 4" — and it is never rewritten. It keys the scene's board image on disk, and it is what a cut entry points at. Position is a separate, optional field that reordering rewrites and nothing else touches. Two fields on purpose: renumbering the world every time you drag something is exactly how references quietly break, and a number that means two things means neither.

  • The scene sets the room; a shot overrides by having a value

    inherits says the location, the time of day and the tone once, for the whole scene. Alongside it a scene may carry defaults — the camera every shot starts from. A shot that names its own value for a field wins for that field only, and the rest still come from the scene. There is no separate "override this" switch anywhere, because the presence of the value is the override: a switch is a second thing that can disagree with the first.

  • Nothing here says which take was chosen

    The scene file is authored structure and nothing else. Which generated result a shot is currently using lives in a separate small file, so that choosing a take never edits something you authored. That is the hinge of the whole design and it has its own page: takes and the cut.

The camera, said in nine fields

camera in the sample above is one free line — "MCU · slow push-in" — and it still works exactly as written. Beside it a shot may carry a structured camera, which is the same nine fields a scene's defaults uses. Every field is optional, so an older scene file is an ordinary scene rather than an incomplete one.

They are all free text on purpose. The list of legal sizes and movements is display vocabulary, not something the file format polices, so a new word for a new kind of shot never needs the file format to change.

Above them sits intent — how the shot should feel, in a sentence, rather than how it should be made. "Held, not slow — she is deciding whether to have heard it." The idea is that the camera can be inferred from the feeling, and that anything you set by hand wins over anything inferred. partly built The field is edited on the shot sheet, versioned and saved, and the assistant can write it; but no code that assembles a shot's instructions reads it, so today it is a note to yourself and to the assistant rather than something that steers the camera.

The rest of a shot

audio
A kind (vo, dialogue, sfx, silence), the speaker where there is one, the line itself, and — beside them — ambience and effects: the bed under the line and the hits next to it. Sound direction sits on the shot rather than on the scene because one global "market noise" applies itself to the quiet room two shots later.
durationSec
How long this shot runs. It is what the running time is added up from, and what decides whether a whole scene fits inside one generation or has to be sent in passes.
beats
Timing rows inside a shot — a label like "0–3s" against a line of what happens. A label, deliberately, not a machine timeline. partly built Edited and stored; not yet read by anything that builds a generation.
continuity
Two halves of one promise. openOnPrevious records that this shot wants to open on the last frame of the one before it — the chaining itself is driven by the actual boundary picture, and this is the authored wish. keepOut is the negative half: things that must not be in the frame, and it really does travel into the generation as an exclusion.

An edited prompt is an override, never a replacement

Arke writes the instructions for a shot from the world: the cited sheets, the scene's location, the world's tone and look, the shot's camera and audio. You can edit that text freely. What is stored when you do is an override sitting beside the shot, together with the version number of every sheet it cited at the moment you edited it.

the shape of an edited prompt, on a shot "promptOverride": { "text": "…the words you actually want sent…", "sheetVersions": { "maren-kest": 4, "the-vigil": 2 } }

Three things follow from storing it that way rather than overwriting the assembled text. The assembled form stays derivable, so it can still be shown next to yours. Reset stays possible, because the thing you replaced was never destroyed. And staleness becomes computable: when Maren advances to v5, Arke can say this shot's prompt was written against v4 and will not pick the change up — which is true precisely because the version was recorded, not guessed.

The script, and which shot covers which line

A scene may carry a script: an ordered list of blocks, each one either action or dialogue, each with a stable identifier that survives editing and reordering. A shot then records which blocks it covers — and, beside each, a short fingerprint of that block's text at the moment it was cited.

the script, and a shot citing it "script": { "blocks": [ { "id": "blk_the-empty-page", "kind": "action", "text": "Maren opens the ledger to the 14th." }, { "id": "blk_at-bells", "kind": "dialogue", "speaker": "maren-kest", "text": "That page was here at bells." } ] }, // on the shot: "covers": [ { "blockId": "blk_at-bells", "textDigest": "sha256:9f2c…" } ]

Nowhere does anything store the words "this shot is out of date". Compare the fingerprint against the block's text now and one of four answers falls out: the shot cites nothing, the text is unchanged, the text has changed since it was cited, or the block it cited no longer exists. Working it out every time is better than storing it, because a stored flag can be wrong and a derivation cannot. Splitting a block in two is an edit plus an insert, and the shot keeps pointing at the identifier it always pointed at.

Two different pictures of a scene

The board

A contact sheet of the scene as it currently stands, compiled locally from the frames already chosen — free, repeatable, and identical every time from an identical scene. It records the scene version it was made from, so it can be marked out of date when the scene moves on. Shots with nothing chosen leave a gap in the grid, which is the point: you are looking at your progress.

The storyboard

A different thing entirely: line art, drawn by a model, made to be read by a video model as a reference. It costs money, so it is dispatched, priced and recorded like any other generation, and it records which scene version and which delivery shape it was drawn at. It lands unaccepted — a board nobody looked at silently steering a scene would be the accept gate inverted.

What the scene was written under

A scene may record the drafting guidance it was written with — which document, which version, which family of models it was written for. This is provenance, in the same spirit as the override's recorded sheet versions, and it earns its place because a scene can be sent to a different model than the one it was written for. When that happens, the dispatch says so before any money moves: this scene was written for one family and you are sending it to another. A scene with no recorded guidance never mismatches, because guidance for nobody in particular is wrong for nobody in particular.

Series, seasons and episodes

For something with more than one instalment, three more records join in. All three are deliberately thin, and thin for one reason: a record that described a character would be a second place that character exists, and a character described in two places is a character that drifts.

RecordWhere it livesWhat it holds
Series series/<name>.json Title, the repeatable premise — the story engine — an ordered list of which productions are its seasons, and only the continuity that is genuinely not world canon. Living inside the world folder is its link to the world; there is no field repeating it.
Season productions/<name>/season.json The season's question, its ending, its direction, its arcs, and its editable defaults. There is no separate season entity — an episodic production is the season, with this file beside it.
Episode productions/<name>/episodes/<stem>.json Its place in the running order, its promise, an ordered list of its scenes, any boundary-crossing link to its neighbours, and its release details.

The season

Two fields that sound alike are deliberately separate. The season's ending is its own authored resolution, in prose — how this season finishes. The per-episode ending policy — "cliffhanger" — lives among the defaults. Two facts, two fields, because one field would have to mean whichever the reader assumed.

An arc is a lane across the season. Each one names, at most, the episode where it is set up, the episode where it turns, and the episode where it pays off:

the shape of an arc in season.json "arcs": [ { "id": "the-tithe", "title": "Who has been paying", "setup": "ep_first-night", "turn": "ep_the-audit", "payoff": "ep_her-own-hand" } ]

A lane with a setup and a turn and no payoff is not stored as a problem anywhere. It is worked out and said out loud when the season is drawn: the arc "Who has been paying" sets up and turns but never pays off. Seven other things are worked out the same way — a hook repeated across episodes, the same cliffhanger twice, a character who appears in no episode, a promise never resolved, a contradiction, an episode introducing too many new things at once, an unusual spend pattern. Each names what it is about and the evidence it stands on. There is deliberately no score of any kind: a number would hide exactly the sentence you needed to read.

The defaults are defaults and never invariants — episode count, the seconds an episode should run between, how long the hook has, the ending policy, the export preset. Choosing "micro drama" at creation writes sixty episodes, forty-five to seventy-five seconds, a three-second hook, cliffhanger endings and a 9:16 delivery shape into the file, where every one of them is a control you can change. They are starting numbers, not rules.

The episode, and the one rule to remember

productions/<name>/episodes/the-missing-night.json { "id": "ep_the-missing-night", "version": 2, "order": 3, "title": "The missing night", "promise": { "opens": "The ledger page for the 14th is gone.", "turn": "It was torn out by someone who signed the page after it.", "closes": "The bell rings once, from under the water." }, "scenes": ["sc_09", "sc_10", "sc_11"], "linked": { "closesInto": "ep_slack-water" } }

The episode's ordered list of scenes is the only authority on which scenes are in it. Scene files carry no episode field at all. One authority means the two can never disagree, and a moment that crosses a release boundary is honestly two linked scenes — one closing, one opening — rather than one scene claimed by two episodes.

The same care shows in the small things. Identity is the file name and the id, both fixed at creation; position is the order field, and reordering rewrites only that. Moving a scene from one episode to another is one change touching both episode files together, so there is no instant where a scene belongs to two episodes or to none. Deleting an episode that still lists scenes refuses by name rather than orphaning them. A scene in no episode, a scene in two, or a list naming a scene that does not exist are each said out loud rather than crashing anything — and each one holds up that episode's export until it is dealt with.

release is the episode's own delivery record: title and description as published, a chosen thumbnail, tags, a recap, a teaser, alternative crops. It belongs to the episode because the episode is the thing released; a film releases as the production itself, and there is deliberately no abstract "release unit" invented to cover both.

The page medium not built

Arke makes prose and it makes moving pictures. It cannot yet make the thing that sits between them: an illustrated page — a picture with words set on it, a spread, a panel with a speech balloon, a book you could send to a printer.

There is a full specification for it and no code behind it. Nothing in the program reads or writes a page today. What the specification settles is worth knowing because of the shape it insists on, which is the shape of everything else here:

A panel is a shot

Not a new kind of thing. A page-based production would share the same dispatch, the same takes, the same review and the same selection as video, with duration and camera movement simply absent rather than defaulted, because a page has no time.

The book is derived

A page is an ordered group of panels with a layout; the book is worked out from the pages and the chosen pictures, exactly as the cut is. A spread is worked out from the page numbering and never stored, so inserting a page cannot leave a stale pairing behind.

Words are a layer, not paint

Narration and balloons would be set on top at render time, from the same script blocks a shot cites — never generated into the picture. Text inside a generated image cannot be corrected, resized, translated or read aloud. The one exception is lettering that belongs to the depicted world, like a sign, which is picture rather than words.

It is honest about its own uncertainty, too. The specification records a real test in which a model was asked, exhaustively, for no text of any kind and returned lettered boat hulls anyway — which is why nothing in the design is allowed to assume that asking worked.

Interactive video built

A production can be one the viewer steers. It is not a fourth medium and not a second kind of scene: it is ordinary video, made of ordinary scenes and shots and takes, with one extra file that says how the scenes connect.

productions/<name>/routing.json { "version": 3, "start": "sc_01", "choices": [ { "id": "ch_follow-the-look", "from": "sc_06", "label": "Follow the look", "to": "sc_07" } ], "endings": [ { "sceneId": "sc_12", "title": "The harbour, level" } ], "excluded": [ { "sceneId": "sc_04", "reason": "cut, kept for the audio" } ], "groups": [] }

A choice selects the next scene and does nothing else. There is no way to write a condition, a variable, an inventory or an unlock — and that is not a rule enforced somewhere, it is a shape the file cannot hold. A file with a condition key in it does not fail a check; it fails to be a routing file at all, with the offending key named. Endings and exclusions are designations of scenes that already exist, not a second kind of scene.

Because the map is a plain graph, everything worth knowing about it is worked out rather than stored: a scene nothing can reach that nobody deliberately excluded, a choice pointing at a scene that is not there, a place from which no ending can be reached, a loop with no way out, a scene two routes arrive at, an ending that still offers choices, and any edge nobody has walked in preview. Each is either something that blocks publishing or something that warns, named, with the scene or choice it is about. Preview walks count as evidence, and a walk stops counting the moment the choice it names is changed — so evidence can never vouch for an edge that no longer exists.

Both halves are built: the branch map screen, the findings, the durable preview evidence, and an export that packages the thing as something you can host yourself. What was designed as a medium of its own is now a kind of video — because a medium is what the audience receives, and interactive video receives moving pictures.
