# 1 · Requirements

## 1.1 Summary

This specification is the implementation authority for epic #393's Programme B and the domain
half of Programme C (issues #395, #400, #397, #396, and the schema questions in #384, #385,
#387, #389, #392). It settles what the brief (rev 5), the revised Scope (§01, §03, §04), and
design turns 47, 48, 53, and 78 decided but did not place: where each entity lives on disk, what
its schema is, who owns each fact, and how worlds already on disk migrate without loss.

Five decisions arrive already bound and are restated here as constraints, not reopened:

1. **Series is thin and created with Season 1** — id, title, the repeatable engine, a world
   reference, ordered season references, and only continuity that is genuinely not world canon.
   Recurring cast stays in world sheets (SPEC-012 D1's drift rule).
2. **Development is the narrative-development layer** inside every production; Story is an
   audience-facing production medium. The workflow reads Development → Production → Release.
3. **Linear episodic seasons are explicitly ordered and board-based, never graph authority.**
   Branching belongs only to Interactive video, direct-choice only.
4. **Formats and delivery profiles sit beneath medium.** Microdrama is a Video format; vertical
   is a delivery profile — format is structure, profile is defaults, and neither creates a
   second entity (turn 47).
5. **A script belongs to a Scene.** Turn 53 removed the Beat entity; an Episode is its promise
   and its ordered Scenes. Where older documents say "beat sheet" or "story beats" they name
   development vocabulary, not a domain record — no Beat entity, candidate, citation, or screen
   exists in this domain.

## 1.2 Scope

**In scope:** production classification (medium / format / delivery) and the legacy
`story | video | stills` migration; the Series, Season, Episode, and Scene-script entities;
episodic versus non-episodic scene ownership; proposal and conversation materialisation for
every new entity; the world schema-version boundary; Microdrama defaults, season intelligence
ownership, and release records; the episode cut/export identity at the domain boundary.

**Out of scope:** the Interactive-video domain beyond its classification slot (its own brief,
issue #392, precedes its specification); the durable scene-dispatch plan (SPEC for issue #391);
board/thread UI layout (bound by turns 48/53 and built by #397/#400); export implementation
(#396).

## 1.3 Acceptance criteria

### Classification

- [ ] One schema authority represents medium, format, and delivery; no parallel string unions
  remain in contracts, frames, coordinator, or client (**R-1..R-5**).
- [ ] Every persisted production opens deterministically under the read-side resolve rule with
  no bulk rewrite; legacy Stills productions keep all authored and paid work (**R-6..R-8**).

### Entities

- [ ] Series, Season, Episode, and Scene script have named files, stable IDs, explicit order,
  reference integrity, versioning, and history exactly as §2.3–§2.6 state (**R-9..R-16**).
- [ ] Episodic versus non-episodic ownership is unambiguous and testable (**R-11**).
- [ ] Episode cut identity and per-episode readiness are defined at the domain boundary
  (**R-24**).

### Materialisation

- [ ] Every new JSON entity stages, reviews, rebases, resolves, accepts, and ripples through
  the one gate, schema-aware; JSON never passes through Markdown merge (**R-17..R-19**).
- [ ] Production-scoped conversations extend #70's shipped model — durable event log, batched
  Wrap-up, non-authoritative talk (**R-20..R-22**).

### Compatibility

- [ ] The world schema-version boundary is implemented and old builds refuse rather than
  mis-open (**R-23**).
- [ ] The migration table in §2.8 is deterministic and idempotent; no loss of productions,
  chapters, scenes, takes, selections, artifacts, proposals, conversations, or history.

## 1.4 Requirements

### Classification (R-1 – R-8)

- **R-1** `production.json` SHALL carry `medium ∈ {story, video, interactive-video}` as the
  backward-readable classification. Current creation writes only Story or Video; a legacy
  `interactive-video` medium resolves as Video with kind `interactive`. The field is optional on
  read and resolved from the legacy
  `format` when absent: `story → story`, `video → video`, `stills → video`. The legacy
  `format` field remains **required** and frozen at `story | video | stills`, set to the
  legacy value the medium maps back to (`story → story`, `video → video`,
  `interactive-video → video`) so the field never lies to a reader that predates `medium`.
  New productions write `medium` and `kind` **only when they differ from what `format` alone
  resolves to** — a plain Video or Story creation writes the same keys it always did and the
  world stays schema-1; a Microdrama or Interactive creation writes the new keys and
  crosses the R-23 boundary.
- **R-2** `production.json` MAY carry `kind` — the named format beneath the medium (Video:
  `film` (default), `microdrama`, `music-video`, `interactive`; Story: `book` by default).
  `kind` is a free string on read (unknown kinds resolve to the medium's default behaviour). The
  current Video step offers `microdrama`, `film`, `music-video`, `interactive`, and `other`; only
  `microdrama`, `music-video`, and `interactive` are persisted, while `film` and `other` use the
  plain Video default. Story has no kind step. Existing `series`, `promotional-short`, `script`,
  `serial`, and unknown values remain readable. Legacy `stills` productions resolve to
  `kind: stills` under medium `video`.
- **R-3** Delivery profile is defaults, not an entity. Choosing a profile at creation writes
  concrete editable fields — `aspect` (existing field, e.g. `9:16`), season defaults including
  `defaults.exportPreset` (R-10) — and stores nothing else. No `profile` discriminator exists
  on disk.
- **R-4** One derived function in contracts — `productionShape(meta)` — SHALL be the only
  place classification becomes behaviour: it returns the resolved medium and kind plus the
  gates every consumer needs (`hasChapters`, `hasScenes`, `isEpisodic`, `isBranching`,
  `dispatchCapability ∈ {image, video}`, display labels). Every current inline
  `meta.format === "…"` branch moves onto it (#395).
- **R-5** The create picker offers Story and Video. Story creates directly because it has one
  current path. Video continues to a five-choice kind step. Interactive is a Video kind, not a
  third medium. Creating a Microdrama writes a Video production (`medium: video`,
  `kind: microdrama`).
- **R-6** ProductionSchema is a read path (SPEC-002 R-2): it SHALL NOT be tightened. New keys
  are optional; a production whose `production.json` carries only legacy keys parses forever,
  and every existing field — `logline`, `status`, `styleOverride`, `aspect`, `musicPolicy`,
  `failureModes`, `created`, `updated` — keeps its current schema, owner, and meaning,
  untouched by every operation this spec adds. `scan` never rewrites a file to inspect it.
- **R-7** Legacy Stills disposition: `format: stills` resolves to medium `video`,
  `kind: stills`, `dispatchCapability: image`. The picker no longer offers Stills; the
  contact-sheet lens and image capability remain reachable on any applicable production. No
  scene, take, selection, or artifact of a Stills production is moved or renamed.
- **R-8** Display surfaces SHALL render classification through `productionShape` labels, never
  the raw stored token — six client sites currently print `meta.format` verbatim and would
  otherwise leak storage vocabulary into UI and aria-labels.

### Series, Season, Episode, Scene script (R-9 – R-16)

- **R-9** A Series lives at `series/<slug>.json` in the world folder (the guide's sketch is
  confirmed): `{ id, version, title, engine, seasons: [production slug, ordered],
  continuity?: string, created, updated }`. Living inside the world folder IS the world
  reference — no redundant world field. The commit track is `series`, history at
  `.history/series/<slug>/vN.json`, proposal kind `series-edit`. A Series with one season is
  mostly hidden: the Season view shows its engine as a read-only card (turn 48); editing it
  opens the Series authority.
- **R-10** A Season is not a new entity: an episodic production (any `isEpisodic` kind —
  `microdrama` and `series` alike) IS the season, plus `productions/<p>/season.json` —
  `{ version, question?, ending?, direction?, arcs?: [{ id, title, note? }], defaults?:
  { episodeCount, episodeSecondsMin, episodeSecondsMax, hookWindowSec, episodeEnding,
  exportPreset } }`. Top-level `ending` is the season's own authored resolution (prose);
  `defaults.episodeEnding` is the per-episode ending policy (e.g. `cliffhanger`) — two facts,
  two fields. `defaults.exportPreset` is the delivery profile's export default (e.g.
  `social-1080x1920`), completing R-3's field list. Track `season`, history
  `.history/productions/<p>/season/vN.json`, proposal kind `season-edit`. Arc lanes live here;
  a missing payoff is worked out at render, not stored (turn 48). A `kind: series` production
  follows the same creation flow as Microdrama — created with (or attached to) a Series,
  receiving `season.json` with its own step-two numbers; only the default values differ per
  kind, never the mechanism.
- **R-11** Episodes exist only on episodic productions (`isEpisodic` — kinds `microdrama` and
  `series`; Interactive-video release grouping is settled by its brief and MUST be reconciled
  against this section there). One file per episode at `productions/<p>/episodes/<stem>.json`.
  **Identity is the stem and the id; order is a field** — the SPEC-012 D3 rule that chapters
  learned (issue #399) and scenes are learning (issue #387) applies from birth: no ordering
  prefix in the filename is ever required or read, and reordering rewrites `order` only.
  Episodic productions require every scene to belong to exactly one episode; a moment that
  crosses a release boundary is two linked scenes — closing and opening. Non-episodic
  productions have no `episodes/` directory and show no episode surfaces (three tabs, not four
  greyed — turn 48). No universal release-unit abstraction is introduced: the concrete Episode
  is the release unit, and films release as the production itself.
- **R-12** EpisodeSchema: `{ id: ep_[a-z0-9-]+, version, order (int ≥ 1), title, promise:
  { opens, turn, closes }, scenes: [SceneId, ordered], linked?: { closesInto?: EpisodeId,
  opensFrom?: EpisodeId }, release?: § R-15 }`. **The episode's `scenes` array is the single
  membership authority, and within an episode it is the order authority** — scene files carry
  no episode field, so membership can never disagree with itself, and a scene's own explicit
  order (issue #387) is simply not consulted where an episode owns the scene: it governs
  non-episodic productions and the unassigned remainder only. A scene in zero episodes sorts
  after every episode by its own order and is a named finding; a scene in two-plus episodes or a
  `scenes`/`linked` entry naming an unknown scene or episode is likewise named. All membership
  integrity failures use the single kind `continuity-contradiction`; message, subject and evidence
  distinguish the case. Findings never crash. Lifecycle: moving a
  scene between episodes is one proposal touching both episode files atomically (the gate
  already stages multi-target proposals); deleting an episode requires its `scenes` list to be
  empty or the same proposal to rehome every scene — otherwise the deletion refuses by name.
  Track `episode`, history `.history/productions/<p>/episodes/<stem>/vN.json`, proposal kind
  `episode-edit`.
- **R-13** Scene script extends `SceneSchema` — it does not replace it. `script?: { blocks:
  [{ id: blk_[a-z0-9-]+, kind: action | dialogue, speaker? (dialogue only), text }] }`. Block
  IDs are stable across edits and reorders. Shots cite coverage as
  `covers?: [{ blockId, textDigest }]` where `textDigest` is the sha256 of the block text at
  citation time: a digest mismatch derives "covers text that changed", a missing block derives
  "covers nothing" — derived, never stored as status. Splitting a block is an edit plus an
  insert, and the shot keeps pointing at the id it cited. Scene identity, inheritance, board,
  storyboard, drafting provenance, and shots are untouched.
- **R-14** Scene identity/order/path separate per issue #387: a scene's id and file stem are
  stable at creation and independent of display position; explicit scene order governs
  ordinary displays and cuts **on non-episodic productions** — on episodic productions the
  episode arrays govern (R-12) and scene order applies only to the unassigned remainder;
  `deriveSpineCut` stays track/anchor ordered everywhere. Episodes reference scenes by stable
  SceneId only — never by number or reconstructed path. Episode work MUST NOT land before
  #387 does.
- **R-15** Release records belong to the Episode: `release?: { title?, description?,
  thumbnailTakeId?, tags?: string[], recap?, teaser?, crops?: [{ label, aspect }],
  metadata?: record }` — written through episode proposals, consumed by episode-aware export
  (#396). A production-level release record for non-episodic work stays in SPEC-013's export
  surface and is not duplicated here.
- **R-16** Microdrama defaults are editable defaults, never invariants (Scope §10's open
  envelope is resolved as *defaults only*): episodeCount 60, episodeSeconds 45–75,
  hookWindowSec 3, episodeEnding `cliffhanger`, aspect `9:16`, exportPreset
  `social-1080x1920`. The count was 7 until 2026-08-23: the form runs 60–100 drops, and a
  season written to seven is a short film in slices — the offered counts are 8 through 100,
  with the short ones kept because a sample cut to sell a longer run is a real thing to make. Creation writes them into `season.json.defaults` and
  `production.json.aspect`, where every one is a control (turn 53). Season intelligence (Scope §04) is derived, never stored: the
  findings vocabulary is `repeated-hook`, `repetitive-cliffhanger`, `absent-character`,
  `unresolved-promise`, `stalled-arc`, `continuity-contradiction`, `new-entity-budget`,
  `cost-pattern` — each names the affected episode/scene/entity and its evidence; no
  aggregate score exists anywhere.

### Materialisation and conversation (R-17 – R-22)

- **R-17** All new entities stage through ProposalManager as whole files with baseVersion and
  baseHash, and accept through the one Committer. New proposal kinds: `series-edit`,
  `season-edit`, `episode-edit`; `story-overview` (reserved since SPEC-012) becomes real
  (issue #385). New commit tracks `series`, `season`, `episode` version JSON exactly as the
  shipped `scene`/`story` tracks do.
- **R-18** JSON is rebased and conflict-resolved schema-aware, never through `mergeMarkdown`
  (which re-serialises with frontmatter fences and destroys JSON — the art-direction
  restatement branch exists because of this). One generalised JSON three-way merge at
  top-level-field granularity (arrays atomic; `script.blocks` merged per block id) serves
  every JSON track; same-field edits surface as ordinary mine/theirs conflicts. Review
  projection (`fieldsOf`) and in-place field edit gain JSON counterparts per track so a
  reviewer sees every field of a structured proposal — a reviewer MUST NOT be asked to accept
  a story overview, season, or episode they cannot read.
- **R-19** Ripples: story-overview, season, and episode proposals produce named ripples for the
  things drafted against them (scenes drafted against an older overview version; episodes
  whose scene lists reference a moved scene). Chapter/scene targets keep their current no-ripple
  behaviour until a citation index exists for them.
- **R-20** Production-scoped conversation extends #70's shipped implementation — same
  `.conversations/cv_*` store, event log, fold, checkpoint, recovery, wrap-up — with new
  context kinds `production { productionId }`, `episode { productionId, episodeId }`, and
  `scene { productionId, sceneId }`, and new change classifications `development.overview`,
  `development.season`, `development.episode`, `development.scene-script`, and
  `development.series` (a production thread may stage a `series-edit` only for the Series its
  production belongs to). The shipped evidence, check-plan, and readiness machinery extends
  unchanged: each `development.*` classification requires `target-read` (plus `canon-search`
  where it introduces names), receipts are coordinator-owned, and wrap-up readiness applies
  the same settledness and evidence rules to production candidates as to world ones. It is one
  continuous conversation with batched Wrap-up; the superseded per-candidate contract from the
  original #70 issue body is not revived. Talking changes nothing; wrap-up stages proposals;
  acceptance stays in the gate.
- **R-21** Initiative modes Assist / Collaborate / Develop (Scope §04) are conversation
  metadata — persisted per conversation, default Collaborate. Mode changes initiative
  (how eagerly the agent proposes), never acceptance authority. They ship with #400 and appear
  nowhere else in the domain.
- **R-22** Production retrieval must not cross worlds or leak attachment bytes; the
  world-chat confinement rules extend verbatim to production scopes, and the
  CONFINEMENT_PREAMBLE gains wording for JSON targets ("keep the exact file format you were
  given" is already binding; the JSON tracks rely on it plus schema validation at
  materialisation).

### Episode deliverables at the domain boundary (R-24)

- **R-24** An episode's cut is derived from that episode's ordered scenes exactly as the
  production-wide ordinary cut derives from all scenes — same pure derivation, narrowed to the
  episode's `scenes` array; its identity is production + episode id. Per-episode export refuses an
  unknown or empty episode, a scene listed more than once, an unknown scene named by the episode,
  or a scene also owned by another episode. Missing accepted takes remain labelled slates, as in
  the production-wide cut. A spine production refuses episode export until an episode-to-spine
  range authority exists. Implementation, presets, batching, and provenance belong to issue #396;
  this R-number is the domain boundary it builds on.

- **R-23** `world.json.schemaVersion` 2 is the one boundary for everything this spec adds and

# 2 · Design

## 2.1 The architectural decision

Classification is resolved on read, exactly like chapter order (issue #399): the schema stays
permissive, one resolve function owns the mapping, and files upgrade only when something real
is written. The alternative — a bulk rewrite on open — would touch every production.json in
every world for zero user-visible benefit and would put a migration in the read path, where a
crash means a half-migrated world. Resolve-on-read means a legacy world is never wrong, only
un-annotated.

The one place this breaks is strictness: ProductionSchema is `.strict()`, so an old build
shown a new key drops the whole production from the bundle — scenes, takes, chapters and all.
That is why the schema version exists (R-23): the boundary is honest ("update the app") instead
of silent data loss. And it is why new fields land in production.json only when the creator
actually uses a new-model feature (R-1's differs-from-resolve rule) — a plain Video production
created by a new build writes the same keys it always did, and the world stays schema-1,
openable everywhere.

## 2.2 Where each fact lives

| Fact | Owner | Never in |
| --- | --- | --- |
| Medium, kind | `production.json` (`medium`, `kind`; legacy `format` frozen) | client copy, route strings |
| Delivery values | `production.json.aspect`, `season.json.defaults` (incl. `exportPreset`) | a `profile` discriminator |
| Logline, status, styleOverride, musicPolicy, failureModes, timestamps | `production.json`, unchanged (R-6) | any new entity |
| Series engine, season order | `series/<slug>.json` | production.json, world sheets |
| Season question/ending/direction, arcs, defaults | `productions/<p>/season.json` | series.json, episode files |
| Episode promise, scene membership + order, release record | `productions/<p>/episodes/<stem>.json` | scene files (no episode field) |
| Scene script blocks | `scenes/<stem>.json` `script.blocks` | any file above the scene |
| Shot coverage | `shots[].covers` (blockId + textDigest) | derived staleness stored anywhere |
| Recurring cast, world facts | world sheets and canon | Series, Season, Episode |
| Season findings | derived at read | any persisted score or status |
| Conversation state | `.conversations/cv_*` (schema-1 event log) | export, world entities |

## 2.3 Series

Thin means thin: the schema has eight fields and no room for character descriptions — a Series
that describes characters is a second world, which is the drift SPEC-012 D1 exists to prevent.
`seasons` is ordered production slugs; deleting a season production leaves a dangling slug that
surfaces as a named world problem, and deleting a Series with seasons refuses. The Series is
created by the same commit that creates its first season production (turn 47: "Create Series
and open day one" — the double creation is atomic, one commit, two files).

## 2.4 Season and Episode

A season is a production so that everything already built — scenes, takes, selections, spine,
queue, ledger, guests — applies to it without a bridge layer. `season.json` rides beside
`production.json` the way `story.json` already does, and uses the same JSON version/history
machinery the `story` track proved.

Episodes take the chapters lesson from birth (issue #399): stem-stable files, explicit
`order`, no numeric prefixes required, reorder rewrites one field. The episode's ordered
`scenes` array is the only membership authority — a scene never records its episode, so the
"scene claims episode 3, episode 3 disagrees" state is unrepresentable. Cross-boundary moments
are two linked scenes; `linked.closesInto` / `linked.opensFrom` record the pairing for
continuity checks without inventing a shared scene.

## 2.5 Scene script

Blocks are the smallest stable things a shot can cite. The digest-at-citation design makes
staleness a pure derivation: no background process marks shots dirty, no stored flag can lie,
and history stays inside the scene file's ordinary versioning. Coverage renders on the board
(turn 53: the board is where a shot is changed) — "covers text that changed" and "covers
nothing" are words on the shot, never blockers.

## 2.6 The gate grows a JSON lane

The shipped gate is Markdown-fluent and JSON-blind everywhere but the commit: staging,
version-reading, version-stamping, and history already treat `scene`/`story` JSON correctly,
while rebase, conflict resolution, review projection, and field edit do not. This spec
generalises the art-direction restatement into a real JSON lane (issue #385 builds it, the
other entities reuse it): three-way merge at top-level-field granularity, per-block for
`script.blocks`; schema validation at materialisation so a malformed candidate throws before
any proposal directory exists (the world-chat materialise pattern); `fieldsOf` and
`applyFieldEdit` per JSON track so review is field-diffed and editable in place.

## 2.7 Conversation scopes

The production thread is #70's conversation with a production context — same store, same
events, same recovery, same wrap-up. Extending `WorldChatContextSchema` (a strict
discriminated union) means every switch over it fails closed until #400 teaches entry-context,
fold, and the client the three new kinds; that is the intended shape of the work, not a
workaround. Candidates targeting production entities materialise through the same
`buildAndStage` path with the new proposal kinds; world facts surfaced in a production thread
still cross as `worldbuilding` proposals, separately — the guide's fourth gate rule.

## 2.8 Migration table

| On disk today | Resolves as | Rewritten when |
| --- | --- | --- |
| `format: story` | medium `story`, kind `book` | production edited (writes `medium`) |
| `format: video` | medium `video`, kind `film` | production edited |
| `format: stills` | medium `video`, kind `stills`, capability `image` | production edited (keeps `kind: stills`) |
| `medium: interactive-video`, no kind | medium `video`, kind `interactive` | production edited |
| No `season.json` | non-season production | Microdrama creation or season proposal |
| No `episodes/` | non-episodic | episode proposal on an episodic kind |
| Scene without `script` | script-less scene (board still works) | scene proposal adds blocks |
| `world.json.schemaVersion: 1` | legacy world, fully usable | first new-model write or first conversation (→ 2) |

Idempotent by construction: the resolve is pure, the upgrade commit writes the same result
however many times it is retried, and no step depends on a previous partial step.

## 2.9 What this deliberately does not do

No Beat entity. No graph or branch map for linear seasons — explicit order is the only
structural authority for a Video production. No `profile` field. No universal release-unit
abstraction. No stored health score or aggregate percentage anywhere. No second transcript,
second prompt authority, or second reference order (those stay with #70, #252, #245). No
separate Interactive medium — its branching behavior is a Video kind.

## 3.4 Decision log

| # | Decision | Why |
| --- | --- | --- |
| D1 | Resolve classification on read; upgrade files only on write | A read path must never lose entities (SPEC-002 R-2); bulk rewrites put migration where crashes hurt most |
| D2 | Keep legacy `format` written and frozen | The strict schema means old builds drop unknown keys; a value they understand plus the schema-version fence is honest twice over |
| D3 | `kind` free on read, closed in the dialog | Unknown kinds must not delete productions; the picker is where vocabulary is enforced |
| D3a | Interactive is a Video kind, not a third medium | It produces moving pictures and reuses Video's scenes, shots, takes and cut; branching is kind-level behavior. The old medium token remains readable for compatibility. |
| D4 | Delivery profile evaporates into concrete fields | Turn 47: profile is defaults; a stored discriminator would be a second entity by the back door |
| D5 | Series at `series/<slug>.json`, world-scoped | The guide's sketch, confirmed; location inside the world folder is the world reference |
| D6 | Season is a production + `season.json` | Everything built for productions applies free; the `story` track already proved sidecar JSON versioning |
| D7 | Episode's `scenes` array is the one membership authority | Two records of membership can disagree; one cannot |
| D8 | Episode files stem-stable with `order` field from birth | Chapters (issue #399) and scenes (issue #387) both had to be repaired; new entities start repaired |
| D9 | Coverage digests at citation time, staleness derived | A stored staleness flag can lie; a derivation cannot |
| D10 | One schemaVersion bump (2) covers conversations and the new domain | Two fences for one boundary would double the refusal matrix; #403 ships it once |
| D11 | Microdrama numbers are editable defaults | Scope §10 keeps the envelope open; the design binds defaults, and a default must look like a control (turn 53) |
| D12 | Season findings derived, never persisted | Stored intelligence goes stale silently; named findings recompute from what is true now |
