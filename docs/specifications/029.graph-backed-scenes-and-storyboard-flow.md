# 1 · Requirements

## 1.1 Summary

Arke currently represents a Scene as one versioned document whose `shots[]` array owns both
shot content and playback order. That is sufficient for a linear strip, but it makes structure
implicit: Storyboard can only render the array, generation can only walk it, and a second Flow
view would either reconstruct the same path every time or become a competing authority.

This specification makes a Scene's internal flow a bounded, typed, canonical node graph. In
version 1 that graph is deliberately linear: one Entry, ordered Shot nodes, one Exit, and one
unambiguous path through every Shot exactly once. The graph is foundational without pretending
Arke is a game engine. There are no intra-scene choices, variables, conditions, inventories,
provider nodes, prompt nodes, or executable user code.

The same canonical graph has two first-class views:

1. **Storyboard** is the readable vertical view: persistent scene navigation, shot writing,
   frames, status, review, and one `Generate storyboard` action.
2. **Flow** is the structural view of the selected Scene: typed nodes, ports, sequence edges,
   and authored storyboard groups, with the same selection and docked Arke.

Rendering compiles that one graph into different outputs without changing it: one image per
Shot, one sheet per authored storyboard group (or ungrouped run), and model-dependent packed
video passes. Provider limits may subdivide an authored group in a dispatch plan; they never
rewrite the group or become narrative authority.

This is a world-schema-3 change. A written graph Scene carries `flow` and no `shots[]`. Legacy
Scenes remain readable and resolve to a deterministic path without a write; the first authored
write to that Scene materialises the graph and raises the world boundary atomically. Older
builds refuse schema-3 worlds before scanning strict Scene records.

Tracking programme: [GitHub issue #479](https://github.com/michaeljosiah/ArkeStudio/issues/479).

## 1.2 Bound decisions

1. **The graph is canonical, not a UI projection.** A graph-backed Scene has no parallel
   `shots[]` order. Every consumer linearises through one contracts function.
2. **V1 is linear by validation.** The data shape is extensible; the accepted shape is not.
   Future node or edge kinds require their own specification and schema boundary.
3. **Storyboard and Flow are two views of one selected Scene.** They share selection, history,
   mutation commands, findings, and Arke's subject.
4. **Storyboard groups are authored structure.** They have stable IDs and names, group
   contiguous Shot nodes, and may guide rendering. They do not change playback order.
   *Superseded by SPEC-035 (2026-08-29): grouping is now derived board packing, with authored
   splits/merges as the only authored input. See the note at §1.9.*
5. **Interactive routing stays scene-to-scene.** `routing.json` remains the sole audience-choice
   authority; production edges cannot target a Shot, and Scene-flow edges cannot leave a Scene.
6. **Narrative and execution graphs remain separate.** Dispatch-plan dependencies, boundary
   frames, take continuation, ComfyUI workflows, and queue jobs never become Scene nodes.
7. **Most creators need not use a canvas.** Storyboard is the default view, the narrow/list
   representation is complete, and every pointer graph operation has a semantic control.

## 1.3 Scope

**In scope:** the canonical Scene-flow schema; node, port, edge, and storyboard-group identity;
strict linear invariants; schema-3 compatibility and lazy per-Scene migration; one linearisation
authority; mutation, version, proposal, history, deletion, and conflict semantics; Storyboard
and Flow views; scene navigation; shot-for-shot and grouped storyboard rendering; integration
with boards, generation planning, takes, continuity, cuts, episodes, and Interactive video;
accessibility, scale, failures, and tests.

**Out of scope:** intra-scene branching; choice, merge, condition, state, inventory, variable,
relationship, unlock, gameplay, or code nodes; arbitrary media-processing graphs; manual graph
layout as authored content; graph interchange; reusable subgraphs; one Shot shared by Scenes;
cross-Scene Shot edges; route-specific takes or boundary frames; an Interactive Episode model;
multi-user graph merging; graph-based Cut editing; provider workflow editing; automatic repair
of malformed graphs.

## 1.4 Acceptance criteria

### Authority and compatibility

- [ ] A schema-3 Scene has exactly one internal-structure authority: `flow`; it cannot also
  carry `shots[]` (**R-1..R-8**).
- [ ] Legacy Scenes resolve without being rewritten; the first authored Scene write migrates
  deterministically and raises the world boundary in the same commit (**R-9..R-15**).
- [ ] Every current Scene consumer obtains ordered Shots through the one linearisation API;
  no independent traversal or fallback array survives (**R-16..R-20**).

### Authoring and views

- [ ] Storyboard and Flow edit the same graph, retain the same selected Scene and Shot, and
  produce one Scene history track (**R-21..R-29**).
- [ ] Authored storyboard groups have stable identity, contiguous membership, explicit
  lifecycle, and no ability to disagree with graph order (**R-30..R-35**).
- [ ] Human edits save directly; Arke/import edits stage complete candidate Scenes and appear
  in place under `Apply changes` / `Keep discussing` (**R-36..R-39**).

### Rendering and downstream behavior

- [ ] The same graph compiles shot-for-shot images, grouped storyboard sheets, per-shot video,
  or packed passes without provider constraints becoming authored structure (**R-40..R-48**).
- [ ] Takes, selections, boards, continuity, Cut, Episode order, spine timing, and Interactive
  routing retain one named authority each (**R-49..R-57**).

### Safety and usability

- [ ] Malformed graphs are named and preserve access to the rest of the world; no consumer
  invents a path through invalid data (**R-58..R-62**).
- [ ] Every graph operation is keyboard-complete and available in a narrow semantic list;
  status is never colour-only (**R-63..R-67**).
- [ ] Projection, validation, and layout meet the scale budgets in **R-68..R-70**.

## 1.5 Canonical Scene flow (R-1 – R-8)

- **R-1** `SceneSchema` SHALL become a read union of exactly two strict shapes:
  `LegacyScene` carrying required `shots: Shot[]` and no `flow`, and `GraphScene` carrying
  required `flow: SceneFlow` and no `shots`. Every other Scene field keeps its current identity,
  owner, optionality, and meaning. A file carrying both or neither structural field fails
  parse with the conflicting/missing keys named.
- **R-2** `SceneFlow` SHALL be:

  ```ts
  interface SceneFlow {
    schemaVersion: 1;
    entryNodeId: SceneFlowNodeId;
    exitNodeId: SceneFlowNodeId;
    nodes: SceneFlowNode[];
    edges: SceneFlowEdge[];
    storyboardGroups: StoryboardGroup[];
  }
  ```

  `SceneFlowNodeId` uses `sfn_<lowercase-token>`, `SceneFlowEdgeId` uses
  `sfe_<lowercase-token>`, and `StoryboardGroupId` uses `sbg_<lowercase-token>`. IDs are stable
  across labels, reorder, layout, and grouping.
- **R-3** V1 node kinds SHALL be `entry`, `shot`, and `exit`:

  ```ts
  type SceneFlowNode =
    | { id: SceneFlowNodeId; kind: "entry" }
    | { id: SceneFlowNodeId; kind: "shot"; shot: Shot }
    | { id: SceneFlowNodeId; kind: "exit" };
  ```

  Entry and Exit contain no Shot payload. A Shot remains one authored record with the existing
  `ShotSchema`; takes and selections remain outside it.
- **R-4** Ports are typed by node kind and SHALL NOT be repeated as mutable arrays on disk:
  Entry exposes `out`; Shot exposes `in` and `out`; Exit exposes `in`. A sequence edge stores
  endpoints as `{ nodeId, port }`, and strict validation rejects a missing or incompatible port.
  A future node kind must define its ports in contracts before a Scene carrying it may parse.
- **R-5** V1 edges SHALL be only:

  ```ts
  interface SceneFlowEdge {
    id: SceneFlowEdgeId;
    kind: "sequence";
    from: { nodeId: SceneFlowNodeId; port: "out" };
    to: { nodeId: SceneFlowNodeId; port: "in" };
  }
  ```

  Edge IDs survive reorder/retarget where the semantic connection survives; inserting a node
  replaces one connection with two newly identified connections and histories that replacement.
- **R-6** One graph-backed Scene SHALL have exactly one Entry and one Exit; the IDs SHALL equal
  `entryNodeId` and `exitNodeId`; Entry has zero incoming and exactly one outgoing edge when a
  Shot exists, otherwise one edge directly to Exit; Exit has exactly one incoming and zero
  outgoing; each Shot has exactly one incoming and one outgoing; every node is reachable from
  Entry and reaches Exit; traversing `out` visits every Shot exactly once. Cycles, branches,
  reconvergence, disconnected nodes, duplicate IDs, self-edges, and parallel sequence edges
  fail graph validation.
- **R-7** `linearizeSceneFlow(scene)` SHALL be the sole ordered-Shot API. For a valid GraphScene
  it follows Entry to Exit and returns referenced Shot payloads. For a LegacyScene it returns a
  non-mutating copy of `shots[]`. It SHALL return an explicit invalid result with named findings
  rather than partially linearising a malformed graph.
- **R-8** No derived property is stored: first/last, ordinal, incoming/outgoing counts,
  reachability, group span, storyboard freshness, accepted-take state, generation readiness,
  and layout coordinates are recomputed. A Scene version remains the version of the whole
  authored aggregate, including graph, Shots, script, defaults, and authored groups.

## 1.6 Compatibility and migration (R-9 – R-15)

- **R-9** `world.json.schemaVersion` 3 SHALL fence GraphScenes. This build raises
  `SUPPORTED_SCHEMA_VERSION` to 3. Builds supporting at most 2 refuse a schema-3 world before
  scanning strict Scene files and leave it unmodified.
- **R-10** Opening, scanning, rendering Storyboard/Flow, compiling a board, estimating, or
  exporting a legacy Scene SHALL NOT migrate it or raise the world. Read is pure.
- **R-11** The first authored operation that writes a LegacyScene — direct human edit,
  accepted proposal, reorder, group edit, or new Shot operation — SHALL materialise one
  GraphScene and raise the world to 3 in the same atomic commit. A new Scene created by a
  schema-3-capable build is born graph-backed and raises the boundary when accepted.
- **R-12** Legacy migration SHALL preserve every Shot payload and Shot ID byte-for-field, in
  existing array order. It mints deterministic node IDs from the Scene and Shot IDs, one Entry,
  one Exit, deterministic sequence edge IDs from adjacent endpoint IDs, and
  `storyboardGroups: []`. Repeating migration produces byte-identical `flow` content.
- **R-13** Migration SHALL snapshot the replaced legacy Scene through the ordinary Scene history
  track before writing the GraphScene. Scene ID, number, order, slug, version progression,
  actual file stem, script, board/storyboard records, drafting provenance, takes, reviews,
  selections, artifacts, plans, proposal bases, and citation joins are not renamed or moved.
- **R-14** A schema-3 world MAY contain untouched LegacyScenes and GraphScenes together. New
  builds read both; every newly written Scene is a GraphScene. This is a lazy entity migration,
  not dual authority: no individual Scene may carry both representations.
- **R-15** Restoring a schema-2 legacy Scene snapshot inside a schema-3 world SHALL restore its
  authored content as a new GraphScene version by passing the snapshot through the same
  deterministic migration. Restore never lowers `world.json.schemaVersion`.

## 1.7 One ordered-Shot boundary (R-16 – R-20)

- **R-16** Contracts SHALL expose one `SceneSequence` result containing ordered `{nodeId,
  shot}` pairs plus Entry/Exit and graph findings. Every consumer named in R-17 SHALL receive
  this result or call the same pure function; consumers SHALL NOT inspect `scene.shots`, scan
  node arrays by storage order, or implement graph traversal.
- **R-17** The mandatory consumer sweep includes: Storyboard UI, shot sheet predecessor/next,
  script coverage and Scene findings, prompt assembly, storyboard planning, board compilation,
  per-shot and packed planning, pass compilation, selection continuity, take review, Cut and
  Episode Cut derivation, spine validation, citation/index projection, deletion blockers,
  Interactive preview/export, exports, conversation context, and proposal review.
- **R-18** Node storage order is not playback order. Reordering JSON node or edge arrays without
  changing endpoints produces the same sequence, board, plan, and Cut.
- **R-19** The Scene sequence owns order only inside the Scene. Non-episodic Scene order remains
  `Scene.order`; episodic membership/order remains `Episode.scenes[]`; music-video playback
  remains `spine.json`; audience branching remains `routing.json`.
- **R-20** SPEC-023's statement that linear episodic seasons are “never graph authority” is
  amended narrowly: season and Episode structure remain ordered boards/arrays, while each
  Scene's internal Shot structure is graph authority. No production-wide linear graph is added
  by this specification.

## 1.8 Storyboard and Flow (R-21 – R-29)

- **R-21** Every Video Scene SHALL open in one authoring shell with: a persistent scene index
  on the left; `Storyboard | Flow` views in the centre; docked Arke on the right; and the
  current production/episode/Scene context in AppChrome. Storyboard is the default.
- **R-22** The scene index SHALL show title, stable Scene number, Shot count, storyboard
  coverage, accepted-take coverage, and a textual finding mark. It switches Scenes without
  returning to the Episode page. Episodic order follows `Episode.scenes[]`; non-episodic order
  follows `sortScenes`; unassigned episodic Scenes are named separately.
- **R-23** Storyboard SHALL render the selected Scene's linearised Shots vertically. Each Shot
  row is the existing rich authoring object: frame, script/description, dialogue/action,
  duration, references, derived status, group name, and `Advanced`. Writing edits the Shot
  node's payload; insertion, duplicate, move, and delete are semantic graph operations.
- **R-24** Flow SHALL render Entry, Shot, and Exit nodes, compatible ports, sequence edges, and
  authored group containers for the same selected Scene. It SHALL NOT display provider,
  generation-job, take, artifact, prompt, or audience-choice nodes.
- **R-25** Selection is shared: a Shot selected in Storyboard focuses the same node in Flow;
  a node selected in Flow switches/scrolls Storyboard to the Shot; Arke's subject follows the
  Scene, Shot, edge, or group; switching views preserves selection and scroll/focus target.
- **R-26** Storyboard reorder and Flow reconnect SHALL call semantic operations against the
  loaded Scene version. Flow does not expose an arbitrary “save graph JSON” command. In v1,
  reconnecting may only produce another valid linear path containing every Shot once.
- **R-27** `Review scene` and generation remain on the Scene, per turn 102. Findings attach to
  the affected Shot, edge, or group in both views. `Generate storyboard` opens a drawer over
  the Scene; `Generate scene` remains the video-take action. Neither navigates to a plan page.
- **R-28** The shell SHALL collapse gracefully: Arke can be put away; the scene index can fold
  to a Scene picker; below 900px Flow becomes the semantic vertical sequence with explicit
  “goes to” rows. The canvas is never required to complete an operation.
- **R-29** An empty Scene shows Entry connected to Exit and offers `Add first shot` and
  `Talk to Arke`. An invalid Scene shows its recoverable authored nodes in a read-only list,
  names why no sequence can be trusted, and offers history/restore; it never invents edges.

## 1.9 Storyboard groups (R-30 – R-35)

> **Superseded by SPEC-035 (2026-08-29).** Grouping is derived, not authored: boards are packed
> live from the clip cap and continuity breaks, and the authored residue is two override sets
> (`splits`, `merges`) keyed by shot id. `StoryboardGroup` remains in the schema for parse
> compatibility and is written by nothing. R-30–R-35 below stand as history; the group
> lifecycle of R-33 is replaced by SPEC-035 R-4/R-5's overrides, R-34's staging rule carries
> over to those overrides unchanged, and R-35's versioning rule applies to writes of `splits`
> and `merges`. R-42/R-43's "authored group" reads as "derived board"; R-43's principle —
> a provider limit is execution policy, not authorship — survives intact and is the reason
> for the supersession.

- **R-30** A `StoryboardGroup` SHALL be `{ id, title, shotNodeIds }`. IDs are stable; title is
  authored; members reference Shot node IDs, never Shot numbers or array positions.
- **R-31** A group SHALL contain one or more Shot nodes forming one contiguous run in the
  canonical linearisation. A Shot may belong to at most one group. Group order is derived from
  the first member. Overlap, duplicate membership, missing nodes, non-Shot nodes, and
  non-contiguous membership fail graph validation.
- **R-32** Groups do not create ports, edges, nesting, playback behavior, or Cut sections. They
  describe authored visual/storyboard beats only. Ungrouped Shots are valid and consecutive
  ungrouped Shots form a derived render run when grouped rendering is requested.
- **R-33** Group lifecycle operations SHALL be: create from a contiguous selection; rename;
  add/remove adjacent boundary Shots; split; merge adjacent groups; and dissolve. Moving a
  Shot across a group boundary requires a visible decision to move the boundary, remove the
  Shot from the group, or refuse; no operation silently makes membership non-contiguous.
- **R-34** Arke may propose group names and boundaries, but those changes remain visibly staged
  in Storyboard and Flow until applied. Provider/model limits SHALL NOT author or rename groups.
- **R-35** Group changes advance the Scene version, stale generated storyboards and unstarted
  dispatch plans under existing source-version rules, and appear in Scene history. They do not
  invalidate accepted takes merely because grouping changed.

## 1.10 Mutations, proposals, deletion, and history (R-36 – R-39)

- **R-36** Direct human edits save immediately through version-aware semantic commands. At
  minimum: insert Shot on edge; move Shot before/after another Shot; duplicate Shot; edit Shot;
  delete Shot; and every R-33 group operation. Each command carries `sceneId` and expected
  Scene version and commits one complete validated GraphScene.
  - *Amended 2026-08-30 by §1.9's supersession:* R-33's group operations are replaced by the
    four board-override commands — set/clear a `split`, set/clear a `merge` — keyed by shot id
    and version-aware like every other command. Setting one clears the other for that shot:
    they are opposite answers to the same question, and holding both would make the packer's
    walk depend on which list it read first.
  - **A position is never an argument.** A command names the shot it moves and the shot it
    moves relative to, never an index: an edit composed against one order and applied to
    another is exactly the merge-by-position failure R-62 forbids, and an anchor by id simply
    means the same thing after somebody else inserts a shot above it.
- **R-37** Arke, conversation Wrap-up, and imports stage a complete candidate GraphScene through
  the existing `scene-edit` proposal track. Additive nodes/edges/groups appear in their final
  place but are not openable, dispatchable, counted complete, or renderable until accepted.
  Surface copy is `Apply changes` / `Keep discussing`; a structural before/after appears only
  for destructive replacement or deletion.
- **R-38** Scene history remains whole-document history. A graph diff may project added,
  removed, moved, retargeted, and regrouped stable IDs, but no parallel graph-history file or
  edge journal exists. Restore writes a new validated GraphScene version.
- **R-39** Shot deletion SHALL name and refuse every live dependency that would become
  unexplainable: accepted selection, spine anchor, active/nonterminal dispatch plan, current
  storyboard panel, or other persisted current reference. When allowed, deletion removes its
  selection in the same commit and updates/dissolves affected group membership explicitly.
  Immutable takes, ledger entries, completed plans, reviews, and history remain as provenance
  and retain the deleted Shot ID; UI labels them `shot deleted from scene`, never orphaned
  unknown media.

## 1.11 Rendering and generation (R-40 – R-48)

- **R-40** `Generate storyboard` SHALL show one recommended scope and one price. Above the fold
  it names what is missing/stale, e.g. `8 frames · attempt one`; existing current accepted
  frames are excluded unless the creator explicitly includes regeneration.
- **R-41** Shot-for-shot image rendering SHALL compile one immutable job per included Shot node.
  Every result lands as a Shot-addressed take/result with the node and Shot IDs in provenance.
  Failure and retry scope is one Shot.
- **R-42** Grouped storyboard rendering SHALL compile one sheet per authored group and one sheet
  per contiguous ungrouped run, subject to a visible panel cap. Each request freezes ordered
  `{panel, nodeId, shotId}` mappings, source Scene version, group ID where present, aspect,
  prompt/reference sources, model, estimate, and job ID.
- **R-43** A model cap may subdivide one authored group into several request sheets. The plan
  names `Group “The approach” · sheets 1–2`; it never rewrites the group. A provider limit is
  execution policy, not authorship.
- **R-44** A generated multi-panel sheet is one immutable parent result. Its panels SHALL NOT
  silently become accepted Shot frames. If panel extraction is implemented, each crop is a
  child image take with deterministic crop geometry, hash, parent job/result, panel mapping,
  independent review, and no loss of the source sheet.
- **R-45** The locally compiled review board remains a free derived projection of current Shot
  frames. It uses canonical graph order and may arrange panels into pages/groups, but it is not
  the generated reference storyboard and never rides to a model as one.
- **R-46** Per-shot video planning and packed whole-Scene planning SHALL consume
  `SceneSequence`. Packed passes may group only contiguous Shot nodes and freeze their node/Shot
  IDs and temporal boundaries. Packing decisions live in `CompiledPass`/`DispatchPlan`, never
  `SceneFlow` or `StoryboardGroup`.
- **R-47** An authored group MAY be offered as a preferred packed-pass boundary, but route
  duration/reference limits may subdivide it and the Director may recommend a different
  execution strategy. The drawer states authored grouping and actual retry units separately.
- **R-48** SPEC-024's dependency DAG remains an ordered execution plan with lower-index
  dependencies. It does not reuse Scene-flow nodes or edges, and Scene-flow edits stale an
  unmaterialised plan through the existing Scene-version check.

## 1.12 Existing production authorities (R-49 – R-57)

- **R-49** Takes remain immutable and keyed to Shot IDs; reviews remain append-only;
  `selections.json` remains current operational choice. Graph nodes display those facts by
  join and store none of them.
- **R-50** Cut derivation follows `SceneSequence` inside each Scene. Gaps remain explicit.
  Episode Cuts follow `Episode.scenes[]`; non-episodic cuts follow `Scene.order`; spine cuts
  follow anchors. The graph does not add another production-wide order.
- **R-51** Storyboard freshness remains source-version based. A reordered or regrouped Scene
  advances version and stales its generated reference storyboard. A review board records the
  source graph/Scene version and panel mapping.
- **R-52** Script coverage stays on Shot payloads by stable block ID and digest. Moving a Shot
  node changes no citation; deleting it preserves citations in history only.
- **R-53** `continuity.openOnPrevious` refers to the previous Shot in canonical linearisation.
  Boundary-frame selection/artifacts remain operational annotations. Sequence edges may display
  continuity state but do not own it.
- **R-54** Automatic next-Shot continuity SHALL use the canonical sequence and SHALL stop at
  the Scene Exit. Cross-Scene continuity requires the authority of the owning production order
  and, for Interactive routes, remains a warning rather than choosing one predecessor silently.
- **R-55** `routing.json` remains the only Interactive audience graph. Its nodes are Scenes and
  its edges are direct choices `{id, from, label, to}`. Production routing cannot target a
  Scene-flow node; Scene-flow edges cannot target another Scene.
- **R-56** Interactive preview and export render the selected Scene deliverable and then follow
  `routing.json`. Internal graph order determines that Scene's cut/render; it does not expose
  intra-scene choices. Reconvergence remains a Scene-level continuity review point.
- **R-57** Episode membership, routing groups, storyboard groups, Cut sections, and dispatch
  passes are distinct named structures. No generic `group` abstraction or untyped node metadata
  may collapse their different ownership and lifecycle.

## 1.13 Validation and recovery (R-58 – R-62)

- **R-58** Parse validation SHALL enforce strict known shapes and ID syntax. Referential graph
  validation SHALL name duplicate/missing nodes and edges, incompatible ports, dangling group
  members, duplicate group membership, and Entry/Exit mismatches. Semantic validation SHALL
  name cycles, branches, reconvergence, disconnected nodes, unreachable Exit, skipped Shots,
  and non-contiguous groups.
- **R-59** Validation findings SHALL include stable IDs and enough evidence to locate the
  problem. There is no graph health percentage or aggregate score. A valid result is
  `linear`; any invalid result refuses mutation, planning, generation, Cut derivation, and
  final export by name rather than guessing.
- **R-60** Scan SHALL continue collecting per-file problems. One malformed Scene does not hide
  other Scenes or the world. The Scene index shows the malformed file and history/restore
  route; Storyboard/Flow expose recoverable parsed identity only when safe.
- **R-61** Semantic commands SHALL construct the candidate, validate it completely, and only
  then commit. A refused operation writes no Scene version, group, selection cleanup, schema
  raise, plan, job, or spend.
- **R-62** External edits follow the existing closed-world reconciliation and stale-base rules.
  If a valid externally edited graph changes while the UI is open, the next semantic command
  refuses against the moved Scene version; it never merges edges by array position.

## 1.14 Accessibility and narrow behavior (R-63 – R-67)

- **R-63** Storyboard uses semantic headings/lists; Flow uses one roving map/listbox focus stop.
  Nodes announce kind, Shot title/number, group, incoming/outgoing count, status, and findings.
  Edges are keyboard reachable and announce source and destination.
- **R-64** Arrow keys move in canonical sequence; Home/End go to Entry/Exit; Enter opens a Shot;
  Space selects; Delete opens the same named blocker/confirmation as pointer deletion. Focus
  moves predictably to the inserted node or surviving neighbour after mutation.
- **R-65** Every drag has controls: move before/after, insert here, connect after, add/remove
  group boundary, rename, and dissolve. Ports may accelerate pointer use but are not the only
  path.
- **R-66** Below 900px Flow renders one vertical sequence with `goes to` rows and group
  boundaries; the scene index becomes a picker; Arke is a dismissible panel. There is no
  page-level horizontal scroll.
- **R-67** Entry, Exit, selected, staged, stale, blocked, group, and continuity states use text
  or shape in addition to colour. Reduced motion disables animated edge/layout transitions.

## 1.15 Performance (R-68 – R-70)

- **R-68** Validation and linearisation SHALL be `O(nodes + edges + group members)` and pure.
  Results may memoize by Scene identity/version but no cache becomes world data.
- **R-69** The supported product envelope SHALL include one Scene with 200 Shot nodes, rendered
  in Storyboard and Flow inside the warm interaction budget. Storyboard virtualises rows where
  needed; Flow may reduce thumbnails but not identity or keyboard access.
- **R-70** Tests SHALL cover 100 Scenes in a production, a 200-Shot Scene, and an Interactive
  route of 500 Scenes/1,000 choices without mixing the two graph scopes. Larger structures may
  fall back to semantic lists but must remain authorable and export-refusable by named findings.

## 1.16 Open questions held outside v1

- Whether a later Scene graph may contain a Choice node. It requires path-specific boards,
  generation, cuts, continuity, and takes and therefore cannot be enabled by widening an enum.
- Whether manual canvas coordinates become authored presentation. V1 uses deterministic layout
  and local ephemeral pan/zoom only.
- Whether a group-level generated sheet can be deterministically segmented across all supported
  model compositions. V1 preserves parent sheets and requires explicit child-take review if
  extraction is added.
- Whether a season-wide review cut concatenates Episode authorities. This specification does
  not change the current Episode/production-wide Cut disagreement; it must be settled separately.

# 2 · Design

## 2.1 Architectural decision

The graph is a bounded domain model, not a generic canvas. Persisting it now separates Shot
identity from sequence topology and gives future node kinds a strict extension seam, while V1's
validation preserves every linear assumption currently relied upon by generation and finishing.

Keeping `shots[]` beside graph edges was rejected. Dual write makes a Scene capable of saying
both `A → B` and `[B, A]`; every consumer then chooses an authority and history cannot explain
which one the creator changed. A graph-backed Scene therefore removes `shots[]` entirely.

A derived-only graph was also rejected for this specification. It would improve orientation but
could not make stable edges, typed ports, authored grouping, or future structural widening part
of the work. The schema-3 fence makes the stronger decision honest to old builds.

## 2.2 Source-of-truth map

| Fact | Sole authority | Flow treatment | Never stored in Scene flow |
| --- | --- | --- | --- |
| Shot payload | Shot node in Scene `flow.nodes` | Node content/detail | take/selection state |
| Shot sequence | `flow.edges` from Entry to Exit | Graph + Storyboard order | array position/ordinal |
| Storyboard beat/group | `flow.storyboardGroups` | Container/header | provider pass |
| Scene script/defaults/provenance | Scene fields | Context/annotations | duplicated node metadata |
| Scene order | `Scene.order` or `Episode.scenes[]` | Left scene index | Scene-flow edge |
| Audience choices | `routing.json` | Separate Branch map | Shot/sequence edge |
| Current take | `selections.json` | Node annotation | Shot node |
| Take media/provenance | immutable `take.json` | Linked detail | node payload |
| Review board | derived/local board record | Scene annotation | group authority |
| Generated storyboard | accepted output + panel map | Group/Scene annotation | sequence authority |
| Cut | pure derivation over selections/order | Never edited in Flow | edge metadata |
| Spine timing | `spine.json` | Separate timeline | sequence edge |
| Boundary frame | selection + artifact | Edge/Shot annotation | edge payload |
| Provider grouping | CompiledPass/DispatchPlan | Generation options | storyboard group |
| Findings/readiness | pure derivation | Overlay/text | status field |
| Canvas position | deterministic/ephemeral client state | Layout only | world folder |

## 2.4 Semantic mutation examples

### Insert a Shot after Shot 14

1. Resolve and validate Scene version 8.
2. Find Shot 14's outgoing edge to Shot 15.
3. Mint the Shot, node, and two edge IDs coordinator-side.
4. Remove the old edge and add `14 → new → 15`.
5. If Shot 14 and 15 share a group, ask whether the inserted Shot joins it; direct insertion
   from within that group defaults visibly to joining it.
6. Validate the full candidate and commit Scene version 9.

### Move Shot 15 before Shot 14

The command names moving and target node IDs, not edge indices. The coordinator rewires the
affected predecessor/successor edges, preserves Shot/node IDs, updates group membership only
under the chosen R-33 outcome, validates, and commits once.

### Delete Shot 14

The coordinator derives blockers first. If allowed, it joins predecessor to successor, removes
the node and incident edges, removes the current selection transactionally, resolves group
membership, validates, and commits. Immutable paid records remain explainable by Shot ID.

## 2.5 UI contract — design turn 103

At 1360×850 the authoring shell is three columns:

```text
scene index (196–220) | Storyboard or Flow (fluid) | Arke (340–360)
```

Storyboard reads downward. It is not a compact inspector: each Shot row still carries enough
of turn 97's card to write and direct the Shot, while cinematic/provider detail stays behind
`Advanced`. The single image action says what it does: `Generate storyboard`, not `Generate
scene`; video generation remains the later takes action.

Flow lays out the selected Scene top-to-bottom or left-to-right deterministically. Entry/Exit
are small terminals; Shot nodes carry thumbnail, number/title, duration, derived state, and
group. Selecting a group exposes rename/split/dissolve and render scope. The view is structural,
not technical: exact JSON, provenance, model limits, and dispatch strategy stay in Advanced.

The persistent scene index is adopted for this dense workspace despite turn 97's folded rail.
It is a contextual index inside the Scene workspace, not a replacement production tree across
all screens. The existing 44px production rail may remain folded outside the three columns.

| --- | --- | --- | --- |

## 2.7 Failure and refusal vocabulary

| Condition | Surface wording / behavior |
| --- | --- |
| Cycle | `Shot 15 leads back to Shot 12. A scene needs one forward path.` |
| Branch | `Shot 15 has two next shots. Choices belong between scenes.` |
| Disconnected node | `Shot 18 is not connected between Scene start and end.` |
| Missing node | `Connection sfe_… points to a shot node that is missing.` |
| Invalid port | `Shot 15's output is connected to a port this node does not have.` |
| Non-contiguous group | `“The approach” skips Shot 15. A storyboard group must stay together.` |
| Delete blocked | Names accepted take, active plan, spine anchor, or current board panel |
| Stale save | `This scene changed since you opened it. Reload before changing its flow.` |
| Legacy read | No warning; it behaves normally until first write |
| Migration failure | Original Scene remains live; no schema raise or partial file |
| Invalid graph | Read-only recovery/history; no generation, Cut, or export guess |

## 2.8 What this deliberately does not do

This specification does not expose a general visual-programming engine. It does not make the
provider graph, prompt graph, dependency DAG, take chain, audio graph, or Interactive routing a
Scene-flow node type. It does not enable Shot-level audience choices by writing a dormant enum
value. It does not persist canvas coordinates. It does not put Storyboard groups into the Cut.
It does not make a generated multi-panel image authoritative over its Shots.

## 3.2 Adversarial test matrix

- [ ] **T-1 — strict shapes:** GraphScene parses; legacy parses; both/neither structural fields
  refuse; unknown node/edge keys refuse.
- [ ] **T-2 — graph invariants:** each cycle, branch, reconvergence, self-edge, parallel edge,
  dangling endpoint, incompatible port, disconnected node, duplicate ID, skipped Shot, and
  wrong Entry/Exit produces its named finding.
- [ ] **T-3 — storage order independence:** permuting `nodes[]` and `edges[]` bytes leaves
  linearisation, board, plan, and Cut order identical.
- [ ] **T-4 — legacy parity:** every existing Scene fixture linearises exactly as its old
  `shots[]`; no read writes or raises schema.
- [ ] **T-5 — migration:** first edit writes one GraphScene and schema 3 atomically, snapshots
  legacy history, preserves every Shot field and external join, and repeated migration is
  byte-stable.
- [ ] **T-6 — old build:** a build pinned to schema 2 refuses a schema-3 world before scanning
  Scenes and leaves all bytes unchanged.
- [ ] **T-7 — mixed world:** schema-3 world with legacy and graph Scenes opens; editing one does
  not rewrite the others.
- [ ] **T-8 — restore:** restoring a legacy snapshot in schema 3 creates a new valid GraphScene
  version and never lowers the boundary.
- [ ] **T-9 — insert/move/duplicate:** semantic operations preserve node/Shot identity as
  specified, create valid edges, and refuse stale expected versions.
- [ ] **T-10 — groups:** overlap, duplicate/noncontiguous/missing members refuse; create,
  rename, split, merge, boundary edit, and dissolve preserve one canonical order.
- [ ] **T-11 — deletion:** each accepted-selection/spine/active-plan/current-panel blocker is
  named; allowed delete cleans selection atomically and leaves immutable history explainable.
- [ ] **T-12 — proposals:** an Arke-created node/group is visible in place but cannot be opened,
  generated, counted, or exported before `Apply changes`; `Keep discussing` preserves it.
- [ ] **T-13 — consumer parity:** legacy and migrated forms produce equivalent prompts,
  reference order, storyboard panel order, pass boundaries, Cut entries, and Interactive Scene
  media for the same Shots.
- [ ] **T-14 — shot-for-shot rendering:** only missing/stale selected scope dispatches, one job
  per Shot, exact price and retry unit, no accepted frame overwritten.
- [ ] **T-15 — grouped rendering:** authored group maps freeze panel/node/Shot identity; model
  cap subdivision does not mutate group; parent sheet remains immutable.
- [ ] **T-16 — packed video:** only contiguous canonical nodes enter a pass; plan source Scene
  version stales after flow/group edit; dependency DAG remains separate.
- [ ] **T-17 — continuity:** previous/next follows graph, stops at Scene boundary, and never
  selects an Interactive predecessor at reconvergence.
- [ ] **T-18 — UI synchronization:** Storyboard and Flow preserve selected Scene/Shot and Arke
  subject across switches and after mutation.
- [ ] **T-19 — accessibility:** every pointer operation works by keyboard/list controls; focus
  survives insert/delete; status has text; reduced motion and sub-900px view pass.
- [ ] **T-20 — scale:** 200-Shot Scene and 500-Scene/1,000-choice production remain within
  agreed interaction/layout budgets without mixing graph scopes.
- [ ] **T-21 — repository gates:** typecheck, lint, build, full tests, packaged desktop smoke,
  and filesystem inspection of migrated/history records pass on supported CI platforms.

## 3.3 Rollout

1. Land contracts, pure validation/linearisation, and fixture parity with no writer.
2. Land schema-3 support and lazy migration behind tests; keep UI on legacy projection.
3. Move every consumer to `SceneSequence`; prove parity before removing direct array access.
4. Land semantic writer commands and safe deletion.
5. Land read-only Flow and vertical Storyboard behind an internal feature flag.
6. Land graph/group editing and Arke proposal overlays.
7. Land shot-for-shot/grouped storyboard generation.
8. Remove the old horizontal strip and direct `shots[]` writer only after parity and migration
   tests pass on legacy and new worlds.

No dual-write phase is permitted. During rollout, the reader may understand both Scene shapes;
each individual write produces only the GraphScene shape.
