# 1 · Requirements

## 1.1 Summary

A local, unmetered image and video capability, so that experimentation — the iteration a shot
goes through before a take is worth paying for — does not accrue Seedance-class per-second
charges. The engine behind it is ComfyUI, but the app never exposes ComfyUI as such: it exposes
a short, Arke-authored menu of **recipes** — "Local · Draft Video (720p, up to 6s)" sitting in
the same model picker as Seedance 2.0, chosen the same way, dispatched the same way, landing
takes the same way.

This is Ollama's role for text (parent §14.1.1), extended to a capability that is far more
hardware-sensitive: a language model degrades gracefully with size, a video model that does not
fit in VRAM does not run at all. Everything in this spec exists to make that ceiling honest
before a dispatch, not after one fails.

## 1.2 Scope

**In scope**

- ComfyUI as a `ProviderClient` (SPEC-008 §2.9) declaring `image`, `video` and `voice-tts`
  capabilities (the last added 2026-08-19; see the amendment below),
  reusing the standing provider interface rather than adding a second one.
- A fixed, versioned, Arke-authored recipe catalogue — not a graph editor, not workflow import.
- Locating the ComfyUI engine: an Arke-managed optional install, or a user-directed existing
  install or already-running instance, discovered the way Higgsfield's CLI and OpenCode already
  are (prefer what is already on the machine).
- Locating recipe model weights: catalogue-driven optional download, or a user-directed existing
  models folder, so a user who already runs ComfyUI does not re-download tens of gigabytes.
- Pinned-dependency verification before dispatch: a recipe names the exact checkpoint and custom
  node versions it was authored against, and a mismatch is refused, not silently run.
- Hardware gating per recipe (VRAM floor), extending the local-runtime pattern already
  specified for Ollama models (parent §14.1, R-PROV-3).
- Process supervision for the Arke-managed engine, mirroring the Voxa sidecar (parent §7.1).

**Out of scope (this spec)**

- Any general ComfyUI workflow authoring, graph import, or custom-node installation beyond what
  a shipped recipe pins. A recipe is the only unit of work; a raw graph never reaches a user, a
  take, or a stored file.
- LLM work through ComfyUI. Ollama already covers local text generation (parent §14.1.1).
- Multi-GPU orchestration and remote/cloud-hosted ComfyUI. A user-directed instance may run
  anywhere reachable by URL (§2.2), but nothing in this spec manages that machine.
- Streamed in-progress previews — and in-flight progress figures of any kind. v1 reports
  **state only**: ComfyUI's queue position is not a fraction of the work done, and a
  `PollResult.progress` derived from it would move like one. A recipe is queued, running, or
  finished, said as such.

**Amended 2026-08-19 (SPEC-022): voice recipes are in scope.** This said "recipes here are image and
video only", on the same reasoning as the LLM exclusion above it — Voxa already covers local speech,
so ComfyUI had nothing to add. That premise is false for one case and it is the case that matters:
**Voxa cannot clone.** Kokoro pins a fixed catalogue of style vectors, and a voice cloned from a
recording is a different kind of thing, needing a model an ONNX sidecar cannot host.

The exclusion is therefore narrowed rather than deleted. Ollama still covers text and Voxa still
covers preset speech; what ComfyUI adds is the local engine for `voice-tts` recipes whose voice is
a reference clip. `ComfyUiRecipe.capability` widens to admit it, and the provider row gains
`voice-tts`. Everything else in this spec — discovery, weight fetching, pinned-dependency
verification, hardware gating, supervision — applies unchanged, which is the whole reason voice
comes here rather than packaging a second runtime (SPEC-022 §2.1).

**Amended 2026-08-19: the engine's own step counter is in scope; queue position still is not.**
The exclusion above rules out "in-flight progress figures of any kind", and its stated reason is
that *queue position* is not a fraction of the work done. That reason is sound and it is about one
signal. ComfyUI emits a second one: a `progress` message on its WebSocket carrying `value` and
`max` for the node currently executing — the sampler's own step counter. That genuinely is a
fraction of the work done for that node, it moves monotonically, and it does not exist until the
node is running.

What made this worth revisiting is that state-only proved not to be honest enough in practice. A
cloned-voice preview ran for half an hour against a benchmark that said eighty seconds, and
`running` was all the app could say — indistinguishable from a wedged engine. It was in fact
sampling at ten seconds a step, which the engine knew and said, and which nothing carried across.
"Running" is the true answer to the wrong question when the question is *should I keep waiting*.

So the exclusion is narrowed, not deleted:

- **Still out**: streamed in-progress previews of any kind, and any figure derived from queue
  position or elapsed time. Both were the original objection and neither has got better.
- **In**: `PollResult.progress` set from the engine's `progress` message for the executing node,
  and only while a node is executing.

A recipe is a graph, not a step, so the figure must **name what it counts** rather than present
itself as the job's own percentage. The cloned-voice recipe is five nodes and the steps belong to
one of them: a bar that sits at nothing through a twenty-second model load, sweeps to full while
sampling, then waits on the vocoder is the moving-like-a-fraction failure the original exclusion
names, wearing a better source. Surfaces say what stage is counting — `speaking · step 20 of 25` —
or they say `running` and stay silent.


## 1.3 Acceptance criteria

### Recipes

- **R-1** A recipe SHALL be the only unit of dispatchable work. No ComfyUI graph, node id, or
  workflow JSON SHALL be shown to a user, stored on a take, or accepted as input.
- **R-2** A recipe SHALL declare, in the shipped catalogue: capability, a bounded params schema,
  its fixed graph template, the checkpoint(s) and custom node(s) it requires with a pinned
  version or digest, its VRAM floor, and its output kind and limits (resolution, duration).
- **R-3** A recipe SHALL appear in the model manifest (SPEC-008 §2.5) exactly like any dispatched
  model, so the picker's capability copy, the pre-dispatch estimate and pass-packing arithmetic
  need no special case for a local recipe.
  - **WHEN** a user opens the model picker for a video shot **THEN** a ready local recipe is
    listed beside Seedance 2.0 with the same capability copy conventions.

### Locating the engine

- **R-4** The application SHALL resolve the ComfyUI engine location in this order: a
  user-directed path or URL, an Arke-managed install, or absent — and SHALL state in Settings
  which was chosen and why.
  - **WHEN** a user has an existing ComfyUI install with its own model library **THEN** pointing
    Settings at it SHALL make its recipes available without any download.
- **R-5** The Arke-managed engine download SHALL be optional and independently skippable, per
  the existing setup-catalogue convention (parent §14.1, `SETUP_CATALOGUE`).
- **R-6** The application SHALL start and remain fully usable when the ComfyUI engine is absent,
  unreachable, or fails to start, with local recipes disabled and a stated reason — mirroring
  R-VOICE-5's guarantee for the Voxa sidecar.

### Locating model weights

- **R-7** Each recipe's required weights SHALL be independently optional and skippable, and
  SHALL be detected as present before any download is offered.
- **R-8** A user SHALL be able to direct Arke to an existing models folder in place of the
  Arke-managed download location, and presence detection SHALL honour that folder.
  - **WHEN** a user's existing ComfyUI install already holds the checkpoint a recipe needs
    **THEN** the recipe reports ready without fetching anything.

### Safety of a fixed recipe

- **R-9** Before a dispatch, the application SHALL verify that the recipe's pinned checkpoint(s)
  and custom node(s) are present at the resolved location and match the pinned digest or
  version, and SHALL refuse the dispatch with a stated mismatch when they do not.
  - **WHEN** a checkpoint file at the resolved path does not match the recipe's pinned digest
    **THEN** the dispatch is refused, naming the file and what was found instead of what was
    expected, before any request reaches the engine.
- **R-10** A recipe unusable on this machine SHALL be listed disabled with the specific measured
  reason — insufficient VRAM, missing engine, missing weights, or a pinned-dependency mismatch —
  never a generic "unavailable".

### Engine version compatibility

*Added 2026-08-28; see the amendment in §2.6, D17 and D18.*

- **R-18** A recipe SHALL declare the minimum ComfyUI version it requires and the newest version
  it has been exercised against, and readiness SHALL evaluate both per recipe.
  - **WHEN** a newly shipped recipe requires a newer engine than the selected one **THEN** that
    recipe alone is disabled, naming its own requirement and the engine's reported version, and
    every other ready recipe remains ready.
  - **AND** a recipe's exercised-through version SHALL be at or above both its own minimum and the
    module floor. A range that is empty, or that lies wholly below the floor the provider already
    refuses, describes a recipe no engine can satisfy on both counts — every usable engine is
    labelled untested, and the check that only compares the two recipe fields would pass it.
  - **AND** the minimum SHALL be re-checked immediately before submission, alongside §2.5's
    dependency verification. A URL engine can be replaced in place beneath a job already admitted,
    and the backstop §2.12 relies on re-verifies pinned files alone.
- **R-19** An engine newer than a recipe's exercised-through version SHALL NOT be refused: the
  recipe stays dispatchable, the untested combination is stated, and any resulting pre-flight or
  dispatch failure SHALL carry the engine's reported version.
  - **AND** the version SHALL be frozen at enqueue as part of R-15's identity, and the pre-submit
    probe SHALL **refuse** a job whose engine no longer reports that version, naming both. Recording
    it at submission instead cannot be built against R-11: `SubmitResult` carries `remoteId`,
    `acceptedAt` and artifacts, and the client is isolated from the queue, so there is no value for
    the dispatcher to journal — and returning one after `/prompt` would still leave a window where
    the prompt was accepted and the version was not yet durable. Refusing makes the frozen value
    true by construction: a job either ran on the version recorded against it or never reached
    `/prompt`. §2.11 already treats a URL engine whose instance digest moved exactly this way.
- **R-20** The application SHALL report when the Arke-managed runtime is older than the version
  the current release pins, and SHALL offer that update as an explicit action. It SHALL NOT
  replace an installed runtime automatically, and SHALL NOT modify a user-directed engine at all.
  - **AND** the installed managed version SHALL be knowable while a user-directed engine is
    selected, when the managed tree is present but is not the engine being probed. A runtime
    installed before stamping shipped SHALL report its currency as **unknown**, never as behind:
    a missing stamp proves only that the install predates the stamp, and reading it as stale
    would offer every existing user a six-gigabyte replacement for the version they already hold.
    `unknown` SHALL NOT be a resting state, and SHALL be resolved by **reading the version the
    tree itself records** rather than by waiting for that engine to be selected — a managed tree
    sitting behind a user-directed engine is never probed, so corroboration alone would leave it
    unknown across every later pin bump, withholding the update from precisely the stale install
    this exists to find. Nor may it be resolved by assuming the current pin: that reports a
    genuinely old tree as current and withholds the update permanently, which is the same failure
    reached from the other side.
  - **AND** the replacement SHALL stop and restart the supervised child **only where that child is
    the managed engine**. A user-directed path is supervised identically (§2.2), and the case this
    update exists to serve is a stale managed tree sitting behind a selected user engine — where
    nothing is running out of that tree at all, and an unconditional stop would interrupt somebody
    else's engine and the work on it, which the sentence above forbids.
  - **AND** it SHALL preserve the models and custom-node folders beneath the managed root — an
    unoverridden managed install keeps its checkpoints inside the tree being replaced — and SHALL
    leave either a working engine or a stated failure, never a displaced tree with those folders
    stranded. The install path this adapts is not transactional: it removes the destination and
    then renames the staged tree into it.
  - **AND** preservation SHALL be a merge, not an overwrite. Moving the old directories wholesale
    onto the staged tree would delete whatever the new archive ships at those paths — a bundled
    configuration, a vendored node — leaving an engine that is updated everywhere except where it
    matters. Files the user's install added are carried across; files the new runtime supplies win
    a collision at the same path, because the runtime's own contents belong to the version being
    installed.
- **R-21** The pinned managed engine version SHALL be at or above every shipped recipe's declared
  minimum, enforced by a check rather than by review.
  - **WHEN** a recipe is added whose minimum exceeds the pinned runtime **THEN** the check fails,
    because a fresh managed install would otherwise disable that recipe on arrival with no update
    to offer — R-20 has nothing to say when installed and pinned already agree.

### Provider interface and cost

- **R-11** The ComfyUI client SHALL implement the standing `ProviderClient` interface (SPEC-008
  §2.9) unmodified — submit, poll, fetch, cancel, plus declarations.
- **R-12** Local recipe runs SHALL be recorded in the ledger at zero cost and labelled unmetered,
  per SPEC-008 R-18 and R-PROV-6.
- **R-13** Every take produced by a recipe SHALL record the recipe id and version in its
  provenance, alongside the canon revision and sheet versions R-DISP-3 already requires.

### Confidentiality, identity and enforcement

- **R-14** No ComfyUI graph SHALL be persisted or displayed by provider-call capture, and no
  landed recipe artifact SHALL retain embedded graph or workflow metadata (§2.10). An artifact
  in a container the sanitiser cannot process SHALL be refused with the container named.
- **R-15** Recipe identity (id, version, template digest, dependency digest) and engine
  identity (source, instance digest) SHALL be frozen on the job before enqueue, survive
  restart, catalogue advance and Settings changes, and be what provenance records (§2.11).
- **R-16** Recipe readiness SHALL be enforced by coordinator enqueue admission, not only
  presented by the picker, and the client SHALL re-verify pinned dependencies immediately
  before submission (§2.12, §2.5).
- **R-17** Cancellation SHALL affect only the requested prompt: a pending prompt is deleted by
  id, a running prompt is interrupted only when it is provably this application's own (§2.6).

## 1.4 Open questions

Three of the four questions this section carried are now decisions — D10, D11 and D12 in the
log, with their mechanics in §2.4 and §2.6. What remains open:

- Whether recipes can be added between app releases the way the model manifest currently cannot
  (SPEC-008 §1.4's open question, restated for a catalogue Arke authors itself rather than
  mirrors from a vendor).
- Whether the managed install ever offers the AMD and Intel portable builds. The upstream
  release publishes one archive per GPU vendor, not per CPU architecture; v1 pins the NVIDIA
  build only (§2.4, D10), and a machine that cannot use it finds out at engine start with the
  reason stated (R-6), not silently.
- Whether the recipes' hardware floors, transcribed at authoring from the engine vendor's own
  stated requirement (§2.7), are replaced by figures measured on Arke's own reference hardware.
  The gate's arithmetic and presentation do not change either way; only the numbers would.

# 2 · Design

## 2.1 Architectural decision

**Recipes are ComfyUI the way model rows are FAL: the engine is what runs it, the recipe is what
the user picks.** FAL exposes dozens of routes behind one gateway; the manifest curates which
ones are dispatchable and how. ComfyUI exposes an open-ended graph editor behind one HTTP API;
the recipe catalogue is the same curation, pushed one layer further because the underlying
surface is strictly more powerful — and more dangerous to expose directly — than a vendor's
fixed model list.

The test for whether something belongs in a recipe or not: **would exposing this field let a
user construct a graph Arke did not author?** A prompt string and an aspect ratio pass. A raw
node id, a sampler name, a LoRA path do not — those are recipe-authoring decisions, made once,
shipped, and versioned like everything else in this codebase.

### Why ComfyUI, and not a runtime of our own

The obvious objection to this whole spec is that ComfyUI is a large dependency to take on for a
short menu of recipes, and that a purpose-built runtime — a thin `diffusers` process, a serving
framework like SGLang-Omni, something Arke controls end to end — would be lighter. It is worth
writing down why it would not be, because the reasoning is not obvious and the question will be
asked again.

**"ComfyUI" is three things, and this spec already declined one of them.** There is the
execution engine (memory management, block swapping, quantised loading), the model zoo (somebody
writing a loader for each new architecture, usually within days of its release), and the node
graph. R-1 already refuses to expose the third. So the choice is not "graph editor or no graph
editor" — it is whether Arke writes its own engine and its own zoo.

**The expensive part is Python and CUDA, not ComfyUI.** D1 defers the managed install because
packaging a portable Python runtime with CUDA wheels, per architecture, is standing maintenance
rather than a one-time cost. That cost is *identical* for any Python-based alternative:
`diffusers`, SGLang-Omni and a bespoke sidecar all need torch and a matching CUDA build. A
lighter Python runtime therefore saves nothing on the expensive part while giving up the zoo —
and the zoo is not a nicety. A model published on a Monday is typically loadable in ComfyUI, with
community quantisations, inside a week. Writing that loader per architecture, per release, is the
same standing-maintenance trap D1 identified, relocated into a component Arke owns.

**Where a lighter runtime genuinely wins is where it is not Python at all.** Arke already ships
this and should keep doing so: `whisper.cpp` and Kokoro run in the Voxa sidecar (parent §7.1) as
native binaries — no torch, no CUDA, no per-architecture wheel problem, supervised by machinery
that already exists. That is dramatically lighter than ComfyUI wherever a maintained native
implementation exists, so the question splits by what a model actually requires rather than by
preference:

| Capability | Native sidecar viable | Why |
|---|---|---|
| Speech (`voice-tts`, `voice-stt`) | **Yes — already shipped** | `whisper.cpp` and Kokoro are mature, native, and need no Python |
| Music | No | The current generation is billions of parameters, flow-matching and CUDA-only; no maintained native implementation exists |
| Image and video | Not today | Native diffusion runtimes lag new architectures badly, and this catalogue's families land in ComfyUI first |

So the rule this spec follows: **prefer a native sidecar wherever one exists, and reach for
ComfyUI only where the alternative is Arke maintaining a Python runtime *and* a model zoo.**
Speech never needs ComfyUI. Image, video and music currently do.

**Two honest costs of this choice**, recorded so the next reader does not have to rediscover
them. ComfyUI is a moving target with a third-party node ecosystem, which is precisely what §2.3's
pinned checkpoint digests and pinned node commits are defending against — that pinning is not
ceremony, it is the price of this decision. And D5's argument that a user's existing checkpoint
library must not be shadowed quietly depends on using their *engine*: weights are portable
safetensors, but quantisation formats, loader conventions and offloading behaviour are not, so a
runtime of our own could read their files without reproducing what their install does with them.

The one place a lighter runtime was a live option was D1 — the choice of *what* to package —
and D10 has since answered it with ComfyUI: the upstream portable build arrived pinnable and
digest-verified, and the shipped recipes need zero custom nodes (D11), which removed the
supply-chain argument a `diffusers` sidecar would have dodged. The trade recorded here stands
for the next time the question is asked: a pinned `diffusers` sidecar is smaller only while
the recipe list stays two or three long, and stops being lighter the moment it grows.

## 2.2 Locating the engine

Three states, discovered in this order, mirroring the "prefer what's already there" pattern
SPEC-005 §1.4 already established for OpenCode and SPEC-008 §2.3 established for the Higgsfield
CLI — a user's own install is not Arke's to duplicate or shadow:

| State | Meaning | Settings shows |
|---|---|---|
| `user-directed` | Settings holds a path to an install or a base URL of a running instance | that path/URL, and whether it currently answers |
| `managed` | No user direction; the Arke-managed install (§2.4, D1) is present and supervised | "Arke-managed · running on 127.0.0.1:‹port›" |
| `absent` | Neither | "Not installed" with the same download/point-me-at-one affordances Ollama's row already has |

A **user-directed path** launches ComfyUI as a child process Arke supervises, identically to the
managed case, once presence is confirmed (an existing `main.py` or portable launcher at that
path). A **user-directed URL** is taken as already running — nothing is spawned, only probed,
the same trust boundary as Ollama's `baseUrl` (packages/providers/src/clients/ollama.ts) except
here the port is not a fixed default, because ComfyUI has no standard install location the way
Ollama's own installer gives it one.

This is also why user direction matters more here than for any other local runtime in the
product: ComfyUI users routinely accumulate tens of gigabytes of checkpoints across an install
they already curate. Forcing a second, Arke-owned copy would be the single worst first
impression this feature could make.

### What a URL can and cannot prove (D13)

A reachable URL proves an engine answers. It cannot prove what is on that engine's disk: a
vanilla ComfyUI reports model *names* over its API, and a name is exactly what §2.5 refuses to
trust — R-9 verifies bytes, and bytes on another machine cannot be hashed from this one.

So the v1 policy is: a **URL is discovered and health-probed, never spawned**, and shipped
recipes against a URL-only engine are **disabled with the verification stated as unavailable** —
*"Arke cannot verify this engine's files"* — never with wording that implies the files are
merely missing. The one unlock is an **explicit filesystem mapping**: when `comfyUiModelsDir`
(§2.4) is also set, the user has asserted that folder is the selected engine's model root, R-9's
hashing runs against those bytes, and the recipes gate on what it finds. The mapping is the
user's assertion to make — Arke states in Settings that the folder must be the one the engine
reads, and applies it nowhere else.

## 2.3 The recipe catalogue

Hand-authored, shipped with the application — not fetched, not user-editable, the same posture
SPEC-008 §2.5 takes toward the model manifest and for the same reason: a recipe that can be
edited by anything other than an Arke release is a recipe Arke can no longer vouch for.

```json
{
  "id": "comfyui-local-draft-video",
  "provider": "comfyui",
  "capability": "video",
  "displayName": "Local · Draft Video",
  "recipeVersion": 1,
  "paramsSchema": {
    "prompt": { "type": "string" },
    "aspect": { "type": "enum", "values": ["16:9", "9:16", "1:1"] },
    "durationSec": { "type": "enum", "values": [2, 4, 6] }
  },
  "graphTemplate": "recipes/local-draft-video.v1.json",
  "requires": {
    "checkpoints": [
      { "file": "ltx-2.3-‹variant›-distilled.safetensors", "sha256": "…", "sizeMb": "‹measured›" }
    ],
    "customNodes": [
      { "id": "ComfyUI-LTXVideo", "pinnedRef": "‹commit›" }
    ]
  },
  "hardware": { "minVramMb": "‹measured›", "recommendedVramMb": "‹measured›" },
  "limits": { "maxDurationSec": 6, "resolutions": ["512p", "768p"] },
  "pricing": { "kind": "unmetered" }
}
```

Illustrative, and every elided value is elided deliberately. The checkpoint choice, its digest,
the pinned node commit and both hardware floors are implementation work (T-3), not decisions this
document makes — and a plausible-looking placeholder is worse than an obvious one, because it
gets copied. An earlier draft named `ltx-video-2b-v0.9` with a 4200 MB size and an 8192 MB VRAM
floor; the LTX generation has moved on since, and quoting numbers that were never measured put a
hardware promise in a document that had not tested one.

The numeric placeholders are deliberately the wrong *type* rather than a zero. A recipe copied
out of this sketch has to fail validation, not validate into something harmless-looking:
`minVramMb: 0` parses, gates nothing, and turns §2.7's refusal into a dispatch that dies on the
user's machine instead — the silent pass this document refuses everywhere else. T-3 establishes
the floors against real hardware, which is the only way a floor means anything.

**Pricing asks nothing new of the manifest: a recipe is `unmetered`.** An earlier draft of this
section called for a new pricing kind named `local`, reasoning that a recipe charges nothing
structurally rather than at a rate that happens to read zero, and that the estimator should not
carry a `perSecond` row valued at `0`. The reasoning holds; the conclusion did not, because
`unmetered` already *is* that kind. SPEC-008 R-11's union already carries an arm for exactly this
situation — work billed by nobody — and it is the one Kokoro, whisper.cpp and every Ollama row in
the shipped manifest already use. R-12 has said "labelled unmetered" since the first draft, and
`dispatcher.ts` already turns that label into an `actualSource` of `local-zero`. A second arm
behaving identically to an existing one is not a clarification, it is a case every estimator,
every price-copy helper and every reader has to learn twice.

So this spec asks for **no schema change to the manifest at all**. R-9 through R-13 apply to a
recipe row unmodified.

**Recipes are versioned, not mutated.** Changing a graph template, a pinned checkpoint or a
pinned node is a new `recipeVersion`, never an edit in place — the same reasoning as R-VER-2 for
sheets: a take's provenance (R-13) must keep meaning what it meant when it was made.

### The shipped pair, and why neither carries a custom node (D11)

The first catalogue is one image recipe and one video recipe, both chosen so that **every node
in their graphs is ComfyUI core**:

- **Local · Draft Image** — SDXL Base 1.0, one checkpoint, the basic text-to-image graph the
  engine has run since 2023.
- **Local · Draft Video** — Wan 2.2 5B (TI2V), the engine vendor's own repackaged files in
  their documented folders, on the node set core has carried since the release that introduced
  them (§2.6's floor).

The catalogue in `@arke-studio/providers` is the authority for their digests, sizes, node sets
and floors; this document deliberately does not restate those values, because a number quoted
twice is a number that drifts. What is binding here is the *shape*: complete dependency sets,
pinned sha256 digests verified against the publisher, an output contract naming the one node
whose output is fetched, and hardware floors presented with both figures (§2.7).

Zero custom nodes is a choice, not an accident. D3 asked whether a recipe's nodes are vendored
into Arke's release or fetched from upstream at install; the v1 answer is **neither, because no
shipped recipe needs one** — which closes the supply-chain question by not opening it. The
verification machinery for pinned nodes still ships and is still tested (R-9 names them), so
the first recipe that does need one pays only the vendoring cost, not a design turn. When that
day comes, the node is **vendored** — a third-party node is code that runs on the user's
machine, and fetching it from a repository at install time is a surface this feature refuses.

## 2.4 Fetching what a recipe needs

Two independent things can be missing, and they are fetched — or pointed at — independently,
following the existing `SETUP_CATALOGUE` shape (`packages/coordinator/src/setup/catalogue.ts`):

**The engine itself (D10 — the managed install ships, detection-first).** A new optional
entry, `comfyui-runtime`, of a new catalogue kind `tree`: the upstream portable Windows build
is one pinned, sha256-verified archive holding a whole runtime directory — an embedded Python
and the application tree — which the existing `archive` kind cannot model, because `archive`
extracts one executable and discards the rest. `tree` extracts the entire archive into a
staging directory and renames it into place whole, so presence is never half a runtime.
Nothing is run silently and nothing reaches PATH, the same posture as the Higgsfield CLI.

Three facts make this packagable where D1 once deferred it:

- The upstream release publishes a **sha256 digest per asset**, so the download verifies the
  way every other catalogue file does.
- The portable archive is 7z, and the **System32 `bsdtar` this codebase already resolves**
  (`systemTar()`, `local-setup.ts`) both reads and writes that format — verified on the
  supported platform — so no new extraction tool ships.
- The release is **per GPU vendor**, not per CPU architecture. v1 pins the NVIDIA build only,
  says so on the row, and a machine that cannot run it learns the reason at engine start (R-6).

**Selection wins; detection only offers.** The entry is `optional: true`, and a user-directed path
or URL selected in Settings satisfies its presence check before download. A live default-port
instance or well-known install is shown as an offer but does not suppress the Arke-managed option;
the user chooses whether to reuse it or install the managed runtime. This keeps discovery from
silently deciding which engine owns future recipe dependencies.

**Amended 2026-08-28: presence is not currency (D17).** `isPresent()` asks whether the tree is
there. That is the right question for *must this be downloaded* and the wrong one for *is this the
runtime this release pins* — nothing here records a version, so a bumped `COMFYUI_VERSION` reaches
new installs only and every existing one keeps what it first extracted. The update offer that
closes this is stated in §2.6's amendment; the fetching mechanics on this page are unchanged, and
no installed runtime is replaced unless the user asks for it (R-20).

**Each recipe's weights**, as `files`-kind entries keyed to the recipe's `requires.checkpoints`,
`optional: true`, `requires: ["comfyui-runtime"]` — identical in shape to how a Gemma model
entry requires `ollama-runtime` today (`catalogue.ts`). The runtime requirement is satisfied by
**any healthy engine**, not only the managed component: a user-directed install is not blocked
from fetching weights by the absence of a component it replaces.

**The location override.** A new setting, `comfyUiModelsDir`, defaulting to
`<comfyUiRoot>/models` but overridable in Settings to any existing folder. `isPresent()`
(`local-setup.ts`) checks that folder rather than the app-owned default when the
override is set — the same detection logic, a different root, so a user's existing checkpoint
library is recognised rather than shadowed by a second download.

**Ownership of an external folder.** A user-directed models folder is the user's, and every
operation against it is scoped to the specific files a recipe names:

- Presence detection, any offered download, engine launch configuration and §2.5's pre-flight
  verification all resolve **the same per-file paths** — one resolver, so what was detected is
  what is verified is what is read.
- Repair is **file-specific**: a failed or mismatched checkpoint is re-fetched under its own
  name via the same staged-rename discipline every download already uses. A user-owned
  directory is **never recursively deleted** — the component-level `repair()` that removes a
  whole directory applies only to Arke-owned component folders.
- Arke writes into an external folder **only on explicit confirmation**, per download, with the
  destination shown. Detection never writes anything.

## 2.5 Pre-flight verification

**A recipe that runs against the wrong checkpoint is a worse failure than a recipe that refuses
to run.** Wrong output from a mismatched weight looks like a bad generation, not a
misconfiguration, and nothing about that failure mode points the user at the fix.

So before every dispatch through a ComfyUI recipe — not only at setup — the resolved checkpoint
and custom-node paths are hashed (or version-probed, for a node) and compared against the
recipe's pinned values. A mismatch refuses the dispatch and names the specific file and what was
found in place of what was expected. This runs whether the weights arrived through Arke's own
download (§2.4, where the digest was already verified once — see `download()` in
`local-setup.ts`) or through a user-directed folder that could hold anything.

This is stricter than SPEC-008's manifest drift (§2.11), which is detected *after the fact* from
diverging cost estimates — a check available only because remote providers report what they
charged. A local recipe has no such signal, so the check has to happen *before* dispatch instead,
against the one thing that is actually knowable up front: what is on disk.

It runs **at the last moment as well as the first**: readiness (§2.12) gates what the picker
offers, and the client re-runs the verification immediately before `submit()` puts anything on
the wire — a checkpoint replaced between the picker rendering and the button being pressed is
still refused, because stale screen state must never be what authorises a dispatch.

## 2.6 The provider client

`ComfyUiClient implements ProviderClient` (`packages/providers/src/types.ts`), registered in
`registry.ts` beside Ollama's:

```
validateKey()         → GET  {baseUrl}/system_stats  — the compatibility probe (below)
submit(key, request)  → pre-flight (§2.5), then POST {baseUrl}/prompt with the recipe's graph,
                         params substituted → { remoteId: promptId, acceptedAt }
poll(key, remoteId)   → GET  {baseUrl}/queue for pending/running, else GET {baseUrl}/history/{id}
                         → queued | running | succeeded | failed — state only, no progress figure
fetchArtifacts(...)   → GET  {baseUrl}/view, for the outputs of the recipe's declared output
                         node only — never every image the history entry happens to name
cancel(key, remoteId) → targeted (below), never a bare /interrupt
```

`key` is unused throughout, as it is for Ollama (SPEC-008 R-18) — ComfyUI authenticates nothing.

**The compatibility probe is the API floor (D14).** `validateKey` is mandatory on
`ProviderClient` and here it earns its keep twice over. First, `/system_stats` must answer with
a parseable `system.comfyui_version` at or above **0.3.45** — the release that introduced the
core node set the shipped video recipe stands on; an engine that answers anything else is
reported *incompatible with its version named*, never generically unavailable. Second, each
recipe's readiness (§2.12) asks `/object_info` for the exact `class_type`s its graph uses — a
per-recipe answer, so a future engine that removes or renames a node disables the one recipe it
breaks with the node named, rather than the whole provider.

**Amended 2026-08-28: the floor belongs to the recipe, and the managed engine was never current
(D17).** The paragraph above has the direction of the problem right and overstates how far the
shipped mechanism carries it. The question that prompted this is whether a user-directed engine
holds the catalogue back — whether what Arke can ship becomes a function of whichever ComfyUI the
user happens to be running, while the managed engine advances with each release. Three gaps, and
the third inverts the premise.

**The floor is a module constant, not a recipe's own requirement.** `VERSION_FLOOR` lives in
`packages/coordinator/src/comfyui/engine.ts`, and again as `COMFYUI_VERSION_FLOOR` in
`packages/providers/src/clients/comfyui.ts`; `ComfyUiRecipe` declares no version of its own.
So the per-recipe blast radius D14 promises is delivered by the node probe alone, and holds only
where a newer engine's requirement happens to surface as a *new class name*. The day the
catalogue gains a recipe needing a newer engine, the options are to raise the constant — which
disables every recipe on every engine below it, including the two that ran yesterday, with a
message naming a floor rather than the recipe that moved it — or to leave it and let readiness
pass a recipe that cannot run. Neither is the answer D14 was written to give. A recipe therefore
declares its **own** minimum engine version, defaulting to the catalogue floor, evaluated in
readiness beside the node probe and stated as that recipe's requirement.
`packages/adapter-claude` already carries a floor this way — `minVersion` per discovery rather
than a constant — and this is the same shape.

What the module constant then means has to be re-derived, because 0.3.45 was never an API floor:
D14 chose it as *the release where the shipped video recipe's core nodes appear*, which under this
amendment is that recipe's own `minEngineVersion` and nothing besides. What is left for the
constant is the oldest engine whose API the client can actually drive — `/system_stats`,
`/prompt`, `/queue`, `/history`, `/view`, `/interrupt`, `/object_info`, and the WebSocket
`progress` message §1.2's second amendment now reads. Until that is derived against upstream,
0.3.45 stands as a conservative placeholder and is described as one. It excludes nothing that
ships today, and every floor above it is a recipe's to state.

**The node probe compares names, not signatures.** `recipeNodeClasses` returns the distinct
`class_type`s of a graph, so an engine that keeps `KSampler` and renames one of its input keys
answers the probe correctly and fails on the wire. Nothing bounds the other end either: there is
no ceiling, and *newer* is the direction a user's own engine drifts, because they update
continuously and Arke ships in batches. A recipe therefore also records the newest engine it was
exercised against, and an engine above that **warns without refusing** — D15's principle, that a
false "disabled" is the failure this spec exists to prevent and an engine's own error is an
honest one. What changes is only that the failure becomes diagnosable: a pre-flight or dispatch
failure carries the engine's reported version alongside the recipe identity §2.11 already freezes.

**The managed engine does not advance with the app.** `isPresent()` for a `tree` component is the
root marker existing under the component directory (`local-setup.ts`); no version is stamped at
install, `CatalogueEntry` has no version field, and nothing compares the installed tree against
the pinned `COMFYUI_VERSION` in `catalogue.ts`. Bumping that pin in a release changes the URL,
the digest and the row's caveat **for machines that have not installed it yet**. Everyone else
keeps the tree they first downloaded, indefinitely, with no row saying so — and were the floor
ever raised past it, that install would report `incompatible` with nothing in the product
offering to repair it. The managed lane drifts exactly as a user's own does; it is merely quieter
about it. So a managed install below the pinned version is stated on the ComfyUI row as an
available update, and is **offered, never applied** — a six-gigabyte re-download over somebody's
connection is their decision, D5's refusal to shadow what a user already has applied to their
bandwidth rather than their disk.

Two mechanics an earlier draft of this amendment assumed wrongly, recorded because both are easy
to assume again. **The health probe does not know the managed version unless the managed engine is
the selected one.** `/system_stats` answers for the *resolved* engine (§2.2) and user direction
wins, so a machine holding a managed tree while Settings points at a URL has a runtime nobody is
asking. The installed version is therefore stamped at install and the probe corroborates it where
the two coincide. A tree carrying no stamp says only that it predates stamping, which is not the
same as being behind — it reports **unknown** until something corroborates it, because the day
this ships every existing managed install is unstamped and already at the pin, and reading those
as stale would offer the whole install base a six-gigabyte replacement for what they have.

**And this is not the Repair path.** `repair()` accepts `files` components only, `retry()` returns
early on anything already `present`, and `remove()` refuses while a dependant exists — every
recipe's weights entry declares `requires: ["comfyui-runtime"]`, so an installed checkpoint blocks
removing the runtime beneath it. The update is a **tree-specific replace**, and it owes three
constraints the download path has never had to honour.

The supervised child is stopped first, because a running engine holds its own files open — but
**only where that child is the managed one**. A user-directed path is spawned and supervised
identically (§2.2), and the case this update exists to serve is exactly the one where the two
differ: a stale managed tree sitting behind a selected user engine, with no managed child running
at all. An unconditional stop there would interrupt somebody else's engine, and the work on it, to
replace a tree nobody is using.

`ComfyUI/models`, with `custom_nodes` beside it, survives the swap, because a managed install with
no `comfyUiModelsDir` override keeps its checkpoints *inside the tree being replaced* — swapping
wholesale would take six gigabytes of verified weights to install an engine.

And the swap needs a way back. The install path removes the destination and then renames the
staged tree into it, which is sound for a first install and strands the preserved folders if a
replacement fails between the two. A failed update leaves a working engine or a stated failure,
never a half-displaced tree (D18).

**What this does not change.** D13 stands: a user-directed URL is probed and never spawned, and
nothing here upgrades, writes to, or restarts an engine the user pointed Arke at. Their install
is theirs, and an out-of-date one is reported, not managed. The selection order of D5 and D10 is
untouched, and no recipe becomes dispatchable that R-9's byte verification would have refused.

**Cancellation targets the requested prompt and nothing else (D14).** `/interrupt` interrupts
whatever the engine is currently executing — on a shared or user-directed engine that can be
somebody else's work. So cancel reads `/queue` first: a prompt still **pending** is deleted by
id (`POST /queue {"delete": [id]}`); a prompt that **is the running one** is interrupted; a
running prompt that is *not* ours is left alone and ours is deleted from pending or already
gone. The one thing this never does is interrupt work it cannot prove is its own.

**Declarations are Ollama's all-false row after all (D12).** An earlier draft argued for
`supportsListRecent: true` via the outbox key embedded in `extra_pnginfo`. Two facts killed it.
The dispatcher only reaches list-recent reconciliation when `supportsIdempotencyKey` is *also*
true — a combination ComfyUI cannot honestly declare — so the flag as proposed was
unreachable, disagreeing with `reconcileStrategy()` rather than extending it. And
`extra_pnginfo` is precisely the metadata that propagates into output files — the channel
§2.10 exists to strip — so the mechanism would have smuggled a correlation id into the very
bytes this spec sanitises. All three reconciliation flags are false; `reportsCost: false`; the
ledger entry is `local-zero` regardless (R-12).

What all-false buys is the **honest user decision** on the one ambiguous window: a job found
`submitting` after a crash against an engine that survived it (a user-directed URL) is held for
the user, and the held copy says what a duplicate actually costs here — *a re-run on this
machine's own GPU time* — not the "may charge again" wording a paid provider's hold carries.
For a **spawned** engine (managed, or a user-directed path), the child does not survive Arke,
its queue and history are in-memory and gone, and the engine is relaunched fresh — so recovery
requeues those jobs outright (§2.11): nothing can still be executing on an engine that no
longer exists, and the cost of being wrong about a leaked process is redundant GPU work nobody
polls, not money.

## 2.7 Hardware gating

Extends the pattern already specified for Ollama models (parent §14.1, R-PROV-3, `SETUP_CATALOGUE`'s
VRAM-sized entries) rather than introducing a second one: a recipe below its `hardware.minVramMb`
on this machine is listed **disabled with both figures** — *"Needs 12 GB VRAM. This machine has
10 GB. Cloud video still works."*

**VRAM detection already exists, and SHALL be reused rather than rebuilt.** `probeRuntime()`
(`packages/providers/src/runtime-detect.ts`) returns `{ vramMb, memMb, diskFreeMb }`, and
`gateLocalRuntimes` (`packages/contracts/src/runtime-gate.ts`) already holds the judgement over
those figures for the Ollama and Kokoro rows. A recipe's floor is the same question asked of a
different row, and a failed probe returns null → unknown, never unavailable, per SPEC-008 R-22.

An earlier draft required `nvidia-smi --query-gpu=memory.total` here, on the correct observation
that `Win32_VideoController.AdapterRAM` is a 32-bit counter which silently truncates any card at
or above 4 GB — the one failure this feature cannot afford, because it would show a capable
machine as unable to run anything. The shipped probe had already solved that, and solved it
better: it reads `HardwareInformation.qwMemorySize` from the display-class registry, which
survives large adapters, spawns no external binary, and is not NVIDIA-only. Measured on an
RTX 3080, the registry reports 10240 MB where `AdapterRAM` reports 4 GB.

## 2.8 Process supervision

The managed engine is supervised exactly as Voxa is (parent §7.1): spawned by Electron main on a
loopback port allocated at startup, health-probed, and the application remains fully usable with
local recipes disabled and a stated reason when it fails to start (R-6). A user-directed running
instance is probed, never spawned, and its absence is reported the same way.

## 2.9 Provenance

A take produced through a recipe carries `provider: "comfyui"`, `model: "‹recipe id›"`, and a
new `recipeVersion` field alongside the existing `provenance.canonRevision` and
`provenance.sheets` (parent §2.3.5). This is what makes *"this take was made with Draft Video v1, which
no longer exists"* an answerable question after a recipe is superseded, the same way sheet
provenance already answers it for canon.

The version the take records is the one **frozen on the job at enqueue** (§2.11), never looked
up at arrival — a job that outlives an app update must land as what it was dispatched as. And
the ledger's `local-zero` survives into the take: arrival carries the ledger entry's
`actualSource` through instead of stamping its own, so a recipe take and its ledger row agree
about where the zero came from.

## 2.10 Graph confidentiality: instrumentation and landed bytes

R-1 says no graph reaches a user, a take, or a stored file. Two standing mechanisms would
break that silently if left alone, so both are scoped here:

**Provider-call capture.** Every instantiated HTTP client is captured, and payload history
persists request and response bodies for Activity to display. A `/prompt` request *is* the
graph; a history response can contain it. Capture is therefore provider-aware for ComfyUI:
a graph-shaped body is replaced before persistence by a summary — recipe id, graph
**digest**, **node count** and **byte count** — and a history response has any embedded
graph replaced the same way. What Activity shows for a recipe dispatch is that summary, which
is also all a diagnostic needs: two digests answer "same graph?" without either graph.

**Landed media.** ComfyUI's save nodes embed the prompt graph and workflow into output
metadata (PNG text chunks, WebP EXIF, MP4 metadata boxes) — server-side, so a managed launch
flag (`--disable-metadata`, passed anyway as defence in depth) cannot cover a user-directed
engine. Before any ComfyUI artifact lands, it is **sanitised**: PNG text chunks stripped, WebP
metadata chunks stripped, MP4 metadata boxes removed. A container the sanitiser does not know
is **refused with the reason stated**, not landed as-is — recipes are Arke-authored, so their
output containers are a closed set, and an unknown one is a recipe bug to fix rather than a
leak to permit.

## 2.11 Durable identity: what a job must remember to survive

`JobSchema` persists provider, model and params — enough for a cloud job, not for one whose
"provider" is a moving process on this machine and whose "model" is a versioned recipe. Two
identities are **frozen onto the job at enqueue**, before any network call:

- **Recipe identity**: recipe id, `recipeVersion`, the graph template's digest and the
  dependency set's digest. A v1 job that stays queued across an app update executes and is
  recorded as v1 — and when the catalogue no longer carries v1, recovery **refuses with that
  stated** rather than silently running v2's graph.
- **Engine identity**: the source kind (user-path, user-URL, managed) and an opaque instance
  digest of the resolved location. Opaque deliberately: job rows reach the renderer, and an
  absolute path does not (SPEC-001 R-9); a digest answers "same engine?" without saying where.

Recovery is then a policy per source, not a guess:

| Found on restart | Spawned engine (managed / user path) | Surviving engine (user URL) |
|---|---|---|
| `running` | Requeue — the engine died with Arke; its in-memory queue and the old prompt id are gone | Same instance: resume polling the recorded id. Different instance: **fail with the reason stated** — an old id is never polled against a new engine |
| `submitting` | Requeue — nothing can be executing on an engine that no longer exists | Hold for the user (§2.6), with the duplicate priced honestly as GPU time |

A location changed in Settings while work is non-terminal is the same "different instance" row:
the job fails with *which* engine it belonged to (by source, never by path), and the user
re-runs against the engine they now have. Child death is never treated as proof the work
stopped — the process leash is best-effort — but for a spawned engine the *relaunched* engine
provably holds no old work, which is the fact recovery actually relies on.

## 2.12 Readiness: one answer, enforced where it matters

R-10's disabled-with-reason is a presentation; this section is the enforcement. One
**recipe-readiness result** combines, per recipe: engine state (§2.2), the compatibility probe
(§2.6), weight presence at the resolved location (§2.4), pin verification status (§2.5) and
the hardware gate (§2.7). That same result is consumed by Settings, the model picker, routing
and — decisively — **coordinator enqueue admission**: a dispatch for a recipe whose readiness
is not `ready` is refused at enqueue with the readiness reason, so a stale picker can never
commit work the coordinator knows cannot run. The client's own pre-submit verification (§2.5)
backstops the remaining gap between admission and the wire.

Unknown hardware stays unknown (SPEC-008 D12): a failed VRAM probe lists the recipe as
`unknown`, **and dispatch is permitted** — the floor could not be checked, which the reason
states, and refusing would disable local generation forever on any machine whose registry probe
fails. The engine's own out-of-memory failure is then an honest job failure, not a silent one.

ComfyUI's engine state is its **own status shape**, not a borrowed one: `ProviderToolStatus`
is a sign-in contract (signed-out, signing-in, a mandatory sign-in command) and every one of
those states would be a lie for an engine that authenticates nothing. The engine status carries
source, state, a display-safe location, and the reason whenever the state owes one.

## 3.2 Testing

**Recipes** — every shipped recipe round-trips through the manifest exactly like a remote model;
`paramsSchema` rejects a param not on the list; no code path can reach `graphTemplate`'s raw JSON
from the renderer.

**Engine discovery** — a user-directed path takes priority over a managed install; a
user-directed URL is probed, never spawned; absence of both reports `absent` with the stated
remedy; a managed engine that fails to start leaves the rest of the app usable (R-6), asserted
the same way R-VOICE-5 is.

**Weights and the location override** — a checkpoint already present in a user-directed
`comfyUiModelsDir` is detected without a download attempt; an entry missing from the override
folder queues normally.

**Pre-flight verification** — a checkpoint whose digest does not match is refused before any
request reaches the engine, naming the file; a missing custom node is refused the same way; a
correct match dispatches.

**Provider interface** — `ComfyUiClient` passes the same fake-provider harness SPEC-008 §3.2
already runs against the declaration flags, proving reconciliation needs no ComfyUI-specific
branch; the version floor refuses an old or unversioned `/system_stats` with the version named;
cancel deletes a pending prompt by id, interrupts only its own running prompt, and leaves a
stranger's running prompt untouched across the same fake `/queue`.

**Graph confidentiality** — a captured `/prompt` request persists digest, node count and byte
count and no graph; a history response's embedded graph is redacted the same way; a landed PNG
and WebP carry no text/EXIF metadata after sanitisation; an MP4's metadata boxes are gone; an
unknown container is refused with its name in the reason.

**Durable identity and recovery** — a job enqueued under recipe v1 lands and records v1 after
the catalogue advances to v2; a v1 no longer in the catalogue refuses recovery with that
stated; a running job against a spawned engine requeues on restart; a running job against a
surviving URL engine resumes on the same instance and fails with the reason stated on a changed
one; a `submitting` job against a URL engine holds for the user with GPU-time wording.

**Readiness enforcement** — picker, routing and enqueue admission read the same result for
every readiness reason; an enqueue for a not-ready recipe is refused with that reason; an
unknown VRAM probe lists `unknown` and does not refuse dispatch.

**Hardware gating** — a recipe below its VRAM floor is disabled with both figures; a
`probeRuntime()` read that returns null reports unknown rather than unavailable, exercised
through the existing injectable `queryVramBytes` so the assertion needs no GPU.

**Ledger and provenance** — every recipe run lands as `local-zero`; a take records the recipe id
and version and that value never changes when the recipe catalogue later advances.

**Engine version compatibility** *(added 2026-08-28, D17)* — a catalogue holding one recipe above
the engine's version and one below it disables exactly one, and the disabled reason names that
recipe's own requirement rather than the module floor; an engine above a recipe's
exercised-through version stays dispatchable and says so; a dispatch failure against such an
engine carries the reported version; and a job whose URL engine has changed version between
enqueue and submission is **refused before `/prompt`**, naming the frozen version and the one now
answering — asserted for a downgrade below the recipe's floor and for an upgrade that still clears
it, since a silently-accepted substitution is what makes the frozen value a lie.

A managed install older than the pinned `COMFYUI_VERSION` reports an available update and nothing
is downloaded or replaced until it is asked for, **including while a user-directed engine is the
selected one** — the case the health probe alone cannot answer; an unstamped install reports
`unknown` rather than offering a replacement for the version it already has, and an unstamped tree
seeded at a genuinely older version reports *that version* after a pin bump and offers the
replacement, which accepting any non-`unknown` answer would not prove; the same comparison against
a user-directed engine reports and changes nothing, and a managed replace while a user path is
selected leaves that user's supervised engine running.

A successful update of the *selected* managed engine ends with the replacement child healthy and
recipes dispatchable again — stopping the engine, installing, and leaving local generation offline
satisfies every other assertion here. A replace preserves both directories, asserted with an
old-data sentinel **and** a replacement-side sentinel **in each** of `models` and `custom_nodes`:
one sentinel per side would pass while the other directory was moved over the staged tree
wholesale, which is the failure being tested. A failure injected at each step of the swap leaves a
working engine or a stated failure, never stranded weights.

Both catalogue invariants fail closed and need no engine: a recipe whose `minEngineVersion`
exceeds `COMFYUI_VERSION` (R-21), and a recipe whose minimum exceeds its own exercised-through
version (R-18).

## 3.3 Definition of done

- [ ] Typecheck, build and test pass across workspaces
- [ ] No raw ComfyUI graph is reachable from the renderer, a take, or a log line
- [ ] A location override is honoured identically by presence detection and by dispatch
- [ ] A pinned-dependency mismatch is refused before any network call to the engine
- [ ] The application starts and remains usable with the engine absent, unreachable, or crashed
- [ ] Reviewer approved

## 3.4 Decision log

| # | Decision | Rationale |
|---|---|---|
| D1 | *Superseded by D10.* Whether the managed install ships was deferred; discovery-only ships regardless | Packaging a portable Python/CUDA runtime was judged standing maintenance. D10 resolves it: the upstream portable build is pinned, digest-verified and extractable with tooling already in the tree, which is what changed. |
| D2 | Recipes, not graphs, are the unit of work | ComfyUI's surface is strictly more powerful, and more dangerous to expose, than any vendor's fixed model list — the same curation principle as the model manifest, pushed one layer further. |
| D3 | *Resolved by D11.* Custom nodes lean toward vendored, not fetched at install | A third-party node is code that runs on the user's machine; fetching it unpinned at install time is a supply-chain surface this feature does not need to open. |
| D4 | A recipe prices as `unmetered`; the proposed `local` kind is withdrawn | A recipe is structurally free rather than free by coincidence of rate — and `unmetered` already carries precisely that meaning, already prices Kokoro, whisper.cpp and every Ollama row, and is already the word R-12 uses. A second arm behaving identically to an existing one is a case every estimator has to learn twice. §2.3. |
| D5 | User-directed engine and models folder take priority over any Arke-managed copy | ComfyUI users routinely hold tens of gigabytes of curated checkpoints; shadowing that with a second download is the worst possible first impression. |
| D6 | Dependency verification runs pre-flight, not post-hoc like manifest drift | A local recipe has no provider-reported charge to diverge from; the only knowable signal is what is actually on disk, checkable before dispatch. |
| D7 | VRAM gating reuses `probeRuntime()`'s registry read — neither `nvidia-smi` nor `Win32_VideoController.AdapterRAM` | The WMI field truncates at 4 GB on any larger card, misreporting exactly the machines this feature depends on sizing correctly. But the shipped probe already avoids it by reading `HardwareInformation.qwMemorySize`, which needs no external binary and is not NVIDIA-only, so the `nvidia-smi` requirement an earlier draft carried would have rebuilt a solved problem more narrowly. Measured on an RTX 3080: 10240 MB, against `AdapterRAM`'s 4 GB. §2.7. |
| D8 | *Withdrawn — see D12.* `supportsListRecent` via a key embedded in the graph's metadata | The proposed flag combination is unreachable in the dispatcher (`reconcileStrategy` requires `supportsIdempotencyKey` alongside it), and `extra_pnginfo` propagates into output metadata — the exact channel §2.10 strips. A mechanism that cannot execute and would leak was two reasons to withdraw it. |
| D9 | ComfyUI rather than a purpose-built local runtime, but only where a native sidecar cannot serve | The cost this spec is avoiding is Python plus CUDA, which every alternative runtime also pays — so a lighter Python runtime saves nothing on the expensive part and gives up a model zoo that tracks new architectures within days. Where a maintained *native* implementation exists there is no such trade, which is why speech already runs on `whisper.cpp` and Kokoro in the Voxa sidecar and never needs ComfyUI. §2.1. |
| D10 | The managed install ships as a pinned `tree` component; selection wins and detection only offers | The upstream archive installs atomically. A selected user path or URL is reused, while a default-port or well-known discovery remains an explicit offer and does not suppress managed Download. §2.4. |
| D11 | v1 ships zero custom nodes; any future node is vendored | Both shipped recipes run on core nodes alone, which closes D3's supply-chain question by not opening it — while the pinned-node verification machinery still ships and is tested, so the first recipe that needs a node pays only the vendoring cost. §2.3. |
| D12 | All three reconciliation flags are false; the honest user decision covers the one real window | The list-recent path is unreachable without `supportsIdempotencyKey`, and the only correlation channel leaks into output bytes. All-false selects ask-user, whose held copy prices a duplicate honestly as GPU time; spawned engines requeue outright because a relaunched engine provably holds no old work. §2.6, §2.11. |
| D13 | A URL is probed, never spawned, and recipes stay disabled against it unless `comfyUiModelsDir` maps its files | Bytes on another machine cannot be hashed from this one, and R-9 trusts bytes, not names. The disabled reason states verification is unavailable — the files are not "missing". An explicit models-dir mapping is the user's assertion that R-9 can run locally, and it is the only unlock. §2.2. |
| D14 | The API floor is `/system_stats` ≥ 0.3.45 plus a per-recipe `/object_info` node probe; cancel is targeted by id | 0.3.45 is where the shipped video recipe's core nodes appear; `/object_info` answers per recipe, so a breaking engine change disables one recipe with the node named. `/interrupt` alone would interrupt whoever happens to be executing on a shared engine — cancel deletes a pending prompt by id and interrupts only a running prompt it can prove is its own. §2.6. |
| D15 | Unknown hardware lists as unknown and dispatch is permitted with the unchecked floor stated | Refusing on a failed probe would disable local generation forever on any machine whose registry read fails — a false "disabled" is the one failure §2.7 exists to prevent, and the engine's own out-of-memory error is an honest failure where a silent gate is not. §2.12. |
| D16 | Progress comes from the engine's per-node step counter, never from queue position or elapsed time, and is stated with the stage it counts | The original exclusion's objection was to a figure that moves like a fraction without being one, and queue position is exactly that. A sampler's `value`/`max` is a real fraction of a real node. State-only left a half-hour run indistinguishable from a wedged engine, which is the honest-failure principle of §2.12 pointed the other way. A graph is not a step, so an unlabelled bar reintroduces the original problem from a better source. §1.2. |
| D17 | A recipe carries its own engine-version floor and an exercised-through ceiling; the managed runtime's currency is reported and offered, never applied | D14's per-recipe promise is delivered by the node probe alone, which reads class names and not signatures, so a floor raised for one new recipe would disable every older one and name the wrong cause — a recipe's own floor keeps the blast radius where D14 put it, and the module floor goes back to meaning what the client's API shape needs. Above the exercised ceiling an engine is warned about rather than refused, per D15: a false disabled is worse than an honest engine error, and newer is the direction a user's own engine drifts. And the managed install was never current in the first place — `isPresent()` asks only whether the tree exists, so a bumped pin reaches new installs only; the remedy is a stated update the user chooses, because D5's refusal to shadow what a user already has covers their bandwidth too. §2.4, §2.6. |
| D18 | The managed update is a tree replace that stops the engine and preserves the models folder, not the Repair path; and the pinned runtime may never sit below a shipped recipe's floor | Repair takes `files` components only, `retry()` returns early on anything `present`, and `remove()` refuses while a weights entry declares `requires: ["comfyui-runtime"]` — so the machinery D17 first pointed at cannot reach a `tree` at all. Replacing one has three costs the download path never had: a running engine holds its own files open — though only the *managed* child may be stopped, since a user-directed path is supervised identically and the case being served is precisely a stale tree behind somebody else's running engine; an unoverridden managed install keeps its checkpoints *inside* the tree, so a wholesale swap would delete six gigabytes of verified weights to install an engine; and the install's `rm`-then-`rename` has nothing to lose on a first install and everything to lose on a replacement. The pin invariant is the same failure approached from the other side — a recipe whose floor outruns the pinned runtime is dead on arrival for every managed user, and R-20 is silent because installed and pinned agree. A review cannot be relied on to notice either. §2.6. |
