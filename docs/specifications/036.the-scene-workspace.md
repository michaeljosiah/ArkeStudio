# 1 · Requirements

## 1.1 Summary

The Scene Workspace is where a creator turns a written scene into rendered footage. It owns one
scene at a time; everything upstream (episode, world, sheets) and downstream (cut, exports)
lives elsewhere. It answers four questions in order: what happens (script), what does each
moment look like (frames), which moments must be generated together to stay consistent
(boards, SPEC-035), and does it play (preview).

Today those questions are answered across six screens with six generate-shaped controls, all of
which navigate to one dispatch dialog — a dialog that opens on `scenes[0]` regardless of which
scene sent you. This specification replaces that geography with one surface, and retires the
dispatch dialog as a destination.

It re-scopes SPEC-029's rollout steps 5–7 rather than competing with them: the vertical
Storyboard and the Flow view land as that rollout describes, with the group semantics amended
by SPEC-035 (derived boards, authored splits/merges) and the surface details bound here. The
reference implementation is `design-system/scene-workspace-vertical.html`, described feature by
feature in `design-system/scene-workspace-vertical.notes.md`; where prototype and this document
differ, this document wins, and §3 records each deliberate difference.

Two principles govern the whole surface:

1. **The scene is authored top to bottom, and every derived thing states where it came from.**
   Nothing is silently inferred without being visible.
2. **One owner per decision** (R-30). Board membership, script text, bulk frame generation,
   single-artefact generation — each has exactly one owning surface, and every other surface
   links to the owner rather than duplicating the control.

## 1.2 Bound decisions

1. **Words mean one thing each.** `Generate frames` produces stills; the word *scene* in a
   spending control is reserved for video. `Board` means SPEC-035's derived board and nothing
   else; the locally compiled review sheet (today `scene.board`) is renamed on-surface. This
   amends SPEC-012's vocabulary.
2. **Frames land on the frame slot, filed as an artifact.** A generated still becomes the
   shot's current frame the moment it lands — the run the user confirmed was the
   authorization, and a second accept per frame would be a toll on a decision already made.
   It is filed on the artifact shelf and named by `selections[shot].startFrameArtifactId`,
   the same field a chained boundary still uses, because **that is the only frame a dispatch
   can send**: the request records `{id, hash}` so the exact bytes can be audited, and a take
   carries no hash. `acceptedTakeId` remains the clip slot. This amends SPEC-013 and feeds
   SPEC-019 R-26's steering unchanged.
3. **A run is the queue, watched.** The run bar is a client view over ordinary jobs (SPEC-009)
   plus a durable run record that sequences them (§2.7) — cancel is the queue's own `cancel-job`;
   pause is the record's advance gate, because the queue has no pause primitive and inventing a
   private engine to fake one is the failure this decision exists to prevent. Navigating away
   loses nothing.
4. **Every retry goes through one path.** Append a new step, let the run bar cover it — from
   the row strip, the report card, and the board sheet alike, and only where SPEC-009's
   classification says a retry is honest (R-18). Two retry paths produced two consecutive
   prototype bugs (a failure banner over a good frame).
5. **The review surface for consistency is the board sheet, not the single frame.** A shot out
   of context always looks fine; drift is visible only side by side.
6. **Preview never lies.** A still is labelled `still · animatic`; motion is labelled
   `motion · rendered`; a frameless shot shows a placeholder, never black.

## 1.3 Scope

**In scope:** the workspace layout and header; the view tabs (Storyboard, Flow, Preview); the
storyboard rows; board bands and their controls; the consolidated prompt; the board sheet
artefact; the `Generate frames` dialog, run bar, failure and retry; frame landing and the
frame slot; the handoff to the generation session (the bench) with provenance; Arke's
narration and report card; scene completion and the exit; the retirement list; cross-cutting
timing and overlay rules.

**Out of scope:** the packing algorithm (SPEC-035); the rich node canvas with reference,
audio and clip nodes (a later specification — its ref/audio/clip nodes conflict with SPEC-029
R-24/R-25 and that conflict is resolved there, not here; until then Flow is SPEC-029's view as
issues #605/#606 scope it); the whole-scene *video* render queue (SPEC-024 plans already model
it; wiring boards to passes is SPEC-035 R-13 and lands with the rendering epic); audio as a
generation reference (a SPEC-019 amendment gated on model capability); voice generation
(SPEC-011/022, reached by link).

## 1.4 Layout and header (R-1..R-5)

- **R-1** The workspace SHALL be the scene detail route, laid out as SPEC-029 R-21 describes:
  scene context in the chrome, the active view in the centre, Arke docked on the right with
  the current selection as its subject. Overlays — lightbox, board sheet, generate dialog —
  mount on the app frame and cover it entirely, including the rail and the dock. *Scoping them
  to the centre column left a third of the app lit and interactive behind a modal.*
- **R-2** The header SHALL carry: breadcrumb (production · episode · scene), title, an
  editable synopsis saving in place (turn 97's rules), the inherited scene context as quiet
  chips (location, time, look, aspect), and the metrics line — `5 shots · 22.5s · 3 frames
  filed` — every number derived, none stored.
- **R-3** The header SHALL offer exactly two actions: `Review scene` (the existing SceneReview
  strip, unchanged) and **`Generate frames`** (primary). There is exactly one `Generate
  frames` control on the surface; every other frame-shaped control is per-shot or per-board.
- **R-4** The view tabs SHALL be `Storyboard` (default) · `Flow` · `Preview`, with the
  coverage line (`2 of 5 without a frame`) and the `Show boards` toggle on the same row. Both
  hide while a run owns the row (R-16).
- **R-5** The production aspect governs every thumbnail, cell and stage in the workspace
  (issue 389's discipline): a 9:16 production gets 9:16 frames, cells and preview. Nothing in
  this specification is landscape by assumption.

## 1.5 Storyboard rows (R-6..R-10)

The vertical storyboard of SPEC-029 R-23, bound to the prototype's row anatomy.

- **R-6** A row SHALL read left to right: the **frame region** (the still, or a hatched
  `no frame yet`; the shot label as the drag handle; aspect · duration · lens along the
  bottom; hover reveals preview and `Prompt` / `Variants` / `Upload`; run states overlay
  here), the **body** (title line with the state chip; the `script changed · Re-read` strip
  where SPEC-023's digests say so; **the script as the dominant text**, editable in place with
  the `@` picker; the optional assembled prompt behind a disclosure with `Rebuild`; reference
  chips inferred from `@` usage; override labels only where a value differs from the scene),
  and the **actions column** (`Generate frame` or `Regenerate` beside the `⋯` menu, and a
  fixed slot beneath for `prompt · auto` / `edited by you` and `Edit` — fixed, because in a
  wrapping row it jumped as content reflowed).
- **R-7** The state chips SHALL be exactly: `story` (script written, no frame — a legitimate
  state, not an error), `storyboard` (framed, not final), `production-ready`, `needs
  attention`, and `rendered` (a clip exists). All derived, none stored — the existing
  `cardState` vocabulary gains `rendered`, keyed on the clip slot.
- **R-8** Between rows, at rest, SHALL be a hover-only divider offering insert (`+`); with
  boards on it also offers `Split board here`; during a band drag it becomes the labelled
  drop target for the boundary. All three write through SPEC-029's semantic commands —
  insert-on-edge, and SPEC-035's split/merge overrides.
- **R-9** Editing SHALL follow turn 97 unchanged: a hand edit saves where it stands, versioned,
  restorable; an assistant edit stages and lands under `Apply changes` / `Keep discussing`.
  This surface adds no new write path.
- **R-10** Reference chips SHALL be inferred from `@` tokens; an explicit add exists only for
  things the script does not name. Removing the token removes the chip.

## 1.6 Board bands (R-11..R-14)

- **R-11** With `Show boards` on, a band SHALL head each board's first row: drag handle and
  letter, member range, the split reason (R-10 of SPEC-035), duration against the cap, two
  icon controls (`Consolidated prompt`, `View board sheet`), and `Merge up`. Warnings (amber)
  and lighting accents (neutral) render beneath the band, visually distinct.
- **R-12** The band name SHALL be the drag handle: dropping it on a divider moves the boundary
  — one gesture writing one split and, where it suppresses an automatic break, one merge, with
  the carried warning appearing immediately (SPEC-035 R-11). No drag can breach the cap.
- **R-13** `Consolidated prompt` SHALL expand one editable prompt for the whole board: scene
  context first, then the member shots as numbered beats with size and lens — assembled by a
  **new** helper over the members' `assembleBlocks` output. Never `storyboardPrompt`: that is
  the line-art drawer's private prompt — rough black-and-white panels, no colour, no rendering
  — and reusing it would steer paid video toward a storyboard drawing. Editable as an
  override, `Rebuild` reassembling from current scripts. Without this, board mode is a black
  box.
  - **An edit is authored state with a stable owner** (SPEC-035 R-4's `boards.prompts`): it is
    stored keyed by the board's frozen member-id set, because letters renumber and boards are
    never stored. A repack that changes the membership retires the override at read — the
    prompt visibly returns to `auto` — and never silently attaches the words to different
    shots. The prototype kept these in component state keyed by letter; that is one of §3's
    recorded divergences, not a behaviour to port.
- **R-14** `View board sheet` SHALL open the board as one image: numbered cells in the
  production aspect (2 columns to 4 members, 3 beyond), each labelled with shot and duration.
  Per-cell **Retry** regenerates that cell against the rest of the sheet as reference; **Retry
  board** redoes the pass; both through the one retry path (R-18). Cells without frames read
  `no frame yet`. The footer states the contract: one image, one pass — cast, light and grade
  are shared.

## 1.7 Generate frames — dialog and run (R-15..R-19)

- **R-15** The dialog SHALL state, in order: a live title (`Generate 2 frames`); the method as
  two cards stating consequences, not techniques — *Per shot* ("fastest, cheap to retry, but
  characters and light drift between shots") and *Shot board* (default; "holds cast, light and
  grade together — a retry redoes the whole board"); in board mode, the packing preview —
  `5 shots → 2 boards`, one card per board with range, duration against cap, headroom (amber
  under 2s), split reason, warnings; the scope — `Shots without a frame` / `Every shot`,
  defaulting to whichever is non-empty — and in board mode the scope narrows **which slots
  update, never what the request carries**: a board render always sends the whole board, with
  already-framed members riding as fixed reference cells, because a lone missing cell
  generated without the cells it must match is the drift this feature exists to prevent (the
  prototype filtered members out of the step; recorded divergence, not behaviour); the model chips with caps, repacking live; and a
  footer with the inherited context, the derived estimate (`2 frames · about 14s`, never
  hardcoded), Cancel, and the primary.
- **R-16** The zero-frame guard SHALL hold at three layers: the scope defaults to *every shot*
  when nothing is missing; a scope resolving to zero replaces the primary with the sentence
  saying why; and the run refuses to start empty. *All three — the first build hung on
  `0 of 0 frames` with only Cancel as an exit.*
- **R-17** Confirming SHALL start the run in place: no modal, no progress screen. The toolbar
  row becomes the run bar and owns the row — progress, current step, count, ETA, Pause,
  Cancel; the two controls never shrink, the label clips first. In board mode a board goes
  active together and its frames land together. Rows stay editable throughout: an edit
  mid-run marks `script changed`, it never blocks. The run is jobs on the queue (SPEC-009)
  sequenced by the durable run record (§2.7); **Pause is the record's advance gate** — the
  queue has no pause primitive and in-flight remote work cannot be suspended, so pausing stops
  the next step from materialising while what is in flight settles, and the bar says so
  (`paused · finishing 2`). Leaving the route and returning finds the bar where it was.
- **R-18** A failed frame SHALL be labelled by the queue's own failure classification
  (SPEC-009 R-7), and the run continues past it. A *retryable* failure — bad output, a
  transient the queue exhausted — reads `came back dark · Retry` on a red strip. A
  *terminal* failure (content policy, invalid parameters, unknown model) shows its actual
  reason and **no Retry**: re-queueing a terminal refusal spends again on the same answer,
  which SPEC-009 forbids. A *provider fault* pauses its lane exactly as SPEC-009 already
  prescribes, and the strip says which. Every retry that is offered — row strip, report
  card, board sheet cell, whole board — SHALL go through one requeue path that appends a new
  step; there is no second path.
- **R-19** Completion SHALL collapse the bar to `5 frames added · 1 failed` with **Review**
  and a dismiss. Review opens the first new frame in the lightbox to arrow through. No
  success screen.

## 1.8 Frame landing and the frame slot (R-20..R-22)

- **R-20** *(amends SPEC-013)* A frame-run result SHALL land as a take (durable, priced,
  provenance-carrying, exactly as today) **and** be filed as an image artifact whose id the
  shot's `startFrameArtifactId` names. No second accept. The clip slot (`acceptedTakeId`) is
  untouched; video acceptance keeps its ceremony.
  - **An artifact, not the take pointer.** A dispatch sends `{id, hash}` so the bytes it used
    can be audited afterwards, and a take has no hash to give — so a frame named only by its
    take could be shown by the workspace and never sent by the route. Filing earns a drawn
    frame the durability a chained one already has: its own bytes, its own hash, and a life
    independent of the take it came from.
  - **A drawn frame outranks a chained one.** The frame slot has two writers: this, and the
    continuity chain that seeds the *following* shot when a take is accepted (SPEC-013 R-12).
    The continuity chain SHALL NOT overwrite a frame the shot was given. Drawing every shot
    and then accepting takes one by one would otherwise replace each following shot's frame
    with its predecessor's footage — silently, and exactly where the point of drawing first
    was to choose what each shot opens on. A shot that wants the predecessor's footage asks
    with `continuity.continuesPrevious` (SPEC-019 R-50).
  - **The two are told apart by provenance already on the sidecar**, never by a new flag: a
    boundary still carries `boundaryExtraction` naming the take it was cut from; a drawn frame
    does not. The guard SHALL be applied both where the accept writes and where the extraction
    later writes, because the extraction re-reads the selections file and would otherwise
    overwrite a frame filed in between.
  - **The landing synchronises both frame pointers, and the slot must be dispatchable.** The
    same commit that sets `startFrameArtifactId` clears the legacy `startFrameTakeId` — that
    pointer names footage that steers, and left standing beside a picture the shot was given
    it would be a second answer to what the shot opens on, still reaching every consumer
    that reads it. Because every frame is filed as an artifact, `resolveBoundaryFrames`
    needs no widening: the slot it already reads is the one being filled, and a frame in the
    slot always carries the `{id, hash}` the dispatch audits.
- **R-21** *(amends SPEC-013)* Accepting a *still* from any surface — the contact sheet
  included — SHALL target the frame slot, never the clip slot. Today's contact-sheet accept
  misfiles a still into `acceptedTakeId`, where it collides with clip acceptance.
- **R-22** Superseding is not deletion: a re-generated frame replaces the slot; the previous
  take remains browsable under `Variants`, and restoring one is setting the slot back. If a
  board is rendered after a shot has a solo clip, the board's result takes the slot and the
  solo clip becomes an ordinary unselected take — the newer decision wins, the older one
  survives as history.

## 1.9 The generation session (R-23..R-25)

This is the screen where the actual clips are generated — the single most consequential
surface in the workspace — and it is **the bench**, extended, never a bespoke dialog beside
it. The bench already owns modes, references, prompt assembly and enhancement, priced model
presets, dispatch, and a take rail; this section adds a *subject* and the filing that follows
from one.

- **R-23** Single-artefact generation SHALL hand off to the bench, prefilled from its subject.
  - **WHEN** opened from a shot's `⋯ → Open in generator` **THEN** the session opens in image
    mode with: the shot's resolved `@` references as reference tiles (each named, with its
    sheet version); the shot's assembled prompt (or its override) in the composer with the
    `@` picker live and `Rebuild` reassembling from the current script; context chips —
    `aspect · <production aspect>`, `duration · <shot's>`, seed; and the priced presets.
  - **WHEN** opened from a band's `Render board` **THEN** the session opens in video mode
    with: the board's consolidated prompt (SPEC-036 R-13); the member shots' references
    merged, first appearance order, deduplicated by sheet; the members' accepted frames as
    the visual reference tiles, under the keyframe rules SPEC-019 already binds — **never the
    compiled board sheet**: SPEC-019 R-49 forbids that dense labelled grid as a generation
    reference and this specification does not amend it (the sheet is the human's review
    surface, R-14, not the model's input); chips `aspect`, `duration · <board total>`,
    `sound · on`; and any
    audio attached to member shots as a waveform tile (`voice sample · @maren · 9.0s`) that
    rides the request where the model's route accepts audio, and is named as not riding
    where it does not — never silently dropped.
  - **WHEN** opened with no subject (today's world-scoped bench) **THEN** nothing changes.
- **R-24** The session SHALL carry provenance, and Accept SHALL file.
  - The header names the chain — production · episode · scene · subject (`Shot 15` /
    `Board A · 3 shots · 13.5s · one pass`) — never `Untitled session`. The subject is part
    of the session record, survives reopening, and is what Accept consults.
  - The take rail and centre preview keep the bench's existing behaviour, with the states the
    prototype binds: a generating take is a hatched placeholder with a spinner; a video take
    plays on a real transport showing elapsed over real duration (R-29's clock rule applies);
    the filter is All / Filed / Discarded.
  - **Accept / Discard sit directly below the playback view**, with the outcome stated beside
    them in one line: `accepting files the frame onto shot 15` / `accepting files the clip
    onto 3 shots`. **WHEN** an image take is accepted **THEN** it lands on the subject shot's
    frame slot (§1.8). **WHEN** a video take is accepted for a board **THEN** each member shot's clip slot
    selects **its own per-shot segment take** — the children arrival already derives from a
    pass (`segment: {passTakeId, inSec, outSec}`), charge-split pro-rata — while the parent
    take (`coversShots` = the members) is kept as provenance and **never selected**: the cut
    rejects a multi-shot parent as `backing-pass` material, so selecting it would show
    `rendered` rows over a preview and export with nothing valid to play. Rows flip to
    `rendered`; one line logs to Arke with the affected shots as report rows. Discard files
    nothing anywhere.
  - A board render **replaces** each member's previous selection under the ordinary rules;
    a member shot's earlier solo clip survives as an unselected take (R-22).
- **R-25** The dispatch itself SHALL be the existing machinery, whole: the request compiled
  the way `compilePasses` compiles a board's members today, priced by the same estimate the
  preset chips show, recorded as a job, landed by take arrival — no second dispatch path, no
  session-private queue. `~$3.63 a take` on the button and the button spends exactly that.

## 1.10 Arke — narration and the report card (R-26..R-27)

- **R-26** Arke SHALL be docked on the scene (the same `ProductionConversation` that docks on
  the season and the episode, one level further down — this retires `Talk it through` and the
  separate scene-chat screen). The header follows the selection: `Arke · Shot 15`, the frame
  as thumbnail. Selection alone provides context.
- **R-27** After a run, Arke SHALL narrate the outcome in one sentence and show a report card:
  one row per step, one row per failure with a live `Retry` where R-18 offers one. Rows
  reconcile against live state, **by evidence and never by presence — and the evidence is
  causal**: a failed row flips green and reads `came back dark · retried` only when a
  successful take for that shot arrived from **this run's own jobs** — the original step or
  a retry step appended for it — never merely a newer take from anywhere: a bench session or
  an unrelated run landing a frame later does not prove this failure was retried, and one
  later take must not reconcile several older failures it belongs to none of. A shot
  regenerated over an old frame whose retry failed still shows the failure. Original words
  are kept as history. *Rows built from a frozen snapshot
  contradicted the rest of the app within seconds.* Clicking a row selects that shot.

## 1.11 Preview (R-28..R-29)

- **R-28** Preview SHALL play the scene end to end on the shots' real durations: the current
  frame on the stage with an honest badge (`still · animatic` / `motion · rendered`), title
  and lens along the bottom, a transport with elapsed over total, and a filmstrip where every
  shot is sized proportionally to duration, the live shot lifted, board boundaries drawn as
  vertical rules, frameless shots hatched. Click seeks. The current shot's script sits
  beneath. Once clips exist it plays them in place of stills.
- **R-29** Every clock in the workspace SHALL compute elapsed from a start timestamp — never
  accumulate per tick. *The prototype accumulated `+0.1` and ran at 0.27× real time, then
  stalled.* Pause freezes the position; the end holds; changing subject resets.

## 1.12 Completion and the exit (R-30..R-31)

- **R-30** One owner per decision, and this table is normative:

  | Decision | Owner |
  |---|---|
  | Board membership | The bands (split · merge · boundary drag) |
  | Script text | The row (and the shot sheet — same field) |
  | Bulk frame generation | Header `Generate frames` |
  | Single-artefact generation | The generation session — **including a single board's
    render**: one pass, one price, one press on the session's own priced `Generate`, the same
    authorization every bench dispatch and the voice dialog already carry (R-25: same
    compilation, same estimate, same queue — no plan is created for one pass) |
  | Multi-pass video authorization | SPEC-024 plans, reached from the band — anything that
    runs more than one pass, chains continuity, or pre-authorizes a cap |

  Every other surface links to the owner. The dispatch dialog ceases to be a destination:
  its estimates, strategies and warnings live behind the plan's `Generation options`; its
  route is retired with a redirect. The takes-view `Scene` seg entry, the bench `Generate…`,
  and the shot card's misnamed `Generate frame` (which navigated to a review surface) are
  rewired to their owners.
- **R-31** The workspace SHALL have an exit: a scene whose shots are all `production-ready`
  or `rendered` offers `Done · back to the episode`, marking nothing — completion is derived
  from the shots, and the episode board reads it from the same derivation. No lock, no stored
  status.

# 2 · Design

This section is written to be implemented without further interpretation: files, schemas,
wire frames, and reference code. Where a code block appears, its behaviour is normative.

## 2.1 What already exists, and is reused unchanged

Takes, selections, accept/reject with citation (SPEC-013); coverage digests and `Re-read`
(SPEC-023); `promptOverride` and `Rebuild` (SPEC-012 R-15); `ShotFraming` inheritance and
override dots (turn 97); `SceneReview` (turn 102); the bench and its enhancer; the queue, its
notification row, SPEC-024 plans and pre-authorization; `storyboardPrompt` and
`assembleBlocks`; the aspect gates of issue 389. The workspace is an assembly of these behind
one surface — the new machinery is the packer (SPEC-035), the frame run, the frame slot
commit, the band controls, and the report card.

## 2.2 What is retired

`SceneChatScreen` and its route; `Talk it through`; the dispatch dialog as a navigated
destination (`/generate/dispatch` redirects into the workspace; the dialog's contents become
the plan drawer's `Generation options`); the takes-view `<select>` shot picker's `Scene` seg
destination; the compiled review sheet's on-surface name `Board` (it becomes the board sheet
of R-14's lineage — SPEC-029 R-45's derived projection — under a name that no longer collides).
The `scenes[0]` dispatch-dialog bug dies with its screen, and is fixed in place until then
(issue filed separately).

## 2.3 Rollout

Lands as the re-scoped SPEC-029 steps: the consumer sweep and semantic commands first
(#602, #604 — group lifecycle re-scoped to SPEC-035's splits/merges), then the vertical
Storyboard (#605, rows per §1.5), editing and bands (#606, re-scoped), then frames-and-boards
generation (#607, re-scoped to derived boards + the run of §1.7). The frame slot (§1.8), the
session handoff (§1.9), narration (§1.10), Preview (§1.11) and the retirements (§1.12) are
new issues under the same epic. The old horizontal strip goes only at the end (#608),
unchanged.

## 2.5 The state chips

`cardState` (`packages/client/src/screens/storyboard.tsx:82`) is today
`blank | story | board | ready`, labelled `needs attention / story / storyboard /
production-ready`. It gains `rendered`, and the derivation stays a pure function of what
exists:

The precedence is exhaustive — every consumer (rows, R-31's completion, the episode board)
derives from this one function and none invents its own reading:

```ts
function cardState(input: {
  blankScript: boolean;     // shot.description empty after trim
  clipAccepted: boolean;    // acceptedTakeId names a take of kind "clip"
  hasFrame: boolean;        // a DISPATCHABLE image stands in the frame slot: a pinned image
                            // artifact that resolves (present, image-kind, unsuperseded).
                            // A `startFrameTakeId` pointer — continuity steering — does NOT
                            // count: the resolver reads only the artifact slot, and
                            // completion offering `Done` over an unsendable frame is
                            // the lie this predicate exists to prevent.
                            // (A legacy still misfiled in acceptedTakeId counts HERE, as a
                            //  frame — old worlds hold them and they are framed, not rendered)
  coverage: "fresh" | "changed" | "uncovered";   // shotCoverage — SPEC-023 digests
}): CardState {
  if (input.blankScript) return "needs attention";      // red — nothing to generate from
  if (input.clipAccepted) return "rendered";            // near-black — a clip exists
  if (!input.hasFrame) return "story";                  // neutral — written, unframed, legitimate
  if (input.coverage !== "fresh") return "storyboard";  // amber — framed, but the script moved on
  return "production-ready";                            // green — framed, current, ready to render
}
```

R-31's completion — and the episode board's rollup — read `production-ready | rendered` from
exactly this derivation. A run failure never changes a chip: failures live on the run strip
and the report card (R-18, R-27), because a failed *attempt* does not change what the shot
*has*.

## 2.7 The frame run

The queue has cancel (`cancel-job`) and **no pause**, so pause is designed at the run level:
jobs are enqueued step by step, and pausing stops the advance. The run is a durable
operational record — like `selections.json`, it is operational state, never gated — folded
with live job facts, never a timer (SPEC-024's discipline).

**Record** — `productions/<p>/runs/<runId>.json`, `packages/contracts/src/frame-run.ts`:

```ts
/** A step's inputs, frozen when the dialog's confirm authorized them (§2.7). */
export const FrameStepRequestSchema = z.object({
  prompt: z.string().min(1),                       // compiled at confirm; a cell retry reuses it
  /**
   * Ordered panel mapping for a board sheet; a per-shot step has exactly one entry. A fixed
   * cell — an already-framed member riding for context — freezes its dispatchable image HERE,
   * at confirm: reading it from live selections at enqueue would rebuild the request from a
   * world that may have moved during a pause or a slow queue, which is exactly what freezing
   * exists to prevent. An update cell has no image; its slot is what the step writes.
   */
  panels: z.array(z.object({
    panel: z.number().int().min(1),
    shotId: ShotIdSchema,
    role: z.enum(["update", "fixed"]),
    fixedImage: z.object({
      source: z.enum(["take", "artifact"]),
      id: z.string().min(1),
      path: z.string().min(1),                    // the media path frozen at confirm
    }).strict().optional(),                       // required when role is "fixed" (validated)
  }).strict()),
  /** What rides: sheet references with the versions they were compiled at. */
  references: z.array(z.object({ sheetId: SlugSchema, version: z.number().int().min(1), path: z.string().min(1) }).strict()),
  aspect: z.string().min(1),
  /** Per update-shot, the frame-slot value standing at authorization — the R-22 guard. */
  slotAtAuthorization: z.record(ShotIdSchema, z.string().nullable()),
}).strict();

export const FrameRunSchema = z.object({
  id: prefixedIdSchema("fr"),
  sceneId: SceneIdSchema,
  sceneVersion: z.number().int().min(1),          // staleness is derivable, never stored
  mode: z.enum(["per-shot", "board"]),
  model: z.string().min(1),
  // One step per board (board mode) or per shot (per-shot mode), frozen at start with the
  // packing that produced it — the run survives a repack of the live surface.
  steps: z.array(z.object({
    label: z.string().min(1),                     // "Board A" / "Shot 15"
    // What the request carries vs what it may change: a partially framed board sends every
    // member (framed ones as fixed reference cells) while only the selected missing shots'
    // slots update at landing. The two are frozen separately or the distinction cannot
    // survive navigation, pause, or resume.
    requestShotIds: z.array(ShotIdSchema).min(1), // the whole board, always
    updateShotIds: z.array(ShotIdSchema).min(1),  // the slots this step may write
    /**
     * The compiled request, frozen when the user confirmed the dialog — prompt text,
     * ordered panel mapping, reference list with sheet versions, aspect, model params, and
     * per-update-shot the frame-slot value standing at authorization (null for none).
     * A later step enqueued after the user edits a shot or a sheet must spend on what was
     * authorized, not on the live world; and arrival compares the recorded slot value so a
     * slow job never overwrites a choice made after it was authorized (R-22).
     */
    request: FrameStepRequestSchema,
    jobId: z.string().min(1).nullable(),          // null until this step is enqueued
  })),
  cursor: z.number().int().min(0),                // first step not yet enqueued
  paused: z.boolean(),
  cancelled: z.boolean(),
  createdAt: IsoDateTimeSchema,
}).strict();
```

**Coordinator** (`productions/frame-run.ts`): `startFrameRun` builds steps from the dialog's
scope + `packBoards`, **freezes every step's compiled request at that moment** (the dialog's
confirm authorized these inputs and no others), refuses zero steps, writes the record, and
enqueues step 0.

- **Per-shot mode:** one image job per shot — `target: { kind: "shot", id, coversShots:
  [id] }`, `params: { frameRun: runId, landing: "frame-slot", request }`.
- **Board mode: one board-sheet job per board, never one per member** — independent calls
  cannot structurally share the cast, light and grade the method card promises, which would
  quietly rebuild per-shot generation under a board label (SPEC-035 R-12). The job is image
  capability, `target: { kind: "board-sheet", coversShots: requestShotIds }`, the frozen
  panel mapping in the request. The result is **one immutable parent sheet**; each
  update-target's panel is extracted as a **child image take** with deterministic crop
  geometry, hash, parent job and panel mapping — SPEC-029 R-44's exact machinery, and R-44's
  "not silently" is satisfied because the run the user confirmed is precisely the
  authorization to file these panels — and each child lands on its shot's frame slot
  (§2.8). Fixed reference cells land nothing.

On a job's terminal event: if every job of the current step is terminal and `!paused &&
!cancelled`, advance `cursor` and enqueue the next step. `pauseFrameRun` sets `paused`
(in-flight jobs finish; the bar says `paused · finishing 2`). **`resumeFrameRun` clears
`paused` and then performs the same advance check the terminal handler performs** — a step
whose last job settled while paused has no future event left to advance on, and a resume
that only flipped the flag would stall the run permanently. `cancelFrameRun` sets
`cancelled` and sends `cancel-job` for every non-terminal job.

**Retries are step-scoped, so board context survives them — the one retry path has two
grains and one implementation:** `retryFrameStep(runId, stepIndex)` re-enqueues that step's
frozen request whole (the `Retry board` button — one pass again, same panel mapping).
**A retry re-snapshots `slotAtAuthorization` at its own authorization** while keeping every
creative input frozen: the first attempt's landings changed the slots, and a guard still
holding the original values would read the run's own results as newer user decisions and
refuse to file the replacements — the retry press is a fresh authorization for the slots as
they stand at that press.
`retryFrameCell(runId, stepIndex, shotId)` appends a single-cell step whose request carries
the parent step's frozen context **and the board sheet as its reference** — which is what
"retry this cell against the rest of the board" means; the sheet is that retry's *input*, an
image conditioning an image, not a video reference (SPEC-019 R-49 is about video routes and
stands). Both clear nothing — the failure flag *is* the old job's terminal state — and the
report reconciles (R-27) when the new result lands. Both refuse a failure SPEC-009
classifies as terminal (R-18), classification named; the surfaces never offer Retry there,
and the coordinator holds the same line for a stale client.

**Wire frames** (added to `packages/contracts/src/frames.ts`, client senders in `store.ts`):
commands `frame-run-start`, `frame-run-pause`, `frame-run-resume`, `frame-run-cancel`,
`frame-run-retry-step`, `frame-run-retry-cell`; event `production.frame-run` carrying the folded state (record + per-job
status/ETA), emitted on every change, exactly as `production.plan-*` events flow today. The
run bar renders that event and sends those commands; it holds no state of its own, which is
what makes leaving and returning free (T-8).

## 2.8 The frame slot — two touch points, no third

1. **Arrival** (`takes/arrival.ts` → `takes/drawn-frame.ts`): after the take record is
   written, a job carrying `params["landing"] === "frame-slot"` files each landed still as an
   image artifact and points that shot's `startFrameArtifactId` at it, clearing
   `startFrameTakeId` in the same commit — one answer to what the shot opens on, never two.
   Keyed on what the dispatch asked for, never on the take's kind alone: a character's main
   photo, a look and a model sheet all land as image takes too, and none of them is a start
   frame. `resolveBoundaryFrames` needs no change at all — the slot it already reads is the
   one being filled.
   - The artifact id SHALL use the `ar_` prefix `ArtifactIdSchema` accepts. Getting this wrong
     fails in the worst way available: the bytes land, the sidecar writes, and `scanWorld`
     then drops the record because it will not parse — so the artifact exists on disk and does
     not exist to the app, and the frame slot points at nothing. *Found by driving it.* Image jobs already land as takes of kind `frame` (`takeKindFor`); this
   adds only the slot write, and only for jobs that asked for it — bench takes without a
   subject, character work, and every other image job are untouched.
2. **Accept** (the `accept-take` handler): branch on the take's kind. `clip` → the existing
   ceremony, unchanged. `frame`/`still` → `acceptStill` (`takes/drawn-frame.ts`), which
   lands the review decision, the image artifact and the slot write in **one commit** — the
   review append rides `fileDrawnFrame`'s commit, because committed separately a crash
   between them leaves a durable review saying the take was accepted while the slot still
   names the old frame (the divergence SPEC-013 R-9/D6 exists to prevent). Nothing touches
   `acceptedTakeId`, and none of the clip ceremony runs — no continuity seed, no
   supersession sweep, no trim reset — for a take that was never footage. `acceptTake`
   itself SHALL throw on a still rather than half-run the clip path, so a routing bug
   upstream fails loudly instead of misfiling. The client's `acceptTake` callers need no
   change; the contact sheet is corrected by this one branch.

Three consequences of the two touch points, each pinned by test:

- **Arrival is fenced; accept is not.** Each frame-run step snapshots the slot at its own
  authorization (`slotAtAuthorization`, §2.7), and `fileDrawnFrame` compares it *inside the
  write gate* — the only point where the answer cannot go stale between reading and writing.
  A mismatch returns a distinct `superseded` outcome: the take stays landed, priced and
  browsable, nothing is filed, and the coordinator logs `drawn-frame.superseded` — an
  overtaken job is the fence working, never an error. An explicit accept carries no fence:
  the person is looking at the picture when they press, and the newest explicit act wins.
- **A filing failure fails the finalization.** `shot` targets are not replayable
  (`REPLAYABLE_FINALIZATION_TARGETS`), so a landing that logged a failure and completed
  anyway would be unretryable — paid-for work silently absent from the slot. The arrival
  hook SHALL throw on a failed filing so the job stays visibly failed and retry stays
  possible; only `superseded` continues quietly.
- **The continuity chain declines in two places.** `chainBoundaryFrame` checks
  `hasOwnFrame` before decoding anything — the common "drew the frames first" path never
  pays for an ffmpeg run whose output is thrown away — and again inside the gate, where it
  catches a frame filed while the extraction was in flight. Both return a distinct
  `skipped: "following-shot-has-own-frame"` outcome, told apart from the stale-source
  refusal so neither is logged as the other.
