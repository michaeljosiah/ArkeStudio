# 1 · Requirements

## 1.1 Summary

Build the cache that makes the product's questions answerable. The world folder is the truth;
it cannot cheaply answer *"everything that cited this sheet at dispatch"*, *"14 reference images
predate v5"*, or *"which entries come closest to a question canon cannot answer"*. This spec
builds a SQLite index that can, and holds the line that it is never the source of anything.

The change log's **writer** landed in SPEC-002, because the commit primitive cannot complete
without it. This spec is its first **reader**.

## 1.2 Scope

**In scope**

- Two SQLite databases: a per-world index and an app-level index.
- Schema, build from a cold scan, incremental update on commit.
- Staleness detection and automatic rebuild.
- The citation model — the thing that makes ripples and cross-references computable.
- Lexical search over canon (FTS5), including the relevance floor that decides refusal.
- The query surface consumed by every screen above this spec.
- The world registry that lets the picker render without opening every world.

**Out of scope (this spec)**

- Ripple *presentation* and the accept gate — SPEC-004. This spec provides the queries it calls.
- Canon Q&A prompting and answer generation — SPEC-006. This spec provides retrieval.
- Job execution and cost capture — SPEC-009. This spec provides the tables and aggregation.
- Semantic search and embeddings. Master spec §2.6 fixes v1 as lexical-only.

## 1.3 Acceptance criteria

### The cache contract

- **R-1** The index SHALL be derivable in full from the world folder, and deleting it SHALL
  cause a rebuild with no data loss.
  - **WHEN** `.index/` is deleted and the world reopened **THEN** every count, citation, search
    result and ripple matches its pre-deletion value.

- **R-2** No write path SHALL persist a value read from the index into a world file, other than
  entity ids being linked.
  - **WHEN** the index is stale or absent **THEN** no world file can be written incorrectly as a
    consequence.

- **R-3** The index SHALL be rebuilt automatically when its schema version, or its recorded scan
  state, does not match the world on disk.
  - **WHEN** files were changed while the application was closed **THEN** the mismatch is
    detected on open and the index rebuilt before any query is served.

- **R-4** A corrupt or unreadable index SHALL be discarded and rebuilt rather than reported to
  the user as an error.

### Structure

- **R-5** There SHALL be a per-world index holding entities, citations, takes and canon search,
  and an app-level index holding the world registry, jobs and the ledger.
  - **WHEN** a world's index is deleted **THEN** spend history and job history survive.

- **R-6** The world registry SHALL hold enough per-world summary for the picker to render
  without opening any world.
  - **WHEN** the picker shows three worlds with their character and production counts and last
    activity **THEN** no world folder was scanned to produce it.

- **R-7** The index SHALL be built on a SQLite instance with FTS5 available, and the native
  binding SHALL be present for every architecture the application ships.
  - **WHEN** the packaged application starts on x64 and on arm64 **THEN** the index opens on both.

### Citations

- **R-8** Every reference between entities SHALL be recorded as a citation carrying the source,
  the target, the relation, and **the target's version at the time the citation was made**.
  - **WHEN** a take was dispatched against Maren v4 and Maren advances to v5 **THEN** the
    citation still records v4.

- **R-9** The citation model SHALL cover, at minimum: a shot's cast references, a take's dispatch
  provenance, a sheet's canon-rule references, a canon entry's links, an artifact's links, a
  reference tile's source sheet, a scene's inherited location, and a sheet's voice assignment.

- **R-10** Citations to retired entities SHALL continue to resolve.

### Queries

- **R-11** The index SHALL answer, for any sheet: how many reference tiles cite it, how many
  productions use it, which artifacts derive from it, and which takes were dispatched against
  which of its versions.

- **R-12** The index SHALL answer, for any canon entry: what cites it, at which versions, and in
  which productions.

- **R-13** The index SHALL answer the ripple questions defined in master spec §3.3 without
  consulting a model: tiles older than a proposed version, productions that will pick up it,
  scenes whose shots reference it, canon entries owning its rules, and accepted takes pinned to
  superseded versions.
  - **WHEN** a sheet proposal is opened **THEN** the ripple list is produced from the index alone.

- **R-14** The index SHALL compute the needs-you queue from world and job state rather than from
  a stored list.

- **R-15** The index SHALL aggregate the ledger by period and by provider.

### Search and refusal

- **R-16** Canon SHALL be lexically searchable over entry titles and statements, ranked by
  relevance.

- **R-17** Retrieval SHALL apply a relevance floor, which is the **first** of the two stages that
  decide refusal (master spec §4.3); grounding verification is the second and is not this spec's
  concern.
  - **WHEN** no entry scores above the floor **THEN** the caller is told canon cannot answer, and
    is given the closest-scoring entries regardless.
  - **AND WHEN** entries score above the floor **THEN** they are returned as *candidate* context,
    and clearing the floor SHALL NOT be represented as evidence that any of them answers the
    question.

- **R-23** Retrieval SHALL return each candidate entry's full statement text, so that a caller
  can verify quoted excerpts against it.
  - **WHEN** an answer quotes a span **THEN** the verifying caller has the source text to check
    it against without a second read.

- **R-18** Retrieval SHALL report the number of entries searched, so the refusal state can state
  it truthfully.

- **R-19** The index SHALL surface contradiction candidates for a proposed canon entry as ranked
  lexical overlap against existing entries, presented for human judgement and never used to
  block a proposal automatically.

### Performance

- **R-20** Incremental update on commit SHALL be applied without a full rebuild.
  - **WHEN** a sheet is accepted **THEN** the index reflects it without rescanning the world.

- **R-21** A cold full rebuild of the benchmark world SHALL complete within ten seconds, and a
  warm open SHALL serve its first query within the master spec's two-second interactive budget.

- **R-22** Index work SHALL NOT block the window.

## 1.4 Open questions

- The relevance floor's value. §2.6 sets a starting point and the method for calibrating it, but
  the number is not knowable without a real world of real entries; it is configuration until
  evidence sets it.
- Whether contradiction candidates are worth surfacing at v1 quality. Lexical overlap will find
  entries sharing vocabulary, not entries in genuine conflict. Specified as an aid labelled for
  human judgement, and easy to remove if it proves noise.
- Whether the app index should also cache per-world citation counts for cross-world queries.
  Deferred; no v1 screen asks a question spanning worlds.

# 2 · Design

## 2.1 Architectural decision

**A rebuildable cache, structurally prevented from becoming a source of truth.**

The risk this spec carries is not performance, it is drift: an index that quietly becomes the
only place some fact lives. R-1 and R-2 are the guard, and they are testable — deleting the
index and re-deriving must produce identical answers, and no write path may read from it.

The discipline that makes this hold is that the index is populated from exactly two inputs, the
world folder and `changes.jsonl`, and never from application state. If a value cannot be derived
from those two, it does not belong in the index; it belongs in a world file.

## 2.2 Two databases

| Database | Path | Holds |
|---|---|---|
| World index | `worlds/<slug>/.index/world.db` | entities, citations, takes, take provenance, canon FTS, scan state |
| App index | `%USERPROFILE%\ArkeStudio\.index\app.db` | world registry, jobs, ledger |

The split follows the master spec's decision that the queue and ledger are global while worlds
are self-contained (§15). It has two consequences worth stating: deleting a world's index cannot
lose spend history (R-5), and the world picker can render every world's summary without opening
any of them (R-6).

That second point is not a micro-optimisation. The home screen shows *"6 characters · 3
productions · 2h ago"* for every world; without a registry, opening the application would mean
scanning every world the user has ever made.

Both databases rebuild: the world index from its folder, the registry from the worlds present,
and jobs and ledger from their append-only logs.

## 2.3 Schema

```sql
-- world.db
entities(id, kind, slug, name, status, version, retired, updated_at)
citations(source_kind, source_id, source_version,
          target_kind, target_id, target_version,
          relation, production_id, created_at)
takes(id, production_id, shot_id, kind, status, provider, model,
      canon_revision, cost_estimated_usd, cost_actual_usd, created_at)
take_sheets(take_id, sheet_id, sheet_version)
canon_fts(entry_id, title, statement)          -- FTS5, external content
scan(path, mtime, size)                         -- staleness detection
meta(schema_version, built_at, last_change_seq)

-- app.db
worlds(slug, name, path, character_count, production_count, canon_count, last_activity_at)
jobs(id, world, production_id, kind, status, provider, model,
     estimated_usd, created_at, completed_at, failure_reason)
ledger(job_id, world, provider, model, estimated_usd, actual_usd, completed_at)
```

`take_sheets` fans out each take's provenance so that *"accepted takes pinned to a superseded
version"* is a join rather than a scan of JSON blobs. It is the single most-queried table in the
ripple path.

## 2.4 The citation model

Citations are the heart of this spec. Everything the product says about how its parts relate —
every count on every card, every ripple, every "used by" list — is a citation query.

A citation records source, target, relation, and **the target's version at the time** (R-8).
That last column is what the master spec's consistency story rests on. Without it,
*"14 reference images predate v5"* is unanswerable and the ripple list becomes guesswork.

| Relation | Source → target | Feeds |
|---|---|---|
| `shot-cast` | shot → sheet | scene cast, ripple, reference attachment |
| `dispatch` | take → sheet / canon | provenance, "predates v5", pinned takes |
| `canon-rule` | sheet → canon entry | sheet's read-only rules, canon "cited by" |
| `entry-link` | canon entry → entity | canon cross-references |
| `artifact-link` | artifact → entity | "from this sheet · 23 artifacts" |
| `tile-source` | reference tile → sheet | stale-tile detection, model-sheet compilation |
| `scene-location` | scene → location | location "appears in", scene inheritance |
| `voice-assignment` | sheet → voice | voice change ripple across productions |

Citations to retired entities keep resolving (R-10), which is the point of retiring rather than
deleting: a take that cited a character three months ago must still explain itself.

## 2.5 Build, update and staleness

**Cold build** walks the world folder, parses entities, extracts citations, and populates the
tables. It is the definition of correctness — every other path must agree with what a cold build
would produce.

**Incremental update** (R-20) applies a delta on each commit. The commit primitive from SPEC-002
already knows exactly which files changed, so the index applies the same set rather than
rescanning. A full rebuild on every accept would put a ten-second pause between a user pressing
Accept and seeing the result.

**Staleness** (R-3) is detected two ways: a schema-version mismatch, and a scan comparison of
path, mtime and size against the `scan` table. The second catches edits made while the
application was closed — the case SPEC-002's watcher cannot see.

**Corruption** is not an error state (R-4). A SQLite file that will not open is deleted and
rebuilt. There is nothing in it worth recovering, and asking a user to think about a cache is a
category error.

## 2.6 Search, and the floor that decides refusal

Canon search is FTS5 with BM25 ranking over titles and statements (R-16). It backs the canon
search box, the "closest match" in the refusal state, and retrieval for Q&A.

**The relevance floor is a product decision wearing a technical costume.** It is the first of the
two stages that decide refusal (R-17), and refusal-with-receipts is the behaviour the website
leads on. Set it too low and retrieval hands the model barely-related entries; too high and it
refuses questions it could have answered, which reads as broken.

The design consequence that matters: **when nothing clears the floor, no LLM call is made at
all.** The refusal renders from retrieval alone (master spec R-CANON-2). This makes refusal fast,
free, and impossible for a model to talk itself out of.

**Clearing the floor is not evidence of an answer, and this spec must not imply that it is.**
BM25 ranks shared vocabulary: a question about who collects rent in the Drowned Quarter scores
the Drowned Quarter entry highly while that entry says nothing about rent. Retrieval's job ends
at *candidates*; whether a candidate actually supports an answer is settled by grounding
verification in master spec §4.3, which requires a quoted supporting span and checks it
mechanically. R-23 exists to serve that check — retrieval returns full statement text so the
verifier has something to compare against.

Calibration method, since the number cannot be guessed: assemble a question set against a real
world — questions canon answers, questions it does not, and near-misses — and choose the floor
that maximises correct refusals without suppressing correct answers. Until then it is
configuration with a conservative default, and §1.4 records it as open.

Retrieval always reports how many entries were searched (R-18), because the refusal state says
so out loud — *"Searched all 42 entries"* — and that claim must be true.

## 2.7 Contradiction candidates

For a proposed canon entry, the index surfaces existing entries with high lexical overlap (R-19).

This is an aid, not a check. Lexical overlap finds entries sharing vocabulary, which is
correlated with, but not the same as, entries in conflict. It is presented for human judgement
and never blocks a proposal. §1.4 records the honest risk: if it mostly surfaces noise, it should
be removed rather than tuned indefinitely.

## 2.8 The query surface

The index exposes named queries, not a general query interface. Callers above this spec do not
write SQL; they call `refsForSheet`, `rippleForSheetVersion`, `needsYou`, `spendByProvider`. Two
reasons: the ripple queries are the correctness-critical part of the product and must be
specified and tested in one place, and a general interface would let a future screen quietly
introduce a query nobody has reasoned about.

## 2.9 Native dependency

`better-sqlite3` is a native module and must be rebuilt against Electron's ABI for every shipped
architecture (R-7). This is the one place SPEC-003 touches packaging, and it is a common source
of "works in development, fails when installed". The definition of done requires it verified in a
packaged build, on both architectures, not in `npm run dev`.

FTS5 must be available in the compiled SQLite. It is not assumed; R-7 makes it testable.

## 2.10 Performance

Budgets from master spec N-3 and N-4: warm open interactive within two seconds, cold rebuild
within ten (R-21).

Index work runs off the main thread (R-22). The cold rebuild reports progress, because ten
seconds of silence on opening a world reads as a hang.

Bodies are not indexed except for canon statements. Sheet prose is not searched in v1, so parsing
it during a rebuild would be work in service of nothing.

## 3.2 Testing

**The cache contract** — the tests that matter most, because they are what stops drift. Build,
snapshot every query result, delete the index, rebuild, assert identical results. Run it over the
fixture world and the benchmark world.

**Citations** — one test per relation in §2.4, asserting the target version is captured at
citation time and does not move when the target advances.

**Ripples** — each query in R-13 against a fixture with known answers, including the awkward
cases: a sheet cited by a retired entity, a take whose provenance names a sheet since retired,
and a scene referencing a sheet only through a shot description.

**Search** — ranking sanity; the floor's behaviour at, just above and just below threshold;
searched-count accuracy; and the assertion that a below-floor query produces a refusal result
with no model call attempted.

**Staleness** — edits made with the app closed are detected; schema bump forces rebuild; a
deliberately corrupted database file is discarded and rebuilt without surfacing an error.

**Incremental correctness** — after a sequence of commits, assert the incrementally-updated index
matches a cold rebuild exactly. This is the test that catches the class of bug where an update
path forgets a relation.

**Packaging** — the index opens in a packaged build on x64 and arm64, with FTS5 present.

## 3.3 Definition of done

- [ ] Typecheck, build and test pass across workspaces
- [ ] Delete-and-rebuild produces byte-identical query results
- [ ] Incremental update matches cold rebuild after a commit sequence
- [ ] Every ripple query in R-13 answered from the index alone
- [ ] Below-floor retrieval produces refusal with no model call
- [ ] R-21 budgets met on the benchmark world
- [ ] Verified in a **packaged** build on both architectures
- [ ] Reviewer approved

## 3.4 Decision log

| # | Decision | Rationale |
|---|---|---|
| D1 | Index populated only from the world folder and `changes.jsonl` | If a value cannot be derived from those two it belongs in a world file, not the cache. This is what structurally prevents drift. |
| D2 | Two databases, per-world and app-level | Follows the global queue and ledger decision; deleting a world's index cannot lose spend history. |
| D3 | World registry in the app index | The picker shows counts for every world; without it, startup would scan every world the user owns. |
| D4 | Citations carry the target version at citation time | Without it, "14 references predate v5" is unanswerable and ripples become guesswork. |
| D5 | `take_sheets` fans out provenance into rows | Makes the most-queried ripple a join rather than a scan of JSON blobs. |
| D6 | Incremental update on commit, full rebuild on staleness | A rebuild per accept would put a ten-second pause between Accept and its result. |
| D7 | Corrupt index is discarded silently | There is nothing in a cache worth recovering, and asking a user to think about one is a category error. |
| D8 | Below-floor retrieval short-circuits the model | Makes refusal fast, free, and impossible for a model to talk itself out of. |
| D9 | Named queries, not a general query interface | The ripple queries are correctness-critical; they must be specified and tested in one place. |
| D10 | Only canon statements are full-text indexed | Sheet prose is not searched in v1; parsing it during rebuild would be work in service of nothing. |
| D11 | Contradiction candidates labelled as an aid, never blocking | Lexical overlap finds shared vocabulary, not genuine conflict. Honest about what it is, cheap to remove. |
| D12 | Native binding verified in a packaged build | "Works in dev, fails when installed" is the characteristic failure of native modules under Electron. |
