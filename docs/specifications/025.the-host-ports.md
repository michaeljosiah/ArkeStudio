# 1 · Requirements

## 1.1 Summary

Arke Studio assumes one person, at one machine, spending their own money, answerable to nobody,
publishing nothing. Every one of those four assumptions is load-bearing somewhere in the code, and
every one of them is wrong for an application hosted on top of the engine.

This specification does not make Arke Studio multi-tenant, metered, moderated or connected. It
makes those four assumptions **replaceable** — it names the four places the engine currently
answers a question by assuming the answer, and turns each into a port with a default
implementation that gives exactly today's behaviour.

| The question | Today's implicit answer | The port |
|---|---|---|
| Who is doing this, and what may they do? | The person at the keyboard, everything | `IdentityProvider` |
| May this work happen, against what allowance? | Yes, always; the ledger records it afterwards | `EntitlementProvider` |
| May this content be generated, and who sees it first? | Anything; the author sees it first | `ContentPolicy` |
| Where does a finished thing go? | A file on this disk | `ReleaseTarget` |

**Why this belongs in Arke Studio and not in the application above it.** Each of the four is a
capability Studio itself wants — collaborative worlds, a spend ceiling that actually stops,
brand-safety constraints, publishing a cut somewhere. Building them in the hosted application
instead would fork the engine within a release: the hosted product would carry a second dispatch
path with quota checks in it, and the two would drift at exactly the point where drift is most
expensive. The ports are the alternative to that fork.

**What this spec is careful not to do.** It adds no accounts, no subscriptions, no payment, no
moderation model, no connector to any service. Those live in the applications that supply the
adapters. Master §0.3 keeps them out of Studio and this spec does not reopen that.

## 1.2 Scope

**In scope**

- Four port interfaces in `packages/contracts`, and the resolution rule that binds one
  implementation of each per coordinator instance.
- The **local defaults**: `SoleAuthorIdentity`, `UnmeteredEntitlement`, `WorldRulesPolicy`,
  `LocalExportTarget` — the four implementations Studio ships, whose behaviour is today's
  behaviour.
- The **call sites**: exactly where in the existing flow each port is consulted, and what the
  caller does with a refusal.
- Actor attribution on the change log, the ledger, review decisions and plan authorization.
- The capability set an actor may hold, and the two the engine refuses to let any port grant.
- Degradation when a port implementation is unreachable.

**Out of scope (this spec)**

- Any hosted implementation of any port. They live in the consuming application.
- Multi-writer concurrency on one world. SPEC-002 §2.7's single-owner lock is unchanged here and
  is the subject of its own spec; §2.9 records why identity lands first and separately.
- Authentication, sessions, tokens, password handling, account recovery.
- Billing, invoicing, plans, payment methods, dunning.
- A moderation model, a classifier, or any judgement about what content is acceptable. This spec
  defines *where* such a judgement is asked for and *what happens to the answer*.
- The page medium, document export, and the delegated-actor client surface. Each depends on this
  spec and none is defined by it.

## 1.3 Acceptance criteria

### The ports

- **R-1** `packages/contracts` SHALL define `IdentityProvider`, `EntitlementProvider`,
  `ContentPolicy` and `ReleaseTarget` as interfaces, each with a declarations record stating what
  the implementation can and cannot answer, in the shape `ProviderClient.declarations` already
  uses (SPEC-008 §2.9).
  - **WHEN** an implementation cannot answer a question **THEN** it says so in its declarations
    rather than throwing at the call site.

- **R-2** The coordinator SHALL resolve exactly one implementation of each port at startup and
  SHALL NOT permit a second to be registered for the lifetime of the instance.
  - **WHEN** no implementation is supplied for a port **THEN** the local default is used.
  - **AND WHEN** a second registration is attempted **THEN** it fails at startup, not at first
    call.

- **R-3** The four local defaults SHALL reproduce today's behaviour exactly.
  - **WHEN** Arke Studio runs with the defaults **THEN** no observable behaviour differs from the
    build preceding this spec: no prompt, no refusal, no new record, no new screen.

### Identity and capability

- **R-4** `IdentityProvider` SHALL resolve the current actor to a stable `actorId`, a display
  name, and a set of held capabilities drawn from a closed enumeration (§2.3).
  - **WHEN** the local default resolves **THEN** it returns one actor holding every capability.

- **R-5** Every record the engine already writes with a `source` SHALL additionally carry the
  `actorId` that caused it: `changes.jsonl` lines, ledger entries, `reviews.jsonl` decisions, and
  plan authorization events.
  - **WHEN** a world written before this spec is opened **THEN** absent `actorId` reads as the
    world's sole author and no migration is required.

- **R-6** The engine SHALL refuse to perform a gated accept (SPEC-004) or a spend-incurring
  dispatch (SPEC-009) on behalf of an actor lacking the corresponding capability, and SHALL do so
  in the coordinator rather than by the client omitting a button.
  - **WHEN** an actor without `accept` attempts an accept **THEN** the transaction does not begin
    and the proposal is left untouched.

- **R-7** No `IdentityProvider` implementation SHALL be able to grant an actor the ability to
  bypass the accept gate or to write to the world outside a commit. These are not capabilities and
  cannot be conferred.
  - **WHEN** an implementation returns an unknown capability string **THEN** it is discarded with
    a logged reason, not honoured.

### Entitlement

- **R-8** `EntitlementProvider` SHALL be consulted before any work that would incur cost, and its
  refusal SHALL prevent that work.
  - **WHEN** it refuses **THEN** no job is enqueued, no provider is called, and the caller
    receives the stated reason and the remedy the implementation supplied.
  - **AND WHEN** it refuses **THEN** nothing is written to the ledger, because nothing was spent.

- **R-9** Entitlement SHALL be checked at three points and no others: before a job is enqueued
  (SPEC-009), at plan authorization for the aggregate (SPEC-024 R-15), and before late
  materialisation of a plan pass whose cost was not in the authorized aggregate.
  - **WHEN** a plan is authorized **THEN** its passes do not re-check individually, because the
    aggregate covered them.

- **R-10** An allowance SHALL follow **reserve, then commit or release**: held before the work is
  submitted, committed at the work's true quantity when it completes, released when it does not.
  A job reaching a terminal failure SHALL release its hold and consume nothing.
  - **WHEN** a job fails after submission **THEN** the allowance is unchanged, whatever the
    provider charged. Cost and allowance are different records answering different questions.
  - **AND WHEN** the committed quantity is below the reserved one **THEN** the surplus is released
    rather than consumed.
  - **AND** the reserve call SHALL carry a caller-generated idempotency key, and replaying it
    SHALL return the existing reservation rather than taking a second hold.
  - **AND** a hold SHALL expire on its own rather than relying on a caller to release it, so a
    coordinator killed between reserve and commit does not strand a family's allowance.

- **R-11** The engine SHALL define allowance in **domain units** the implementation names, and
  SHALL NOT assume money. The existing USD ledger is unchanged and continues to record what was
  spent.
  - **WHEN** an implementation meters in units of its own **THEN** the ledger still records USD,
    and neither derives from the other.

- **R-12** The local default SHALL grant everything, unmetered.
  - **WHEN** Studio runs **THEN** the spend threshold continues to alert and never block
    (SPEC-008 R-19, D10), which this spec does not change.

### Content policy

- **R-13** `ContentPolicy` SHALL be consulted at three points: **before dispatch**, where it MAY
  refuse the request outright; when a generation request is composed (SPEC-012), where it MAY
  contribute constraints that ride along with the dispatch; and **before a take is shown to
  anyone**, where it MAY permit, refuse or hold it.
  - **WHEN** it refuses before dispatch **THEN** no job is enqueued and no allowance is consumed,
    which is the cheapest possible refusal and the only one that happens before money moves.
  - **WHEN** it holds a take **THEN** the take is still immutable, still filed, and still appears
    in Activity — held is a review state, not a deletion.

- **R-13a** The post-generation check SHALL issue a **permit naming the exact take and modality**,
  and the surfaces that display a take SHALL require one. A permit SHALL NOT be constructible by
  any caller outside the policy implementation.
  - **WHEN** a display path omits the check **THEN** it has nothing to display with, rather than
    displaying unchecked content.
  - **AND WHEN** a permit for one take is presented for another **THEN** it does not authorise it.
  - *Why a permit and not a boolean:* a boolean makes "did you remember to check?" a convention,
    and conventions are what fail on the path nobody tested. This is the same discipline SPEC-004
    applies to the world — a proposal cannot become a commit by being forgotten about.

- **R-13b** A refusal or a hold SHALL release any allowance reserved for that work (R-10).
  - **WHEN** content is refused **THEN** the user's allowance is unchanged, because charging for
    work whose result was withheld is indefensible whatever it cost to produce.

- **R-14** A held take SHALL be releasable only by an actor holding `review`, and the release
  SHALL be recorded in `reviews.jsonl` like any other decision. A hold SHALL NOT create a review
  surface of its own ([ADR-001](../decisions/001-one-gate-per-thing.md)).
  - **WHEN** a policy holds content **THEN** it joins the needs-you queue the engine already
    computes, carrying its reason — one queue, not a second one beside it.
  - **WHEN** no actor holds `review` **THEN** the take stays held rather than defaulting to
    released.

- **R-14a** An implementation SHALL distinguish **a check that could not run** from **a check that
  is switched off**, and the engine SHALL treat only the first as a fault.
  - **WHEN** a check cannot run **THEN** content is withheld and the condition is reported as a
    fault, because a classifier silently returning "safe" on error is the worst defect available
    here.
  - **AND WHEN** a check is switched off **THEN** content passes and nothing is reported, because
    a feature nobody enabled is not an outage.

- **R-15** Constraints contributed by `ContentPolicy` SHALL be versioned with the world and bound
  to the generation that used them, the way art direction already binds (SPEC-017 R-3).
  - **WHEN** a take is inspected **THEN** the constraint version in force when it was made is
    readable from the take.

- **R-16** The local default SHALL contribute the world's own rules record and hold nothing.
  - **WHEN** a world has no rules **THEN** the policy contributes nothing and every take lands
    exactly as it does today.

### Release targets

- **R-17** `ReleaseTarget` SHALL accept a completed export or document and return a durable
  reference to where it went, and SHALL support withdrawal of anything it published.
  - **WHEN** a target cannot withdraw **THEN** it declares so, and the engine refuses to publish
    to it without an explicit acknowledgement recorded against the release.

- **R-18** Publishing SHALL require an actor holding `publish` and SHALL be recorded as a release
  event naming the actor, the target, the exported artifact and its version.
  - **WHEN** the same artifact is published twice **THEN** two release records exist; a release is
    an event, not a status field.

- **R-19** The local default SHALL write to the filesystem, which is what §16 exports do today.

### Degradation

- **R-20** An unreachable port implementation SHALL degrade to a stated refusal, never to a
  permissive default.
  - **WHEN** `EntitlementProvider` cannot be reached **THEN** work is refused with the reason,
    because a metering service that is down must not become free service.
  - **AND WHEN** `IdentityProvider` cannot be reached **THEN** the engine holds no actor and
    performs nothing that requires a capability.
  - **AND WHEN** `ContentPolicy` cannot be reached **THEN** takes are held rather than released.
  - **AND** the local defaults, being in-process, SHALL have no unreachable state.

## 1.4 Settled during review

The first draft of this spec was written without reference to any host implementation. Reviewing
it against one settled two of its three open questions, in both cases against the draft.

| # | Question | Resolution |
|---|---|---|
| 1 | Whether `ContentPolicy` may refuse a *dispatch* outright, rather than only constrain it and judge what returns. | **It may, and it should** — R-13. The objection was that judging a prompt is less reliable than judging a result. True, and not a reason to skip it: a prompt-stage check catches the deliberate cases before a provider is paid, and the output check still runs. Cheap first, thorough last. |
| 2 | Whether an allowance is reserved at submission or consumed at completion (R-10). | **Reserved** — R-10 rewritten. The draft's objection was that a reservation is a second durable record whose outcome the engine may not witness. An idempotency key on reserve and a self-expiring hold dispose of it, and consume-on-completion turns a subscription limit into a suggestion under concurrency. §2.5 records the full reasoning. |

| # | Still open | Held until |
|---|---|---|
| 3 | Whether `ReleaseTarget` withdrawal should be *attempted* or merely *recorded as requested*. No external service guarantees the former. | A connector exists. |
| 4 | Whether the engine should carry a fifth port for **where the world is stored**, so a world can live somewhere other than a local folder. §2.10 records why it is not in this spec. | The multi-writer question is settled, since the two are the same question wearing different clothes. |

# 2 · Design

## 2.1 Architectural decision

**Four ports, in `contracts`, resolved once per coordinator, with in-process defaults that are
today's behaviour.**

The pattern is not new to this repository. `ProviderClient` (SPEC-008 §2.9) is an interface in
contracts with a declarations record, several implementations, and a registry that binds them; the
job queue calls it without knowing whether FAL or a local ComfyUI is on the other side. These four
ports are that pattern applied to four more questions. Choosing a different shape for them would
mean two conventions for the same problem.

**Why a default rather than an optional port.** A port that may be absent forces every call site to
branch, and a branch that is almost never taken in development is a branch that is wrong in
production. `UnmeteredEntitlement` returning "yes, always" costs one function call and keeps a
single path through the code — the path the hosted application also takes.

**Why the refusal direction is inverted from spend.** SPEC-008 R-19 D10 settled that the spend
threshold alerts and never blocks, on the reasoning that a local tool must not stand between an
author and their own money. That reasoning does not survive the money being someone else's: an
allowance that only alerts is not an allowance. So entitlement blocks where spend does not, and
both exist, and neither derives from the other. R-11 keeps them separate records deliberately —
collapsing them would make the ledger's meaning depend on who was hosting.

## 2.2 What each port is asked

```
IdentityProvider    resolve()        → Actor { actorId, displayName, capabilities }
EntitlementProvider reserve(work, idempotencyKey)
                                     → Held { holdId } | Refused { reason, remedy }
                    commit(holdId, actualQuantity) → void
                    release(holdId)  → void          (idempotent)
ContentPolicy       screen(request)  → Proceed | Refused { reason }
                    constrain(req)   → Constraint[]  (rides along with the dispatch)
                    inspect(take)    → Permit | Refused { reason } | Hold { reason }
ReleaseTarget       publish(export)  → Reference     withdraw(ref) → void
```

Each returns a value; none throws to signal a normal answer. A refusal carries a **reason** the
client can render and a **remedy** the client can act on, because "no" without either is a dead
end at exactly the moment a user needs a route forward.

## 2.3 Capabilities

A closed enumeration, because an open one is a permission system, and a permission system that
grows by string is one that eventually grants something nobody designed:

| Capability | Permits |
|---|---|
| `author` | Drafting: proposals, chapter prose, scene conversation. Produces nothing final. |
| `accept` | The gate. Turning a proposal into a commit. |
| `review` | Take decisions, including releasing a held take. |
| `dispatch` | Enqueuing work that spends. |
| `publish` | Sending a release to a target. |
| `configure` | Providers, credentials, settings, art direction. |
| `administer` | Actors and their capabilities. |

Two things are deliberately **not** capabilities, per R-7: bypassing the accept gate, and writing
to the world outside a commit. Neither is a permission an implementation may confer, because both
are the mechanics the product's guarantees rest on. An actor with every capability in the table
still cannot do either, and the master specification's §3.1 mutation matrix is unchanged.

The delegated actor that a hosted application needs — a child, a junior, a reviewing client — is
`author` alone, or `author` plus `review`. It requires no new concept: it is a subset of a set
that already had to exist.

## 2.4 Where entitlement is consulted

Three points, named exhaustively in R-9 so that a fourth cannot be added by habit:

1. **Before enqueue** (SPEC-009). The single-job path. A refusal here is cheap and total: the job
   record is never written.
2. **At plan authorization** (SPEC-024 R-15). The plan already computes an authorized aggregate
   and already treats it as the record the user confirmed. Entitlement checks the aggregate once,
   and the plan's passes inherit that grant.
3. **Before late materialisation** of a pass whose cost was not in the aggregate — the case
   SPEC-024 exists for, where pass 2 opens on a frame cut from pass 1's landed clip.

The reason for naming them exhaustively is that a check inside the dispatcher's retry path would
mean a retry could be refused mid-plan, leaving a scene half-generated and an allowance half-spent
with no record explaining either. Retries do not re-check; the grant covers the work, not the
attempt.

## 2.5 Reserve, commit, release

R-10 holds the allowance before the work runs and settles it at the true quantity afterwards. This
is the authorise/capture shape payment systems use, and it is here for the same reason: the work
may cost less than expected, or may not happen at all.

An earlier draft of this spec chose the simpler alternative — consume once, on completion, with no
hold — on the grounds that a reservation is a second durable record and SPEC-009 has already paid
once for the problem of records whose outcome the engine did not witness. That reasoning was
wrong in two ways.

It was wrong on the engineering, because an **idempotency key on the reserve call** disposes of
the durability objection: replaying a reserve returns the existing hold rather than taking a
second one, which is precisely the property SPEC-009's outbox exists to provide, obtained here for
the cost of a caller-supplied string. And a hold that **expires on its own** removes the remaining
failure mode, which is a coordinator killed between reserve and commit; nothing has to survive to
release it.

It was wrong on the product, because consume-on-completion lets a user submit more work than their
allowance covers if they submit it fast enough. Under a local tool that is a rounding error. Under
a subscription it is the difference between a limit and a suggestion, and the plan that says six
stories a month has to mean six.

The **commit-below-reserve** case in R-10 matters more than it looks: a scene dispatched as four
passes that completes in three must return the fourth, and returning it to the *tail* of the
draw-down order rather than pro-rata keeps a monthly allowance being spent before a purchased
top-up — otherwise a refund burns the units that never expire and returns the ones that do.

## 2.6 Content policy: refuse, constrain, permit

Three call sites, deliberately unlike each other, ordered by what they cost.

**Refuse** runs before dispatch, on the request. It is the cheapest refusal available and the only
one that happens before money moves, which is why R-13 has it despite the earlier draft holding it
as an open question. The objection then was that judging a prompt is less reliable than judging a
result; that is true and it is not a reason to skip the check, because the cases a prompt-stage
check catches are the deliberate ones, and catching those before a provider is paid is strictly
better than catching them after.

**Constrain** contributes to the request being composed. It is the same mechanism art direction
already uses — a versioned world-level record that rides along with every generation and binds to
what it produced (SPEC-017 R-3) — and it is versioned the same way, for the same reason: a take
whose constraints cannot be reconstructed is a take nobody can explain later.

**Permit** runs before anyone sees the result. R-13a makes it issue a permit naming the exact take
rather than returning a boolean, and makes the display surfaces require one. The difference is not
stylistic. A boolean check can be forgotten, and the forgetting is invisible until the day it
matters; a display path that cannot render without a permit cannot forget. The permit names the
take because a permit that named only the viewer would be a bearer token — hold one valid permit
and any unchecked content could be paired with it.

A held take is not deleted, not hidden, and not re-generated: SPEC-013's takes are immutable and
this spec does not weaken that. Hold is a review state, so it composes with machinery that already
exists — the take is filed, it appears in Activity's needs-you queue (SPEC-014) because its state
says it is waiting on a human, and releasing it appends to `reviews.jsonl` like every other
decision.

R-14's refusal to default a held take to released when no actor holds `review` is the same
discipline as SPEC-006's refusal: silence is not consent, and a policy that fails open is not a
policy. R-14a is the other half of that — the engine must be able to tell a classifier that broke
from a check nobody switched on, because treating the second as a fault means the fault report is
noise, and noise is how the first one gets missed.

## 2.7 Release targets

A release is an **event**, not a status field on the artifact (R-18). Two publications of the same
export produce two records, and a withdrawal produces a third. This follows the take/review split
settled in master §20.1 defect 6: the thing is immutable, and the decisions about it accumulate
beside it.

R-17's acknowledgement requirement exists because "unpublish any time" is a promise an engine
cannot keep on a target's behalf. A target that cannot withdraw must say so, and publishing to it
must be a decision somebody made in the knowledge that it is one-way.

## 2.8 Degradation, and the direction of failure

R-20 fixes the direction once: **unreachable means refused, never permitted.** Each of the four
has an obvious permissive failure mode and each is wrong in the same way — a metering service that
is down becoming free service, an identity service that is down becoming an administrator, a
policy service that is down becoming no policy.

This is a departure from how Studio degrades elsewhere. SPEC-001 R-6 has the application reach an
interactive state with either child process absent, and SPEC-005 degrades authoring honestly when
the harness is missing. Those degrade towards *less capability, still usable*. These four degrade
towards *nothing happens*, because what they gate is not a feature of the application but a
constraint on it, and a constraint that disappears when a network call fails was never a
constraint.

The local defaults are in-process and have no unreachable state, so this affects no Studio build.

## 2.9 What this spec deliberately leaves broken

**One process still owns a world.** SPEC-002 §2.7's lock is untouched. This spec gives the engine
actors and capabilities; it does not give it two writers. A hosted application binding several
people to one world must still route them through one coordinator instance, and the lock becomes a
lease on that instance rather than a file on a disk. That is a real piece of work and it is not
this one.

> **Scoped, not settled.** [ADR-002](../decisions/002-ownership-is-a-revision.md) takes this
> paragraph apart and finds it was right. Ownership can become a property of a deployment, but the
> single-writer guarantee is retained rather than replaced: SPEC-002 R-27's base-hash check is a
> staleness check verified *under* ownership, not a concurrency primitive, so a lease needs a real
> fence (R-3a). The ADR also corrects the prerequisites — a client-chosen commit id and content
> addressing, neither of which the engine has today. Still open, and still not this spec: how a
> lease is granted and renewed over a network and by whom — which is **not** this spec's
> `IdentityProvider`, since a lease belongs to a coordinator instance and must outlive any actor.

Identity lands first, and separately, because attribution is useful immediately and independently:
a change log that records *who* is worth having even while the answer is always the same person,
and retrofitting `actorId` onto four record types after they have accumulated history is
considerably worse than reserving the field now. R-5's rule that an absent `actorId` reads as the
sole author is what makes landing it early free.

## 2.10 The fifth port this spec does not add

The four ports here all concern *decisions* the engine makes. There is a fifth question with the
same shape and a different answer: **where the world is stored.**

Master §1.1 fixes the filesystem as the only durable truth, and SPEC-002 §2.7 lets one process own
a world at a time behind a lock file. A hosted application needs neither of those to be false, but
it does need the folder to live somewhere it can serve from and several people to reach it. That
is the same question as multi-writer concurrency, which §2.9 leaves open, because a second writer
and a remote store are two views of one problem: what happens when the bytes a coordinator holds
are not the only bytes.

It is not in this spec for a reason worth recording. A storage port is not a seam over a decision
— it is a seam under the whole of SPEC-002: the commit journal, the atomic rename, the `.history/`
snapshots, the external-edit hashes. Putting an interface there without settling what a *revision*
is, and what happens when two of them descend from the same parent, would produce an abstraction
shaped like a local filesystem with a network behind it, which is the classic way to get the worst
of both.

So the ordering is: settle revisions and divergence first, then the storage port falls out of it.
Open question 4 holds it.

**What is worth noting now** is that a host may already have solved this, and if it has, the
engine's job is to fit rather than to invent. A storage layer that versions an opaque tree,
sequences revisions, and represents a divergent revision as a durable thing a human accepts or
rejects — rather than as a rejected write the client must remember — is answering the same
question SPEC-004's gate answers about facts, one level down. The engine should look there before
designing its own.

## 2.11 Fitting a host: what an adapter has to bridge

The ports are deliberately narrower than any real host's API, and an adapter absorbs the
difference. Three mismatches are predictable enough to name, because each is a place where an
adapter written carelessly would leak the host's model into the engine:

**Units.** A host meters in codes of its own — `stories`, `videos`, `child-profiles`. The engine
counts work. The adapter owns that mapping and the engine never learns a meter code, or the port
has quietly become the host's API with a different name.

**Meter shapes.** Not every allowance is a countdown. A limit on *how many things may exist at
once* — child profiles, seats, stored bytes — is claimed and released rather than consumed, and
deleting the thing must return the slot; a countdown that returned units on delete would let a
user reset their month by deleting last week's work. R-10 covers the countdown case. An adapter
whose host distinguishes the two should map the engine's per-work check onto the countdown and
handle existence limits at the point the object is created, not through this port.

**Identity granularity.** A host's notion of who is paying — an account, a family, a tenant — is
coarser than the engine's notion of who is acting. One payer, several actors. `IdentityProvider`
returns the actor; the adapter holds the payer and does not surface it, because an engine that
learned about payers would be one refactor from learning about invoices.

**Which gate decides.** A host will have an approval mechanism of its own, and it will be built on
the same principle as the accept gate — agents propose, humans decide. Two gates over one product
is how a parent gets asked twice about the same page, or how each system assumes the other asked
and nobody did. [ADR-001](../decisions/001-one-gate-per-thing.md) settles the boundary: the engine
gates what a family sees or keeps, the host gates what touches money or the world outside, nothing
is gated twice, and a policy hold joins the engine's queue rather than opening another.

**And one thing an adapter must never bridge.** Arke Studio must not acquire a build-time or
run-time dependency on any host. The engine ships and runs with its four local defaults, on a
machine with no network and no account, or the AGPL promise in the README is not true. That
constraint is what the ports are for; an adapter that inverts it — a host package the engine
imports — would defeat the whole arrangement while appearing to honour it.

# 3 · Tasks

## 3.1 Implementation plan

- [ ] **T-1** Port interfaces and declarations in `packages/contracts`, with the capability
      enumeration and the refusal shape (R-1, R-7, §2.3).
- [ ] **T-2** Resolution in the coordinator: one implementation per port, bound at startup,
      second registration fails there (R-2).
- [ ] **T-3** The four local defaults, and the test that asserts R-3 — behaviour identical to the
      preceding build.

## 3.2 Testing

The load-bearing test is **R-3**: a build with the local defaults must be indistinguishable from
the build before this spec. Everything else in this specification is machinery for an application
that does not exist yet, and the way machinery like that damages a product is by changing its
behaviour slightly while nobody is looking.

Beyond that, per port: a refusal carries a reason and a remedy; an unreachable implementation
refuses rather than permits; an unknown capability string is discarded rather than honoured; a
failed job releases its hold and consumes nothing; a commit below its reservation returns the
surplus; a replayed reserve returns the same hold rather than a second one; a permit issued for one
take does not authorise another; a refused or held take releases its allowance; and a held take is
still filed, still immutable, and still in the needs-you queue.

One test belongs to no port and matters more than most: **the engine builds, starts and generates
with no host adapter present, on a machine with no network.** §2.11's last paragraph is a promise
the README makes, and a promise nobody tests is a promise that breaks the first time somebody adds
a convenient import.
