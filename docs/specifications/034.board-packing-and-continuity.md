# 1 · Requirements

## 1.1 Summary

Generating each frame of a scene independently causes drift: the character's face, the light
and the grade all move between shots. Generating several consecutive shots as one pass — one
grid image for stills, one clip for video — forces one rendering of cast, light and grade
across all of them. But video models cap a clip at 10–30 seconds, so a scene maps to a
*sequence* of such groups, not one. This specification names that group a **board** and defines
the one algorithm that produces boards.

The central decision, and the reason this is a specification rather than a function: **boards
are derived, never authored.** SPEC-029 §1.9 made storyboard groups authored structure — stable
ids, titles, a lifecycle of create/rename/split/merge/dissolve. This specification supersedes
that. What is authored is two thin overrides — a **split** before a shot, and a **merge** across
a boundary the packer would otherwise break at — and everything else is computed from the shots
as they stand, under the cap of whichever model is in hand. The reasons are practical:

1. A board's membership depends on the model's cap, and the cap is not authored. An authored
   group either ignores the cap (and lies) or is rewritten by it (and stops being authored).
   SPEC-029 already conceded this in R-43 — "a provider limit is execution policy, not
   authorship" — which left groups authoring nothing the packer did not immediately re-decide.
2. Continuity breaks are facts of the shots — a time-of-day change, a cast change — and facts
   should not need to be maintained by hand in a second place. When a shot's time changes, the
   boards change with it; an authored group would instead go quietly stale.
3. The failure mode of authored groups is silence: a seam nobody drew and nobody warns about.
   The failure mode of derived boards is a visible warning — see the honesty rule (R-11) —
   which is the failure mode we prefer.

Boards are ephemeral until spending freezes them: a dispatch plan (SPEC-024) or a generation
request records the boards it was packed under, and that record is immutable. The live surface
repacks freely; money never does.

Tracking: the scene-workspace epic (SPEC-035 §5 names the issues).

## 1.2 Bound decisions

1. **Boards are derived.** No board object is ever stored on the scene. SPEC-029's
   `storyboardGroups` (R-30..R-35) is superseded; the field remains parseable and is written by
   nothing.
2. **Splits and merges are the only authored input**, keyed by shot id — never by ordinal or
   array position, so reordering shots cannot silently change what an override means.
3. **The clip limit is never overridable.** Every other break can be merged across; the cap
   cannot, because a request over the cap is a request the provider refuses.
4. **A suppressed break is a carried warning.** Whenever a continuity break does not produce a
   seam — because of a merge, or the single-shot collapse — the reason appears on the surviving
   board as a warning. A seam the user chose stays visible; a seam that appears by accident is
   impossible.
5. **Lighting is not a break.** A practical lantern inside a blue-hour scene is an accent, not
   a continuity failure. It surfaces as a neutral note, visually distinct from warnings.
6. **Boards are lettered, not titled.** `Board A`, `Board B`, renumbered freely on every
   repack. Letters carry no identity worth preserving, which is the point: identity lives in
   the member shot ids, and anything durable (a plan, a request) records those.
7. **One packer, every consumer.** Frame-sheet generation, whole-scene video planning, and the
   workspace surface all call the same function. Two packers would be two answers to where the
   seams are.

## 1.3 Scope

**In scope:** the packing algorithm — inputs, break rules, overrides, the single-shot
collapse, carried warnings, accents, letters and labels; the authored override state on the
scene record; the modal derivation of the scene's own values; memoisation requirements; what
consumers receive and what dispatch freezes.

**Out of scope:** every surface that renders boards (SPEC-035); the generation session;
video pass compilation itself (SPEC-024, SPEC-019 — this spec only changes what proposes the
pass boundaries); Interactive routing (SPEC-029 §1.12 is untouched).

## 1.4 Inputs and the scene's own values (R-1..R-3)

- **R-1** The packer SHALL take: the scene's shots in canonical order (through SPEC-029's one
  linearisation authority, never a private read of `shots[]`); each shot's duration, time of
  day, lighting, cast, and solo-clip status; the authored overrides (R-4); and a cap in
  seconds. The cap comes from the model in hand — the manifest's duration limit for video, the
  storyboard panel limit expressed as the equivalent duration for sheets — and changing the
  model repacks live.
- **R-2** The scene's own `time` and `light` SHALL be derived as the **modal value across the
  scene's shots** — the value most shots share — never read from static defaults. A shot
  "overrides" only if it differs from that modal value. *A scene whose defaults say dusk while
  four of five shots say night is a night scene with one dusk shot, and comparing against the
  stored default would break it into five boards.*
- **R-3** A shot's cast SHALL be its resolved `@` references (live sheets, SPEC-012), not a
  hand-maintained list. A shot with no references is treated as overlapping with everything —
  an empty cast is an unknown, not a cast change.

## 1.5 Packing (R-4..R-9)

- **R-4** The authored overrides SHALL be stored on the scene record as two sets of shot ids:
  `splits` (a board begins at this shot) and `merges` (the automatic break that would begin at
  this shot is suppressed). Both are authored state: writing either advances the scene version
  under the ordinary rules. A stored id that no longer names a shot in the scene is dropped at
  read time, never an error.
- **R-5** The packer SHALL walk the shots in canonical order, accumulating into the current
  board, and start a new board when, in priority order:

  | Condition | Reason label | Overridable |
  |---|---|---|
  | board duration + shot duration exceeds the cap | `clip limit` | never |
  | the shot's id is in `splits` | `by hand` | remove the split |
  | the shot's time of day differs from the previous shot's, where either differs from the scene's modal value | `time of day changes` | merge |
  | the shot's cast and the previous shot's cast have no overlap | `cast changes` | merge |

  A shot id in `merges` suppresses the time and cast breaks at that boundary and carries the
  suppressed reason as a warning (R-11). It never suppresses the cap or a hand split.
- **R-6** Lighting SHALL NOT break a board. A shot whose lighting differs from the scene's
  modal value contributes a neutral **accent** note to its board — e.g. `lighting accent ·
  shot 12 · practical lantern, inside a blue hour scene`.
- **R-7** After the walk, any single-shot board SHALL be folded into whichever neighbour has
  room under the cap (previous first), **except** a board the user split by hand. A board of
  one delivers zero cross-shot consistency — it is per-shot generation wearing a board label.
  When the fold suppresses a continuity reason, that reason is carried onto the surviving
  board as a warning (R-11). When no neighbour has room, the board of one stands.
- **R-8** Boards SHALL be lettered `A`, `B`, `C`… in order on every pack. Letters, member shot
  ids, duration against the cap, headroom, the split reason, warnings and accents are all
  derived outputs; none is stored.
- **R-9** A shot rendered separately from its board — a solo clip exists for it — SHALL
  contribute a warning to its board: `shot 15 rendered separately · may not match this board`.

## 1.6 The honesty rule (R-10..R-11)

- **R-10** Every board SHALL state why it begins (`split · time of day changes`, `split · by
  hand`, `split · clip limit`); the first board states nothing, having nothing before it.
- **R-11** Whenever a break the rules would have made does not appear — a merge, or the
  single-shot collapse — the surviving board SHALL carry the suppressed reason as a warning,
  in the warning tone: `spans a time-of-day change · shot 15 dusk in a night board`, `spans a
  cast change · shot 14 brings Sereth`. Warnings and accents are visually distinct (SPEC-035
  owns the rendering); they are distinct *kinds* here — a warning is a risk the user accepted,
  an accent is a fact nobody needs to accept.

## 1.7 Consumers and freezing (R-12..R-14)

- **R-12** Frame-sheet generation SHALL request one sheet per board — the panel mapping,
  member shot ids, scene version, aspect, model and estimate frozen per request exactly as
  SPEC-029 R-42 already requires, with **derived boards in place of authored groups**. A model
  panel cap subdivides a board across sheets in the request; it never changes the board.
- **R-13** Whole-scene video planning SHALL take the boards as its pass boundaries, packed at
  the dispatch model's cap. Packing decisions freeze into `CompiledPass` / `DispatchPlan`
  (SPEC-024) at authorization, per SPEC-029 R-46..R-48 — a repack after authorization changes
  the next plan, never a standing one.
- **R-14** The packer SHALL be memoised on a key covering: the cap, the shot order, each
  shot's duration/time/lighting/solo status/cast, and the two override sets. It runs on nearly
  every render of the workspace; an unmemoised pack is a dropped frame budget (SPEC-035
  carries the interaction budget).

# 2 · Design

## 2.1 Where the overrides live

On the scene record, beside the flow:

```jsonc
{
  "flow": { /* SPEC-029 */ },
  "boards": {
    "splits": ["sh_14"],
    "merges": ["sh_15"]
  }
}
```

Absent means empty. `storyboardGroups` remains in the schema for parse compatibility and is
written by nothing; nothing ships that authored one, so there is no migration to run.

## 2.2 The algorithm, sketched

The reference implementation is the prototype's `packBoards`
(`design-system/scene-workspace-vertical.html`; described in
`design-system/scene-workspace-vertical.notes.md` §6). The port differs in exactly two ways:
overrides key by shot id rather than ordinal, and cast comes from resolved references rather
than a stored list. Everything else — the modal derivation, the walk, the collapse, the carried
warnings — ports as written, with its tests.

# 3 · Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Derived boards supersede authored groups | The cap already re-decided membership; continuity is a fact of the shots; the authored version fails silently where the derived one fails loudly. |
| D2 | Overrides key by shot id | The prototype keyed by ordinal; a reorder would have silently moved every split. |
| D3 | Letters, not titles | Identity lives in member ids; a stable name on an unstable grouping is a promise the packer cannot keep. |
| D4 | Lighting exempt from breaking | An earlier build broke on lighting and produced four single-shot boards from five shots, defeating the feature. |
| D5 | Empty cast overlaps everything | A shot that names nobody is not a cast change; breaking on it would punish terse writing. |
| D6 | The collapse never touches a hand split | The user said seam; the packer does not un-say it. |

# 4 · Adversarial test matrix

- [ ] **T-1** Modal values: 4×night + 1×dusk packs as one board with one override, not five.
- [ ] **T-2** Cap breaks are never merged: a merge id at a cap boundary changes nothing.
- [ ] **T-3** A merge across a time change carries `spans a time-of-day change` on the board.
- [ ] **T-4** Single-shot collapse folds into the neighbour with room and carries the reason;
      a hand-split board of one survives.
- [ ] **T-5** Reordering shots leaves splits attached to the same shots (id-keyed).
- [ ] **T-6** A split id naming a deleted shot is dropped at read, not an error.
- [ ] **T-7** Changing the model cap repacks; a frozen plan does not move.
- [ ] **T-8** Memoisation: identical inputs return the identical object.
- [ ] **T-9** Empty-cast shots never produce `cast changes`.
- [ ] **T-10** Letters renumber after any repack; no consumer stores them.
