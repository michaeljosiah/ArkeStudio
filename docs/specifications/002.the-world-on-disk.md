# 1 · Requirements

## 1.1 Summary

Make the filesystem the world. Replace SPEC-001's mock `WorldProvider` with a real one that
discovers, reads, validates and writes world folders; implement the two-track versioning model,
the `.history/` snapshot store and the append-only change log; and make every write crash-safe
and every name safe on Windows.

This is the spec the whole product stands on. If it is wrong, everything above it inherits the
error, and there is no database to hide behind.

## 1.2 Scope

**In scope**

- App root and world discovery, creation and opening.
- Parsing and serialising every entity format, with round-trip fidelity.
- Naming: slugification, collision handling, Windows path safety, id allocation.
- Atomic, crash-safe writes.
- The two-track versioning model and the `.history/` snapshot store.
- `changes.jsonl` as the append-only audit trail.
- Single-process ownership and external-edit detection.
- Schema versioning and forward compatibility.
- Entity retirement.

**Out of scope (this spec)**

- The derived index and citation queries — SPEC-003. This spec provides the scan that feeds it.
- Proposals, ripple computation and the accept gate — SPEC-004. This spec provides the atomic
  commit primitive the gate calls.
- Any provider, job or generation.
- World archival, hard deletion, and world-to-world copying.
- Artifact binary handling beyond filing and linking — SPEC-015.

## 1.3 Acceptance criteria

### Discovery and lifecycle

- **R-1** The application SHALL locate its app root at `%USERPROFILE%\ArkeStudio`, creating it
  and `worlds/` on first run, and SHALL treat any child of `worlds/` containing a valid
  `world.json` as a world.
  - **WHEN** the app root does not exist **THEN** it is created without prompting.
  - **AND WHEN** a child of `worlds/` has no `world.json` **THEN** it is ignored, not reported
    as corrupt.

- **R-2** Opening a world SHALL scan, parse and validate every entity, and SHALL report the
  world as openable only when `world.json` parses and its schema version is supported.
  - **WHEN** individual entity files fail to parse **THEN** the world still opens, the failures
    are surfaced individually with their file paths, and the valid entities are usable.

- **R-3** A world SHALL be owned by one writer at a time. On a local deployment that ownership
  SHALL be enforced by a lock file recording pid and start time.
  - **WHEN** a second instance opens a locked world **THEN** it reports the conflict rather than
    opening read-write.
  - **AND** a lock SHALL be **refreshed on a heartbeat** while it is held, and SHALL be treated as
    stale when its pid no longer exists **or** its heartbeat has not advanced within a stated
    window. The recorded start time is not a staleness test (§2.9).
  - **WHEN** either is true **THEN** the lock is reclaimed, because the alternative is a user
    locked out of their own work by a crash — and because a pid alone is not enough after the
    operating system has reused it.
  - *The heartbeat is what makes reclamation safe against pid reuse, and it is also the reason
    ownership can be lost by a process that is merely slow (R-3a). Both halves belong here: an
    implementation reading only "reclaim a dead pid" would build neither, and R-3a's exposure would
    read as a defect in something unspecified rather than a consequence of this rule.*
  - **AND** ownership SHALL be enforced by a **lease** where a pid cannot answer the question — a
    hosted deployment, or any world whose writer is not on the machine that holds the files. A
    lease holder SHALL be identified by an opaque per-run id, never by a machine identifier (R-24).

- **R-3b** Recovery of an interrupted commit (R-15) SHALL run **only after ownership has been
  acquired**, and SHALL NOT run at all on a read-only open.
  - **WHEN** a second instance opens a world whose owner holds a journal **THEN** it does not
    resolve that journal, because resolving it is a write and the world is not its own.
  - **AND** a read-only consumer finding an unresolved journal SHALL report it rather than complete
    it — recovery renames live files, and an open that renames files is not read-only.
  - *This is what lets R-15 and R-3a both be true: the fence stops a deposed process, the
    transaction is completed by the new owner, and "the new owner" only means something if recovery
    waits for ownership.*

- **R-3a** **Every path that mutates a world** — the commit primitive and the app-owned writes
  outside it alike — SHALL be **fenced by the ownership in force**: the check that ownership is
  still held and the write that claims the files SHALL be one indivisible step, and the check SHALL
  establish that ownership is *current*, not merely that no one else holds a path at that instant.
  - **WHEN** a lease expires and a new writer takes it, and the deposed writer completes a write it
    began first **THEN** that write is refused because ownership moved, whether or not the files it
    targeted changed and whether or not it won a race to claim them.
  - **AND WHEN** a deposed writer holds a journal already in `committing` **THEN** refusing it
    SHALL NOT abandon that commit: R-15's roll-forward still applies, and it is the **new owner**
    that performs it on open. What the fence stops is the deposed *process* continuing to write,
    not the *transaction* completing.
  - **AND** every path that mutates a world SHALL be **recoverable** — journalled, or idempotently
    re-runnable — before ownership of that world can be transferred at all. Recoverability is a
    **precondition** of the fence, not an alternative to it.
  - **AND** there SHALL be no exception permitting an admitted operation to run on past a
    takeover.
  - **AND** the fence SHALL govern writers that reach a world **through the coordinator**. A file
    the product deliberately opens to outside editors — `bible.md`, and nothing else today
    (R-23) — is outside that boundary by construction: a text editor cannot join an ownership
    store, and requiring it to would forbid the workflow the product invites.
  - **AND** adopting an outside edit SHALL make it **visible to whatever staleness check guards
    that file** — by advancing its version, or by the check comparing content rather than a version
    number. An edit that is adopted but invisible is worse than one that is refused.
  - **AND** the guarantee for that file SHALL be stated as **best-effort**, because a check cannot
    close the window between itself and the rename that follows it. An editor saving in that gap is
    overwritten whatever the check concluded, and no arrangement available to an unfenceable writer
    removes it: the writer is a text editor, and it will not participate in anything.
  - *Narrowing the window is worth doing and is not the same as closing it. What the spec must not
    do is imply a guarantee the arrangement cannot give — this is the one file where "your edit is
    safe" is a promise about timing rather than about correctness.*
  - *The cost is stated rather than hidden: that one file is resolved by adoption rather than by
    ownership, which is what it already does and what ungated prose can afford. Extending the
    exemption to anything gated would give back exactly what R-3a buys.*
  - *Resolved historical defect: "last write wins" was the wrong description. World Chat's
    `applyTurnBibleEdits()` refused a turn whose frontmatter base moved, but a hand edit once changed
    only the body. The guard therefore passed and the turn edited sections it had never read. Bible
    adoption now commits the hand edit as the next version before publishing it, so the guard sees
    the move and refuses the stale turn.*
  - *Take arrival is the case that forces this. Inside one `gateOp()` it creates the take
    directory, **renames the paid media into it**, deletes the staging directory, measures, draws a
    poster, and only then writes `take.json` — with no journal anywhere. The code says as much
    where it swallows every diagnostic failure: "finalization is not replayable, and a paid clip
    must never be lost".*
  - *Three ways round it were tried and each moved the failure rather than removing it. Refuse the
    deposed writer mid-operation, and the media is orphaned with no recovery to finish or undo it.
    Let it run on to completion, and it writes while its successor writes — two writers at once,
    which is the thing this requirement exists to prevent. Make the successor wait, and a single
    hung operation holds a world hostage with no bound. There is no fourth option that leaves the
    path unrecoverable, which is why recoverability is stated above as a precondition rather than a
    cost: with it, refusal is immediate, nothing is orphaned because the new owner rolls forward,
    and no concurrent window opens.*
  - *This is R-15's guarantee, needed on the paths that never had it. A deposed writer is only a
    new way for an operation to stop half-done; crash-safety already demanded all-or-nothing for
    commits, and the direct paths were merely untidy without it. Fencing them makes it dangerous.*
  - **AND** the check and the claim SHALL be one indivisible operation **in a single store**. A
    design that establishes ownership in one system and writes in another SHALL NOT be treated as
    satisfying this, however the two are sequenced.
  - **AND** a fence covering only commits SHALL be insufficient: take media landing and reference
    images are written outside the committer by design, and a deposed writer can reach them.
  - **AND** this SHALL NOT be scoped to hosted deployments. R-3's own reclaim rule — a dead pid
    **or** a cold heartbeat — deposes a process that is unresponsive rather than dead, and nothing
    revalidates ownership between acquiring the lock and writing.
  - *The local window is narrower than a lease's, not absent. A heartbeat that stops while its
    process lives is an ordinary event: the beat is a `utimes` whose failures are swallowed, so a
    permissions change or a disconnected drive silences it, and a sleeping laptop silences it too.
    Ninety seconds later another instance owns the world and the first one has not noticed.*
  - **AND** R-27's base-hash check SHALL NOT be relied on for this. It is a staleness check for
    work drafted against content that has since changed, it is verified under ownership rather than
    atomically with the rename, and a writer whose targets nobody else touched passes it.
  - *Recorded because an earlier draft of [ADR-002](../decisions/002-ownership-is-a-revision.md)
    claimed the opposite — that the base hash is itself the fence, so no fencing token is needed.
    It is not: a successor may take ownership and commit nothing, or commit elsewhere, leaving every
    base the deposed writer targeted untouched. The commit path's own comment states the real
    precondition — "verify bases under the lock".*

### Formats and fidelity

- **R-4** Entity files SHALL be UTF-8 without BOM, written with LF line endings, and parsed
  tolerantly of CRLF.
  - **WHEN** a file with CRLF line endings is parsed **THEN** its frontmatter keys resolve
    correctly and the document does not parse empty.

- **R-5** Parsing and re-serialising an unmodified entity SHALL produce a byte-identical file.
  - **WHEN** a world is opened and closed with no edits **THEN** no file's mtime or content
    changes.

- **R-6** Unknown frontmatter keys and unknown JSON fields SHALL be preserved across a
  read-modify-write cycle.
  - **WHEN** a world written by a newer version is edited by an older one **THEN** fields the
    older version does not understand survive unchanged.

### Naming and path safety

- **R-7** User-supplied names SHALL be slugified to a filesystem-safe form, and the resulting
  slug SHALL be unique within its collection, compared case-insensitively.
  - **WHEN** a user creates "Maren Kest" and later "maren kest" **THEN** the second receives a
    distinct slug rather than overwriting the first.

- **R-8** Slugification SHALL reject or escape Windows-reserved device names, forbidden
  characters, and trailing dots or spaces.
  - **WHEN** a character is named "Nul", "AUX" or "COM1" **THEN** the slug produced is a legal
    filename on NTFS.
  - **AND WHEN** a name is entirely unslugifiable **THEN** a generated fallback slug is used and
    the display name is preserved in frontmatter.

- **R-9** Display names SHALL be carried in frontmatter and SHALL NOT be derived from filenames.
  - **WHEN** a slug is a fallback or a collision-suffixed form **THEN** the UI still shows the
    name the user typed.

- **R-10** Slugs SHALL be capped in length, and filesystem operations SHALL not fail because a
  generated path exceeded the platform limit.
  - **WHEN** a world, production and take produce the deepest path the layout allows **THEN**
    every read and write on that path succeeds.
  - **AND WHEN** the app root sits deep enough to threaten the budget **THEN** the condition is
    reported before worlds are created there.

- **R-11** Canon ids SHALL be allocated monotonically from a persisted counter and never reused,
  including after retirement.
  - **WHEN** CANON-043 is retired and a new entry is created **THEN** it is CANON-044.
  - **AND WHEN** the counter is missing **THEN** it is recovered as the maximum of existing ids
    and ids recorded in `changes.jsonl`, never lower.

- **R-12** Take, proposal and job ids SHALL be lexicographically sortable and collision-free
  without coordination.

### Writing and crash safety

- **R-13** Every write to a world file SHALL be staged to a temporary file and atomically renamed
  into place.
  - **WHEN** the process is killed at any point during a write **THEN** the target file is
    either its complete previous content or its complete new content, never partial.

- **R-14** A rename that fails because the target is transiently locked SHALL be retried with
  backoff before being reported.
  - **WHEN** a virus scanner or search indexer holds a handle briefly **THEN** the write succeeds
    on retry rather than surfacing an error.

- **R-15** A commit spanning several files SHALL be all-or-nothing, implemented as a journalled
  transaction per master spec §3.5.
  - **WHEN** a commit touching a sheet and two canon entries is interrupted **THEN** on next open
    the world reflects either all three changes or none — including `world.json`, `.history/` and
    `changes.jsonl` — and any partial staging is discarded.
  - **AND WHEN** the interruption occurred before the journal reached `committing` **THEN**
    recovery rolls back and the world is byte-identical to before the commit.
  - **AND WHEN** it occurred after **THEN** recovery rolls forward idempotently to completion.

- **R-27** A commit SHALL verify each target's recorded base hash before writing, and SHALL
  refuse when a base has moved.
  - **WHEN** a file changed between a proposal's materialisation and its accept **THEN** the
    commit refuses rather than overwriting the newer content.

- **R-28** Entity files changed while the world was closed SHALL be reconciled explicitly per
  master spec §2.7, not absorbed by the open scan.
  - **WHEN** a sheet is hand-edited with the application closed **THEN** the next open reports it,
    and accepting the reconciliation snapshots the prior version, bumps the entity version and
    writes a `changes.jsonl` line with `source: "external-edit"`.
  - **AND WHEN** a world has no `.history/` or `changes.jsonl` **THEN** it is adopted as-is at
    version 1 rather than reported as externally edited.
  - **AND** the snapshot taken at adoption SHALL be of the **last committed version**, not of the
    bytes being adopted.

### Versioning and history

- **R-16** Accepting a canon change SHALL increment `world.canonRevision` exactly once and stamp
  every affected entry with the new revision.
  - **WHEN** one commit accepts two canon entries **THEN** the revision advances by one and both
    entries record it.

- **R-17** Accepting a sheet change SHALL increment that sheet's version by one, leaving all
  other sheets and the canon revision untouched.

- **R-18** A commit SHALL write the outgoing version of each changed file to `.history/` before
  the live file is replaced.
  - **WHEN** the process is killed mid-commit **THEN** either the live file is intact or its
    snapshot exists; no version is lost from both.

- **R-19** History SHALL be full snapshots, addressed by canon revision for canon entries and by
  sheet version for sheets.

- **R-20** Restoring a historical version SHALL produce a new version rather than rewriting
  history.
  - **WHEN** Maren v4 is restored while the sheet is at v6 **THEN** the result is v7 and v5 and
    v6 remain in `.history/`.

### The change log

- **R-21** Every accepted change, discard, retirement and id allocation SHALL append one line to
  `changes.jsonl`, and the file SHALL never be rewritten, reordered or compacted.
  - **WHEN** the log is replayed **THEN** it reconstructs every version transition the world has
    undergone.

- **R-22** A truncated final line in `changes.jsonl` — the signature of a crash mid-append —
  SHALL be tolerated on read and repaired on next append.

### External edits and portability

- **R-23** Changes made to **inventoried entity files** by another program while a world is closed
  SHALL be reconciled explicitly on open (R-28), and SHALL NOT be silently merged.
  - **AND** files outside that inventory — take media, and anything else the scan does not
    manifest — are **not** reconciled, and this requirement SHALL NOT be read as promising it.
  - **AND** while a world is **open**, the watcher SHALL adopt a moved `bible.md` and SHALL NOT
    otherwise compare manifests or declare the world stale.
  - *Superseded in the code, and this requirement had not caught up: `startWatcher()`
    records that "everything else the watcher used to do — compare byte manifests, wait, compare
    again, and declare the world stale — is gone with the banner it fed". Corrected here because
    R-3a's neighbouring text would otherwise sit beside a requirement the product stopped meeting.*
  - *And the closed-world half was overstated in the same edit. `detectExternalEdits()` compares
    the scan's entity manifest, so a take's media replaced while the app was shut is not detected
    and never was. Promising reconciliation for "world files" claimed a guarantee for binaries that
    nothing provides.*
  - *`adoptBibleIfMoved()` commits changed Bible text as the next version before publishing the
    refreshed scan. A turn's base-version check therefore observes a hand edit even though the
    Bible remains ungated.*

- **R-24** No file in a world SHALL contain an absolute path, a machine identifier or a
  credential, and internal path references SHALL use forward slashes.
  - **WHEN** a world folder is moved to another machine and opened **THEN** every reference
    resolves.

- **R-25** Opening a world whose schema version is newer than the application supports SHALL be
  refused with a clear message, and SHALL NOT modify the world.

- **R-26** Retiring an entity SHALL leave it on disk and resolvable, marked retired, so existing
  citations continue to resolve.

## 1.4 Open questions

- Whether `.history/` should be pruned after some depth. Unbounded in v1: a sheet is 2–5 KB, and
  a pruning policy is a data-loss decision that wants evidence before it is taken.
- Whether **closed-world** external-edit reconciliation should offer a diff rather than a reload
  prompt. Reload only in v1; a merge UI is a product surface, not a foundation concern. There is no
  open-world equivalent to decide: the watcher stopped declaring worlds stale (R-23).
- Whether world folders should carry a marker file identifying the app and format version
  separately from `world.json`, for the benefit of tools that never parse it.

# 2 · Design

## 2.1 Architectural decision

**The folder is the only durable truth, and every mutation goes through one commit primitive.**

Everything above this spec — the gate, the index, the UI — calls `commit(files[])`. That
function is where atomicity, history, versioning and the change log live, together, once. The
alternative, letting each feature write its own files and remember to snapshot, is how a
format without a database rots: one path forgets the snapshot, another forgets the version
bump, and six months later nobody can say what happened to a sheet.

**There are exceptions, and this spec no longer claims to know how many.** `WorldStore.gateOp()`
and `ownedWrite()` write app-owned bytes directly — take media landing from a job and its
`take.json`, reference images copied and removed. `WorldChatStore` writes `.conversations/` through
neither of them. Those have no version to bump and no history to snapshot: a take is immutable and
addressed by id, so there is nothing for the two-track model to track. The exception is about
*what* is written rather than about convenience, and anything belonging to the authored record
still goes through `commit()`.

**The criterion, not the list.** Any path that writes inside a world directory is a mutation path
and is subject to R-3a, whether or not it is named here. That is deliberately phrased as a rule
because the list has been enumerated three times and been wrong three times — one path, then two,
then three — and there are upwards of forty modules in the coordinator issuing direct filesystem
writes. Enumerating them belongs to T-12a as mechanical work, ideally a check that fails on an
unfenced write, rather than to a paragraph anyone maintains by hand.

## 2.2 The two roots

The current implementation's operation-by-operation create, replace, append, move, and remove
effects are catalogued in [`../filesystem-operations.md`](../filesystem-operations.md). That
ledger also identifies lazy directories and temporary files that a static layout cannot show.

**App root** — `%USERPROFILE%\ArkeStudio`. Holds `config.json`, `worlds/`, the global job queue,
the ledger and logs. Created on first run without prompting.

**World root** — `worlds/<slug>/`. Self-contained and portable. A folder is a world if and only
if it holds a parseable `world.json` with a supported `schemaVersion`. Anything else in
`worlds/` is ignored rather than reported as broken, so a user can keep notes there.

## 2.3 Formats and parsing

Prose in Markdown with YAML frontmatter; structure in JSON. Per master spec §2.3.

**Encoding is UTF-8 without BOM; writes use LF; reads tolerate CRLF.** This is not incidental.
Arke shipped exactly this bug and fixed it in `spec-doc.ts`:

> *"Strip a trailing CR so CRLF frontmatter (git `autocrlf` checkout on Windows) parses: `.` in
> the value regex does not match `\r`, so without this every key silently failed and the doc
> parsed empty."*

Arke Studio is Windows-first and its files are hand-editable by users whose editors will write
CRLF. The failure is silent — a document that parses to an empty object rather than throwing —
which is the worst kind. R-4 exists so it is not re-introduced.

**Round-trip fidelity (R-5) and unknown-field preservation (R-6)** are what make the format
honest. A user opens a sheet in a text editor, adds a key the app has never heard of, and the
app must not eat it. A world written by a later version must survive being opened by an earlier
one. Both are achieved by parsing into a structure that retains its unrecognised remainder, and
serialising from the original text where nothing changed.

## 2.4 Naming and path safety

User-authored names become filenames, on Windows, which is a hazard surface the master spec
does not address and this spec must.

**Slugification** lowercases, transliterates to ASCII where a mapping exists, replaces runs of
non-alphanumerics with a single hyphen, trims hyphens, and caps length. The cap is 48
characters, which §2.4.1 shows is what the path budget affords.

**Rejected forms.** Windows reserves `CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9` and `LPT0`–`LPT9`,
with or without an extension, and forbids `< > : " / \ | ? *` and control characters, and
filenames ending in a dot or a space. A reserved name is escaped rather than refused — the user
named a character "Nul" and is entitled to keep the name. The display name lives in frontmatter
(R-9), so the slug is free to be ugly.

**Collisions** are resolved by numeric suffix, compared **case-insensitively**, because NTFS is.
"Maren Kest" and "maren kest" are different names and must become different files; on a
case-sensitive comparison they would become the same one and the second would silently destroy
the first.

**Unslugifiable names** — a name consisting entirely of emoji, or of a script with no ASCII
transliteration — fall back to a generated slug. The name survives in frontmatter, and nothing
in the product reads a name off a filename.

### 2.4.1 The path budget

The deepest path the layout generates:

```
%USERPROFILE%\ArkeStudio\worlds\<world>\productions\<production>\takes\<takeId>\clip.mp4
```

With a typical profile root (~20), fixed segments (~52), two 48-character slugs and a 29-character
take id, this lands near 200 characters against the 260-character default limit — workable, but
without much margin on a long profile path or a redirected home directory.

Two mitigations, both required by R-10: filesystem operations use extended-length path prefixes
so the 260-character limit does not apply to the app's own reads and writes, and the app checks
its root depth at first run and reports the problem before any world is created somewhere that
cannot hold one.

### 2.4.2 Id allocation

| Id | Form | Allocation |
|---|---|---|
| World, sheet | slug | Slugified from the name, collision-suffixed |
| Canon entry | `CANON-nnn` | Monotonic counter in `world.json`, never reused (R-11) |
| Take, proposal, job | `tk_`/`pr_`/`jb_` + ULID | Sortable, collision-free, no coordination (R-12) |

The canon counter is persisted rather than derived, because deriving it from the maximum existing
id would let a retired entry's number be reused — and a citation to CANON-043 must never come to
mean a different entry than it did. The recovery path (R-11) takes the maximum of existing ids
and the ids recorded in `changes.jsonl`, so a lost counter can only ever be restored too high,
never too low.

## 2.5 Atomic writes and the commit primitive

Every write is staged and renamed (R-13). Renames are atomic on NTFS, so a kill at any moment
leaves the target either wholly old or wholly new.

**The rename retry (R-14) is a Windows requirement, not a nicety.** Windows Defender and the
search indexer routinely hold transient handles on files in a user's profile, and a rename onto a
handle-held target fails with `EPERM` or `EBUSY`. Without a bounded retry, the product produces
occasional inexplicable save failures on exactly the machines it targets. Excluding the app root
from indexing is a good installer suggestion but cannot be relied on.

**A commit is a journalled transaction** (R-15), per master spec §3.5. Ordering alone is not
sufficient: a crash between the first rename and the last leaves the world half-changed, with
`world.json`, `.history/` and `changes.jsonl` potentially out of step, and the absence of a
change-log line tells the recovery pass only *that* a commit failed, not which of its files
already landed.

The commit primitive implements the journal protocol in full: write `.commit/<commitId>.json`
in `planning` with the complete plan, snapshot bytes and per-file base and target hashes; flush;
validate history destinations; write staged files; reverify bases and history; move the journal
to `committing`; install snapshots and rename into place with `world.json` last; append indexed
records to `changes.jsonl`; mark `done` and clean up.

Recovery on open is driven by the journal phase — roll back from `planning`, repair and roll back
legacy `prepared` journals, roll forward from `committing`, and clean up from `done`. Roll-forward
is idempotent because every step from the point of no return is checked against recorded hashes
or indexed audit records. The world lock guarantees at most one journal exists, so what is found
is never ambiguous.

## 2.6 Versioning

Two tracks, per master spec §2.4: one monotonic canon revision per world, independent monotonic
versions per sheet. Implemented in the commit primitive so no caller can forget it.

A commit bumps `world.canonRevision` once if it touches any canon entry, regardless of how many
(R-16), and bumps each sheet it changes (R-17).

**A commit may move both tracks.** An earlier draft forbade this, on the reasoning that it kept
take provenance unambiguous. That reasoning was wrong — a take made after a mixed commit records
`{canonRevision: 43, sheets: {maren-kest: 5}}`, which is no more ambiguous than either alone —
and the prohibition broke referential integrity outright: a proposal that creates CANON-044 *and*
adds it to Maren's `canonRules` must land atomically, or the world passes through a state where a
sheet cites an entry that does not exist. Splitting into two ordered commits guarantees that
window rather than avoiding it.

## 2.7 History

Full snapshots under `.history/`, addressed by the version they hold:

```
.history/canon/CANON-002/v42.md
.history/characters/maren-kest/v4.md
```

Snapshots rather than diffs, because there is no VCS underneath and reimplementing patch
application to save 20 KB per sheet is a bad trade. Restoring is a file copy that becomes a new
version (R-20); history is append-only in the same spirit as the change log.

Binaries are never snapshotted. Takes are immutable and addressed by id, so the reference is
the version.

## 2.8 The change log

`changes.jsonl`, append-only, one JSON object per line, per master spec §2.5. It is the audit
trail, the index's rebuild input, and the evidence a commit completed.

**Truncated last lines are expected** (R-22). A crash during an append leaves a partial line;
the reader discards it and the next append repairs the file by ensuring it begins on a fresh
line. Anything stricter would turn an ordinary crash into a corrupt world.

## 2.9 Ownership and external edits

A lock file holds pid and start time and is refreshed on a heartbeat while held (R-3). It is stale
when its pid no longer exists, or when its heartbeat has not advanced within the window.

The recorded start time does **not** currently distinguish a reused pid, and R-3 should not be read
as saying it does: `WorldLock` records the moment the lock was *acquired*, not the operating
system's start time for that process, so comparing it says nothing about whether the pid you are
looking at is the one that wrote it. Detecting reuse would mean recording the OS process start time
and comparing against that. Staleness therefore rests on the two conditions R-3 states — a dead pid, or a cold heartbeat — and
it is the **heartbeat** that catches a reused pid, by going cold rather than by disagreeing. Stale
locks are reclaimed, because the alternative is a user locked out of their own work by a crash.

While a world is open a watcher observes it, debounced, and its only remaining job is adopting a
`bible.md` that moved — the one authored file the product invites a user to open in an editor
(R-23). Hand edits made while a world is **closed** are reconciled explicitly on open
(R-28). Merging is deliberately not attempted in either case: the app cannot know which of two
divergent versions the user meant, and guessing would violate the one promise the format makes.

**The lock is doing real work, and R-27 is not a substitute for it** (R-3a, ADR-002). The commit
primitive verifies every target's base hash and refuses a base that has moved — but it does so
*under the lock*, as its own comment says, and the rename that claims the files happens later.
Between the check and the swap there is a window that only exclusive ownership closes. R-27 catches
work drafted against content that has since changed; it does not catch two writers reading the same
base at the same moment, and it does not notice a writer whose targets nobody else touched.

What can change is **who the owner is and how their liveness is established**, and that is a
property of the deployment rather than of the format. A world on a laptop keeps the lock file,
because one machine can answer whether a pid is alive and a good error beats a silent race. A world
whose writer is elsewhere cannot use a pid at all and takes a lease instead — the heartbeat already
exists; the identity and the liveness test change, and the commit gains a fence against a holder
that has been deposed (R-3a). What does not change is that one writer holds a world at a time, or
that divergence is detected and reported rather than merged.

## 2.10 Schema versioning

`world.json` carries `schemaVersion`. Older worlds are migrated forward on open, with the
pre-migration state snapshotted to `.history/`. Newer worlds are refused, unmodified, with a
message telling the user to update (R-25) — an older build must never "helpfully" write a world
it does not fully understand, because R-6's field preservation protects fields it can round-trip,
not semantics it lacks.

## 2.11 Retirement

Entities are retired, not deleted (R-26). A retired entity stays on disk, marked, and keeps
resolving, so a take that cited it three months ago still explains itself. Hard deletion is out
of scope; it is a data-loss operation and wants its own design.

## 2.12 Error handling

Partial failure is normal and must not be fatal (R-2). A world with one malformed sheet opens
with that sheet listed as unreadable, its path shown, and everything else working. The failure
mode this avoids is the one where a stray character in one file makes an entire world
inaccessible — for a hand-editable format, that is not a hypothetical.

## 2.13 Performance

The open scan is bounded by file count, not content size: frontmatter is parsed eagerly, bodies
lazily. The master spec's two-second interactive budget (N-3) is met with a warm index
(SPEC-003); this spec's obligation is that a cold full scan of a 50-sheet, 200-entry, 500-take
world completes in under ten seconds so that the index rebuild budget holds.

Scanning is off the main thread, and no filesystem call blocks the window.

## 3.2 Testing

**Formats** — round-trip fidelity per entity type; CRLF frontmatter parses (the regression test
for the Arke bug); unknown keys and fields survive read-modify-write; UTF-8 without BOM in, same
out.

**Naming** — every Windows reserved device name, with and without extensions; forbidden
characters; trailing dots and spaces; case-insensitive collision; emoji-only and non-Latin names;
the length cap; the deepest path the layout can generate, read and written successfully.

**Crash safety** — the important tests, since these are the failures with no second chance.
Kill-at-every-step of a multi-file commit, asserting the world opens afterwards in exactly one of
the two valid states. Rename against a held handle, asserting retry succeeds. Truncated final line
in `changes.jsonl`, asserting tolerant read and repaired append. Orphaned staging directory,
asserting recovery discards it.

**Versioning** — canon revision advances once per commit regardless of entry count; sheet versions
move independently; restore produces a new version and leaves history intact; the canon counter
recovers no lower than the true maximum.

**Ownership** — second instance refused; stale lock reclaimed, on a dead pid and on a cold
heartbeat separately; external edit detected and not merged.

**The lease** — acquire, renew, expire, take over. Assert that renewal **extends** it: a lease held
past its own expiry window by a live holder is still held, which is the only assertion that
distinguishes renewal working from renewal being unnecessary in a short test. Assert that a lease
which stops being renewed expires; that a successor can take a world whose holder is gone; that a holder whose lease expired
cannot write afterwards; and that two coordinators cannot hold one world at once. T-12b is
otherwise completable without evidence any of it works.

**Recovery waits for ownership** — open a world whose owner holds a journal and assert the second
instance neither resolves it nor writes. Open read-only and assert both halves of R-3b: no file is
renamed, **and** the unresolved journal is reported. A consumer that silently ignores it passes the
first assertion and leaves a reader believing the world is intact.

**The fence** — a writer that has lost ownership cannot write, and this is the test the local lock
never had. Depose a holder while it is still alive (stop its heartbeat, let a second process take
the world) and assert that the first one's next write is refused on **each** mutation path, not
only through the committer. Assert it too when the successor has written nothing at all, since a
deposed writer whose targets nobody touched is the case a base-hash check cannot catch (R-3a).

**And the in-flight window specifically.** A write that *begins* before the takeover and lands
after it is the case that separates an atomic fence from a check-then-write, and a test that lets
the takeover finish first will pass an implementation that has only the latter. Start the first
holder's write, interpose the takeover while it is in progress, and assert the write still fails —
on each path, and at each point the implementation could be interrupted.

**Every path fails in flight, and nothing is destroyed by it.** Interpose the takeover inside take
arrival, between the media rename and `take.json`; assert the write is refused **and** that the
paid media is still reachable, because a recovery can finish or undo what was started. Both halves
are the test: refusing without recovery orphans provider output, and recovering without refusing
leaves two writers in the world at once.

**Portability** — a world created on one path opens on another; no absolute path appears in any
file.

## 3.4 Decision log

| # | Decision | Rationale |
|---|---|---|
| D1 | One commit primitive owns atomicity, history, versioning and logging | Distributing them is how a database-less format rots — one path forgets the snapshot, another the version bump. |
| D2 | LF on write, CRLF tolerated on read | Users hand-edit with editors that write CRLF; Arke already shipped and fixed this exact silent-empty-parse bug. |
| D3 | Unknown fields preserved on round-trip | Protects hand edits and forward compatibility across version skew. |
| D4 | Case-insensitive slug uniqueness | NTFS is case-insensitive; a case-sensitive check would let one sheet silently destroy another. |
| D5 | Reserved names escaped, not refused | The user named their character "Nul" and is entitled to. Display names live in frontmatter, so slugs may be ugly. |
| D6 | Persisted canon counter, recovery takes the maximum | Deriving from existing ids would let a retired number be reused, changing what an old citation means. |
| D7 | Bounded rename retry | Defender and the search indexer hold transient handles; without retry the product fails saves inexplicably on its target platform. |
| D8 | Journalled commit, not ordering alone | Ordering makes failure detectable but not recoverable — it cannot say which renames landed. The journal's recorded hashes make roll-forward idempotent and roll-back exact. |
| D15 | Base-hash verification inside the commit primitive | Puts the staleness check where no caller can skip it, and makes out-of-band writes detectable at the only point that matters. |
| D16 | Closed-world edits reconciled, not absorbed | Absorbing them would let a change enter the record with no version, snapshot or audit line — defeating the gate for anyone with a text editor. |
| D9 | A commit may move both version tracks | Reversed from an earlier draft. Forbidding it broke referential integrity — a new canon entry and the sheet citing it must land together — and the provenance argument for forbidding it does not hold. |
| D10 | Snapshots, not diffs | No VCS underneath; reimplementing patch application to save 20 KB per sheet is a bad trade. |
| D11 | External edits are reconciled on open, never merged — and while a world is open the watcher only adopts `bible.md` (R-23) | The app cannot know which divergent version was meant, and guessing breaks the format's only promise. |
| D12 | Retire, never delete | Keeps historical citations resolvable. Hard deletion is a data-loss operation needing its own design. |
| D13 | Newer schema versions refused, unmodified | Field preservation protects round-trippable fields, not semantics an older build lacks. |
| D14 | Malformed files fail individually | For a hand-editable format, one stray character must not make a world inaccessible. |
