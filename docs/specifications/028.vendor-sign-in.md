# 1 · Requirements

## 1.1 Summary

Let a person author with a model subscription they already pay for, signed in the way the vendor
intends, without Arke Studio ever handling the credential.

The harness already does this work. OpenCode brokers OAuth sign-in for OpenAI, Copilot, Grok and
others alongside every API-key provider, and stores the result in its own credential file. That
makes the bundled harness the whole multi-vendor story: Arke does not need a vendor integration per
vendor, and does not need a second harness to reach a second vendor's models.

There are two people to serve here, and they need opposite things.

**Someone who already uses the harness** has a sign-in sitting in their own state directory, and
should not be asked for it twice. What stands in their way is Arke's own isolation. SPEC-005 spawns
the harness with its state directory redirected somewhere Arke owns, so that Studio's configuration
is the configuration and nothing on the machine can quietly outrank it. That redirect works by
making the person's own harness state invisible — and their sign-in lives inside exactly that
state. The isolation that made authoring deterministic is the thing hiding the credential. One file
therefore crosses the boundary, by reference and never by copy.

**Someone installing Arke for the first time** has no sign-in anywhere and has never heard of the
harness. Arke signs them in itself, driving the harness's sign-in API and sending them to their
vendor's own login page. The credential is created inside Arke's owned state directory from the
start, so nothing crosses any boundary and no link exists at all. This is the simpler of the two
paths and the one most people will take.

Neither path shows the harness. A person signs in to ChatGPT, not to OpenCode.

**Amends SPEC-005 R-6.** That requirement says credentials reach the harness by environment
variable at spawn. It holds for API keys and is unchanged for them. It cannot hold for an OAuth
connection, which is not a secret Arke possesses but a session the person established with their
vendor, held in a file the harness refreshes on its own schedule. R-6 is therefore narrowed to
keys, and this spec owns the other case.

## 1.2 Scope

**In scope**

- Signing in from nothing: Arke driving the harness's sign-in API and the hand-off to the vendor.
- Making a person's pre-existing vendor connections reachable from the harness Arke spawns.
- The sign-in surface: what exists, which one authoring uses, and how to add or remove one.
- The credential's lifecycle as Arke observes it — never as Arke manages it.
- Refresh failure: how it presents, why readiness cannot pre-empt it, and how a person recovers.
- Which of a connection and a configured key authoring uses, where somebody holds both.
- Degradation when no vendor connection exists, or when it cannot be reached.

**Out of scope (this spec)**

- Media provider credentials — SPEC-008. Those are keys Arke holds and dispatches with.
- Harness discovery, lifecycle, the agent roster and confinement — SPEC-005.
- Which model authoring routes to, and the Ollama fallback — SPEC-005 R-7.
- Claude Code's own subscription auth, which the Claude binary owns end to end and which Arke
  neither sees nor redirects — SPEC-005.
- Spend accounting for subscription turns. A subscription bills nothing per turn, and a notional
  per-turn cost SHALL NOT enter the ledger — SPEC-008 owns the ledger and this is a note, not a
  requirement of this spec.

## 1.3 Acceptance criteria

### The credential

- **R-1** Arke Studio SHALL NOT read, parse, copy, store or transmit a vendor **token**. It SHALL
  refer to the credential file only by path and SHALL NOT inspect its contents.
  - **WHEN** a vendor connection is used for authoring **THEN** no vendor token appears in any file
    Arke writes, in its settings, or in any log line it emits.
  - Stated as things that can be looked for rather than as an absence that cannot be proven. "No
    token passed through the process" is not a claim any test can settle; "no token is in the files
    or the logs" is, and it is what a reviewer can actually check.
  - Two things do pass through Arke, and the requirement is written as "token" rather than
    "credential material" so that it stays true. The first is the single-use authorization code the
    vendor returns during sign-in (R-6): Arke relays it from the browser to the harness and retains
    it nowhere. It expires in moments, is spent on first use, and is not itself a credential — the
    harness exchanges it and keeps whatever comes back. The second is an API key a person chooses to
    type (R-6), which is handed to the harness and likewise not retained. Neither is a token Arke
    holds, and both are stated here rather than left to be discovered as violations.

- **R-2** **Where a vendor connection already exists on the machine**, it SHALL be reachable from
  Arke's owned state directory through a filesystem link sharing one identity with the original —
  not a copy.
  - **WHEN** the harness refreshes a token **THEN** the person's own installation and Arke both
    observe the new token, and neither holds a stale second copy.
  - **AND** Arke SHALL NOT acquire responsibility for a refresh lifetime it would then have to
    keep alive.
  - The precondition is load-bearing rather than decorative. Most people will have no existing
    connection, so this requirement simply does not engage for them, and R-8 governs instead. A
    reading that made this unconditional would fail the common case.

- **R-3** Only the credential file SHALL cross the isolation boundary. No other state from the
  person's own harness installation SHALL be reachable by the harness Arke spawns.
  - **WHEN** the harness starts **THEN** its sessions, database, configuration and cached state
    are Arke's own, and nothing the person has configured elsewhere outranks Studio's settings.
  - Written as an enumerable claim rather than as "isolation is total", because the second cannot
    be tested and the first can: the owned state directory is compared against the person's, and
    the credential file is the only name they share.

- **R-4** Where the link cannot be created, the person SHALL be offered a fresh sign-in (R-5–R-9)
  rather than being blocked, and any limitation SHALL be stated.
  - **WHEN** Arke's state directory and the person's profile are on different volumes **THEN**
    the link is impossible, and signing in through Arke produces a working connection anyway —
    it simply lands in Arke's own directory instead of being shared with their installation.
  - **AND WHEN** the filesystem does not support the link **THEN** the same applies.
  - Copying the credential to work around either case is prohibited by R-1. The cost of the
    fallback is that the person signs in twice over the life of the machine, not that they lose
    the feature.

### Signing in and out

- **R-5** Arke SHALL drive sign-in through the harness's API, and SHALL NOT expose the harness's
  own interface to the person.
  - **WHEN** a person signs in **THEN** they see Arke, then their vendor's page, then Arke. The
    harness is not named, shown, or launched in a terminal at any point.
  - Recorded as a requirement because the harness's command-line sign-in is a keyboard-driven
    terminal menu that cannot be put in front of anybody. The API is not a preference here, it is
    the only viable path.

- **R-6** **Where the chosen method is a browser sign-in**, authentication SHALL happen on the
  vendor's own page. Arke SHALL NOT present a field that accepts a vendor password, under any
  method.
  - **WHEN** a browser sign-in begins **THEN** Arke obtains the address from the harness and opens
    it in the person's browser, and they authenticate with the vendor directly.
  - Typing an API key by hand remains available where a vendor offers that method, for people
    without a subscription. It is handed to the harness and not retained by Arke (R-1). The
    qualifier exists because without it this requirement would forbid the key method it goes on to
    permit — a key is entered in Arke by definition, and there is no vendor page involved.
  - The password prohibition carries no qualifier and admits no method. A vendor password SHALL
    never be typed into Arke.

- **R-7** The options offered SHALL be the ones the harness reports, in the harness's own words.
  - Arke SHALL NOT carry its own list of vendors or methods. The harness's list changes with its
    version, and an invented label would drift from what the flow actually does.

- **R-8** A sign-in performed through Arke SHALL write only into Arke's owned state directory.
  - **WHEN** somebody with no existing connection signs in **THEN** the credential is created
    inside Arke's owned state directory, no link is involved, and no file outside that directory
    is written.
  - **AND WHEN** a connection is already linked under R-2 and the person signs in again **THEN**
    the write lands in Arke's owned state directory as required, and reaches their own
    installation because the two are one file. This is correct and intended: their installation
    receives the same fresh token rather than being left on a dead one.
  - The second case is called out because an earlier reading of this requirement forbade it, and
    R-13 routes people into it by design — a stale token sends them to sign in again, and if a
    link is in place that sign-in necessarily writes through it. A requirement that forbade the
    recovery path it mandates would be unimplementable. What R-8 prohibits is Arke reaching into
    the person's installation *other than* through the one file R-2 already shares — writing their
    configuration, their sessions, or a second credential elsewhere in their profile.

- **R-9** Every method the harness reports for a vendor SHALL be offered, including hand-operated
  ones, and the person SHALL choose among them.
  - **WHEN** a vendor offers a headless method alongside a browser one **THEN** both are offered,
    and somebody whose browser hand-off does not come back can complete sign-in by the other.
  - Arke SHALL NOT attempt to detect that a browser hand-off has failed in order to offer the
    alternative. There is no reliable signal: a browser that opened and was never returned to is
    indistinguishable from a person reading slowly. Offering both from the start needs no such
    judgement, and an earlier draft that triggered the fallback on undetectable failure specified
    something nobody could build.

- **R-9a** A person SHALL be able to remove a vendor connection from within Arke.
  - **WHEN** a connection is removed **THEN** it stops being offered for authoring, and the
    removal is performed by the harness rather than by Arke deleting a file.
  - **AND WHEN** the credential was linked under R-2 **THEN** removal is reported as also
    affecting their own installation, before it happens, because one file cannot be signed out of
    on one side only.
  - Stated because sign-in without sign-out is not a complete surface, and because somebody who
    signed in through Arke on a machine with no other harness installation has nowhere else to go
    to undo it — R-15 cannot serve them.

### The surface

- **R-10** Arke SHALL show which vendor connections exist and which one authoring will use.
  - Labels, vendor names and states only. The reasoning lives here, not on the screen.

- **R-11** Where a person holds both a vendor connection and a key configured in Studio for the
  same vendor, Arke SHALL show which of the two authoring will use.
  - **WHEN** both are present **THEN** the surface names the one in effect, and does not leave the
    person to infer it.
  - The harness resolves a stored connection ahead of a key passed at spawn. That is its
    behaviour, observed rather than chosen, and Arke cannot invert it — so it is recorded here as
    a fact the design accommodates, not as a requirement Arke could be tested against. What is
    Arke's to satisfy, and all this requirement asks, is that the outcome is legible rather than
    surprising.

- **R-12** Vendor sign-in SHALL be optional in full. Authoring SHALL work unchanged on configured
  keys or on local models, and nothing in this spec SHALL become a precondition for authoring.

### Staleness

- **R-13** A credential that cannot be refreshed SHALL be surfaced as a request to sign in again,
  never as a failed authoring turn.
  - **WHEN** a turn fails because a token could not be refreshed **THEN** the session ends with
    that stated reason, the proposal is preserved untouched, and the connection is marked as
    needing sign-in.
  - **AND** the person SHALL be able to recover by signing in again, without losing staged work.

- **R-14** Readiness SHALL NOT claim a vendor connection is usable, only that one is present.
  - A dead refresh token is indistinguishable from a live one until it is used: the credential
    file is well-formed, the connection lists normally, and the model catalogue resolves. The
    first failing turn is the only detector, so readiness SHALL NOT report a health it cannot
    establish.

- **R-15** A connection removed or replaced in the person's own installation SHALL be reflected in
  Arke without further action, where the credential was carried across rather than created here.
  - Follows from R-2 — one identity, so there is nothing to synchronise — and is stated because it
    is a property worth not losing in a later refactor.

## 1.4 Open questions

- **How the code comes back.** The sign-in returns an address and the vendor returns a one-time
  code, but whether that arrives by a local redirect Arke must listen for, or by the person
  copying it, is not established and may differ per vendor and method. It changes what step 3 of
  §3.1 has to build, and it is the first thing to settle.
- **Volume layout.** R-4 falls through to signing in when Arke's state directory and the person's
  profile sit on different volumes. How common that is on the installed base is unmeasured. If it
  is common, sharing an existing sign-in is rarer than assumed and the carrying path matters less
  than the sign-in path — which is an argument for building §2.2 first regardless.
- **Harness line parity.** The link mechanism and the sign-in API are both measured on the stable
  line. The v2 line shares the credential path but neither has been exercised on it end to end,
  and SPEC-005's adapter is what will drive it.
- **A profile under folder redirection.** Where the user profile is redirected to a synchronising
  provider, link behaviour is not established and may differ per provider.
- **Other brokered vendors.** The harness reports sign-in methods for Copilot, Grok, GitLab, Poe,
  DigitalOcean and Snowflake alongside OpenAI. Only OpenAI has been exercised for authoring, and
  whether every vendor's models suit authoring is a separate question from whether sign-in works.

# 2 · Design

## 2.1 Architectural decision

**Two paths, chosen by whether a sign-in already exists on the machine.**

Where one does, one file crosses the isolation boundary — by identity rather than by value.
Where none does, Arke conducts the sign-in and the credential is born on Arke's side of the
boundary, so there is nothing to cross. The second path is the common one and the simpler one;
the first exists so that an existing user is not asked to sign in twice.

For the carrying path, four approaches were considered and three rejected.

*Copy the credential in.* Rejected outright by R-1. A copy makes Arke the holder of a vendor
credential, and — worse than the holding — the owner of a second refresh lifetime. Two copies with
independent expiry is a bug that presents months later as an inexplicable sign-out. This is the
same objection that ended the equivalent attempt for Claude Code, where redirecting the harness's
configuration directory took the credential with it and there was no way to bring it back that did
not amount to owning the token.

*Abandon the redirect.* Rejected because the redirect is load-bearing. It exists because the
harness loads the person's stored connections and they outrank anything passed at spawn — which,
with a stale stored connection, fails turns for a reason nothing on screen can explain. Giving that
up to gain sign-in trades a legible problem for an illegible one.

*Have Arke implement the OAuth exchange itself and write the credential file.* Rejected. Arke would
hold the vendor's tokens, own their refresh, and have to track each vendor's protocol as it
changed. Note the distinction from what §2.2 adopts: Arke **conducting** a sign-in by asking the
harness to start one is not the same as Arke **being** the OAuth client. In §2.2 the harness
performs the exchange and keeps the result; Arke opens a browser and passes back a code.

*Link the credential file into the owned directory.* Adopted for the carrying path. The link and
the original are one file with two names, so a refresh written through either is visible through
both, there is no second copy, and nothing needs synchronising. Isolation survives for every other
piece of state, because every other piece of state is genuinely Arke's.

## 2.2 Signing in from nothing

This is the path for someone who installs Arke and has never used the harness. It rests on the
harness exposing sign-in over its API rather than only through its own interface, which it does.

The shape is four steps:

1. Arke asks the harness which vendors can be signed in to and by what methods. The answer is a
   list per vendor — for OpenAI, a browser subscription sign-in, a headless equivalent, and manual
   API-key entry. Arke renders that list; it does not carry one of its own (R-7).
2. The person chooses one, and Arke asks the harness to begin it. The harness returns an address
   and any instructions that go with it.
3. Arke opens that address in the person's browser. It is the vendor's real sign-in page, on the
   vendor's domain, and the person authenticates there (R-6).
4. The vendor returns a one-time code. Arke passes it to the harness, which performs the exchange
   and writes the resulting credential into Arke's owned state directory.

The person's experience is: a list in Arke, their vendor's familiar login page, then back to Arke
signed in. The harness is not named at any point (R-5), and on this path nothing outside Arke's
own state directory is written (R-8).

Step 1 offers every method the harness reports, not only the browser one, and the person picks.
There is no cleverness where Arke tries a browser sign-in, decides it failed, and falls back —
a browser that opened and was never returned to looks exactly like somebody reading slowly, so
there is nothing to detect (R-9).

Two consequences worth stating. **No link is involved on this path** — the credential is created on
Arke's side from the outset, so §2.3 does not apply and neither do its failure modes. And this is
why a different volume (R-4) costs so little: the person signs in through Arke instead of sharing
an existing sign-in, which is a second sign-in once, not a lost capability.

The harness's command-line sign-in was examined and is unusable for this: it is a keyboard-driven
terminal menu that waits for input and does nothing without a terminal attached. That is a
statement about the harness rather than a preference, and it is why R-5 names the API specifically.

## 2.3 Carrying an existing sign-in, and what was measured

The mechanism rests on a property of the harness that had to be established rather than assumed:
**that it mutates the credential file in place, rather than writing a replacement and renaming it
over the top.** Write-and-rename is the common way to save a file safely, and it would break this
design silently — the replacement is a different file, the second name would still refer to the
old one, and Arke would sit on a credential frozen at the moment the link was made.

It writes in place. Established 2026-08-26 across all three writers that touch the file: signing
out, signing in, and refreshing an expired token mid-turn. In each case the file's identity and
link count were unchanged and both names were byte-identical afterwards. The refresh case was
forced deliberately, by expiring the token through the linked path and running a real turn, and is
the one that matters most, because it is the one that happens without anybody asking for it.

This property belongs to the harness and not to Arke, so it SHALL be covered by a regression test
(§3.2) rather than trusted to stay true.

## 2.4 The surface

Sign-in is a short list: the vendors with a connection, and which one authoring uses. Adding one
hands off to the vendor and reports what came back. Removing one is available from the same list,
and says plainly where it will also sign the person out of their own installation — before it
happens, because a shared file cannot be signed out of on one side only (R-9a). A vendor needing
attention says so in those words.

Copy on this screen stays at labels and states. Why a connection is used ahead of a key, and why a
connection can look healthy and then fail, are explained here in the spec and not on the screen.

## 2.5 Staleness, and why it cannot be pre-empted

This is the failure mode most likely to be mistaken for an Arke defect, so it is worth stating
plainly what it looks like from inside.

An expired refresh token is invisible to inspection. The credential file is well-formed. The
connection lists as present. The model catalogue resolves and returns the vendor's real model
family. Every check that could be run before a turn passes. The failure appears only when the
harness tries to exchange the refresh token and the vendor declines it — which happens inside a
turn, after the person has asked for something.

There is therefore no readiness check to write, and R-10 forbids inventing one that would report a
health it cannot establish. What remains is to make the failure land well: end the session with the
reason stated, keep the staged work, mark the connection, and offer the way back. Tokens observed
here last on the order of days, so this is a state that will find people who return to Arke after a
break — the recovery path is the design, not an edge case.

## 2.6 Degradation

No vendor connection, an unusable one, and a link that could not be made all reduce to the same
outcome: authoring continues on configured keys or local models, and the reason is stated where
sign-in is shown. None of them is an error. A person who never signs in to a vendor should not be
able to tell that this spec exists.

The link case degrades further than the others, because the person can simply sign in through Arke
instead (§2.2). It is the only degradation that costs a step rather than a capability.

# 3 · Tasks

## 3.1 Implementation plan

**Signing in (the common path).**

1. Read the available vendors and methods from the harness, and offer every method it reports for
   a vendor — browser and hand-operated alike — for the person to choose between.
2. Begin the chosen method, take back the address and instructions, and open the address in the
   person's browser.
3. Take the returned code, hand it to the harness to complete, and report only the outcome.
4. Remove a connection on request by asking the harness to remove it, warning first where the
   credential is linked and removal would reach the person's own installation too.

**Carrying an existing sign-in.**

5. Locate the person's credential file for the harness in use, and detect whether a link into
   Arke's owned state directory is possible — same volume, supporting filesystem.
6. Create the link when the owned state directory is prepared, and remove that name — never the
   original — when it is torn down.
7. Where the link is impossible, fall through to signing in (step 1) and state why sharing was
   not available.

**Both paths.**

8. Report the outcome as part of harness readiness: connections present, and how each arrived.
9. Surface the connection list, and which of a connection and a configured key is in effect where
   somebody holds both.
10. Classify a refresh failure out of the turn's error and end the session with that reason,
    preserving the proposal.
11. Mark the connection as needing sign-in, and clear the mark on success.

## 3.2 Testing

**Signing in and out**

- The offered list comes from the harness and is not hard-coded: with the harness reporting a
  changed set of methods, the surface changes with it.
- Every method the harness reports is offered, hand-operated ones included, without Arke having
  to judge that a browser hand-off failed.
- With no link in place, a completed sign-in writes the credential inside Arke's owned state
  directory and the person's own harness state is byte-unchanged throughout.
- With a link in place, a re-sign-in writes through it and their installation receives the same
  fresh token — asserted as correct behaviour rather than prohibited, since R-13 sends people
  down this path.
- Nothing outside Arke's owned state directory is written on either path, the shared credential
  file excepted.
- The authorization code is not written to any file Arke owns and does not appear in any log.
- A refused or abandoned sign-in leaves no partial credential and returns a stated outcome.
- Removing a connection stops it being offered, and is performed through the harness rather than
  by deleting a file.
- Removing a linked connection warns that the person's own installation is affected, before it
  happens and not after.
- The harness's terminal sign-in is never spawned. Asserted directly, because reaching for it is
  the obvious shortcut and it would strand a person at a menu they cannot answer.

**Carrying an existing sign-in**

- The in-place-write property, as a regression test against the harness: mutate the credential
  through the linked name with synthetic values, assert the file identity and link count are
  unchanged and both names agree. This guards the assumption §2.3 rests on. It uses synthetic
  credentials and never touches a real one.
- The link is a link: same file identity from both paths, link count of two, and a write through
  either visible through the other.
- Teardown removes one name and leaves the original intact, with its content unchanged.
- Different volumes: link creation fails, sign-in is offered instead, and no copy is made anywhere.
- Signing out in the person's own installation is observed by Arke without a restart.

**Both**

- Refresh failure mid-turn ends the session with the stated reason, leaves the proposal untouched,
  and marks the connection.
- Isolation holds: whichever path produced the credential, nothing else from the person's own
  harness state is visible to the spawned harness.

## 3.3 Definition of done

- A person can remove a vendor connection from inside Arke, and is told first where doing so
  reaches their own installation.
- A person who has never used the harness can sign in to their vendor from inside Arke, and the
  harness is never named or shown.
- A person who already uses the harness is not asked to sign in a second time.
- No file Arke writes contains a vendor token, and no log line does.
- A dead refresh token produces a sign-in prompt and a preserved proposal, not a failed turn with
  a provider error.
- Every degradation path leaves authoring working and says why sign-in is unavailable.
- The in-place-write regression test is green, and its failure would block a harness upgrade.
