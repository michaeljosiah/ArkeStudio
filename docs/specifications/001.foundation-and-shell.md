# 1 · Requirements

## 1.1 Summary

Stand up the Arke Studio foundation: an npm-workspaces monorepo, schema-first domain contracts
for the world model, a coordinator embedded in the Electron main process, a supervisor for the
two child processes the product depends on, and a React client that reproduces the approved
design baseline with every v1 screen reachable.

This is Phase 1 groundwork (master spec §19). Nothing persists to a real world folder and
nothing generates; the client runs against fixtures served by a mock world provider. The point
of this spec is that the shape is right before any of it is load-bearing.

## 1.2 Scope

**In scope**

- Monorepo structure, shared TypeScript config, lint and format scaffolding.
- `packages/contracts`: zod schemas for the world model, proposals, jobs, domain events, and
  the harness adapter interface adopted from Arke.
- `packages/coordinator`: WebSocket transport, read model, append-only change log, mock world
  provider, and a generic child-process supervisor.
- `apps/desktop`: Electron main, preload, window lifecycle, updater wiring, child supervision.
- `packages/client`: React client reproducing the design baseline; every v1 screen reachable.
- The launch screen and its readiness probe.
- The design-system port: tokens, the component layer, and Arke Studio's own domain primitives.

**Out of scope (this spec)**

- Reading or writing real world folders — SPEC-002.
- The SQLite index and citation queries — SPEC-003.
- The accept gate, proposals and ripple computation — SPEC-004.
- A live OpenCode session; the adapter ships as an interface with a mock behind it — SPEC-005.
- Any provider call, job execution, cost or ledger — SPEC-008, SPEC-009.
- The Voxa sidecar's own protocol; only its supervision skeleton lands here — SPEC-011.
- Installer signing and packaging beyond a working `electron-builder` target — SPEC-016.

## 1.3 Acceptance criteria

- **R-1** The repository SHALL be an npm-workspaces monorepo containing `packages/contracts`,
  `packages/coordinator`, `packages/adapter-opencode`, `packages/client`, `packages/providers`,
  `packages/voice`, and `apps/desktop`.
  - **WHEN** `npm install` runs at the root **THEN** every workspace resolves without error.
  - **AND WHEN** `npm run typecheck` runs at the root **THEN** every workspace typechecks.

- **R-2** The contracts package SHALL define, as zod schemas, the world entity model (world,
  sheet, canon entry, production, scene, shot, take, artifact), the proposal and ripple shapes,
  the job shape, the normalised domain-event union, and the `HarnessAdapter` interface with
  capability flags.
  - **WHEN** a malformed entity or event is parsed **THEN** validation fails at the boundary
    rather than propagating a partial object.
  - **AND WHEN** a fixture world is parsed **THEN** every entity round-trips through its schema
    unchanged.

- **R-3** The coordinator SHALL push ordered, monotonically sequenced, schema-validated frames
  over WebSocket — one `snapshot` followed by `event` frames — and SHALL append every mutation
  to a change log.
  - **WHEN** the coordinator starts with the mock world provider **THEN** a connecting client
    receives a snapshot followed by sequenced events, and the change log grows.
  - **AND WHEN** a client reconnects with a last-seen sequence **THEN** it receives a fresh
    snapshot rather than a partial replay.

- **R-4** The coordinator SHALL run inside the Electron main process, not as a separately
  launched server.
  - **WHEN** the application starts **THEN** no external port is required for the client to
    reach the coordinator, and quitting the app stops it.

- **R-5** A child-process supervisor SHALL start, health-probe, restart and gracefully stop
  supervised processes, allocating a loopback port per child and surviving a child that never
  becomes healthy.
  - **WHEN** a supervised child exits unexpectedly **THEN** it is restarted with backoff, and
    repeated failure is reported as a stated reason rather than a silent absence.
  - **AND WHEN** the application quits **THEN** every supervised child is stopped before exit,
    leaving no orphan process.

- **R-6** The application SHALL start and reach an interactive state when either supervised
  child is unavailable, degrading the affected features with a stated reason.
  - **WHEN** neither OpenCode nor Voxa can start **THEN** the client still opens, browses
    fixtures and navigates every screen, with authoring and voice disabled and explained.

- **R-7** The client SHALL reproduce the approved design baseline, with every v1 screen
  reachable from the shell navigation.
  - **WHEN** `npm run build -w @arke-studio/client` runs **THEN** it succeeds and emits `dist/`.
  - **AND WHEN** the client is opened **THEN** every screen enumerated in §2.9 is reachable by
    navigation without editing a URL by hand.

- **R-8** The client SHALL present a launch screen on start that probes readiness — coordinator,
  harness, voice sidecar — and hands off to first-run when no world exists, or to the world
  picker when one does.
  - **WHEN** the application starts with no worlds **THEN** the launch screen hands off to
    first-run.
  - **AND WHEN** it starts with at least one world **THEN** it hands off to the world picker.
  - **AND** the launch screen SHALL respect `prefers-reduced-motion`.

- **R-9** The renderer SHALL run with `contextIsolation` enabled, `nodeIntegration` disabled and
  sandboxing on, reaching the coordinator only through a typed preload bridge.
  - **WHEN** the renderer attempts to reach Node or Electron APIs directly **THEN** they are
    unavailable.

- **R-10** The client SHALL hold no provider credentials and SHALL have no code path that reads
  one.
  - **WHEN** the client bundle is searched for credential handling **THEN** none exists; keys
    are a main-process concern (master spec §14.2).

- **R-11** The design-system port SHALL express every colour, type, spacing and effect value as
  a token from the approved token contract, with no hard-coded values in component code.
  - **WHEN** the `.dark` theme class is applied **THEN** the entire client re-themes without a
    component change.

- **R-12** A world card on the picker SHALL be a constant height, and SHALL be the same height as
  the "Create a world" card beside it. Both SHALL take that height from one declaration.
  - **Issue 929:** "Create a world" SHALL be the first card, including in an empty collection,
    using the world-card frame and title geometry, a quiet plus mark and one keyboard-accessible
    control. Its position SHALL NOT move as worlds are added.
  - **WHEN** one world has a one-line logline and another a paragraph **THEN** both cards are the
    same height and their meta lines sit at the same offset.
  - **WHEN** a world has no logline **THEN** its card keeps the logline box empty at full height
    rather than being shorter than its neighbours.

## 1.4 Open questions

- Whether `packages/providers` and `packages/voice` ship as empty typed skeletons in this spec
  or are created by SPEC-008 and SPEC-011. Created here as skeletons, so the workspace graph is
  settled once.
- Whether the fixture world lives in the repository or is generated. Committed as files, so it
  doubles as the SPEC-002 parser's first test corpus.
- Whether to adopt Vite's Electron plugin or wire the renderer dev server manually. Manual, to
  keep the build honest and avoid a plugin between the shell and its own bundle.

# 2 · Design

## 2.1 Architectural decision

**A thin React client over a coordinator embedded in Electron main, with the filesystem as the
only durable truth** (master spec §1.1). No cloud backend, no database of record, no git.

The coordinator is embedded rather than spawned because it is not a server anybody else talks
to — it is the application's domain layer, and giving it a lifecycle independent of the window
would create a class of failure the product has no use for. This mirrors Arke's `apps/desktop`,
which embeds `@arke/coordinator` and serves the client as one signed app.

The two child processes are the opposite case: OpenCode and Voxa are foreign runtimes with
their own lifecycles, and both must be allowed to fail without taking the application down.
Hence the supervisor, and hence R-6.

## 2.2 Target architecture

```
React client ⇄ (preload bridge → in-process WS) ⇄ coordinator
                                                      │
                                    ┌─────────────────┴─────────────────┐
                                    ▼                                   ▼
                          ChildSupervisor("opencode")        ChildSupervisor("voxa")
                                    │                                   │
                             HTTP + SSE                            HTTP + WS
```

In this spec the coordinator is backed by a **mock world provider** reading fixtures, and the
harness adapter is the mock from `@arke/adapter-opencode`. SPEC-002 replaces the provider with
the real filesystem; SPEC-005 replaces the adapter's backing with a live OpenCode.

## 2.3 Package map

```
arke-studio/
  package.json               workspaces root
  tsconfig.base.json
  apps/desktop/              Electron main, preload, updater, supervision
  packages/contracts/        zod schemas — the shared vocabulary
  packages/coordinator/      domain layer, transport, change log, supervisor
  packages/adapter-opencode/ harness adapter (adopted from Arke)
  packages/providers/        skeleton — FAL, Higgsfield, ElevenLabs, OpenAI, Anthropic
  packages/voice/            skeleton — Voxa supervision and client
  packages/client/           React client
  design-system/             the approved baseline (read-only reference)
  docs/                      specification.md and specifications/
```

Package names are scoped `@arke-studio/*` to avoid collision with Arke's `@arke/*` on a machine
that has both checked out.

## 2.4 Data model

No database in this spec, and no database of record in the product. State homes per master spec
§2: the world in its folder, history in `.history/`, the audit trail in `changes.jsonl`, derived
state in a rebuildable index (SPEC-003), client view state in memory only.

This spec introduces the **schemas** for that model and a fixture world that satisfies them. It
does not introduce reading or writing.

The fixture is a trimmed Undersong: one world, three characters (one a sketch), two locations,
one faction, six canon entries (one an open thread), one video production with one scene of four
shots, and a handful of takes in each state. It exists so that every screen has something honest
to render, and so that SPEC-002's parser has a corpus on day one.

## 2.5 API contracts

**Coordinator transport.** Two frame types over WebSocket:

```ts
type Frame =
  | { kind: "snapshot"; seq: number; state: ClientState }
  | { kind: "event";    seq: number; event: DomainEvent }
```

Sequence numbers are monotonic per connection. A reconnecting client sends its last seen
sequence and receives a fresh snapshot; partial replay is deliberately not offered, because the
world is small enough to re-send and a replay protocol is a source of divergence bugs with no
compensating benefit at this scale.

**Harness adapter.** `HarnessAdapter` and its `Capability` probe, adopted verbatim from Arke
(master spec §1.4). The probe reads the harness's OpenAPI document rather than pinning a
version, which is what makes OpenCode v2 safe to target.

**Preload bridge.** The renderer receives one typed object on `window.arke`, exposing connect,
send and subscribe. Nothing else crosses the boundary.

## 2.6 Application services

| Service | Responsibility |
|---|---|
| `WorldProvider` | Reads the world model. Mock in this spec; filesystem in SPEC-002. |
| `ReadModel` | Folds world state and events into the shapes the client renders. |
| `ChangeLog` | Append-only writer over `changes.jsonl`. Adopted from Arke's `trace.ts`. |
| `ChildSupervisor` | Generic process lifecycle: spawn, port allocation, health probe, backoff restart, graceful stop. |
| `Transport` | WebSocket server, frame sequencing, reconnect handling. |

`ChildSupervisor` is generic on purpose. OpenCode and Voxa differ in protocol but not in
lifecycle, and the failure modes that matter — never becomes healthy, dies under load, leaves an
orphan on quit — are identical. One implementation, two configurations.

## 2.7 Security

No credentials in the renderer (R-10). Provider keys are a main-process concern held in
Electron `safeStorage` (master spec §14.2) and are introduced by SPEC-008; this spec establishes
only that the client has no path to them.

The renderer runs sandboxed with context isolation on and node integration off (R-9). The
coordinator runs inside the trust boundary, in main.

Supervised children bind to loopback only, on ports allocated at start-up rather than fixed, so
two running instances cannot collide and nothing off-machine can reach them.

## 2.8 Performance

Event-driven, never polled. Pushes are ordered and sequenced. The client transport is a
reconnecting state machine from the outset, because reconnection is not an edge case when the
coordinator shares a lifecycle with the window.

The startup budget from master spec N-3 — interactive in under two seconds — is not testable
against fixtures and is deferred to SPEC-002, but the shell must not introduce work that would
make it unreachable: no synchronous filesystem scanning on the main thread, and the launch
screen renders before readiness probing begins.

## 2.9 Screen inventory

Every screen below is reachable in this spec, rendering fixtures. Behaviour arrives with its
own spec; reachability and fidelity arrive here.

**Shell** — launch, first run, world picker, new world, settings (providers · local runtime ·
who does what · about), activity.

**World** — overview, characters, character detail, character edit, reference kit, model-sheet
generate, voice picker, new character, locations, location detail, new location, factions,
canon list and ask, canon entry detail, canon thread, new canon entry, artifacts, productions,
new production.

**Production** — dashboard (day-one and established variants), story overview, chapter tree,
scenes, scene detail (shots · board), new scene, generate workspace, dispatch dialog, voice-line
dialog, cut, audio, exports, stills contact sheet.

## 2.10 Design system

The approved baseline is the SpecOne monochrome system in `design-system/_ds/`: a shadcn/ui
neutral token contract, Geist and Geist Mono, near-black primary on white surfaces, one red for
destructive, and a restrained status palette used only for state — never for chrome. The
imagery carries all the colour, which is why the UI must not depend on it (master spec N-8).

**Tokens are ported verbatim.** `tokens/colors.css`, `typography.css`, `spacing.css` and
`effects.css` are copied into the client unchanged, including the `.dark` scope. Every value in
component code is a token reference (R-11).

**Cards are fixed, and their copy is clamped** (R-12). The picker lays its cards out with
`align-items: flex-start`, so nothing stretches — each card is exactly its own content, and a
logline that runs from a sentence to a paragraph takes the card with it. Left alone the front
door was the most ragged screen in the product: 528, 508 and 450 pixels against the dashed "New
world" card, which has always been a fixed height sized for a two-line logline.

Every band is therefore pinned — key art, name, a two-line logline box, the meta line — and the
card height and the placeholder's height come from **one** custom property, so the two cannot
drift apart. Two details are easy to miss. A world with no logline still renders the box, empty,
or its card is short. And the counts in the meta line must be their own clipped element: left as
a bare text node they form an anonymous flex item that wraps internally, which is what made that
band 38px rather than 15px once the timestamp grew from *"2h ago"* to a full date.

**Components are reimplemented, not bundled.** `_ds_bundle.js` is a prototype runtime, not a
production library. The client implements the component layer as proper React components against
the same token contract: `Button`, `IconButton`, `Input`, `Textarea`, `Switch`, `Tabs`, `Card`,
`Badge`, `StatusDot`, `Callout`, `Avatar`, `AgentMessage`.

`KanbanCard` and `SpecCard` are Arke's domain primitives and are **not** ported. Arke Studio's
equivalents are introduced here as the vocabulary the rest of the specs build on:

| Primitive | Used by |
|---|---|
| `SheetCard` | cast, locations, factions |
| `CanonEntryRow` | canon list, search results, citations |
| `ShotCard` | scene shots, stills frames |
| `TakeStrip` | generate workspace, contact sheet |
| `ProposalPanel` | every accept gate (SPEC-004) |
| `RippleList` | proposal panels |
| `ReferenceTile` | reference kits |
| `JobRow` | activity |

`ProposalPanel` and `RippleList` are specified here despite the gate landing in SPEC-004,
because they appear on eight screens and defining them late would mean eight retrofits.

## 3.2 Testing

**Contracts** — zod parse and round-trip tests per entity and per event; a negative test per
schema proving malformed input fails at the boundary.

**Coordinator** — frame sequencing and monotonicity; snapshot-on-reconnect; `ReadModel`
derivation against the fixture world; `ChangeLog` append and read-back.

**Supervisor** — the failure modes, because they are the ones that will actually happen: a child
that never becomes healthy, a child that dies after becoming healthy, a child that ignores a
stop signal, and quit-with-children-running leaving no orphan.

**Client** — build succeeds; smoke render of the root router; a navigation test asserting every
screen in §2.9 is reachable; a theme test asserting `.dark` re-themes without component change.

## 3.3 Definition of done

- [ ] `npm install`, `npm run typecheck`, `npm run build` and `npm run test` pass at the root
- [ ] Every screen in §2.9 reachable, design baseline matched
- [ ] The application starts and navigates with both children unavailable
- [ ] No credential path exists in the client bundle
- [ ] Quitting leaves no orphan process
- [ ] Reviewer approved the spec and the scaffold

## 3.4 Decision log

| # | Decision | Rationale |
|---|---|---|
| D1 | npm workspaces, not pnpm | Matches Arke; no additional toolchain on the target machine. |
| D2 | Coordinator embedded in Electron main | It is the domain layer, not a server. An independent lifecycle would invent failures the product has no use for. |
| D3 | One generic `ChildSupervisor` for both children | OpenCode and Voxa differ in protocol, not lifecycle; the failure modes that matter are identical. |
| D4 | Snapshot on reconnect, no partial replay | A world is small enough to re-send. A replay protocol is a divergence-bug source with no benefit at this scale. |
| D5 | Tokens ported verbatim, components reimplemented | The `_ds` bundle is a prototype runtime. The token contract is the durable part. |
| D6 | `ProposalPanel` and `RippleList` defined here | They appear on eight screens; defining them in SPEC-004 would mean eight retrofits. |
| D7 | Fixture world committed as files | Doubles as SPEC-002's first parser corpus, and keeps the screens honest. |
| D8 | `@arke-studio/*` package scope | Avoids collision with Arke's `@arke/*` on a machine holding both. |
| D9 | Providers and voice created as skeletons now | Settles the workspace graph once rather than twice. |
