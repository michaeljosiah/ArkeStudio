# 1 · Requirements

## 1.1 Summary

Build the gate. Everything a production cites enters the world through one path: a proposal is
materialised, edited by an agent or a human, previewed with its ripples, verified against the
base it was drafted from, and accepted as a single transaction — or discarded, leaving nothing.

This is the product. §0.1 of the master specification names three mechanics that carry Arke
Studio, and this is the first of them; the other two are built on it. It is also the spec that
makes the harness confinement story true (master §17.3), because the proposal directory is what
an authoring session is given instead of the world.

**Boundary with SPEC-002.** SPEC-002 owns `commit(plan)` — the journal, atomicity, snapshots,
version bumps, the change log. This spec owns turning a proposal into a plan, and everything
that happens before and around that call. It adds no filesystem primitives of its own.

## 1.2 Scope

**In scope**

- The proposal lifecycle: create, materialise, edit, preview, verify, accept, discard.
- Materialisation: what a proposal is populated with, and base capture.
- Staleness detection and **rebase**, including the field-level merge.
- Ripple preview and the authoritative recomputation at accept.
- Translating a proposal into a SPEC-002 commit plan, including which versions move.
- Canon id reservation and release.
- Chat and form as two editors over one proposal.
- Concurrent proposals on one entity; abandonment and recovery.

**Out of scope (this spec)**

- The commit transaction itself — SPEC-002.
- The ripple *queries* — SPEC-003. This spec calls them and presents their results.
- Harness sessions and how an agent is driven — SPEC-005. This spec provides the directory a
  session runs in.
- Take review, which is a different decision on a different object — SPEC-013.
- Entity-specific authoring surfaces: canon (SPEC-006), sheets (SPEC-007), scenes (SPEC-012).
  Each supplies its editors; this spec supplies the gate they all pass through.

## 1.3 Acceptance criteria

### Lifecycle

- **R-1** A proposal SHALL be a directory under `.proposals/<proposalId>/` containing whole
  proposed files, a `proposal.json` manifest, and a computed ripple preview.

- **R-2** Creating a proposal SHALL materialise copies of every entity in scope, and SHALL record
  each one's version and content hash at that moment.
  - **WHEN** a session begins editing Maren **THEN** the proposal holds a copy of
    `characters/maren-kest.md` and records `baseVersion: 4` with its hash.

- **R-3** A proposal whose content is identical to the live world SHALL NOT be acceptable, and
  SHALL be reported as a no-op rather than committed.
  - **WHEN** an agent runs and changes nothing **THEN** no empty commit is produced and no
    version is bumped.

- **R-4** Discarding SHALL delete the proposal directory, release any reserved canon ids without
  making them available for reuse, and append one `changes.jsonl` line recording the discard.

### Staleness and rebase

- **R-5** Accepting SHALL verify every recorded base hash while holding the world lock, and SHALL
  refuse when any base has moved.
  - **WHEN** a sheet advanced from v4 to v5 while a proposal against v4 was open **THEN** the
    accept is refused, the newer content is not overwritten, and a rebase is offered.

- **R-6** Rebase SHALL perform a three-way merge at field granularity, using the recorded base
  from `.history/`, the current live file, and the proposed file.
  - **WHEN** the proposal changed Appearance and the live file changed Voice **THEN** both
    changes survive the rebase without user intervention.
  - **AND WHEN** both changed Appearance **THEN** the field is reported as a conflict and the
    user chooses; no automatic resolution is applied.

- **R-7** A rebase SHALL produce a new base record and a recomputed ripple set, and SHALL NOT be
  acceptable until the user has seen the merged result.

### Ripples

- **R-8** Ripple facts SHALL be computed by the SPEC-003 query surface, and model output SHALL
  supply only their human-readable explanation.
  - **WHEN** the model's prose and the computed set disagree **THEN** the computed set is
    displayed and the prose is suppressed.

- **R-9** Ripples SHALL be recomputed at accept, under the world lock, after base verification;
  the preview SHALL NOT be the set that governs.

- **R-10** A material difference between the preview and the authoritative set SHALL be surfaced
  and re-confirmed rather than committed silently.
  - **WHEN** a category gains or loses entries, or a count changes, **THEN** the difference is
    shown and the accept requires a second confirmation.
  - **AND WHEN** only explanatory prose differs **THEN** no re-confirmation is required.

### The commit plan

- **R-11** Accepting SHALL translate the proposal into one SPEC-002 commit plan and SHALL make
  exactly one `commit()` call.
  - **WHEN** a proposal touches a sheet and two canon entries **THEN** one commit lands all
    three, bumping the canon revision once and the sheet once.

- **R-12** Version movement SHALL be derived from the entity table in master specification
  §2.4.1, not from the caller.
  - **WHEN** a proposal changes production metadata **THEN** no version is bumped and the change
    is logged.

- **R-13** Canon ids SHALL be reserved at the point a proposal first requires one, atomically
  under the world lock, from the persisted `nextCanonId`.
  - **WHEN** two proposals each create an entry **THEN** they receive different ids, and neither
    id is issued twice even if one proposal is discarded.

### Editors and concurrency

- **R-14** Chat and form SHALL edit one proposal, and switching between them SHALL NOT discard
  staged content.

- **R-15** More than one proposal MAY target an entity at once; the second to accept SHALL be
  refused as stale and offered a rebase.
  - **WHEN** a second proposal on the same sheet is opened **THEN** the user is told one is
    already open, and is not prevented from proceeding.

- **R-16** Proposals SHALL survive process restart, and a proposal whose authoring session is
  gone SHALL remain editable by form and acceptable.
  - **WHEN** the application is killed with three proposals open **THEN** all three are present
    on next start, with their bases and previews intact.

- **R-17** Open proposals SHALL appear in the needs-you queue.

## 1.4 Open questions

- Whether a rebase conflict should offer a merged-text editor or only a field-level choice.
  Field-level choice in v1: it is comprehensible and cannot produce a file that fails schema
  validation, which free-text merging can.
- Whether proposals should expire. They do not in v1 — a proposal is work in progress, and
  deleting a user's unfinished thinking on a timer is a poor trade for disk that costs nothing.
- Whether a no-op proposal (R-3) should be silently discarded or reported. Reported, because an
  agent that ran and changed nothing is usually a failure the user wants to know about.

# 2 · Design

## 2.1 Architectural decision

**One gate, one transaction, and a proposal that is a directory rather than a diff.**

Proposals hold whole files. That choice costs a little disk and buys three things the product
depends on: the side-by-side comparison is a two-file read with no patch application to get
wrong; the proposal directory doubles as the working directory an authoring session is confined
to (master §17.3); and accepting is a set of renames the SPEC-002 journal already knows how to
make atomic.

The gate is deliberately uniform. Canon, sheets, scenes, locations, factions, story overviews and
agent-drafted chapters differ in their editors and their ripples, not in their path into the
world. Anything that special-cases the commit path for one entity kind is a bug in this spec.

## 2.2 The proposal lifecycle

```
        materialise                 edit                    verify + accept
world ──────────────▶ proposal ──────────────▶ proposal ──────────────────▶ world
        base captured    ▲    agent or form       │  hashes checked, ripples
                         │                        │  recomputed, one commit
                         └────── rebase ◀─────────┘  (refused if base moved)
```

## 2.3 Materialisation

Creating a proposal copies the entities in scope into the proposal directory, alongside
read-only context the editor needs but may not change. Two things happen in one act, and that is
the point: the copy is what an authoring session is given *instead of* the world, and the hashes
recorded at copy time are what later detects an accept racing another writer.

Scope is declared by the caller — "this sheet", "this canon entry and the sheets citing its
rules" — and is not open-ended. An editor that discovers it needs another entity mid-session
extends the proposal, which materialises the addition and records its base at that moment,
because a base captured later than the read it justifies would be a lie.

```
.proposals/pr_01J8H.../
  proposal.json              manifest: targets, bases, reservations, source, timestamps
  characters/maren-kest.md   materialised, editable
  canon/CANON-044.md         created by this proposal
  _context/                  read-only: canon extract, related sheets
  ripple.json                preview, advisory
```

## 2.4 Base capture and staleness

Each target records `baseVersion` and `baseHash` (master §3.3). At accept, under the world lock,
every hash is recompared against the live file.

A mismatch means the world moved — another proposal was accepted, or a file was hand-edited
between materialisation and now. It is refused (R-5). This is also the mechanism that makes
harness confinement honest: an out-of-band write by an agent changes the hash and the accept
refuses, so nothing reaches the record unnoticed even though nothing prevented the write.

## 2.5 Rebase — a field-level three-way merge

Refusing a stale proposal and making the user redo the work would be correct and miserable. It is
also unnecessary, because all three inputs to a proper merge are available: the **base** in
`.history/`, **theirs** in the live file, and **mine** in the proposal.

Merging is done **at field granularity, not by line**. Entities are structured — frontmatter keys
and named prose sections — so the merge unit is `Appearance`, `Voice · written`, `links`, not a
line of text. Two consequences, both good:

- **Disjoint edits merge cleanly and silently.** A proposal that rewrote Appearance rebases onto
  a live file that changed Voice with nothing for the user to do (R-6). This is the common case
  when two sessions work on one character.
- **A merged file cannot fail schema validation.** Field-level merging picks whole values; it
  cannot produce the half-spliced prose that line-level merging yields on a paragraph edited at
  both ends. §1.4 records that this is why free-text conflict editing is not offered in v1.

Overlapping edits to one field are a **conflict**, reported per field with both values, resolved
by choosing (R-6). Nothing is auto-resolved: the master specification's rule is that staleness is
detected and never silently merged, and a same-field conflict is exactly the case where silence
would lose an author's work.

A rebase produces a new base record and a recomputed ripple set, and the result must be seen
before it can be accepted (R-7) — a rebase that merged something surprising should not be one
click from landing.

## 2.6 Ripples: preview and authority

The preview in `ripple.json` is computed at materialisation and refreshed as the proposal is
edited. It is advisory, and the spec says so in its filename comment, because between drafting
and accepting a take may land, a tile may be locked, or another proposal may be accepted.

**The authoritative set is computed at accept**, under the lock, after base verification (R-9).
Comparing the two is not pedantry — it is the difference between showing a user the consequences
of their action and showing them the consequences of a hypothetical.

**Material difference** (R-10) is defined, so the implementation is not left to guess: a ripple
*category* gaining or losing entries, or a *count* changing. Explanatory prose changing is not
material. A user who was told "14 reference images predate v5" and would now be told 15 is
re-confirmed; one whose sentence was reworded is not interrupted.

## 2.7 The commit plan

Accepting translates the proposal into exactly one SPEC-002 commit plan (R-11):

| Proposal element | Plan element |
|---|---|
| Each changed target | A file entry with base hash, new hash and history path |
| Each created entity | A file entry with `action: create` and no history path |
| Entities from master §2.4.1 that are versioned | Version increment |
| Any canon entry touched | One `canonRevision` increment for the whole commit |
| Reserved ids actually used | Recorded; unused reservations released |

**Version movement is derived, never passed in** (R-12). The table in master §2.4.1 is the single
authority for what is versioned; a caller that could declare its own version bumps would be a
second authority, and the two would disagree.

**Mixed commits are required, not merely allowed.** A proposal that creates CANON-044 and adds it
to Maren's `canonRules` must land as one commit; splitting it would guarantee a window in which a
sheet cites an entry that does not exist. SPEC-002's earlier one-track rule was corrected for
this reason.

## 2.8 Canon id reservation

An id is reserved when a proposal first needs one, atomically under the world lock, from
`world.nextCanonId` (R-13). Reservation is early rather than at accept because a thread must be
citable as CANON-043 while it is still being discussed — the prototype's *"Open as thread ·
CANON-043"* offers the number before the entry exists.

A discarded proposal releases its reservation **without returning the number to the pool**. The
gap is correct: reuse would make a citation written during the conversation resolve, later, to a
different entry.

## 2.9 Chat and form

Two editors, one proposal (R-14). Chat produces field values by drafting; form produces them by
typing. Both write to the same materialised files, so switching is free and mid-edit state
survives — the proposal is the state, the conversation is not.

This is why the master specification insists the proposal rather than the session holds the work:
a session can end, crash, or be superseded, and the user's edits must not go with it.

## 2.10 Concurrency

More than one proposal may target an entity (R-15). Preventing it would mean locking entities for
the duration of a conversation, which in a product where conversations are long and exploratory
is worse than the problem.

The second to accept is refused and offered a rebase, which — for disjoint fields — resolves
without the user doing anything. The UI tells the user at open time that another proposal is live,
so the collision is not a surprise at accept.

## 2.11 Abandonment and recovery

Proposals persist across restart (R-16), and one whose authoring session no longer exists stays
editable by form and acceptable. This matters because sessions are the fragile part: the harness
may be unreachable, the model may be unconfigured, the app may have been killed. A user's staged
work must not depend on a foreign process still being alive.

Open proposals appear in needs-you (R-17), because a proposal is precisely a thing waiting on the
user.

Recovery on open: proposal directories are validated against their manifests, previews are
recomputed, and any proposal whose targets no longer exist in the world — the entity was
retired — is reported and can only be discarded.

## 2.12 What the gate does not cover

Per master §3.1, and repeated here because it is the rule most likely to be violated by a later
spec in good faith: the gate covers **gated** entities. It does not cover operational records,
direct-authored chapter prose, or generated media coming into existence. A take arriving is not a
proposal; a take *becoming a shot's answer* is a different decision on a different object, and
belongs to SPEC-013.

## 3.2 Testing

**The merge** is where the subtle bugs live, so it gets the most tests: disjoint fields merge
silently; same-field edits conflict; a field added in one side and removed in the other; frontmatter
list fields (`links`, `canonRules`) merged as sets rather than as strings; and a property test
asserting every merge output parses against its schema.

**Staleness** — accept refused after a competing accept; after a hand edit; after a retirement.
Base verification happens under the lock, proven by a test that mutates the file between
verification and commit and asserts the commit still refuses.

**Atomicity boundary** — accepting makes exactly one `commit()` call; a proposal spanning a sheet
and two canon entries produces one plan with one canon-revision increment; version movement
matches §2.4.1 for every entity kind including the unversioned ones.

**Reservation** — two concurrent proposals get different ids; a discarded reservation leaves a
gap and is never reissued; a reservation survives restart.

**Ripples** — preview and authoritative sets computed from the same queries; material difference
triggers re-confirmation; prose-only difference does not.

**Lifecycle** — no-op proposals refused; proposals survive restart with bases intact; a proposal
whose target was retired can only be discarded; discard leaves nothing but a log line.

## 3.3 Definition of done

- [ ] Typecheck, build and test pass across workspaces
- [ ] Every gated entity in master §3.1 enters the world only through this gate
- [ ] Accept makes exactly one `commit()` call, verified by instrumentation
- [ ] Disjoint concurrent edits rebase without user intervention
- [ ] Every merge output validates against its schema
- [ ] Canon ids are never reissued across discard and restart
- [ ] Reviewer approved

| # | Decision | Rationale |
|---|---|---|
| D1 | Proposals hold whole files, not diffs | Comparison is a two-file read; the directory doubles as the harness working directory; accepting is renames the journal already makes atomic. |
| D2 | Materialisation captures the base | One act produces both the agent's sandbox and the staleness check, so they cannot drift apart. |
| D3 | Rebase merges at field granularity | Entities are structured, so fields are the natural unit — and a field-level merge cannot emit a file that fails schema validation. |
| D4 | Same-field conflicts are never auto-resolved | This is exactly the case where silence loses an author's work. |
| D5 | Ripples computed twice, authority at accept | Otherwise the user is shown the consequences of a hypothetical world. |

| D7 | Version movement derived from §2.4.1, never passed in | A caller that declares its own bumps is a second authority, and two authorities disagree. |
