# 1 · Requirements

## 1.1 Summary

Make authoring work. Discover or start an OpenCode v2 host, configure it from Arke Studio's own
settings, run authoring sessions confined to proposal directories, expose the world to those
sessions through a read-only query tool rather than the filesystem, normalise the event stream
into the domain model, and degrade honestly when none of it is available.

This is the spec where master §17.3's confinement layers stop being a design and become a
process with a working directory, a tool list and an environment.

**Boundary with SPEC-004.** SPEC-004 owns proposals — materialisation, bases, rebase, accept.
This spec owns the agent that edits inside one. It never writes to the world, never calls
`commit()`, and never decides what a ripple is.

## 1.2 Scope

**In scope**

- OpenCode discovery: preferring an existing installation, falling back to the bundled one.
- Lifecycle on SPEC-001's `ChildSupervisor`; capability probe from the OpenAPI document.
- Configuration written by Studio; credentials passed by environment.
- The agent roster and per-agent model routing, including the Ollama fallback.
- Authoring sessions: creation, binding to a proposal, cancellation, timeouts, cleanup.
- Confinement: working directory, denied tools, and the read-only world-query tool.
- Event normalisation: SSE to domain events, including tool activity as user-visible progress.
- Permission surfacing and remembered grants.
- Degradation when the harness is absent, unreachable or under-capable.

**Out of scope (this spec)**

- Proposal semantics, rebase, ripples and the commit — SPEC-004.
- What each agent is *for* and how its output is shaped — SPEC-006 (canon), SPEC-007 (sheets),
  SPEC-012 (scenes and story).
- Canon Q&A answer construction and grounding verification — SPEC-006. This spec delivers the
  retrieval tool and the structured-response plumbing.
- Any media generation. The harness never dispatches media (master §17.1).
- An OS confinement boundary. Master §20.2 holds it as the top post-v1 hardening.

## 1.3 Acceptance criteria

### Discovery and lifecycle

- **R-1** The application SHALL prefer a reachable existing OpenCode installation over the
  bundled one, and SHALL report which it is using and at what version.
  - **WHEN** both are present **THEN** the existing installation is used and Settings names it.

- **R-2** Capabilities SHALL be probed from the harness's OpenAPI document at start-up, never
  assumed from a version number.
  - **WHEN** an installation lacks an optional endpoint **THEN** the dependent feature is
    disabled with a stated reason rather than failing at first use.
  - **AND WHEN** the event stream is absent **THEN** readiness fails with a clear reason, because
    authoring cannot work without it.

- **R-3** The harness SHALL run under SPEC-001's `ChildSupervisor`, bound to loopback on a port
  allocated at start-up, and SHALL be stopped on application quit leaving no orphan.

- **R-4** The application SHALL start and remain fully usable for non-authoring work when the
  harness is absent, unreachable or under-capable, with authoring disabled and the reason stated.

### Configuration and credentials

- **R-5** Studio SHALL write the harness's provider configuration from its own settings, and the
  user SHALL never configure the harness directly nor supply a key twice.

- **R-6** Credentials SHALL reach the harness by environment variable at spawn; where a
  configuration file is unavoidable it SHALL be per-session, user-only, and deleted on session
  end and on next start-up.
  - **WHEN** the application is killed with a session open **THEN** no plaintext credential file
    survives the next start-up.
  - Narrowed 2026-08-26 to credentials Arke holds — that is, API keys. It cannot cover a vendor
    OAuth connection, which is not a secret in Studio's possession but a session the person
    established with their vendor, living in a file the harness refreshes on its own schedule.
    There is no environment variable that carries it and no per-session file that could hold it
    without Arke first taking a copy. SPEC-030 owns that case, and prohibits the copy.

- **R-7** When no cloud LLM provider is configured or selected and Ollama is running, authoring
  SHALL route to Ollama through the harness rather than being disabled.

- **R-8** The agent roster SHALL be application-owned and SHALL NOT live inside a world folder.
  - **WHEN** a world is copied to another machine **THEN** it carries no agent definitions, and
    product behaviour is identical.

### Sessions and confinement

- **R-9** An authoring session's working directory SHALL be the proposal directory it is bound
  to; the live world SHALL NOT be reachable as the working directory.
  - **WHEN** an agent writes to any relative path **THEN** the write lands inside the proposal.

- **R-10** Shell and process-execution tools SHALL be disabled in authoring sessions, and this
  SHALL be documented as risk reduction rather than as a security boundary.
  - Amended 2026-08-23. Network tools were named here too, as a permanent denial. They are now
    a confinement intent (`web`) governed by the `research.web` setting, which is off until the
    person turns it on. The reason for the change is that the blanket denial was never a policy
    anyone chose for research: asking an agent to go and look something up produced a refusal no
    confinement had decided and none could lift, while the person who asked saw only an agent
    that would not do as it was told. Reading a public page is not a way out of the working
    directory, which is what the rest of this requirement is about.
  - **WHEN** `research.web` is off **THEN** network tools SHALL be disabled exactly as before.

- **R-11** World content beyond the materialised scope SHALL be reached through a read-only query
  tool backed by the index, not by filesystem access.
  - **WHEN** an agent needs a canon entry outside its proposal **THEN** it retrieves it through
    the tool, and no read path to the live world folder is required.
  - **AND** the tool SHALL expose no write operation.

- **R-12** A session SHALL be bound to exactly one proposal, and ending, cancelling or losing a
  session SHALL leave that proposal intact and acceptable.

- **R-13** Sessions SHALL be cancellable at any time, and SHALL be bounded by a wall-clock
  timeout and a token budget, both of which end the session with a stated reason rather than
  silently.

### Events and permissions

- **R-14** The harness event stream SHALL be normalised into the domain-event union, and every
  event SHALL be schema-validated at the boundary.
  - **WHEN** an unrecognised event arrives **THEN** it is recorded and ignored, not propagated
    as a partial object.

- **R-15** Tool activity SHALL surface as user-visible progress in the product's own language.
  - **WHEN** the agent retrieves canon while drafting **THEN** the user sees a canon-check line
    naming the entries consulted, not a tool-call payload.

- **R-16** Harness permission prompts SHALL be presented in Studio's language, without exposing
  harness-internal tool names, and remembered grants SHALL persist across restarts and be
  revocable.

- **R-17** The product's user-facing gate SHALL be the accept gate; harness permission prompts
  SHALL be a backstop and SHALL be rare in the confined authoring configuration.

## 1.4 Open questions

- Whether the bundled OpenCode's licence permits redistribution in a signed installer, and under
  what attribution. A task, not an assumption — T-1 verifies it before any bundling work.
- Whether the world-query tool should be exposed over MCP or as a harness-native tool. MCP in
  v1, because it is the interface both OpenCode and any future harness can consume.
- Whether per-agent model overrides are worth exposing to users. Not in v1; the "who does what"
  defaults cover it, and a per-agent picker is a settings surface with no demonstrated demand.

# 2 · Design

## 2.1 Architectural decision

**The agent is given a workspace and a question-answering tool, not the world.**

The instinct when putting a file-editing agent on a folder of files is to point it at the folder.
That instinct is what made the earlier confinement claim false, and correcting it produced a
better design rather than merely a safer one:

- The agent's working directory is its **proposal** — a small, purpose-built copy of what it is
  meant to change (SPEC-004 §2.3).
- Everything else it needs to *read*, it asks for through a **read-only query tool** backed by
  the SPEC-003 index.

The second point is the one worth defending on its own merits. Handing an agent a folder and
hoping it greps well is worse than giving it ranked retrieval: it scales past what fits in
context, it goes through the same lexical search the product's own canon Q&A uses, and it means
the agent's reads are observable — which is what makes R-15's canon-check progress lines possible
at all. Confinement is a consequence of the right architecture here, not a tax on it.

## 2.2 Discovery and lifecycle

Discovery order: a reachable configured path, then an installation on `PATH`, then the bundled
binary. Whichever is chosen, capabilities come from `GET /doc` (R-2), never from a version string
— the adopted Arke adapter already works this way, and it is what makes an OpenCode Arke Studio
does not control safe to prefer.

Readiness has two tiers. **Required**: the event stream. Without it there is no way to observe a
session and authoring is unavailable. **Optional**: everything else, each disabling its dependent
feature with a reason rather than failing at first use.

Lifecycle rides SPEC-001's `ChildSupervisor` (R-3) — spawn, loopback port, health probe, backoff
restart, graceful stop, no orphan on quit. Nothing harness-specific about the lifecycle belongs
in this spec beyond the probe.

## 2.3 Configuration and credentials

Studio owns provider configuration and writes it at spawn (R-5). Credentials go by **environment
variable**, never into a configuration file (R-6, master §14.2) — Arke Studio launches the
process, so its environment is Arke Studio's to set. Where a harness version genuinely cannot
read credentials from the environment, a per-session, user-only file is written and deleted on
session end *and* on next start-up, so a crash cannot leave keys on disk indefinitely.

A user-installed OpenCode may hold its own credentials for its own use. Arke Studio neither reads
nor modifies them, and Settings names which provider credentials came from where, so a user is
never unsure which key is paying.

**The agent roster is application-owned** (R-8). Agents are product behaviour, not user content:
putting them in a world would make them user-editable, which would mean versioning them, gating
them, and carrying them between machines — turning a copied world into a copied product. They
are bundled and written to a per-session configuration directory.

| Agent | Purpose | Writes |
|---|---|---|
| `world-author` | Draft a new world from a name and a sentence | world, first sheets |
| `sheet-editor` | Draft and revise character, location and faction sheets | sheets |
| `canon-author` | Draft canon entries and settle threads | canon entries |
| `scene-writer` | Draft scenes into shot lists | scenes |
| `story-writer` | Draft story overviews and chapters | overview, chapters |
| `canon-qa` | Answer questions from retrieved canon | nothing |

`canon-qa` writes nothing and needs no proposal; it is a session over the query tool alone.

Model routing follows the "who does what" default for the LLM capability, with the Ollama
fallback (R-7) so authoring degrades to local rather than disappearing when no cloud key is
present.

## 2.4 Sessions

One session, one proposal (R-12). The session is created after SPEC-004 has materialised the
proposal, so the working directory exists and its bases are already captured before the agent
runs.

Sessions are **cancellable, time-bounded and token-bounded** (R-13). All three end the session
with a stated reason and leave the proposal exactly as the agent left it — a run that hits its
budget mid-draft has still produced work the user may want, and discarding it would be the
product deciding on the user's behalf.

Losing a session never costs the proposal (SPEC-004 R-16). This is the property that makes the
harness's fragility tolerable: OpenCode may be missing, misconfigured, or killed, and the user's
staged work is unaffected.

## 2.5 Confinement in practice

The four layers from master §17.3, as they land here:

| Layer | Implementation | Strength |
|---|---|---|
| Working directory | cwd is the proposal; the world is never passed | Structural for relative paths |
| Tool denial | shell and exec disabled; public-web tools disabled unless `research.web` is on | Best-effort; depends on the harness honouring its own config |
| World reads | read-only MCP query tool, index-backed | Removes the *reason* to touch the world folder |
| Detection | base-hash verification at accept; reconciliation on open | The layer that actually holds |

The honest summary, repeated from the master specification because it must not be softened in
implementation: a malfunctioning agent with shell access can still damage world files between
commits. Arke Studio detects that and preserves history; it does not prevent it. Prevention needs
an OS boundary, which master §20.2 holds as the top post-v1 hardening.

### 2.5.1 The world-query tool

Exposed over MCP, read-only (R-11):

| Operation | Backed by |
|---|---|
| `search_canon(query, limit)` | SPEC-003 FTS5 with BM25, returning full statement text |
| `get_entry(id)` | Index lookup |
| `get_sheet(id)` | Index lookup, current version |
| `list_entities(kind, status)` | Index query |
| `related(id)` | Citation query |

`search_canon` returns full statement text deliberately — it is the same retrieval the canon Q&A
path uses, and returning full text is what lets a grounded answer quote a verifiable span
(SPEC-003 R-23).

There is no write operation, and there is no path parameter anywhere in the surface, so the tool
cannot be steered at the filesystem.

## 2.6 Events

The SSE stream is normalised into the domain-event union and validated at the boundary (R-14).
Unrecognised events are recorded and dropped rather than passed through half-parsed — the same
rule SPEC-001 applies to every contract boundary.

**Tool activity becomes product language** (R-15). This is not decoration: the design prototype's
inline canon checks — *"checked: CANON-002, the cost is already canon · no contradiction"* — are
exactly a `search_canon` call rendered as progress. Mapping tool calls to those lines is what
makes the agent's grounding visible instead of asserted, and it comes free from a stream Arke
Studio is already parsing.

## 2.7 Permissions

Harness permission prompts are surfaced in Studio's language, with remembered grants persisting
and revocable (R-16), reusing Arke's `grant-store`.

**They should be rare** (R-17), and it is worth being explicit about why rather than leaving the
implementation to wonder if something is broken. In the confined configuration the agent's only
capability is editing files inside its own proposal, which is exactly what the user asked it to
do — there is nothing there worth interrupting for. The product's gate is the **accept gate**;
harness permissions are a backstop for tools a future harness version might introduce.

A permission prompt appearing frequently in normal authoring is a signal that the confinement
configuration has drifted, and is worth treating as a defect rather than a UX problem.

## 2.8 Degradation

Authoring is the only thing that needs the harness. Everything else — browsing, form editing,
dispatch, review, the cut, exports — works without it (R-4).

The states, each with distinct user-facing copy: **absent** (no installation found, bundled one
failed to start), **unreachable** (present but not responding), **under-capable** (running but
missing the event stream), and **unconfigured** (running, capable, but no LLM provider and no
Ollama). The last is the one most likely to be hit on first run, and it points at Settings rather
than reporting an error.

## 3.2 Testing

**Confinement** — the tests that matter most, since this is where a false claim was corrected
once already. An agent instructed to write outside its proposal by relative path lands inside it.
An agent given a world path in its prompt cannot reach the world through the query tool, because
the tool takes no paths. A deliberate out-of-band write to a live file is caught by base-hash
verification at accept and by reconciliation on open — both asserted directly, since these are
the layers the design actually leans on.

**Credentials** — no key reaches a configuration file when the environment path is available; a
fallback file is deleted on session end and again on start-up after a simulated crash; no key
appears in any log line or diagnostics bundle.

**Lifecycle** — existing installation preferred over bundled; missing optional endpoint disables
its feature with a reason; missing event stream fails readiness; quit leaves no orphan.

**Sessions** — a session lost mid-run leaves an acceptable proposal; timeout and token budget
each end with a stated reason and preserve work; cancellation is immediate.

**Events** — unknown event shapes are dropped and recorded, not propagated; a `search_canon` call
renders as a canon-check line naming the entries.

**Degradation** — each of the four states reached deliberately, with the rest of the application
verified fully usable in every one.

## 3.3 Definition of done

- [ ] Typecheck, build and test pass across workspaces
- [ ] Licence verification complete and recorded before any binary is bundled
- [ ] An authoring session drafts a sheet end to end into an acceptable proposal
- [ ] No credential reaches a configuration file, a log or a diagnostics bundle
- [ ] Out-of-band writes are detected at both accept and open
- [ ] The application is fully usable in all four degradation states
- [ ] Reviewer approved
