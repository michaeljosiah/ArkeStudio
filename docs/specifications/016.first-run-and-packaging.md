# 1 · Requirements

## 1.1 Summary

The first ninety seconds, and everything needed to ship the thing at all.

A user installs Arke Studio, opens it, and is making a world before anything has been configured
— no key, no model download, no account. Everything the application needs beyond that is offered
rather than required, and arrives in the background.

Plus the unglamorous half: what goes in the installer, whose licences permit it being there, how
it is signed, how it updates without interrupting work, what diagnostics may contain, and what
uninstalling does and does not delete.

## 1.2 Scope

**In scope**

- Launch, readiness probing and hand-off.
- First run: app-root creation, environment checks, onboarding.
- The provider-optional path and what works without any credential.
- Local model acquisition, offered at first run and otherwise on first use.
- The installer: contents, architectures, size, signing.
- Third-party licence obligations and the checks that gate shipping.
- Updates, and their relationship to running work.
- Diagnostics contents.
- Uninstall.
- The About surface.

**Out of scope (this spec)**

- Feature behaviour of anything being configured — the specs that own each.
- World schema migration mechanics — SPEC-002 R-25.
- macOS and Linux packaging. Master §0.4 makes Windows the only shipped target.

## 1.3 Acceptance criteria

### Launch and first run

- **R-1** The launch screen SHALL probe coordinator, harness and voice readiness, respect
  reduced-motion, and hand off to first run when no world exists or to the world picker when one
  does.

- **R-2** First run SHALL create the app root and its subdirectories without prompting, and SHALL
  verify the environment before any world can be created.
  - **WHEN** the app root sits at a depth that would breach the path budget **THEN** the problem
    is reported before a world is created there.

- **R-3** A user SHALL be able to create a world, author it by form, and browse it with **no
  provider credential configured and no model downloaded**.
  - **WHEN** Arke Studio is opened for the first time with no network **THEN** a world can still
    be created and written to.

- **R-4** Provider configuration SHALL be offered during onboarding and SHALL be skippable, with
  the features it unlocks named rather than implied.

- **R-5** Local model download SHALL be offered at first run as a non-blocking background task,
  and anything not downloaded SHALL download on first use.
  - **WHEN** a user declines at first run and later uses local voice **THEN** the model downloads
    at that point without a separate setup step.

- **R-6** Onboarding SHALL offer creating a world, importing a folder, and installing the sample
  world.
  - **WHEN** the build carries a sample world **THEN** it is offered at first run, on an empty
    world picker, and in Settings, and installing it SHALL need no network and no credential.
  - **WHEN** the build carries none **THEN** the offer is absent and the Settings pane says so,
    rather than presenting an action that cannot complete.
  - Installing SHALL copy the world under a fresh identity, leaving the shipped copy untouched, so
    that installing twice yields two independent worlds rather than an overwrite.

### Packaging

- **R-7** The application SHALL ship as a signed NSIS installer for Windows x64. Windows on ARM
  runs that installer under emulation.
  - **CURRENT** Release workflows produce unsigned installers; signing remains a v1 shipping
    requirement and SmartScreen warns on current builds.
  - **WAS** x64 and arm64, until 0.2.9. The retreat this specification already named under
    *native-binding cost* is the one that happened: `better-sqlite3` is a per-ABI addon with no
    published ARM64 prebuild for Electron, so it must be cross-compiled, and the MSVC ARM64
    tools are a Visual Studio component no packaging machine here has carried. The build
    tolerated the failure, so every ARM64 installer shipped with the derived index disabled and
    said nothing. Restoring the target means installing that component and deleting the
    tolerance, not changing code.

- **R-8** The installer SHALL contain the client, the coordinator, the harness binary, the voice
  sidecar, ffmpeg, the sample world and the native index binding built for the target
  architecture; it SHALL NOT contain local inference models.
  - The sample world SHALL be carried at the resolutions the application renders, not at export
    resolution. It was 31 MB of full-size PNG before anyone measured what was being shipped.

- **R-9** Every bundled third-party component's licence SHALL be verified as permitting
  redistribution in a signed installer, and its obligations recorded, **before** it is bundled.
  - **WHEN** a component's licence cannot be satisfied **THEN** it is not shipped, and the feature
    depending on it degrades per its own spec.

- **R-10** GPL-licensed executables SHALL be invoked as separate processes and never linked.

- **R-11** The packaged application SHALL be verified on the shipped architecture, including the
  native index binding and both child processes. A native binding that fails to build SHALL fail
  the package step rather than shipping the application without it.

### Updates

- **R-12** Update checks SHALL run at start-up and on demand, and installation SHALL be
  user-initiated.

- **R-13** An update SHALL NOT interrupt running jobs, a held world lock, or an in-flight commit.
  Explicit installation SHALL visibly finish local work and confirm clean shutdown before the
  installer runs; the user MAY instead arm installation for the next clean close.
  - **WHEN** an update is accepted while a scene is dispatching **THEN** installation waits for
    orderly shutdown and never treats a shutdown timeout as permission to install.
  - **WHEN** the user chooses **Install and restart** **THEN** the updated application reopens and
    confirms the installed version once.

- **R-14** After updating, a world whose schema version is older SHALL migrate on open, and one
  whose version is newer SHALL be refused unmodified.

### Diagnostics and uninstall

- **R-15** Diagnostics SHALL be user-initiated and SHALL contain no world content and no
  credential material, passing through the same redaction boundary as logs.

- **R-16** Uninstalling SHALL NOT delete the app root by default; removing worlds and removing
  stored credentials SHALL each be separate, explicit, clearly-labelled opt-ins.
  - **WHEN** a user uninstalls without opting in **THEN** every world, the ledger and the
    credential file remain.

- **R-17** The About surface SHALL show version and build, the licence, third-party licences, the
  data location with a route to open it, and the diagnostics action.

## 1.4 Open questions

- ~~Whether to ship a sample world.~~ **Settled at 0.4.1: it ships.** The objection was size —
  "tens of megabytes of art" — and it did not survive being measured. The world was 31 MB because
  twelve images of painterly art were stored at full resolution as PNG; at the resolutions the
  application actually renders them it is 12 MB, on an installer already above 200 MB. What that
  buys is a first run that keeps its promise: no account, no key, **no network**, and still
  something to look at. A sample world reachable only by download contradicts that in the one
  moment it exists to help. The website's claim is now true. See R-6, R-8, D12.
  - The licensing question is not the size question and is answered separately: the imagery is
    the project's own, generated from the prompts recorded in `design-system/image-prompts.md`,
    and is covered by the repository's MIT licence like the rest of it.
- ~~Whether arm64 is worth shipping at v1.~~ **Settled at 0.2.9: x64 only.** Not on CI time, which
  was the anticipated cost, but on the native binding — see R-7. The defensible retreat named here
  is the one taken.
- Whether update checks should be opt-out. They are on by default and check only; nothing installs
  without the user, which seems the right balance for a free tool with no telemetry.

# 2 · Design

## 2.1 Architectural decision

**Nothing is required before the user can start.**

The temptation in a product with providers, a harness and local models is a setup wizard: enter a
key, download the runtime, then begin. It is the wrong shape here, for a reason specific to this
product. Arke Studio's claim is that the world is the asset and it lives on your machine — and a
first run that demands a cloud credential before you can write a sentence contradicts that in the
first ninety seconds.

So the whole configuration surface is **offered, not required** (R-3, R-4). A user with no key and
no network can create a world, write canon by form, add characters and locations, link artifacts,
and browse all of it. What they cannot do is have an agent draft for them or generate an image,
and those are named where they are unavailable rather than blocking the door.

This is also why the form editor exists as a first-class peer of chat throughout the product
rather than a fallback: it is what makes the no-credential path a real one instead of a
technicality.

## 2.2 Launch and readiness

The launch screen probes coordinator, harness and voice readiness (R-1) and hands off — to first
run with no worlds, to the picker with any. Reduced-motion is respected, per master N-8.

Probing is not gating. A failing harness or sidecar hands off exactly the same way; the readiness
result becomes the degraded-state copy each of those specs defines.

## 2.3 First run

Creating the app root needs no permission (R-2) — it is the application's own directory in the
user's profile, and asking would be ceremony.

**The environment check happens here**, once, before any world exists: path-budget depth
(SPEC-002 R-10), available disk, and whether the native index binding loads. Catching a
too-deep app root at first run is the difference between a clear message and a user discovering
months later that some file operations fail on their longest-named production.

Onboarding then offers three doors (R-6): create a world, import a folder, or install the sample
world. The second is SPEC-015's on-ramp and is the more important one for anybody arriving with
existing material.

The third is for everybody else. "Every world starts as a name" is true and is also a blank page,
and a blank page is a hard place to begin from if you have never seen one of these finished. The
Undersong is what the application was designed against, so it is the one world that exercises every
screen: a cast with reference kits, canon that has been revised, a production part-way through,
and a proposal still waiting at the gate.

It arrives as a **copy under a fresh identity**, and that is the whole of the mechanism — a world
is plain files, so there is no import format and nothing to unpack. Only `worldId` and `slug` are
rewritten: the id because two folders claiming one id would shadow each other in the app index,
the slug because it is the folder name and a second install must be `the-undersong-2` rather than
an overwrite. Timestamps are left as authored; a world stamped today whose change log starts in
May would be lying on its own overview.

The copy is assembled outside `worlds/` and renamed in. Done the other way round there is a
window — long, because it is megabytes — in which the library holds two worlds claiming the same
id, and a `listWorlds()` landing inside it indexes the wrong one.

Nothing about the installed copy is read-only. That is the point of offering it: it is a world to
take apart, and a user who thinks it is a museum piece learns nothing from it.

## 2.4 Local models

Offered at first run, non-blocking, and otherwise acquired on first use (R-5).

The design prototype's setup screen — *"downloading runtime · voice models (2 of 5) · 312 MB /
1.2 GB"* — already carries **"Continue in the background →"**, so it was never a blocking gate,
and this spec keeps it that way. A user who only ever uses cloud voice should never wait for
Kokoro; a user who declines and later presses a local voice gets the download then, in Activity,
without a separate setup step.

The figures shown must be the real ones. Master §7.1 records that the prototype's *"2.1 GB"*
overstates Kokoro by roughly an order of magnitude.

## 2.5 What ships

| In the installer | Not in the installer |
|---|---|
| React client, coordinator | Kokoro TTS models |
| OpenCode harness binary | whisper.cpp models |
| Voxa sidecar, self-contained | |
| ffmpeg | |
| espeak-ng | |
| `better-sqlite3` for the target arch | |
| The sample world, 12 MB (§1.4, R-6) | |

Two child processes, two native concerns, and a native module — which is why R-11 requires
verification in a **packaged** build on both architectures rather than in development. "Works when
run from source, fails when installed" is the characteristic failure of exactly this combination.

Master N-7 puts the result above 200 MB. That is the honest cost of an application that bundles
its own agent runtime and voice stack, and the alternative — downloading them on first run — trades
installer size for a worse first ninety seconds.

## 2.6 Licensing, as a gate

**Every bundled component's licence is verified before it is bundled** (R-9), not discovered during
packaging. Three specific obligations already known:

- **OpenCode** — redistribution in a signed installer, with attribution. SPEC-005 T-1 blocks
  bundling on this.
- **espeak-ng** — GPL, so it stays a separate executable and is never linked (R-10). This is the
  arrangement Voxa already makes.
- **ffmpeg** — licence varies by build. A build whose licence permits redistribution must be
  chosen deliberately, and it is invoked as a subprocess, never linked, for the same reason as
  espeak-ng.

Arke Studio is MIT (master N-6), and third-party licences are enumerated in-app (R-17). A licence
question found at packaging time is a shipping delay; found here it is a task.

## 2.7 Signing

Windows code signing, without which SmartScreen warns users away from a free tool they have no
reason to trust yet. Current release workflows are unsigned; the installer and bundled
executables must be signed before v1 satisfies R-7.

## 2.8 Updates

Checked at start-up and on demand; **installed only when the user says so** (R-12).

**Installation follows confirmed shutdown** (R-13). This application holds a world lock, may have
an in-flight commit journal, and may have jobs running against paid providers. **Install and
restart** keeps a visible finishing-local-work surface while the coordinator quiesces, drains its
local records and releases the world lock; only then does the desktop hand off to the installer and
force the updated application to reopen. A shutdown failure defers installation. **Install when I
close** uses the same safety gate but intentionally leaves Arke closed.

The desktop updater is authoritative for startup and manual checks. Its progress and target version
are retained in the application snapshot. A minimal marker outside every world records only target
version and flow; the next launch compares that target with the running version before showing a
one-time success notification.

After an update, older worlds migrate on open and newer ones are refused unmodified (R-14), per
SPEC-002. That second case is real: a user with worlds synced across two machines can open a world
written by a newer build, and the older build must decline rather than helpfully damage it.

## 2.9 Diagnostics

User-initiated, and passing through the same redaction boundary as logs (R-15) so no new field can
leak by omission. Contents: version and build, OS and architecture, readiness probe results,
configured provider *names*, index schema version, a queue-state summary, and recent redacted log
lines.

Not contents: any world content, any credential, any prompt, any generated media.

The rule is that a diagnostics bundle should be safe to paste into a public issue without thinking
about it, because that is what people will do.

## 2.10 Uninstall

**The app root is not deleted** (R-16). It holds the user's worlds — their work — plus the ledger
and the credential file, and an uninstaller that removes years of authorship because someone was
tidying up their applications folder would be unforgivable.

Removing worlds and removing credentials are separate explicit opt-ins, each labelled with what it
actually destroys. The default for both is off.

## 3.2 Testing

**The no-credential path** is the one that proves the product's claim, so it is tested as a
scenario rather than a unit: a clean machine, no network, no keys — create a world, add a
character by form, write a canon entry, link an artifact, reopen the application, and find it all
intact.

**First run** — app root created without prompting; a deliberately over-deep root is reported
before a world is created; a missing native binding is reported clearly rather than crashing;
declining the model download leaves the application fully usable.

**Packaging** — the packaged application starts on x64; the index opens with FTS5; both
child processes start; ffmpeg is invocable; no development-only path is reachable.

**Updates** — updater events retain target and progress across renderer reload; duplicate install
requests hand off once; explicit installation waits for coordinator and world-lock closure and
relaunches; failed or timed-out shutdown does not install; the next launch confirms only the exact
target version. A world written by a newer schema is refused unmodified, asserted by hashing it
before and after the attempt.

**Diagnostics** — a bundle generated from a world with rich content and configured providers
contains no world text, no key material and no prompts, asserted by scanning the bundle for known
sentinel values planted in each.

**Uninstall** — an uninstall without opt-ins leaves every world, the ledger and the credential
file present; each opt-in removes only what it names.

## 3.3 Definition of done

- [ ] Typecheck, build and test pass across workspaces
- [ ] A world can be created and authored with no credential and no network
- [ ] Every bundled component's licence is verified and its obligations recorded
- [ ] The packaged application is verified on x64
- [ ] No update installs while work is running or a lock is held
- [ ] A diagnostics bundle is safe to post publicly, verified by sentinel scan
- [ ] Uninstalling deletes no world by default
- [ ] Reviewer approved
