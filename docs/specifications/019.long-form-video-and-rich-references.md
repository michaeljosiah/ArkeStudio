# 1 · Requirements

## 1.1 Summary

A generation of video models has arrived that takes tens of reference assets rather than none or
four, answers timestamps rather than shot numbers, edits and extends existing footage, and locks
some of its output parameters to whatever was fed in. Arke's dispatch planning was designed against
the previous generation, and three of its premises are now wrong.

**Scarcity is no longer the binding constraint.** SPEC-010's reference budget ranks candidates and
truncates because models accepted a handful of images. When a model accepts thirty, truncation
almost never fires — and two constraints it has no concept of start to bind instead: how many
distinct *subjects* the model can hold apart, and how many bytes the transport can carry.

**Identity can no longer be left implicit.** With one reference, the model has nothing to confuse.
With eight, the mapping from asset to character has to be stated in words. Arke states it nowhere:
prompt assembly resolves `@maren` to a name and an appearance clause, and the reference array is
ordered by a ranking rule the prompt never mentions. The labels drawn inside a composite model
sheet are the only binding on offer, and that is precisely the binding these models are documented
to confuse.

**Output parameters are no longer all ours to choose.** Editing and extension derive aspect ratio,
and sometimes duration, from the input asset. A planner that always sends a chosen resolution and a
chosen length is composing a request the route must override — and pricing a duration the user
never picked.

This spec fixes those three, and takes the two capabilities that fall out of them: dispatching a
scene as an ordered keyframe sequence, and continuing a shot from its predecessor's footage rather
than from a still extracted out of it.

**Boundary.** SPEC-012 still plans the dispatch and SPEC-009 still executes it. This spec changes
what planning composes and what the manifest must describe. SPEC-013 still owns takes; §2.10 adds
one edge to the take graph and says what it costs.

## 1.2 Scope

**In scope**

- Reference binding: numbering assets, stating each one's role, and where that text lives.
- Timestamped pass prompts, and the boundary snapping that makes them expressible.
- Task modes, and the output parameters each one locks to its input.
- Estimating a task whose duration is dictated by its input.
- The reference budget's three dimensions, and which of them truncate and which only warn.
- Reference kinds: image, video and audio, and carrying a character's voice as one.
- Keyframe-sequence dispatch, and why the compiled board is not an input to it.
- Continuation: extending a take, and what that does to the take graph.

**Out of scope (this spec)**

- Job execution, retries and cost capture — SPEC-009, unchanged.
- Take immutability, review and the cut — SPEC-013, extended only by §2.10.
- The ranking rule inside the reference budget — SPEC-010 §2.9, still correct, now one dimension
  of three.
- Which provider route reaches which model — SPEC-008. §2.11 records the open question.
- Any change to the accept gate. Nothing here proposes a new authored-fact path.

## 1.3 Acceptance criteria

### Reference binding

- **R-1** Every reference asset carried in a dispatch SHALL be numbered, and the prompt SHALL state
  what each number depicts and what it is a reference *for*.
  - **WHEN** a shot cites three characters and a location **THEN** the prompt names each asset by
    index and by subject, and identity is never left to be inferred from text drawn inside an
    image.

- **R-2** The numbering in the prompt SHALL be the order the assets are transmitted in, and the two
  SHALL be composed from one structure so they cannot disagree.

- **R-3** The binding preamble SHALL be composed at dispatch from the attachment plan and SHALL NOT
  be part of the overridable prompt body.
  - **WHEN** a shot's prompt is overridden **THEN** the override replaces the direction and the
    binding preamble is still composed, because the preamble describes the payload rather than the
    intent.

- **R-4** Each carried asset SHALL declare which aspect of its subject it is a reference for, drawn
  from its attachment mode, so that a model sheet, a main photo and a scoped look are not asked to
  mean the same thing.

### Timestamped passes

- **R-5** A pass prompt SHALL express its shot boundaries as timestamps rather than shot numbers
  where the target model answers timestamps, and the manifest SHALL be what says whether it does.

- **R-6** Timestamps SHALL be whole seconds, contiguous from zero to the pass duration, with no gap
  between one shot's end and the next shot's start.

- **R-7** Where shot durations are not whole seconds, the *cumulative* boundary SHALL be rounded
  rather than each duration, so that error does not compound across a pass, and the resulting
  change SHALL be named before commit.
  - **WHEN** two 3.5-second shots pack into one pass **THEN** the boundaries are 0–4s and 4–7s,
    the pass is 7 seconds, and the dialog says the shots were snapped.

- **R-8** The boundaries stated in the prompt SHALL be the same boundaries SPEC-013 segments on.
  There SHALL NOT be a second set computed for display or for the provider.

### Task modes and locked parameters

- **R-9** The manifest SHALL describe, per model, which task modes it supports — generate, edit,
  continue, first-frame, last-frame, keyframe-sequence — and, per mode, which output parameters
  that mode locks to its input asset.

- **R-10** A dispatch in a mode that locks a parameter SHALL NOT send a chosen value for it, and
  SHALL send the provider's required sentinel where the route defines one.

- **R-11** A mode a model does not support SHALL be offered and disabled with the reason stated,
  never omitted from the surface.

- **R-12** Vendor-stated capacities and reliability ranges SHALL live in the manifest as data, not
  in code as constants, because they are published guidance and they move.

- **R-13** Where a model accepts a continuous range of aspect ratios rather than an enumeration,
  the manifest SHALL express the range, and world art direction SHALL be able to declare the
  production's aspect within it.

### Estimating a locked duration

- **R-14** The estimate for a mode that locks duration SHALL be computed from the input asset's
  measured duration, not from a chosen length.

- **R-15** Where the provider states a tolerance on that duration, the estimate SHALL be computed
  at the top of the tolerance.
  - **WHEN** a route states the output may exceed the input by up to 0.3 seconds **THEN** the
    figure shown includes those 0.3 seconds, because an estimate that can come in under is honest
    and one that can come in over is not.

- **R-16** A locked-mode dispatch SHALL NOT be offered where the input asset's duration cannot be
  measured locally; the reason SHALL be named.

### The reference budget

- **R-17** The budget SHALL be computed over three dimensions — asset count per kind, distinct
  subject count, and total payload bytes — and its notice SHALL name which dimension bound it.

- **R-18** Asset count SHALL truncate, using SPEC-010 §2.9's existing ranking, and the drop SHALL
  be named as it is today.

- **R-19** Subject count exceeding the model's stated reliable range SHALL warn and SHALL NOT
  truncate.
  - **WHEN** a shot cites ten characters and the model is reliable to eight **THEN** all ten are
    carried and the dialog says stability may be reduced, because dropping a character the user
    wrote into the shot is a worse failure than a shakier take they can retry.

- **R-20** Payload byte overflow SHALL be computed during planning and named before commit. It
  SHALL NOT first appear as a dispatch failure.

- **R-21** A reference SHALL carry its kind — image, video or audio — and each kind SHALL be
  budgeted against its own limit and its own total-duration limit where the model states one.

- **R-22** Where a model accepts audio reference and a cited character has an accepted voice, that
  voice SHALL be offerable as a subject-audio reference bound to the same subject as that
  character's images.

### Keyframe sequences

- **R-23** A scene SHALL be dispatchable as an ordered keyframe sequence, carrying each shot's
  accepted or pinned frame as an independent image, with the prompt stating the ordering.

- **R-24** Only an accepted or pinned frame SHALL qualify as a keyframe. A shot without one SHALL
  be named before commit and the sequence SHALL NOT silently close the gap.

- **R-25** The compiled board SHALL NOT be carried as a generation input.

### Continuation

- **R-26** A shot SHALL be able to declare that it continues its predecessor, and a continuing shot
  SHALL dispatch as an extension of the predecessor's accepted take rather than from a frame
  extracted out of it.

- **R-27** Continuation SHALL be unavailable where the predecessor has no accepted take, named
  rather than hidden.

- **R-28** A take produced by continuation SHALL record the take it continued.

- **R-29** Where the take a continuation was built on stops being the selection, the continuing
  take SHALL be marked superseded rather than deleted, and its own review decisions SHALL stand.

## 1.4 Open questions

- **Which route reaches the model.** The capability model here is written against a published
  vendor API that names roles on assets, takes a sentinel for a locked duration, and asks for a
  lossless container on both sides of an extension. Arke reaches this family of models through an
  aggregator whose request shape has none of those. Whether the manifest can describe these modes
  over the existing route, or whether a direct provider client is required, is unresolved and is
  the first thing T-1 must settle. It changes nothing above and much of §3.1.
- Whether continuation should chain more than one hop. One hop in v1: a chain of *n* takes has
  *n* ways to be invalidated by a single reselection, and the supersession rule gets harder to
  reason about with every link.
- Whether keyframe-sequence dispatch replaces whole-scene packing or sits beside it. Beside it in
  v1 — they answer different questions, one about cost and one about fidelity — but two modes that
  both produce one clip per scene is a picker the user has to understand.
- Whether the subject-count range belongs to the model or to the model *and* the kind of subject.
  Vendor guidance separates image subjects from audio-and-video subjects and gives them different
  ranges; the manifest can express that, but a dialog that says two numbers may say nothing.
- Whether snapping fractional durations should instead be prevented at authoring time for video
  productions. Snapping in v1, because SPEC-012 already contemplates fractional shot lengths and
  a constraint introduced late would invalidate existing scenes.

# 2 · Design

## 2.1 Architectural decision

**The payload describes itself.**

Every asset that goes over the wire is numbered, and the prompt says what each number is. That
sentence is the whole of the first half of this spec, and it is a correction rather than a feature:
Arke already decides which images to send and why — attachment modes, budget ranks, roles — and
then discards all of it, transmitting an ordered array whose ordering is never explained to the
thing consuming it. The information existed and was thrown away at the last step.

The second decision is that **abundance is not the absence of limits, it is different limits**. A
model that takes thirty images has not stopped having a capacity; it has moved capacity from a
number that truncates to a range that degrades. Those are not the same kind of constraint and must
not be handled the same way. Truncation is enforced and named. Degradation is named and *not*
enforced — because the user asked for ten characters in the shot, and giving them a stable take of
eight is not a smaller version of what they asked for, it is a different shot.

## 2.2 The binding preamble

Prompt assembly today resolves `@maren` to `Maren (a tall woman in a salt-stained coat)` and stops.
The reference array is built separately, ordered by SPEC-010's ranking rule, and nothing connects
the two. With one reference this is fine; the model has nothing to confuse it with. With eight it
is the documented failure mode — subjects blend, or one character appears twice.

So the dispatch opens with a preamble derived from the attachment plan:

```
Image 1-2: Maren — subject reference, appearance identity.
Image 3: Corwin — subject reference, appearance identity.
Image 4: The Drowned Hall — location reference, environment and composition.
Audio 1: Maren — voice reference, timbre only.
```

Every line is already known at planning time. `AttachmentDecision` carries the sheet, the file and
the mode; the budget carries the order. The preamble is a projection of that structure, which is
what R-2 means by composing both from one place: an array whose order can drift from the text
describing it is a bug that will present as the model confusing two characters, and it will be
diagnosed as a model problem.

**Mode becomes a role phrase** (R-4). A designated model sheet is appearance identity. A main photo
carried as a second reference is identity depth on the same subject, not a second subject — the
distinction the vendor guidance asks for when it says to state which *part* of an asset to use. A
scoped look attached to a production is that character as they appear *here*, which is a narrower
claim than the model sheet makes and should not be phrased as though it were the sheet.

## 2.3 Where the preamble lives

**Outside the override** (R-3), and this is the load-bearing choice in §2.2.

SPEC-012 stores an edited prompt as an override on the shot, replacing the assembled text. If the
preamble were part of that text, then every override would silently drop it — and an override is
exactly what a user writes when a shot is hard, which is exactly the shot with the most cast in it.
The convenience feature would disable the correctness feature at the moment it mattered most. That
is the same shape as SPEC-012 D7, where an override quietly stops picking up sheet changes, and it
was worth flagging there; here it can be designed out instead.

The division is clean because the two texts answer different questions. The override is **authored
intent** — what happens in the shot. The preamble is a **description of the payload** — what was
attached and why. The user does not author the payload; the planner does. So a payload description
that a user can edit is a description that can be wrong about facts nobody asked them to know.

The preamble is shown in the prompt preview, greyed and uneditable, because a user debugging a
confused take needs to see what the model was told about the assets. Hiding it would make §2.2
invisible exactly when someone is trying to work out why identity drifted.

## 2.4 Timestamps and boundary snapping

Pass prompts are built today as `[shot 3 · 4s]` — shot numbers with the duration annotated. That is
the vocabulary of the previous model generation, which answered shot numbers and ignored times. The
current generation answers whole-second timestamps, so the same data is written as `0-3s:` and
`3-7s:`.

This is a small change with a disproportionate payoff, because of what SPEC-013 R-4 already
insists on: **pass segments are cut on boundaries computed before dispatch, never inferred from
what came back**. Until now that was a one-sided contract — Arke knew where it intended to cut and
the model did not. Stating the boundaries in the prompt makes it a shared one. The `ShotPlanEntry`
values already exist; they simply stop being private.

Which forces the question R-7 answers. Shot durations may be fractional — SPEC-012's own criteria
use a 19.5-second scene as the worked example — and fractional timestamps are outside what these
models are documented to follow. There are two ways to reconcile that and only one of them is
honest.

Rounding *for the prompt only* keeps the plan exact and tells the model 0–4s while the segmenter
cuts at 3.5s. That reintroduces the divergence timestamps were adopted to remove, in a form that
is harder to see because both numbers are individually correct.

So the plan itself snaps, and **the cumulative boundary rounds rather than each duration**. Two
3.5-second shots become 0–4s and 4–7s: the first gains half a second, the second loses it, and the
pass total is what rounding the true total would give. Rounding each duration independently would
make both shots 4 seconds and the pass 8, and a twelve-shot pass would drift six seconds from what
was planned. Bounding the error at the boundary rather than letting it accumulate is the whole
reason to snap cumulatively, and it means a long pass is no worse than a short one.

The snap is named before commit (R-7), like every other thing this planner does to a user's numbers
without being asked.

## 2.5 Task modes and locked parameters

Dispatch composition today branches on capability — image sizes from width and height, video sizes
from a resolution word — and otherwise sends what the user chose. That holds while every task is
*generate*. It stops holding the moment a task takes an existing asset as its subject rather than
its reference.

Three modes lock parameters to their input:

| Mode | Locked | Free |
|---|---|---|
| Edit | Aspect ratio, duration | Everything else |
| Continue | Aspect ratio | Duration, resolution |
| First frame / first and last | Aspect ratio | Duration, resolution |

The manifest is where this is described (R-9), for the same reason it describes durations as a map
from seconds to the provider's own word for them: the routes disagree, the disagreement is data,
and code that hard-codes one route's answer will be wrong about the next one. A locked parameter is
not simply omitted, either — a route may require a sentinel in its place, and R-10 says the mode
description carries that too.

**Unsupported modes are offered and disabled** (R-11), which is SPEC-008's established rule for
size tiers applied to a new axis. A user who cannot find *Continue* on a model concludes the
product cannot do it; a user who sees *Continue — this model has no extension route* has learned
something about the model.

R-12 is the discipline that keeps all of this from rotting. The numbers in vendor guidance —
how many subjects hold together, how long an editable input should be, how many panels a
storyboard can carry — are published advice, they are revised, and they differ per model. In the
manifest they are one row to update. In code they are a constant somebody has to find.

## 2.6 Estimating a locked duration

An edit's output is as long as its input, and the user chose neither.

Arke prices video per second against a duration taken from the plan. In a locked mode that number
is not the plan's to give, so it comes from measuring the input asset (R-14) — and the measurement
must be local, which is why R-16 refuses the mode outright when it cannot be taken. A dispatch
priced on a guessed length is worse than a dispatch not offered.

Where the route states a tolerance — output may run up to some fraction of a second longer than
input — **the estimate takes the top of it** (R-15). This is not caution for its own sake. SPEC-008
already settled the principle when it chose to assume no cache discount and to state assumed token
counts high: the contract is that a figure is shown and accepted before money is spent, and a
figure that can come in under is honest where one that can come in over is not. A tolerance is the
same problem in a different unit and gets the same answer.

## 2.7 The budget's three dimensions

SPEC-010 §2.9 ranks candidates — characters before locations, leads before support, first
appearance first — and truncates at the model's accepted count. The ranking is still right. What
changes is that it is now one of three constraints, and only one of them truncates.

**Asset count truncates** (R-18). Unchanged behaviour, and at thirty it will rarely fire, which is
the point: the notice goes quiet on its own rather than needing to be silenced.

**Subject count warns** (R-19). This is a new dimension and it is not the same number as asset
count — a character carrying both a model sheet and a main photo spends two assets and is one
subject. Vendor guidance gives a range where subjects hold apart reliably and a wider range where
stability drops. That is a description of degradation, not a limit, and R-19 refuses to truncate
against it. The user wrote ten characters into the shot. Silently making it eight produces a stable
take of the wrong scene, and the user has no way to know why, because the thing that would have
told them was the warning we replaced with an action.

**Payload bytes warn, at planning time** (R-20). The transport inlines references as base64, which
costs about a third again on top of the file, against a fixed ceiling. Thirty images at high
resolution passes that ceiling comfortably. Today the check lives in the client and raises at
dispatch — acceptable when four small images could not plausibly breach it, and unacceptable now
that the common case can. It moves into planning, beside the other two, because a limit discovered
after the user commits is not a limit the user was told about.

**Kind is a property of the reference** (R-21). The array is a list of image paths today; models
that take video and audio need each kind budgeted separately, and against a total-duration limit as
well as a count where the route states one.

## 2.8 Identity travels as voice

A sheet already has a voice. SPEC-011 generates it, SPEC-013 places it on the cut's dialogue track,
and it has never been able to reach a video dispatch — there was no input for it.

R-22 makes it a carried reference bound to the same subject as that character's images. This is the
product's third mechanic reaching a surface it was always meant to reach: *identity travels* has
meant a main photo and a composite sheet because those were the only two things a video route would
accept. A character whose face and whose voice both arrive with them, in one request, bound to one
subject index, is the same idea with the missing half restored.

It is offered rather than automatic, and subject to the same accept discipline as any other
reference: an unaccepted voice is not carried, in exactly the way an unaccepted model sheet is not.

## 2.9 Keyframes, not boards

Board compilation produces a grid of a scene's selected frames. These models accept multi-panel
storyboards. The two facts sit next to each other and suggest an obvious move, and it is the wrong
one.

Vendor guidance is specific about what a storyboard input should be: simple line art, few panels,
no text drawn on it, and explicitly *not* a dense AI-generated grid — the failure mode is a still
output or panels rendered out of order. Arke's board is a fixed four-column grid of generated
frames with no cap on panel count, so a twenty-shot scene produces a twenty-panel board with text
labels. It is the discouraged input, in the discouraged quantity, in the discouraged style. R-25
settles it: the board is a review artifact and it stays one.

**The keyframe path is the right one, and it is a better fit than the storyboard path ever was.**
Storyboard input is documented as loose — a high-level plot reference the output need not match.
Keyframe input is documented as strict: the output aligns with the images. Arke has exactly the
right assets for it, per shot, already selected, and R-24 makes the accept gate the qualifier — a
frame is a keyframe because someone accepted it, and a shot with nothing accepted is named rather
than skipped. Closing the gap silently would produce a sequence that omits a shot the user believes
is in it.

This is the first time boards-adjacent data does generation work instead of only being looked at,
and it required no new authored entity to get there.

## 2.10 Continuation and the take graph

SPEC-013 R-12 extracts an accepted take's final frame and offers it as the next shot's start frame.
That is a workaround for models that could not take video, and it loses everything a still cannot
carry: motion, momentum, and the audio running underneath. Extension continues the footage.

It is also the one capability in this spec that does not drop in cleanly, and it should be adopted
knowing that. SPEC-013's takes are immutable, carry no review state, and each retries alone —
SPEC-012's second mechanic, *the unit of work is the shot, each its own brief and its own retry*.
A continued take depends on a specific predecessor take. That is a new edge, and edges have
consequences: reject the predecessor, or select a different one, and the continuation was built on
footage that is no longer the scene.

The resolution is to record the edge and let selection changes mark rather than delete (R-28,
R-29). A superseded take keeps its media, its provenance and its own review decisions; it is simply
no longer describing the current cut. This preserves immutability and the append-only decision log
exactly as they are, and adds one derived state alongside SPEC-013's existing derived *unreviewed*.
Deleting would have been the simpler rule and it would have destroyed paid-for footage on a
selection change the user might undo in the next minute.

Continuation is per-shot and opt-in (R-26), never a default. Most cuts are cuts: consecutive shots
in a scene are usually discontinuous, and extending across a cut would fight the edit rather than
serve it. Where the predecessor has no accepted take the mode is named and unavailable (R-27),
because the dependency is on a specific take and there is not one yet.

§1.4 records that chains stop at one hop in v1.

## 2.11 The provider surface

Everything above is written against published vendor documentation for the model family: assets
carrying declared roles, a sentinel standing in for a locked duration, a lossless container on both
sides of an extension. Arke reaches this family through an aggregator, and that route's request
shape has a flat array of image URLs and a duration string from a fixed list. It has no obvious
place to put a role, a sentinel or a kind.

So T-1 is a spike, and it comes before everything else that touches the wire. Either the aggregator
exposes these controls and the manifest describes them over the existing client, or it does not and
this family needs a direct provider client beside the current one. SPEC-008's registry makes the
second option a known shape rather than a new one, but it is a real cost and the choice should be
made deliberately rather than discovered at the first failed dispatch.

Nothing in §1.3 depends on the answer. §2.2 through §2.4 and §2.7 are ours regardless of route —
they are about what Arke composes and what it tells the user before spending. Modes, sentinels and
continuation are where the answer bites.

## 3.2 Testing

**Binding** — a shot citing four sheets produces four numbered lines whose indices match the
transmitted order exactly; reordering the budget reorders both together; an overridden prompt still
carries the preamble; a preamble is never editable through the override path; each attachment mode
produces its own role phrase and a main photo carried as a second reference is bound to its
character's existing subject rather than a new one.

**Snapping** — two 3.5-second shots produce 0–4s and 4–7s and a 7-second pass; twelve fractional
shots drift less than one second in total; whole-second shots are unchanged and produce no notice;
boundaries stated in the prompt equal the boundaries SPEC-013 segments on, asserted against the
same structure rather than two computations of it; no pass prompt contains a gap or an overlap.

**Modes** — a locked mode sends no chosen value for the parameter it locks; the required sentinel
is sent where the manifest declares one; an unsupported mode renders disabled with its reason and
cannot be dispatched; a mode's availability comes from the manifest and never from a code branch.

**Locked estimates** — an edit's estimate derives from the measured input duration; the stated
tolerance is added rather than subtracted; an unmeasurable input refuses the mode with a reason
rather than estimating; no locked-mode estimate reads from the duration picker.

**Budget** — thirty assets under a thirty cap produce no notice; the notice names which of the
three dimensions bound; ten subjects against a range of eight warns and carries all ten; asset
overflow still truncates by SPEC-010's ranking and still names the drops; payload overflow is
reported by planning and never first raised by the client; each kind is counted against its own
limit, and a total-duration limit is enforced where declared.

**Keyframes** — accepted and pinned frames only; a shot with neither is named and the sequence
does not close the gap; the ordering stated in the prompt matches the transmitted order; a compiled
board is never carried as an input on any path.

**Continuation** — unavailable and named where the predecessor has no accepted take; a continued
take records its predecessor; changing the predecessor's selection marks the continuation
superseded, leaves its media and its review decisions intact, and deletes nothing; a superseded
take is derived from selection state rather than stored on the take.

**Regression** — every existing per-shot and whole-scene fixture dispatching to a model with none
of these capabilities composes byte-identical requests to those it composes today.

## 3.3 Definition of done

- [ ] Typecheck, build and test pass across workspaces
- [ ] Stated asset numbering and transmitted asset order are composed from one structure
- [ ] No override path can drop or edit the binding preamble
- [ ] One set of pass boundaries exists, and the prompt and the segmenter both read it
- [ ] No locked parameter is chosen by a picker or priced from one
- [ ] Every new limit is named during planning; none first appears as a dispatch failure

## 3.4 Decision log

| # | Decision | Rationale |
|---|---|---|
| D1 | Every carried asset is numbered and named in the prompt | The planner already knows each asset's subject and role and was discarding it at the last step; with several references, an unstated mapping is the documented cause of subjects blending or duplicating. |
| D2 | Stated order and transmitted order come from one structure | Two representations of the same ordering will drift, and the drift presents as the model confusing two characters — diagnosed as a model problem, not as our bug. |
| D3 | The binding preamble sits outside the overridable prompt | An override is what a user writes for a hard shot, which is the shot with the most cast; if the preamble lived inside it, the convenience feature would disable the correctness feature exactly when it mattered. |
| D4 | The preamble is visible but uneditable | Someone debugging drifted identity needs to see what the model was told about the assets; the payload is not theirs to author. |
| D5 | Timestamps replace shot numbers where the model answers them | Makes SPEC-013's "boundaries computed before dispatch" a contract shared with the model rather than one Arke keeps privately. |
| D6 | Cumulative boundaries snap, not individual durations | Rounding each duration compounds — twelve shots drift six seconds; rounding the running total bounds the error at half a second no matter how long the pass. |
| D7 | The plan snaps, rather than the prompt rounding a plan that stays exact | Prompt-only rounding recreates the plan-versus-output divergence timestamps were adopted to remove, in a form that is harder to see because both numbers are individually correct. |
| D8 | Task modes and their locked parameters live in the manifest | Routes disagree about what locks and what sentinel stands in its place; that disagreement is data, and code encoding one route's answer will be wrong about the next. |
| D9 | Unsupported modes are offered and disabled with a reason | SPEC-008's rule for size tiers on a new axis: an absent mode reads as a missing product capability, a disabled one teaches something about the model. |
| D10 | Locked durations are measured from the input and priced at the top of the stated tolerance | SPEC-008 already settled that a figure which can come in under is honest where one that can come in over is not; a tolerance is that problem in a different unit. |
| D11 | Subject count warns, asset count truncates | They are different kinds of constraint. Truncating against a degradation range gives the user a stable take of a scene they did not write, with the warning that would have explained it replaced by the action. |
| D12 | Payload bytes are budgeted during planning | Four small images could not plausibly breach the ceiling; thirty large ones routinely will, and a limit discovered after commit is not a limit the user was told about. |
| D13 | Vendor capacities live in the manifest as data | They are published guidance, they are revised, and they differ per model — one row to update rather than a constant to find. |
| D14 | The compiled board is not a generation input | It is a dense grid of generated frames with labels and no panel cap: the discouraged input, in the discouraged quantity, in the discouraged style. |
| D15 | Keyframes come only from accepted or pinned frames, and gaps are named | Makes the accept gate the qualifier for what steers generation, and refuses to produce a sequence quietly missing a shot the user believes is in it. |
| D16 | Continuation is opt-in per shot | Consecutive shots are usually cuts; extending across one fights the edit rather than serving it. |
| D17 | A superseded continuation is marked, never deleted | Preserves take immutability and the append-only decision log, and does not destroy paid-for footage over a selection change the user may undo a minute later. |
