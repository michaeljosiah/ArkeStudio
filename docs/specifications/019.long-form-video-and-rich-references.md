# 1 · Requirements

## 1.1 Summary

A generation of video models has arrived that takes tens of reference assets rather than none or
four, reads a structured brief rather than a sentence, answers timestamps rather than shot numbers,
edits and extends existing footage, and locks some of its output parameters to whatever was fed in.
Arke's dispatch planning was designed against the previous generation, and four of its premises are
now wrong — and fixing them exposes a fifth gap that is not about planning at all.

**Identity can no longer be left implicit.** With one reference, the model has nothing to confuse.
With eight, the mapping from asset to character has to be stated in words. Arke states it nowhere:
prompt assembly resolves `@maren` to a name and an appearance clause, and the reference array is
ordered by a ranking rule the prompt never mentions. The labels drawn inside a composite model
sheet are the only binding on offer, and that is precisely the binding these models are documented
to confuse.

**The prompt is shaped for a model that read a sentence.** Assembly concatenates style, location,
time of day, description, camera and audio into one run-on joined by full stops. These models read
a brief with parts — what the clip is, what holds throughout, what happens when — and they respond
to negative controls Arke has never had a way to express. Two of those negatives are not stylistic
preferences: burned-in subtitles cannot be removed from an immutable take, and a model scoring
every clip fights the score track SPEC-013 assembles.

**Scarcity is no longer the binding constraint.** SPEC-010's reference budget ranks candidates and
truncates because models accepted a handful of images. When a model accepts thirty, truncation
almost never fires — and two constraints it has no concept of start to bind instead: how many
distinct *subjects* the model can hold apart, and how many bytes the transport can carry.

**Output parameters are no longer all ours to choose.** Editing and extension derive aspect ratio,
and sometimes duration, from the input asset. A planner that always sends a chosen resolution and a
chosen length is composing a request the route must override — and pricing a duration the user
never picked.

Fixing the second of those exposes a fifth problem that is not about assembly at all. Assembly can
only compose what was written, and what these models answer depends on how a shot was *drafted* —
general action rather than beat-by-beat choreography, plain description rather than idiom, standard
camera vocabulary. That knowledge belongs to the drafting agent, it is pages long, it differs per
model family, and Arke has nowhere to put it: agent briefs are compiled in, one per agent, and
replaceable from Settings. So this spec introduces **skills** — versioned authoring documents
shipped with the application and selected by model family — and gives the first two to scene
drafting and to storyboards.

This spec fixes those five, and takes the three capabilities that fall out of them: drawing a
storyboard a model can actually use, dispatching a scene as an ordered keyframe sequence, and
continuing a shot from its predecessor's footage rather than from a still extracted out of it.

**Boundary.** SPEC-012 still plans the dispatch and SPEC-009 still executes it. This spec changes
what planning composes and what the manifest must describe. SPEC-013 still owns takes and the cut;
§2.6 reads the cut's audio design and §2.13 adds one edge to the take graph.

## 1.2 Scope

**In scope**

- Reference binding: numbering assets, stating each one's role, and where that text lives.
- The assembled prompt's structure, and which of its parts hold for the whole clip.
- Negative controls, and deriving them from the production rather than authoring them per shot.
- What a carried reference image makes redundant in prose.
- Skills: where model-family authoring knowledge lives, how it is selected, and what it may not do.
- Storyboard authoring: a board drawn to be a reference, and how it differs from the review board.
- Timestamped pass prompts, and the boundary snapping that makes them expressible.
- Task modes, and the output parameters each one locks to its input.
- Estimating a task whose duration is dictated by its input.
- The reference budget's four dimensions, and which of them truncate, block or only warn.
- Reference kinds: image, video and audio, and carrying a character's voice as one.
- Keyframe-sequence dispatch, when it is preferred to a storyboard, and why the compiled review
  board is not an input to either.
- Continuation: extending a take, and what that does to the take graph.

**Out of scope (this spec)**

- Job execution, retries and cost capture — SPEC-009, unchanged.
- Take immutability, review and the cut — SPEC-013, read by §2.6 and extended by §2.13.
- The ranking rule inside the reference budget — SPEC-010 §2.9, still correct, now one dimension
  of four.
- Which provider route reaches which model — SPEC-008. §2.14 records the open question.
- Any change to the accept gate. Nothing here proposes a new authored-fact path.
- Rewriting an assembled prompt at dispatch, by any means. Assembly stays derivable; see §2.14.
- Harness session lifecycle, confinement and tool denials — SPEC-005, read by §2.7.

## 1.3 Acceptance criteria

### Reference binding

- **R-1** Every reference asset carried in a dispatch SHALL be numbered, and the prompt SHALL state
  what each number depicts and what it is a reference *for*.
  - **WHEN** a shot cites three characters and a location **THEN** the prompt names each asset by
    index and by subject, and identity is never left to be inferred from text drawn inside an
    image.

- **R-2** The numbering in the prompt SHALL be the order the assets are transmitted in, and the two
  SHALL be composed from one structure so they cannot disagree.

- **R-3** The binding preamble SHALL be composed at dispatch from the attachment plan and SHALL NOT
  be part of the overridable prompt body.
  - **WHEN** a shot's prompt is overridden **THEN** the override replaces the direction and the
    binding preamble is still composed, because the preamble describes the payload rather than the
    intent.
  - The preamble is one of two machine-composed regions; the derived negatives of R-13 are the
    other, and both sit outside what an override replaces.

- **R-4** Each carried asset SHALL declare which aspect of its subject it is a reference for, drawn
  from its attachment mode, so that a model sheet, a main photo and a scoped look are not asked to
  mean the same thing.

### Prompt structure

- **R-5** The assembled prompt SHALL be composed as named blocks — the binding preamble, a summary
  line, a standing description, a spatial layout, a camera anchor, the timed body, and a trailing
  block of what holds throughout — rather than as a flat concatenation of fragments.

- **R-5a** Where a video dispatch's scene inherits a location whose `Look` is nonblank, the prompt
  SHALL carry that location's complete authored `Look` as a named `SPATIAL LAYOUT` block, and the
  standing description SHALL NOT also carry the location's first `Look` clause.
  - **WHEN** no location resolves, its sheet is not a location, or its `Look` is blank **THEN** the
    prompt is assembled exactly as it was before this block existed.
  - Stills do not carry it: placing a camera in a room over time is not a question a still asks.
  - A whole-scene pass states it once for the pass, never once per beat, and derives it from the
    scene — so a pass keeps its room even where every beat in it is overridden, exactly as the
    standing description does.

- **R-5b** Where the spatial layout is present and the shot authored a camera value, that value
  SHALL be carried verbatim as a named `CAMERA ANCHOR` block and SHALL NOT also trail the beat.
  Nothing SHALL be inferred: an anchor is never parsed out of ordinary camera vocabulary, because
  a fixture nobody wrote is a fixture nobody can be held to — and inventing one is the failure this
  block exists to prevent.
  - A per-shot prompt override receives no generated spatial or camera-anchor text. The override
    owns every word of its body, including whatever it says about the room (D10's reasoning).

- **R-6** Elements that hold for the whole clip SHALL be stated once in the trailing block rather
  than interleaved with the beats, and the summary line SHALL lead with the world's art direction.
  - **WHEN** a pass carries four shots under one art direction **THEN** the look is stated twice —
    once leading the summary and once as a standing constraint — and never once per beat.

- **R-7** A block with nothing to say SHALL be omitted rather than emitted empty, and no block
  SHALL be built by joining sentence fragments with punctuation.

- **R-8** Where a cited sheet carries a reference image, its prose appearance clause SHALL reduce
  to the subject's name, because the image is the stronger carrier and restating the description at
  every mention competes with it.
  - **WHEN** a sheet is a sketch citation with no image to carry **THEN** the prose clause remains,
    because it is then the only description of that subject the model receives.

### Negative controls

- **R-9** The prompt SHALL carry negative controls derived from the production's audio design,
  never authored per shot.

- **R-10** Subtitles SHALL be negated on every video dispatch.
  - Burned-in text cannot be removed from an immutable take, no Arke surface asks for it, and the
    cut renders titles itself.

- **R-11** Generated score SHALL be negated where the cut composes a score track, while
  environmental and action sound SHALL remain permitted.
  - **WHEN** a production's cut carries score **THEN** the prompt asks for environmental and action
    sound only, because a model scoring every clip lays music under the track SPEC-013 assembles.

- **R-12** A shot whose audio direction is silence SHALL say so in the prompt rather than leaving
  it unstated.

- **R-13** Derived negatives SHALL be composed at dispatch outside the overridable prompt body and
  appended after it, exactly as the binding preamble is (R-3).
  - **WHEN** a shot's prompt is overridden **THEN** the subtitle and score negatives are still
    emitted, because a prompt the user rewrote is still a video dispatch and R-10 admits no
    exception.

### Authoring skills

- **R-14** Model-family authoring guidance — how actions, expressions, camera moves and storyboards
  are best written for a given family — SHALL be carried as a **skill**: a versioned document
  loaded into the authoring session, not a manifest field and not a compiled agent brief.

- **R-15** Skills SHALL ship with the application, versioned in the repository, and SHALL NOT be
  fetched at runtime.
  - Authoring sessions have no network tools (SPEC-005 R-10), so a skill that had to be fetched
    could not be fetched by the agent that needs it.

- **R-16** A skill SHALL be selected by the target model family, and a session drafting for one
  family SHALL NOT be given another's.

- **R-17** A skill SHALL shape what an agent authors and SHALL NOT rewrite what assembly emits at
  dispatch.
  - **WHEN** a skill is in force **THEN** the draft it shaped still arrives as a proposal and still
    waits for an accept, and the assembled prompt remains derivable from the world.

- **R-18** A skill SHALL NOT be able to remove the confinement preamble, the tool denials or the
  proposal directory that the accept gate assumes.

- **R-19** The skill and its version SHALL be recorded on the proposal it shaped.

- **R-20** Where no skill exists for the target family, drafting SHALL proceed under general
  guidance and SHALL say so, rather than failing or silently using another family's.

- **R-21** Dispatch planning SHALL compare the skill family recorded on a scene against the family
  of the model actually selected, and SHALL name the mismatch before commit.
  - SPEC-008 R-21 lets any dispatch override the routed model, so a scene drafted under one
    family's guidance can be sent to another's without R-19 ever being violated.

### Storyboards

- **R-22** A scene SHALL be able to produce a **storyboard drawn to be a reference**, distinct from
  the compiled review board.

- **R-23** A generated storyboard SHALL be line art, SHALL carry no text within the image, and SHALL
  be capped at the panel count the manifest states for the target family.
  - **WHEN** a dispatch covers more shots than the cap **THEN** the excess is named before commit
    rather than drawn into an over-long board.

- **R-24** A storyboard's panels SHALL be derived from the same shot descriptions the prompt is
  assembled from, so that the board and the prompt cannot contradict each other.

- **R-25** A generated storyboard SHALL be dispatched, priced and recorded like any other
  generation, and SHALL be accepted before it may steer one.

- **R-26** Where every shot in a dispatch has an accepted or pinned frame **and** the whole
  sequence survives the reference budget intact, keyframe reference SHALL be preferred to
  storyboard reference, and the choice SHALL be stated.
  - **WHEN** a scene has more shots than the model's image-reference cap **THEN** keyframes are not
    chosen, because a truncated sequence no longer carries every shot's frame as R-47 requires;
    the storyboard is used instead, or the mode is disabled with the reason.

- **R-27** A storyboard SHALL record the scene version it was drawn from, SHALL be stale once that
  scene advances, and a stale storyboard SHALL NOT steer a generation until it is redrawn and
  accepted again.
  - Otherwise an edited shot description and an unredrawn panel contradict each other, which is
    the one thing R-24 exists to make unrepresentable.

### Timestamped passes

- **R-28** A pass prompt SHALL express its shot boundaries as timestamps rather than shot numbers
  where the target model answers timestamps, and the manifest SHALL be what says whether it does.

- **R-29** Timestamps SHALL be whole seconds, contiguous from zero to the pass duration, with no gap
  between one shot's end and the next shot's start.

- **R-30** Where shot durations are not whole seconds, the *cumulative* boundary SHALL be rounded
  rather than each duration, so that error does not compound across a pass, and the resulting
  change SHALL be named before commit.
  - **WHEN** two 3.5-second shots pack into one pass **THEN** the boundaries are 0–4s and 4–7s,
    the pass is 7 seconds, and the dialog says the shots were snapped.

- **R-31** Snapped boundaries SHALL be strictly increasing: every shot SHALL receive an interval of
  at least one whole second.
  - **WHEN** a shot is short enough that rounding would give it a zero-length interval — a 0.4
    second shot snapping to 0–0s — **THEN** it SHALL be named and either merged into its neighbour
    or refused, never dispatched as an empty range.
  - `ShotSchema` admits any positive duration, and SPEC-013 segments on exactly these boundaries
    (R-4), so a collapsed interval would produce a zero-length take for a shot that really exists.

- **R-32** The boundaries stated in the prompt SHALL be the same boundaries SPEC-013 segments on.
  There SHALL NOT be a second set computed for display or for the provider.

### Task modes and locked parameters

- **R-33** The manifest SHALL describe, per model, which task modes it supports — `generate`,
  `edit`, `continue`, `first-frame`, `first-and-last-frame`, `keyframe-sequence` — and, per mode,
  which output parameters that mode locks to its input asset.
  - A paired boundary-frame operation is its own mode, named once. `last-frame` is not a mode: a
    trailing boundary frame is an asset role within `first-and-last-frame`, and treating it as a
    mode would leave a last-frame-only request and a paired request indistinguishable.

- **R-34** A dispatch in a mode that locks a parameter SHALL NOT send a chosen value for it, and
  SHALL send the provider's required sentinel where the route defines one.

- **R-35** A mode a model does not support SHALL be offered and disabled with the reason stated,
  never omitted from the surface.

- **R-36** Vendor-stated capacities and reliability ranges SHALL live in the manifest as data, not
  in code as constants, because they are published and they move.
  - Prose guidance is not manifest data; it is a skill (R-14). The manifest carries the numbers a
    picker or an estimate reads, including the storyboard panel cap of R-23.

- **R-37** Where a model accepts a continuous range of aspect ratios rather than an enumeration,
  the manifest SHALL express the range, and the **production** SHALL be able to declare its aspect
  within it.
  - Art direction is one world-level record (SPEC-017 R-1), and one world routinely holds a 16:9
    film and a 9:16 cut of the same material. A world-scoped aspect cannot express both without
    one production silently changing the other's. Any world value is a default the production
    inherits and may override.

### Estimating a locked duration

- **R-38** The estimate for a mode that locks duration SHALL be computed from the input asset's
  measured duration, not from a chosen length.

- **R-39** Where the provider states a tolerance on that duration, the estimate SHALL be computed
  at the top of the tolerance.
  - **WHEN** a route states the output may exceed the input by up to 0.3 seconds **THEN** the
    figure shown includes those 0.3 seconds, because an estimate that can come in under is honest
    and one that can come in over is not.

- **R-40** A dispatch in a mode that **locks duration** SHALL NOT be offered where the input
  asset's duration cannot be measured locally; the reason SHALL be named.
  - Scoped to duration-locking modes only. `first-frame` and `first-and-last-frame` lock aspect
    ratio and leave duration free, and their input is a still image with no duration to measure —
    refusing them for an unmeasurable duration would disable a mode that never needed one.

### The reference budget

- **R-41** The budget SHALL be computed over four dimensions — asset count per kind, distinct
  subject count, total reference duration per kind, and total payload bytes — and its notice SHALL
  name which dimension bound it.
  - Reference duration is its own dimension because a request can sit inside every count and still
    exceed the aggregate video or audio seconds R-45 requires enforcing; without it the notice has
    no way to report the constraint that actually bound.

- **R-42** Asset count SHALL truncate, using SPEC-010 §2.9's existing ranking, and the drop SHALL
  be named as it is today.

- **R-43** Subject count exceeding the model's stated reliable range SHALL warn and SHALL NOT
  truncate.
  - **WHEN** a shot cites ten characters and the model is reliable to eight **THEN** all ten are
    carried and the dialog says stability may be reduced, because dropping a character the user
    wrote into the shot is a worse failure than a shakier take they can retry.

- **R-44** Payload byte overflow SHALL be computed during planning, and planning SHALL either
  reduce the payload deterministically or block the commit. It SHALL NOT be a warning the user can
  commit past, and SHALL NOT first appear as a dispatch failure.
  - The transport ceiling is a hard limit, not a degradation range: a request over it is one the
    client already refuses. Naming a certain failure and then allowing the commit applies R-43's
    enforce/warn distinction backwards.
  - Where reduction is chosen it SHALL use SPEC-010 §2.9's ranking and SHALL name the drops,
    exactly as asset-count truncation does.

- **R-45** A reference SHALL carry its kind — image, video or audio — and each kind SHALL be
  budgeted against its own limit and its own total-duration limit where the model states one.

- **R-46** Where a model accepts audio reference and a cited character has a **designated voice
  sample**, that sample SHALL be offerable as a subject-audio reference bound to the same subject
  as that character's images.
  - SPEC-011 assigns a provider voice identity to a sheet (R-11) and produces a voice take per
    dialogue line (R-16); neither is a single canonical sample to transmit. The designated sample
    is nominated the way a model sheet's designated compilation is — one asset, either a filed
    cloning recording (SPEC-011 R-13) or a nominated voice take.
  - A character with no designated sample SHALL carry no audio reference, and the absence SHALL be
    stated rather than resolved by picking a take.

### Keyframe sequences

- **R-47** A scene SHALL be dispatchable as an ordered keyframe sequence, carrying each shot's
  accepted or pinned frame as an independent image, with the prompt stating the ordering.

- **R-48** Only an accepted or pinned frame SHALL qualify as a keyframe. A shot without one SHALL
  be named before commit and the sequence SHALL NOT silently close the gap.

- **R-49** The compiled review board SHALL NOT be carried as a generation input.

### Continuation

- **R-50** A shot SHALL be able to declare that it continues its predecessor, and a continuing shot
  SHALL dispatch as an extension of the predecessor's accepted take rather than from a frame
  extracted out of it.
  - **WHEN** the predecessor's accepted take is a pass segment **THEN** the selected in/out range
    SHALL be materialised losslessly before dispatch, or carried through provider-side range
    semantics where the route offers them. A pass segment owns only a range into media holding
    several shots (SPEC-013 R-3); sending that backing file would extend the wrong footage.
  - Materialisation SHALL NOT re-encode, on the same grounds as SPEC-013 R-13.

- **R-51** Continuation SHALL be unavailable where the predecessor has no accepted take, named
  rather than hidden.

- **R-52** Continuation SHALL be unavailable where the predecessor's accepted take was itself
  produced by continuation, named rather than hidden.
  - This is what holds §1.4's one-hop decision to something testable. Without it every shot in a
    scene may declare continuation, and a single reselection invalidates the whole tail.

- **R-53** A take produced by continuation SHALL record the take it continued.

- **R-54** Where the take a continuation was built on stops being the selection, the continuing
  take SHALL be marked superseded rather than deleted, and its own review decisions SHALL stand.

- **R-55** A superseded take SHALL cease to be the shot's selection, so that the derived cut renders
  that shot as an explicit gap rather than continuing to show it.
  - The cut is derived from selections (SPEC-013 R-14) and a shot with none renders as a labelled
    gap (SPEC-013 R-15). Marking the take without clearing the selection would leave footage in the
    active cut that §2.13 says no longer describes it.

## 1.4 Open questions

- ~~**Which route reaches the model.**~~ **Settled by T-1.** The aggregator ships this generation
  as three sibling routes — text-to-video, image-to-video and reference-to-video — taking up to
  fifty multimodal references, and it spells the locked-parameter sentinels `"auto"` rather than
  the vendor API's `-1` and `adaptive`. So **mode is a route, not a parameter**, which the
  catalogue already models for the `/edit` sibling, and no direct provider client is needed. The
  manifest describes each mode as a route plus the sentinels its locked parameters take, and the
  spelling stays data because the two surfaces already disagree about it. Recorded in §2.14.
- Whether the standing description should be assembled per pass or per shot. Per pass in v1, since
  a pass is one clip and a description restated per beat is the repetition R-6 exists to stop —
  but shots within a pass can change location, and a standing description that is wrong for the
  back half is worse than one stated twice.
- Whether ambience should be negated alongside score. Not in v1: environmental sound is what the
  model is best at and hardest to replace, and SPEC-013's ambience track is usually a filed
  artifact laid *under* a scene rather than a replacement for what a clip already sounds like.
  If the two routinely fight, this becomes the same rule as score.
- **Who draws the storyboard.** An image model prompted by an agent is assumed, because it is the
  only path that exists today — but it makes previz a paid generation, which is a strange bill for
  a stick-figure board. Local deterministic drawing is free and cannot draw; an imported board the
  director drew themselves is free, accurate, and asks for work Arke was meant to save. If the
  generated route proves expensive relative to what it saves, import is the fallback and SPEC-015
  already files it.
- Whether a skill should be able to carry examples, or only rules. Rules in v1: worked examples
  are most of the length, and an authoring session that reads five example prompts before drafting
  spends its context on someone else's shots. Revisit if drafts miss the shape without them.
- Whether skills should be user-editable in the world folder, the way art direction is. Not in v1
  — a skill is application knowledge rather than world content, and the Settings brief override
  already exists for a user who wants to steer an agent. But "your worlds stay yours" has an
  awkward edge where the thing shaping your drafts is not yours to read. It is at least readable.
- Whether continuation should chain more than one hop. One hop in v1: a chain of *n* takes has
  *n* ways to be invalidated by a single reselection, and the supersession rule gets harder to
  reason about with every link.
- Whether keyframe-sequence dispatch replaces whole-scene packing or sits beside it. Beside it in
  v1 — they answer different questions, one about cost and one about fidelity — but two modes that
  both produce one clip per scene is a picker the user has to understand.
- Whether the subject-count range belongs to the model or to the model *and* the kind of subject.
  Vendor guidance separates image subjects from audio-and-video subjects and gives them different
  ranges; the manifest can express that, but a dialog that says two numbers may say nothing.
- Whether snapping fractional durations should instead be prevented at authoring time for video
  productions. Snapping in v1, because SPEC-012 already contemplates fractional shot lengths and
  a constraint introduced late would invalidate existing scenes.

# 2 · Design

## 2.1 Architectural decision

**The payload describes itself, and the prompt has parts.**

Every asset that goes over the wire is numbered, and the prompt says what each number is. That is a
correction rather than a feature: Arke already decides which images to send and why — attachment
modes, budget ranks, roles — and then discards all of it, transmitting an ordered array whose
ordering is never explained to the thing consuming it. The information existed and was thrown away
at the last step.

The same is true one level up. Assembly knows which of its inputs describe the whole clip and which
describe one moment in it — art direction and location hold throughout, a shot's action does not —
and it flattens that distinction into a single run-on. These models read a brief with parts, and
Arke has the parts. It is joining them with full stops.

The second decision is that **abundance is not the absence of limits, it is different limits**. A
model that takes thirty images has not stopped having a capacity; it has moved capacity from a
number that truncates to a range that degrades. Those are not the same kind of constraint and must
not be handled the same way. Truncation is enforced and named. Degradation is named and *not*
enforced — because the user asked for ten characters in the shot, and giving them a stable take of
eight is not a smaller version of what they asked for, it is a different shot.

## 2.2 The binding preamble

Prompt assembly today resolves `@maren` to `Maren (a tall woman in a salt-stained coat)` and stops.
The reference array is built separately, ordered by SPEC-010's ranking rule, and nothing connects
the two. With one reference this is fine; the model has nothing to confuse it with. With eight it
is the documented failure mode — subjects blend, or one character appears twice.

So the dispatch opens with a preamble derived from the attachment plan:

```
Image 1-2: Maren — subject reference, appearance identity.
Image 3: Corwin — subject reference, appearance identity.
Image 4: The Drowned Hall — location reference, environment and composition.
Audio 1: Maren — voice reference, timbre only.
```

Every line is already known at planning time. `AttachmentDecision` carries the sheet, the file and
the mode; the budget carries the order. The preamble is a projection of that structure, which is
what R-2 means by composing both from one place: an array whose order can drift from the text
describing it is a bug that will present as the model confusing two characters, and it will be
diagnosed as a model problem.

**Mode becomes a role phrase** (R-4). A designated model sheet is appearance identity. A main photo
carried as a second reference is identity depth on the same subject, not a second subject — the
distinction the vendor guidance asks for when it says to state which *part* of an asset to use. A
scoped look attached to a production is that character as they appear *here*, which is a narrower
claim than the model sheet makes and should not be phrased as though it were the sheet.

## 2.3 Where the preamble lives

**Outside the override** (R-3), and this is the load-bearing choice in §2.2.

SPEC-012 stores an edited prompt as an override on the shot, replacing the assembled text. If the
preamble were part of that text, then every override would silently drop it — and an override is
exactly what a user writes when a shot is hard, which is exactly the shot with the most cast in it.
The convenience feature would disable the correctness feature at the moment it mattered most. That
is the same shape as SPEC-012 D7, where an override quietly stops picking up sheet changes, and it
was worth flagging there; here it can be designed out instead.

The division is clean because the two texts answer different questions. The override is **authored
intent** — what happens in the shot. The preamble is a **description of the payload** — what was
attached and why. The user does not author the payload; the planner does. So a payload description
that a user can edit is a description that can be wrong about facts nobody asked them to know.

**The same carve-out covers the derived negatives** (R-13). They are the other machine-composed
region, and they fail the same way: an override is what a user writes for a hard shot, and a hard
shot is still a video dispatch, so dropping the subtitle negative there would burn text into
precisely the take somebody worked hardest on. R-10 admits no exception, which means the negatives
cannot live anywhere an override can reach. They are appended after the overridden body.

That gives one rule rather than two: **what the planner composes, the planner keeps.** The preamble
describes the payload, the negatives describe the delivery, and neither is authored intent. The
override owns the direction — which is all it ever claimed to own.

Both regions are shown in the prompt preview, greyed and uneditable, because a user debugging a
confused take needs to see what the model was told about the assets, and a user debugging burned-in
titles needs to see whether the negative was there. Hiding them would make §2.2 and §2.6 invisible
exactly when someone is trying to work out why something drifted.

## 2.4 The shape of the prompt

What assembly emits today is one line:

```
Salt-bleached neo-noir. The Drowned Hall — flooded marble under a broken dome. dusk. Maren
(a tall woman in a salt-stained coat) crosses to the altar. low tracking shot. dialogue: "It
held."
```

Every fact in it is right and the shape is wrong. Fragments are joined with full stops until they
look like sentences, the standing look of the world sits in the same run as a single action, and
nothing tells the model which parts describe the whole clip. The guidance these models publish
asks for something with named parts, and Arke has every part already:

| Block | Source |
|---|---|
| Binding preamble | The attachment plan (§2.2) |
| Summary line | Art direction, cast, location, the event |
| Standing description | Sheet appearance, location look, time of day, camera setup |
| Timed body | The shot plan's boundaries and each shot's direction (§2.8) |
| Standing constraints | Art direction restated, recurring camera behaviour, audio, negatives |

**Persistent things are stated once, at the end** (R-6). Art direction leads the summary because it
frames everything that follows, and it returns in the trailing block because that is where these
models look for what must not drift. What it must not do is appear beside every beat: a four-shot
pass repeating the world's look four times spends the model's attention arguing with itself about
which mention is authoritative.

**Empty blocks are omitted, not emitted** (R-7). A shot with no camera direction should produce no
camera line, not an empty one — and no block is built by joining fragments with punctuation, which
is what produces `dusk. Maren crosses` today and the `..` cleanup that follows it.

This is a change to composition, not to content. Every input is one Arke already reads; nothing new
is authored, and nothing about the accept gate moves.

## 2.5 What the images already say

Assembly inlines a sheet's appearance clause at **every** mention. Once a model sheet is carried,
that is redundant against a better carrier and repeated on top: the guidance is explicit that where
a reference asset is accurate, it should be cited rather than described again, and that repeating
descriptions competes with the asset.

So the clause shortens to the name where an image is carried, and stays where one is not (R-8). The
condition is already computed — `AttachmentDecision.mode` distinguishes a designated compilation
from a sketch citation — so this is a branch on data assembly already has.

The asymmetry is the point. A sketch citation is a sheet with no image to send, and its prose is
the only description of that character the model will ever receive; stripping it there would lose
the subject entirely. This is the same reasoning as SPEC-010's budget notice, which says prose
remains when images are dropped.

## 2.6 Negatives Arke has to state

Two of these are not stylistic preferences.

**Subtitles, always** (R-10). These models will burn text into the frame, and a take is immutable
by SPEC-013 R-1 — there is no version of that take without the text. No Arke surface asks for
subtitles, and the cut renders its own titles at export. A negative that costs a clause and
prevents unremovable damage to paid-for footage is not a close call.

**Score, where the cut composes one** (R-11). SPEC-013 R-17 gives the cut dialogue, score and
ambience tracks. A model that scores every clip means every take arrives with music baked into its
audio, underneath the score the cut is assembling — two pieces of music, one of them unremovable,
and the take that sounded best in isolation is the one that fights the cut hardest.

What is *not* negated is environmental and action sound. That is what these models are best at, it
belongs to the shot rather than to the sequence, and replacing it would mean sourcing a foley track
for every clip. Dialogue is likewise generated where a shot carries a line, which is what the shot's
audio direction already says.

**Derived, never authored** (R-9). The user does not write "no subtitles" into a shot. Assembly
knows the production's format, knows whether the cut carries score, and knows the shot's audio
direction; the negatives fall out of those three. A per-shot negative is a per-shot thing to forget,
and the failure is silent until an export has titles burned into it.

§1.4 records why ambience is not negated with score in v1.

## 2.7 Where the authoring knowledge lives

The guidance these models publish is as much about how to *write* a shot as how to assemble one:
general descriptions of action rather than beat-by-beat choreography, plain descriptive sentences
for expression rather than idiom, standard camera vocabulary written directly and unusual terms
explained. That advice lands on the drafting agent, not on assembly — by the time assembly runs the
description is written, and a shot drafted as *"she is beside herself"* contains an idiom the model
will render literally or ignore, which no amount of good composition recovers.

Three places could hold it. Two are wrong, and the reasons are worth recording because both look
reasonable.

**Not the manifest.** R-36's rule is right about *capacities* — numbers and enumerations that a
picker or an estimate reads. Authoring guidance is pages of prose with worked examples. Putting it
in a manifest row makes "one row to update" false, and makes the file that pricing depends on carry
three pages of style advice.

**Not an agent brief.** This is the closest existing thing, and the roster already proves the
pattern: the art-director agent's brief tells an image-prompt writer to avoid text, logos,
watermarks and panels — model-facing craft knowledge, exactly the shape needed. But briefs are
compiled into the application, one per agent rather than one per model family, and Settings can
replace them. The harness's own note on that override says an agent talked out of its constraints
*fails in ways that look like our bugs*. Knowledge the product's output quality depends on should
not sit in a field a user can overwrite while adjusting something else.

**A skill** (R-14): a versioned document, shipped with the application, selected by model family
(R-16), loaded into the authoring session. Per-family selection is the requirement neither of the
other two could meet — a world targeting one family should not be drafted under another's advice.

**Shipped, never fetched** (R-15). Here architecture settles what principle only argues: SPEC-005
R-10 disables network tools in authoring sessions, so a skill that had to be fetched could not be
fetched by the agent that needs it. Vendoring it in the repository is also what keeps first run
working on a machine that has never been online, and keeps a vendor's CDN out of the path of
drafting a scene.

**A skill shapes authoring and never touches dispatch** (R-17). This is the line that keeps the
gate intact. What a skill influences is a *draft*, and a draft arrives as a proposal and waits for
an accept — the ordinary path, with a human still saying yes. It does not rewrite the assembled
prompt, so Reset still restores the assembled form and override staleness stays computable. A skill
also cannot reach the confinement preamble, the tool denials or the proposal directory (R-18);
those are what the accept gate assumes, and SPEC-005 already refuses to let a brief override them.

**Recorded on the proposal it shaped** (R-19), which is the same discipline as provenance at
dispatch. A scene drafted under one version of the guidance and a scene drafted under the next
differ for a reason that is otherwise unrecoverable — and this is a product whose whole argument is
that the reasons stay attached to the work.

**Absence is graceful** (R-20). A family with no skill drafts under general guidance and says so.
Refusing to draft would make a missing document into a broken feature, and silently borrowing
another family's advice would produce shots written for a model that will not read them.

## 2.8 Timestamps and boundary snapping

Pass prompts are built today as `[shot 3 · 4s]` — shot numbers with the duration annotated. That is
the vocabulary of the previous model generation, which answered shot numbers and ignored times. The
current generation answers whole-second timestamps, so the same data is written as `0-3s:` and
`3-7s:`.

This is a small change with a disproportionate payoff, because of what SPEC-013 R-4 already
insists on: **pass segments are cut on boundaries computed before dispatch, never inferred from
what came back**. Until now that was a one-sided contract — Arke knew where it intended to cut and
the model did not. Stating the boundaries in the prompt makes it a shared one. The `ShotPlanEntry`
values already exist; they simply stop being private.

Which forces the question R-30 answers. Shot durations may be fractional — SPEC-012's own criteria
use a 19.5-second scene as the worked example — and fractional timestamps are outside what these
models are documented to follow. There are two ways to reconcile that and only one of them is
honest.

Rounding *for the prompt only* keeps the plan exact and tells the model 0–4s while the segmenter
cuts at 3.5s. That reintroduces the divergence timestamps were adopted to remove, in a form that
is harder to see because both numbers are individually correct.

So the plan itself snaps, and **the cumulative boundary rounds rather than each duration**. Two
3.5-second shots become 0–4s and 4–7s: the first gains half a second, the second loses it, and the
pass total is what rounding the true total would give. Rounding each duration independently would
make both shots 4 seconds and the pass 8, and a twelve-shot pass would drift six seconds from what
was planned. Bounding the error at the boundary rather than letting it accumulate is the whole
reason to snap cumulatively, and it means a long pass is no worse than a short one.

**A boundary that collapses is not a rounding artefact, it is a lost shot** (R-31). Cumulative
snapping bounds the drift but does not guarantee every shot survives it: a 0.4-second opening shot
rounds to 0–0s, and since SPEC-013 segments on exactly these boundaries, that produces a zero-length
take for a shot the user wrote. `ShotSchema` admits any positive duration, so this is reachable
rather than theoretical. Boundaries are therefore strictly increasing by construction — every shot
gets at least a whole second, and one that cannot is named and merged or refused rather than
dispatched as an empty range.

The snap is named before commit (R-30), like every other thing this planner does to a user's numbers
without being asked.

## 2.9 Task modes and locked parameters

Dispatch composition today branches on capability — image sizes from width and height, video sizes
from a resolution word — and otherwise sends what the user chose. That holds while every task is
*generate*. It stops holding the moment a task takes an existing asset as its subject rather than
its reference.

Three modes lock parameters to their input:

| Mode | Locked | Free |
|---|---|---|
| `edit` | Aspect ratio, duration | Everything else |
| `continue` | Aspect ratio | Duration, resolution |
| `first-frame` | Aspect ratio | Duration, resolution |
| `first-and-last-frame` | Aspect ratio | Duration, resolution |

The paired boundary-frame operation is named once, as its own mode (R-33). There is no `last-frame`
mode: a trailing boundary frame is an asset *role* inside `first-and-last-frame`, and promoting it
to a mode would leave a last-frame-only request and a paired request indistinguishable in the
manifest — two different provider operations behind one name.

Only `edit` locks duration, which is why R-40 scopes its refusal there. The boundary-frame modes
take a still image as input; asking them to measure a duration that does not exist would disable
generation they support.

The manifest is where this is described (R-33), for the same reason it describes durations as a map
from seconds to the provider's own word for them: the routes disagree, the disagreement is data,
and code that hard-codes one route's answer will be wrong about the next one. A locked parameter is
not simply omitted, either — a route may require a sentinel in its place, and R-34 says the mode
description carries that too.

**Unsupported modes are offered and disabled** (R-35), which is SPEC-008's established rule for
size tiers applied to a new axis. A user who cannot find *Continue* on a model concludes the
product cannot do it; a user who sees *Continue — this model has no extension route* has learned
something about the model.

R-36 is the discipline that keeps all of this from rotting. The numbers and advice in vendor
guidance — how many subjects hold together, how long an editable input should be, how to write an
action — are published, they are revised, and they differ per model. In the manifest they are one
row to update. In code they are a constant somebody has to find.

## 2.10 Estimating a locked duration

An edit's output is as long as its input, and the user chose neither.

Arke prices video per second against a duration taken from the plan. In a locked mode that number
is not the plan's to give, so it comes from measuring the input asset (R-38) — and the measurement
must be local, which is why R-40 refuses the mode outright when it cannot be taken. A dispatch
priced on a guessed length is worse than a dispatch not offered.

Where the route states a tolerance — output may run up to some fraction of a second longer than
input — **the estimate takes the top of it** (R-39). This is not caution for its own sake. SPEC-008
already settled the principle when it chose to assume no cache discount and to state assumed token
counts high: the contract is that a figure is shown and accepted before money is spent, and a
figure that can come in under is honest where one that can come in over is not. A tolerance is the
same problem in a different unit and gets the same answer.

## 2.11 The budget's four dimensions

SPEC-010 §2.9 ranks candidates — characters before locations, leads before support, first
appearance first — and truncates at the model's accepted count. The ranking is still right. What
changes is that it is now one of **four** constraints, and they do not all behave alike.

**Asset count truncates** (R-42). Unchanged behaviour, and at thirty it will rarely fire, which is
the point: the notice goes quiet on its own rather than needing to be silenced.

**Subject count warns** (R-43). This is a new dimension and it is not the same number as asset
count — a character carrying both a model sheet and a main photo spends two assets and is one
subject. Vendor guidance gives a range where subjects hold apart reliably and a wider range where
stability drops. That is a description of degradation, not a limit, and R-43 refuses to truncate
against it. The user wrote ten characters into the shot. Silently making it eight produces a stable
take of the wrong scene, and the user has no way to know why, because the thing that would have
told them was the warning we replaced with an action.

**Reference duration is its own dimension** (R-41). A model that caps aggregate video or audio
seconds can refuse a request that sat inside every count — three short clips and one long one is a
different constraint from four clips. Without duration as a dimension the notice would have to
report that nothing bound while the dispatch failed anyway.

**Payload bytes block or reduce** (R-44), and this is the one place the first draft of this spec
had it wrong. The transport inlines references as base64, which costs about a third again on top of
the file, against a fixed ceiling; thirty images at high resolution passes it comfortably. Today
the check lives in the client and raises at dispatch — acceptable when four small images could not
plausibly breach it, and unacceptable now that the common case can.

Moving it into planning is necessary but not sufficient. A ceiling is a **hard limit**, not a
degradation range: a request over it is one the client is already known to refuse, so naming it and
then letting the user commit produces a guaranteed failure they were invited to walk into. That is
R-43's enforce/warn distinction applied backwards. Planning either reduces the payload by the same
ranking that truncates on count, naming the drops, or it blocks — and the choice between those is
the user's, offered rather than assumed.

**Kind is a property of the reference** (R-45). The array is a list of image paths today; models
that take video and audio need each kind budgeted separately, and against a total-duration limit as
well as a count where the route states one.

**Identity travels as voice.** A sheet already has one: SPEC-011 generates it, SPEC-013 places it on
the cut's dialogue track, and it has never been able to reach a video dispatch because there was no
input for it. R-46 makes it a carried reference bound to the same subject as that character's
images — the product's third mechanic reaching a surface it was always meant to reach. It is
offered rather than automatic, and an unaccepted voice is not carried, exactly as an unaccepted
model sheet is not.

## 2.12 Storyboards and keyframes

Two ways to steer a generation with pictures, and Arke needs both because they belong to different
moments.

**Keyframes need footage that already exists.** A keyframe sequence carries each shot's accepted
frame, so it presupposes stills generated, reviewed and accepted for every shot in the dispatch.
Early in a scene's life there are none, and the frames are exactly what has not been made yet.

**A storyboard is what you have before anything is shot.** Line art is cheap, it is what a director
would draw anyway, and it can exist the moment the shot list does.

So they are not alternatives to pick between on aesthetics. The guidance is explicit that storyboard
input is *loose* — a high-level plot reference the output need not match — while keyframe input is
*aligned*. R-26 makes that preference automatic rather than a picker: nobody should have to know
which is stricter.

But "every shot has a frame" is not sufficient on its own, and the gap is easy to miss. A scene can
have a frame per shot and still have **more shots than the model's image-reference cap** — at which
point R-42 truncates the sequence, and the dispatch carries some shots' keyframes and not others,
which is no longer the thing R-47 describes. A partial sequence is worse than none: the model aligns
to the frames it received and invents the shots it did not, with nothing saying which is which. So
the preference is conditional on the whole sequence surviving the budget intact, and where it does
not, the storyboard is used or the mode is disabled with the reason.

**The storyboard has to be drawn to be read** (R-23). Line art, no text inside the image, and no
more panels than the manifest says the family handles. The no-text rule is not cosmetic: text drawn
on a panel is text the model may render into the frame, which is what R-10 already spends a clause
preventing at the other end. And the panel cap is a real cap — past it, the documented failure is a
still output or panels rendered out of order, so the excess is named before commit (R-23) rather
than drawn and hoped for.

**Panels come from the shot descriptions** (R-24), the same source assembly reads. The guidance
warns specifically about a board and a prompt that contradict each other, and two artefacts authored
separately will diverge the first time a shot is edited and only one of them is redrawn. Deriving
both from one source makes the contradiction unrepresentable rather than merely discouraged.

**A storyboard is a generation like any other** (R-25): it is dispatched, priced, recorded in the
ledger, and it must be accepted before it can steer anything. That is the same rule as R-48 for
keyframes and it is the same reason — the accept gate decides which images drive generation. A
storyboard nobody looked at, silently steering a scene, would be the gate's exact inversion.

**And it goes stale** (R-27). Deriving panels from the shot descriptions makes board and prompt
agree at the moment of drawing; it does nothing about the moment after, when a shot is edited and
the board is not redrawn. Then the accepted board and the newly assembled prompt contradict each
other — the exact condition R-24 exists to make unrepresentable, reintroduced by time rather than
by authorship. So a storyboard records the scene version it was drawn from and stops steering once
that scene advances, which is the rule SPEC-012 R-12 already applies to the compiled board. The
difference is consequence, and it is why this one blocks where that one flags: a stale review board
is merely out of date, and a stale reference board is actively misinforming a generation somebody
is about to pay for.

**And the compiled review board stays out of it** (R-49). It is a dense four-column grid of
generated frames with labels and no panel cap: the discouraged input, in the discouraged quantity,
in the discouraged style. A purpose-drawn line-art board is close to its opposite, which is why this
is a new artefact rather than a reuse of one that happens to be a grid of pictures.

## 2.13 Continuation and the take graph

SPEC-013 R-12 extracts an accepted take's final frame and offers it as the next shot's start frame —
a workaround for models that could not take video, losing motion, momentum and the audio running
underneath. Extension continues the footage.

It is also the one capability here that does not drop in cleanly, and it should be adopted knowing
that. SPEC-013's takes are immutable, carry no review state, and each retries alone — SPEC-012's
second mechanic, *the unit of work is the shot, each its own brief and its own retry*. A continued
take depends on a *specific* predecessor take, and rejecting or reselecting that predecessor leaves
the continuation built on footage that is no longer the scene.

The resolution is to record the edge (R-53) and let selection changes **mark rather than delete**
(R-54). A superseded take keeps its media, its provenance and its own review decisions; it is simply
no longer describing the current cut. Immutability and the append-only decision log hold unchanged,
and one derived state joins SPEC-013's existing derived *unreviewed*. Deleting would have been the
simpler rule and it would have destroyed paid-for footage on a selection change the user might undo
a minute later.

**Marking is not enough on its own** (R-55). The cut is derived from selections, so a take that is
only flagged stays in the picture while the prose insists it no longer describes it — the mark would
be a fact nothing acted on. Superseding therefore clears the selection too, and SPEC-013 R-15 does
the rest for free: a shot with no selection renders as a labelled gap. The take survives, its
reviews survive, and the cut stops showing footage built on a predecessor that is no longer there.

**The input is the segment, not the file it lives in** (R-50). This is the sharpest edge in the
capability. A take derived from a pass owns an *in/out range* into media holding several shots
(SPEC-013 R-3) — segments are ranges, not files. Handing the provider that backing file would
extend whatever sits at its end, which is usually a different shot entirely, and the result would
read as a model failure rather than as a dispatch that sent the wrong footage. So the range is
materialised losslessly first, or carried through provider-side range semantics where a route offers
them. No re-encode, on the same grounds SPEC-013 R-13 gives for frame extraction.

Continuation is per-shot and opt-in (R-50), never a default. Most cuts are cuts: consecutive shots
in a scene are usually discontinuous, and extending across one would fight the edit rather than
serve it. Where the predecessor has no accepted take the mode is named and unavailable (R-51),
because the dependency is on a specific take and there is not one yet.

**One hop is enforced, not merely intended** (R-52). §1.4 settles v1 on a single link, but a
decision nothing checks is one an implementation walks straight past — every shot in a scene
declaring continuation, and a single reselection invalidating the whole tail. So continuation is
unavailable where the predecessor's take was itself a continuation, and it says why.

## 2.14 The provider surface, and what this spec declines

Everything above is written against published vendor documentation for the model family: assets
carrying declared roles, a sentinel standing in for a locked duration, a lossless container on both
sides of an extension. Arke reaches this family through an aggregator, and that route's request
shape has a flat array of image URLs and a duration string from a fixed list. It has no obvious
place to put a role, a sentinel or a kind.

**T-1 settled this, and the answer is better than the alternative.** The aggregator ships this
generation as three sibling routes — text-to-video, image-to-video and reference-to-video — the
last taking up to fifty multimodal references. Two consequences follow.

**Mode is a route, not a parameter.** Which task a request performs is decided by where it is sent,
not by a field inside it. The catalogue already models exactly this for the `/edit` sibling, so
R-32's mode description is a route plus the parameters that route locks, and dispatch selects the
endpoint rather than adding a field. No direct provider client is required.

**The sentinels are spelled differently here.** Where the vendor API takes `-1` for a locked
duration and `adaptive` for a locked ratio, the aggregator takes `"auto"` for both. That
disagreement is exactly why R-32 keeps sentinels in the manifest rather than in code: two surfaces
onto one model already spell the same idea two ways, and a third will spell it a third.

Nothing in §1.3 depended on the answer. §2.2 through §2.8, §2.11's budget and §2.12's boards are
ours regardless of route.

**What is declined.** The vendor ships this guidance as an installable skill that rewrites a prompt
before dispatch, fetched by a package runner from a vendor CDN. Two separable things are bundled
there and they get different answers.

The *knowledge* is adopted, and §2.7 is where — vendored in the repository rather than fetched,
because authoring sessions have no network and a first run may have none either.

The *rewriting* is declined. A step that rewrites the assembled prompt at dispatch produces text
that is no longer derivable from the world, which breaks Reset and makes override staleness
uncomputable — the two properties SPEC-012 D6 exists to protect. It would also place an
unreviewable transformation after the last point at which a human said yes, which is the one thing
the accept gate exists to prevent. Assembly stays deterministic; the guidance shapes what is
*authored*, upstream of the gate, where a proposal still waits.

## 3.2 Testing

**Binding** — a shot citing four sheets produces four numbered lines whose indices match the
transmitted order exactly; reordering the budget reorders both together; an overridden prompt still
carries the preamble; a preamble is never editable through the override path; each attachment mode
produces its own role phrase and a main photo carried as a second reference is bound to its
character's existing subject rather than a new one.

**Prompt structure** — every block is separately addressable and asserted on its own; a shot with no
camera direction produces no camera block rather than an empty one; art direction appears in the
summary and the trailing block and nowhere else, once per pass regardless of shot count; no
assembled output contains a fragment joined to another by a full stop, and the `..` cleanup has
nothing left to clean; a sheet with a designated compilation contributes its name only, the same
sheet as a sketch citation contributes its appearance clause, and both are asserted against the
same fixture with the kit swapped.

**Negatives** — subtitles are negated on every video dispatch, including overridden prompts and
keyframe sequences; score is negated when the cut carries a score track and not when it does not;
environmental and action sound are never negated; a silence-directed shot says so; no negative is
reachable from an authored field, and removing a shot's audio direction changes which negatives
appear without any user text changing.

**Skills** — a session drafting for one model family is given that family's skill and never
another's; a dispatch that overrides the routed model to another family names the mismatch before
commit; a family with no skill drafts under general guidance and the fallback is stated rather
than silent; no skill is reachable over the network, and a session with the network denied loads
one successfully; a skill cannot replace the confinement preamble, the tool denials or the proposal
directory, asserted by attempting each; the skill and version are recorded on the proposal it
shaped; no authoring advice appears as a string literal in the drafting path, and none appears in
the manifest.

**Storyboards** — a generated storyboard contains no text, asserted on the artifact rather than on
the prompt that asked for it; a board whose source scene has advanced is stale and cannot steer a
generation until redrawn and accepted; panel count never exceeds the manifest cap and the overflow is named
before commit; panels derive from the same shot descriptions assembly reads, so editing a shot and
redrawing changes both; a storyboard steers nothing until accepted; where every shot has an
accepted frame the keyframe path is chosen and the choice is stated; the compiled review board is
never carried as an input on any path.

**Snapping** — two 3.5-second shots produce 0–4s and 4–7s and a 7-second pass; twelve fractional
shots drift less than one second in total; whole-second shots are unchanged and produce no notice;
boundaries are strictly increasing for every fixture, and a 0.4-second shot is named and merged or
refused rather than emitted as 0–0s; no shot plan ever contains a zero-length interval;
boundaries stated in the prompt equal the boundaries SPEC-013 segments on, asserted against the
same structure rather than two computations of it; no pass prompt contains a gap or an overlap.

**Modes** — a locked mode sends no chosen value for the parameter it locks; the required sentinel
is sent where the manifest declares one; an unsupported mode renders disabled with its reason and
cannot be dispatched; a mode's availability comes from the manifest and never from a code branch;
`first-and-last-frame` is one mode and no `last-frame` mode exists; a boundary-frame dispatch whose
input is a still image is offered rather than refused for an unmeasurable duration.

**Locked estimates** — an edit's estimate derives from the measured input duration; the stated
tolerance is added rather than subtracted; an unmeasurable input refuses only the duration-locking
modes, with a reason, and leaves the boundary-frame modes available; no duration-locked estimate
reads from the duration picker.

**Budget** — thirty assets under a thirty cap produce no notice; the notice names which of the four
dimensions bound, including reference duration; a request inside every count but over the aggregate
seconds is bound by duration and says so; ten subjects against a range of eight warns and carries
all ten; asset overflow still truncates by SPEC-010's ranking and still names the drops; payload
overflow reduces by rank or blocks and can never be committed past, and is never first raised by the
client; each kind is counted against its own limit.

**Keyframes** — accepted and pinned frames only; a shot with neither is named and the sequence does
not close the gap; the ordering stated in the prompt matches the transmitted order; a scene with a
frame per shot but more shots than the reference cap does not choose keyframes, and states the
fallback rather than dispatching a truncated sequence.

**Continuation** — unavailable and named where the predecessor has no accepted take, and where the
predecessor's take was itself a continuation; a continued take records its predecessor; a
predecessor that is a pass segment is materialised to its own media before dispatch, byte-comparable
to the source range and not re-encoded, and the backing pass file is never sent; changing the
predecessor's selection marks the continuation superseded, clears the continuing shot's selection so
the cut renders a labelled gap, and leaves media and review decisions intact with nothing deleted.

**Compatibility** — this replaces the byte-identical assertion an earlier draft carried, which was
unsatisfiable: R-5 through R-13 restructure the prompt and add negatives unconditionally, and R-49
withdraws an input SPEC-012 §2.9 previously described, so no legacy request can stay byte-identical.
What is asserted instead is that nothing capability-gated leaks to a model that did not declare it.
For a model declaring none of these capabilities: no timestamped body is emitted and the
shot-number form is used; no asset role, reference kind or mode sentinel appears in the request; the
reference set is the same set today's planner selects, in the same ranked order; no locked-parameter
handling engages and the duration and resolution are the ones chosen. The prompt text differs by
construction — restructured, with negatives appended — and that is the intended change, asserted
against a recorded expectation per fixture rather than against today's output.

## 3.4 Decision log

| # | Decision | Rationale |
|---|---|---|
| D1 | Every carried asset is numbered and named in the prompt | The planner already knows each asset's subject and role and was discarding it at the last step; with several references, an unstated mapping is the documented cause of subjects blending or duplicating. |
| D2 | Stated order and transmitted order come from one structure | Two representations of the same ordering will drift, and the drift presents as the model confusing two characters — diagnosed as a model problem, not as our bug. |
| D3 | What the planner composes, the planner keeps: the binding preamble *and* the derived negatives sit outside the overridable prompt | An override is what a user writes for a hard shot, which is the shot with the most cast; if the preamble lived inside it, the convenience feature would disable the correctness feature exactly when it mattered. |
| D4 | The preamble is visible but uneditable | Someone debugging drifted identity needs to see what the model was told about the assets; the payload is not theirs to author. |
| D5 | The prompt is composed in blocks, not concatenated | Assembly already knows which inputs describe the whole clip and which describe one moment, and flattening that into a run-on throws the distinction away at the last step — the same loss as D1, one level up. |
| D6 | Persistent constraints trail the beats, and lead the summary | These models look for what must not drift at the end of a brief; repeating the world's look beside every beat spends attention arguing about which mention is authoritative. |
| D7 | An imaged subject loses its prose appearance clause; a sketch citation keeps it | The image is the stronger carrier and restating the description competes with it — but where no image is carried, the prose is the only description of that subject the model receives. |
| D8 | Subtitles are negated on every video dispatch | A take is immutable, so burned-in text is damage with no version of the take without it; no surface asks for subtitles and the cut renders its own titles. |
| D9 | Score is negated where the cut composes one; environmental sound is not | Two pieces of music, one baked into the take, and the clip that sounds best alone fights the cut hardest. Environmental sound belongs to the shot and replacing it would mean foley for every clip. |
| D10 | The derived negatives are appended after an override, never inside it | An override is what a user writes for a hard shot, and a hard shot is still a video dispatch; leaving them in the body would burn titles into precisely the take somebody worked hardest on, and D8 admits no exception. |
| D11 | Negatives are derived, never authored | A per-shot negative is a per-shot thing to forget, and the failure stays silent until an export has titles burned into it. |
| D12 | Authoring guidance goes to the drafting agent, not to assembly | By the time assembly runs the description is written; an idiom drafted into a shot is not recoverable by any amount of good assembly. |
| D13 | That guidance is a skill, not a manifest field or an agent brief | The manifest carries numbers a picker reads, and three pages of style advice in it makes "one row to update" false. Briefs are compiled in, one per agent rather than per model family, and Settings can replace them — the harness's own note warns that an agent talked out of its constraints fails in ways that look like our bugs. |
| D14 | Skills ship with the application and are never fetched | Architecture settles it rather than principle: SPEC-005 R-10 denies network tools in authoring sessions, so a fetched skill could not be fetched by the agent needing it. It also keeps first run working offline and a vendor CDN out of the path of drafting a scene. |
| D15 | A skill shapes authoring and never rewrites dispatch | What it influences is a draft, and a draft arrives as a proposal and waits; assembly stays derivable, so Reset and override staleness survive. |
| D16 | The skill in force is recorded on the proposal | Same discipline as provenance at dispatch: two scenes drafted under different guidance differ for a reason that is otherwise unrecoverable. |
| D17 | A skill mismatch is caught at dispatch, not only recorded at drafting | SPEC-008 R-21 lets any dispatch override the routed model, so a scene drafted under one family's guidance can reach another's without the drafting rule ever being violated. |
| D18 | A missing skill drafts under general guidance and says so | Refusing would make a missing document a broken feature; borrowing another family's advice would write shots for a model that will not read them. |
| D19 | Storyboards and keyframes both exist, and the preference is automatic | They belong to different moments — a storyboard is available before anything is shot, keyframes presuppose accepted frames — and the guidance makes storyboards loose where keyframes align, which nobody should have to know. |
| D20 | A generated storyboard is line art, capped, and carries no text | Text on a panel is text the model may render into the frame, which D8 already spends a clause preventing at the other end; past the cap the documented failure is a still output or panels out of order. |
| D21 | Storyboard panels derive from the shot descriptions | Two artefacts authored separately diverge the first time a shot is edited and only one is redrawn; one source makes the contradiction the guidance warns about unrepresentable rather than discouraged. |
| D22 | A storyboard must be accepted before it steers | The accept gate decides which images drive generation; a board nobody looked at, silently steering a scene, is the gate inverted. |
| D23 | A storyboard goes stale with its scene, and a stale one blocks | Deriving panels from shot descriptions makes board and prompt agree when drawn, not afterwards. SPEC-012 R-12 flags a stale review board; this one blocks, because a stale reference board actively misinforms a generation somebody is about to pay for. |
| D24 | Keyframes are preferred only when the whole sequence survives the budget | A scene can have a frame per shot and still exceed the image cap; a truncated sequence is worse than none, because the model aligns to the frames it received and invents the rest with nothing saying which is which. |
| D25 | Timestamps replace shot numbers where the model answers them | Makes SPEC-013's "boundaries computed before dispatch" a contract shared with the model rather than one Arke keeps privately. |
| D26 | Cumulative boundaries snap, not individual durations | Rounding each duration compounds — twelve shots drift six seconds; rounding the running total bounds the error at half a second no matter how long the pass. |
| D27 | The plan snaps, rather than the prompt rounding a plan that stays exact | Prompt-only rounding recreates the plan-versus-output divergence timestamps were adopted to remove, in a form that is harder to see because both numbers are individually correct. |
| D28 | Snapped boundaries are strictly increasing | Cumulative snapping bounds drift but does not protect short shots: a 0.4-second shot rounds to 0–0s, and SPEC-013 segments on exactly these boundaries, so the shot becomes a zero-length take. `ShotSchema` admits any positive duration, so this is reachable rather than theoretical. |
| D29 | The vendor's guidance is adopted; its prompt-rewriting step is not | Two separable things ship together. The knowledge is worth having and is vendored (D13, D14). A rewrite at dispatch produces text no longer derivable from the world — breaking Reset and override staleness, the properties SPEC-012 D6 protects — and places an unreviewable transformation after the last point a human said yes. |
| D30 | Task modes and their locked parameters live in the manifest | Routes disagree about what locks and what sentinel stands in its place; that disagreement is data, and code encoding one route's answer will be wrong about the next. |
| D31 | A paired boundary-frame operation is one named mode | `last-frame` as a mode would leave a last-frame-only request and a paired request indistinguishable in the manifest — two provider operations behind one name. A trailing frame is an asset role, not a task. |
| D32 | Unsupported modes are offered and disabled with a reason | SPEC-008's rule for size tiers on a new axis: an absent mode reads as a missing product capability, a disabled one teaches something about the model. |
| D33 | Locked durations are measured from the input and priced at the top of the stated tolerance | SPEC-008 already settled that a figure which can come in under is honest where one that can come in over is not; a tolerance is that problem in a different unit. |
| D34 | Only duration-locking modes require a measurable input duration | The boundary-frame modes lock aspect ratio and take a still image; refusing them for a duration that does not exist would disable generation they fully support. |
| D35 | Reference duration is a budget dimension of its own | A request can sit inside every count and still exceed the aggregate video or audio seconds; without the dimension, the notice cannot report the constraint that actually bound. |
| D36 | Subject count warns, asset count truncates | They are different kinds of constraint. Truncating against a degradation range gives the user a stable take of a scene they did not write, with the warning that would have explained it replaced by the action. |
| D37 | Payload overflow reduces by rank or blocks; it is never a warning to commit past | Four small images could not plausibly breach the ceiling and thirty large ones routinely will — but a ceiling is a hard limit, not a degradation range. A request over it is one the client already refuses, so naming a certain failure and allowing the commit applies D36's enforce/warn distinction backwards. |
| D38 | The aspect a production delivers in belongs to the production | Art direction is one world-level record, and one world routinely holds a 16:9 film and a 9:16 cut of the same material; a world-scoped aspect cannot express both without one production silently changing the other's. |
| D39 | The voice reference is a designated sample | SPEC-011 assigns a provider voice identity and produces a take per line; neither is a canonical asset to transmit. Designation follows the model sheet's designated compilation, and no designation means no audio reference rather than a take chosen by guess. |
| D40 | Vendor capacities live in the manifest; vendor prose does not | Numbers a picker or an estimate reads are manifest data and differ per model. Pages of craft advice are a skill (D13) — putting them in a row makes "one row to update" false. |
| D41 | The compiled review board is not a generation input | It is a dense grid of generated frames with labels and no panel cap: the discouraged input, in the discouraged quantity, in the discouraged style. The board drawn for the purpose (D20) is close to its opposite, so this is a new artefact rather than a reuse. |
| D42 | Keyframes come only from accepted or pinned frames, and gaps are named | Makes the accept gate the qualifier for what steers generation, and refuses to produce a sequence quietly missing a shot the user believes is in it. |
| D43 | Continuation is opt-in per shot | Consecutive shots are usually cuts; extending across one fights the edit rather than serving it. |
| D44 | Continuation extends the selected segment, not the file holding it | A take derived from a pass owns an in/out range into media holding several shots; sending the backing file extends whatever sits at its end, and the result reads as a model failure rather than as the wrong footage being dispatched. |
| D45 | One hop is enforced, not merely intended | A decision nothing checks is one an implementation walks past: every shot declaring continuation, and a single reselection invalidating the whole tail. |
| D46 | A superseded continuation is marked, never deleted | Preserves take immutability and the append-only decision log, and does not destroy paid-for footage over a selection change the user may undo a minute later. |
| D47 | Superseding also clears the selection | The cut is derived from selections, so a take that is only flagged stays in the picture while the prose insists it does not; clearing the selection makes SPEC-013 R-15 render a labelled gap for free. |
| D48 | Legacy compatibility is capability-gating, not byte-identity | The prompt is restructured and the negatives added unconditionally, so byte-identical legacy requests were never possible; what must hold is that nothing capability-gated reaches a model that did not declare it. |
