Executive Summary

Four validated startup defects were found and filed as GitHub issues. The primary theme is that the launch UI is constructed after the work it is meant to report. Synchronous OpenCode probing adds about 0.7 seconds on the measured machine and can block for timeout-length periods. Queue reconciliation also grows superlinearly with durable history, reaching 6.58 seconds for 1,000 synthetic terminal jobs. Separately, the cached world registry never discovers valid world folders added while the app is closed.

Issues #126, #127, #128, and #129 contain reproduction details and acceptance criteria. The blank/unhandled startup-failure path and unbounded recovery cost should be addressed before treating the under-two-second startup requirement as satisfied.

Detailed Findings

MAJORCERTAIN Launch UI follows initialization and fatal startup failures are unhandled main.ts:188-560

Dimension: Bad TypeScript/Node practices; startup performance

Evidence:

async function start(): Promise<void> {
  await provider.ensureAppRoot();
  const swept = await childLedger.reapStale();
  // discovery and coordinator construction
  const { port } = await coordinator.start(0);
  await sweepSpool(appRoot);
  window = new BrowserWindow({ show: false, ... });
}

app.whenReady().then(() => {
  void start();
});

Why it matters: The user sees no launch screen while app-root setup, child cleanup, runtime discovery, journal seeding, queue reconciliation, and world listing execute. This directly contradicts SPEC-001 section 2.8, which requires the launch screen to render before readiness probing. Because the discarded promise has no rejection handler and no window exists, a core startup rejection cannot be shown as an actionable failure.

Recommendation: Create and load the launch window immediately after Electron becomes ready. Run initialization behind an explicit startup state machine and catch fatal startup errors into a visible retry/open-data-folder/quit state.

Effort: Moderate. GitHub: #126.

MAJORCERTAIN OpenCode discovery blocks Electron main discovery.ts:19-79

Dimension: Performance / bad Node practice

Evidence:

const result = spawnSync(command, ["--version"], {
  timeout: 10_000,
  shell: process.platform === "win32",
});

const result = spawnSync(probe, [command], {
  timeout: 5_000,
});

Why it matters: discoverOpenCode() is called before the first window. Five healthy local probes took 721, 687, 691, 705, and 692 ms. A stalled configured, PATH, or bundled candidate can block Electron main for its full timeout, preventing event processing and first paint.

Recommendation: Use asynchronous child processes and perform discovery after the launch window paints. Publish a starting health state, then update health/version when discovery settles.

Effort: Moderate. GitHub: #127.

MAJORCERTAIN Queue recovery is superlinear in durable history dispatcher.ts:721-760

Dimension: Performance / simplification

Evidence:

const folded = [...byId.values()].map((job) => ({
  ...job,
  attempt: Math.max(job.attempt,
    history.filter((row) => row.id === job.id && row.status === "submitting").length),
}));

if (!(await this.opts.ledger.has(job.id))) { ... }

// Desktop composition:
has: async (jobId) =>
  (await this.ledger!.readAll()).some((e) => e.jobId === jobId)

Why it matters: The journal and ledger are append-only and never compacted. Startup filters the full history per job and reparses the full ledger up to three times per terminal job. A no-network temporary-file benchmark measured 167 ms for 100 jobs, 805 ms for 300, and 6,582 ms for 1,000. This recovery is awaited before coordinator transport and first-window construction.

Recommendation: Fold status and submission counts in one journal pass. Read the ledger once into a Set<jobId>, update the set when recovery appends, and perform constant-time membership checks.

Effort: Moderate. GitHub: #128.

MAJORCERTAIN Seeded registry misses worlds added while closed provider.ts:106-116

Dimension: Correctness

Evidence:

async listWorlds(): Promise<WorldSummary[]> {
  await this.ensureAppRoot();
  if (this.appIndex?.seeded) {
    return this.appIndex.listWorlds(this.worldsDir());
  }
  const summaries = await this.scanAllSummaries();
  ...
}

Why it matters: AppIndex.listWorlds() validates only known registry rows. It never enumerates unknown directories. A restart reproduction with two valid folders returned {"folders":2,"listed":1,"names":["Original"]}. A copied, restored, or synced world therefore remains invisible indefinitely.

Recommendation: Reconcile cheap directory/world-metadata identity against registry rows at startup. Add missing valid worlds and remove absent rows without full-scanning the contents of every known world.

Effort: Moderate. GitHub: #129.

Confirmed-Intentional

  • Children start without gating UI readiness: Coordinator.start() invokes supervisors without awaiting their health at packages/coordinator/src/coordinator.ts:559-561. This correctly implements degraded optional features under SPEC-001 R-6.
  • Stale-child cleanup is startup-critical: ChildLedger.reapStale() verifies owner and child identity before killing at packages/coordinator/src/child-ledger.ts:270-310. The cleanup is justified by orphan/file-lock history and should remain, though it can report progress through an already-painted launch UI.
  • Registry summaries avoid full world scans: SPEC-003 R-6 and section 2.2 deliberately cache picker counts. ST-4 does not recommend scanning every world; it requires discovering directory additions with a cheap reconciliation.
  • Queue reconciliation gates new work: SPEC-009 R-18 requires non-terminal recovery before accepting new jobs. ST-3 preserves that ordering and changes only the data structures used to perform it.

Quick Wins

  1. Replace per-job ledger reads with one startup Set; this is the smallest high-value performance fix.
  2. Make OpenCode path/version probes asynchronous so timeout cases cannot freeze Electron main.
  3. Add startup tests for a delayed coordinator, a rejected coordinator, and a world directory added between runs.
  4. Move first-window construction ahead of initialization, then expose existing readiness states through that window.
