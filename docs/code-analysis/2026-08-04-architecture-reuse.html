Executive Summary

Yes, mostly. The authoritative business logic is substantially separated from the React/Electron UI. React sends validated commands and renders coordinator snapshots/events; filesystem mutation, proposal acceptance, ripple computation, queueing, provider dispatch, extraction verification, and review operations live outside the UI. A second interface can reuse the existing WebSocket protocol immediately, or use the coordinator's lower-level Node services.

The qualification is important: Coordinator is an application server and protocol dispatcher, not a clean UI-independent application API. Its client-message dispatcher is private and its read model is explicitly client-shaped. A new interface can reuse the core, but either needs to speak the existing WebSocket contract or work around the coordinator by assembling lower-level services.

Nothing found blocks shipping the current desktop UI. The main architectural improvement before committing to multiple interfaces is to expose a public application-command service and keep WebSocket transport as an adapter around it.

Detailed Findings

MAJORCERTAIN Coordinator API is coupled to the client protocol coordinator.ts:641-677

Dimension: Business-logic placement & layering

Evidence:

private async handleClientMessage(msg: ClientMessage): Promise<void> {
  switch (msg.kind) {
    case "open-world":
      await this.openWorld(msg.worldId);
    case "create-world":
      await create({ name: msg.name, ... });
      await this.openWorld(worldId);
      ...

Why it matters: The same class constructs its WebSocket transport at coordinator.ts:280-289, returns a ClientState read model, and dispatches a large UI command union from contracts/src/frames.ts:20-125 (the union continues to line 707). A second React-like client can reuse the protocol. A CLI, REST API, native UI, or embedded host cannot call the command operations directly because the dispatcher is private and there is no public application-command interface. Such clients must either implement the WebSocket protocol or duplicate orchestration around lower-level services.

Recommendation: Extract a public application facade, for example CoordinatorCommands, with methods grouped by use case. Keep Transport as an adapter that validates ClientMessage, invokes the facade, and broadcasts snapshots/events. Do not move business rules into the new interface; move only command routing and request-shape translation.

Effort: Involved, but incremental. Existing tests can pin each extracted command path before transport is reduced.

Resolution, 2026-09-05 (#828): The coordinator package intentionally owns the shared desktop/dev launcher in harness/v2-launch.ts, so both concrete adapters remain runtime dependencies. Concrete adapter imports are confined to that launcher; coordinator.ts consumes contracts. Harness credential-environment policy moved to contracts, and the dev entry's providers/voice imports are declared runtime dependencies. The recommendation below is historical; a separately packaged minimal core is deferred.

MINORLIKELY Coordinator package has an avoidable OpenCode dependency coordinator/package.json:14-20

Dimension: Business-logic placement & layering

Evidence:

"dependencies": {
  "@arke-studio/adapter-opencode": "*",
  "@arke-studio/contracts": "*",
  ...
}

The core options instead accept the replaceable contract adapter: HarnessAdapter | null and injected adapter configuration builders at coordinator.ts:124-147. The desktop composition root supplies the concrete adapter at apps/desktop/src/main.ts:169-182.

Why it matters: A host using a different authoring harness still installs and resolves the OpenCode adapter through the coordinator package, even though the core's main runtime path is contract-based. This weakens the stated dependency direction and makes alternate-host packaging less minimal.

Recommendation: Move the dev entrypoint and any adapter-specific wiring to a host/dev package, then remove the production dependency if the coordinator source no longer imports the adapter. Keep the injected HarnessAdapter contract in contracts.

Effort: Trivial to moderate; verify with typecheck and coordinator tests.

MINORCERTAIN Core packages are source-level reusable, not independently consumable artifacts coordinator/package.json:6-12

Dimension: Simplification / optimization

Evidence:

"main": "./src/index.ts",
"types": "./src/index.ts",
"scripts": {
  "typecheck": "tsc -p tsconfig.json --noEmit"
}

The shared packages use noEmit: true in tsconfig.base.json:2-16. The client is explicitly an application bundle, with no library entrypoint, at packages/client/package.json:5-12.

Why it matters: Another interface can reuse the core inside this monorepo with a TypeScript loader or bundler. It cannot currently consume a stable compiled package with declarations from a separate repository or ordinary runtime without reproducing the workspace toolchain and source layout.

Recommendation: If a second interface becomes a real product, add a build/publish boundary for contracts and the intended core facade: emitted JavaScript, declarations, explicit exports, and a compatibility policy. Do not package the entire coordinator surface prematurely.

Effort: Moderate; unnecessary until an external consumer or separately deployed interface exists.

Confirmed-Intentional Design

  • Thin UI boundary: The product specification explicitly says the React client is a thin client over a local coordinator, docs/specification.md:99-145. The preload exposes a narrow bridge for connection, sending, and subscription at apps/desktop/src/preload.ts:38-75.
  • Injected host/provider capabilities: Files, credentials, SQLite, ffmpeg, providers, voice, and updates are passed through CoordinatorOptions at packages/coordinator/src/coordinator.ts:124-187; Electron supplies them at apps/desktop/src/main.ts:169-249. This is a useful host seam, not speculative abstraction.
  • Client event folding: React folds snapshots/events in packages/client/src/lib/store.ts:194-263. This is synchronization of a client read model, not authoritative persistence or business mutation. The coordinator remains the source of events and state.
  • Reusable pure/core operations: The coordinator exports world, gate, queue, extraction, production, and reference operations at packages/coordinator/src/index.ts:1-185; tests exercise these without React, including transport, read model, gate, queue, and world-provider tests.

Quick Wins

  1. Document the supported reuse levels: existing WebSocket protocol for alternate clients; Node service imports for in-workspace hosts; no stable external package API yet.
  2. AR-2 resolved by explicit shared-launcher ownership (#828): retain the required adapter dependencies and keep the Coordinator class independent of concrete adapters.
  3. When a second interface is approved, extract the command facade before adding interface-specific behavior. Keep transport translation outside the use-case methods.
